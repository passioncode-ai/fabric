## Immediate dependencies sent to current implementer

1. Hub product-call bindings/grants are **not project participation authority**. Reuse authentication plumbing, not their current permissions. Add separately enrolled estate/project communication capabilities after hub convergence; do not widen 0.3.1's existing tool list just because a bearer authenticates.
2. Generic `TABLE_SCOPE` can narrow by only one project column. A cross-project message needs sender/recipient visibility. Estate-only scope would leak other projects; recipient-only scope loses sent history. Use dedicated participant-authorized reader RPCs (mark underlying tables private), or an explicit participant-edge projection, rather than generic estate journal replay.
3. A provider/service registry entry has no estate/project/session authority. Managed sessions derive provider identity from server-owned runtime. External clients get server-minted consumer instance identity; supplied provider labels remain **asserted provenance** until adapter evidence establishes them. Never trust `provider: codex` as authentication.

These change the future COM contract, not the current hub fix. Parent was notified immediately through agent messages.

## Research and implications

Fetched 2026-10-04. Technical decisions below are **our proposed application** of sources, not promises those sources make about Fabric.

| Primary source / expert discussion | Confirmed mechanism | COM consequence |
|---|---|---|
| [PostgreSQL17 SELECT locking](https://www.postgresql.org/docs/17/sql-select.html#SQL-FOR-UPDATE-SHARE) | SKIP LOCKED is suitable for competing queue consumers but does not return a general consistent view | Optional worker claiming optimization only. Board queries/cursors must not omit locked events. Claim inside a short transaction; do not leave transaction open during agent reasoning |
| [PostgreSQL17 advisory locks](https://www.postgresql.org/docs/17/explicit-locking.html#ADVISORY-LOCKS) | Transaction locks end with transaction; session locks have different lifetime | Match existing estate-first transaction lock. No session-level lock held by a process as durable ownership evidence |
| [PostgreSQL17 NOTIFY](https://www.postgresql.org/docs/17/sql-notify.html) | Notifications are commit-bound; duplicates may coalesce, payload bounded, listener transactions can delay notifications | Wakeups contain record identity/cursor, not payload/authority. Persisted query/poll remains recovery path; no lost-notification success claim |
| [Martin Kleppmann's locking analysis](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html) | Paused stale holder can resume after lease takeover; writes need storage-enforced fencing tokens | Generation and claim-attempt fence must be validated at every mutation/effect gateway, not just at claim. Lease TTL alone is insufficient |
| [pg-boss transaction support discussion #667](https://github.com/timgit/pg-boss/issues/667) and [official jobs API](https://github.com/timgit/pg-boss/blob/master/docs/api/jobs.md) | Scheduling can participate in a caller-owned database transaction | Board event and outbox eligibility must commit together. No promise from two separate service-role RPC calls; implement one Fabric RPC/projector transaction |
| [pg-boss maintainer PR review #890](https://github.com/timgit/pg-boss/pull/890) | Review reproduced duplicate committed side effects when a worker lost its claim but completion affected zero rows; revised design checks ownership before commit | COM test must let obsolete consumer continue after replacement and attempt completion, then verify no state/effect committed. Checking takeover alone misses the failure. We reuse semantics; no pg-boss dependency is proposed |

The pg-boss review also discusses long transactions blocking vacuum and keeping claim visibility separate from the work transaction. A 30-minute agent task must not hold a DB snapshot/connection throughout. Use short registration/claim/ack/renew/complete transactions, persisted epochs and separately mediated effects.

## COM-01 packet: freeze the contract before storage work

**Owner:** Fabric command/contract author with fabric-agent-contract fixture owner. **Prerequisites:** parent hub convergence and schema readiness; reserve ADR/migration ids under the actual coordination config. Suffix78/79 belong to another pending workstream and suffix80 is hub recovery; do not infer next schema version from a filename or reserve an id in this research note.

**Deliverable files proposed:** `apps/desktop/src/shared/projectComms.ts`, `apps/desktop/src/shared/projectComms.test.ts`; contract owner's versioned schema/fixture files; numbered ADR; then a schema migration reserved by the implementer. Existing ingress rules and table-scope map must be updated in the same implementation change.

**Envelope, proposed `ProjectCommunication@1`:** canonical UUID `message_id`; fixed schema/version; trusted estate and sender project/principal supplied by server; recipient project/capability; kind enum request/reply/finding/announcement/cancel; nullable thread/parent-message ids; correlation/causation ids; idempotency key; body or artifact references; priority; optional requested expiry. Database supplies occurred_at/seq and permitted expiry. Provider/session data is provenance, not address or caller-selected authority. Declare which fields are optional/null, exact allowed keys and supported capabilities.

**Idempotency:** durable unique command receipt `(estate_id, sender_project_id, command_kind, idempotency_key)` plus canonical admitted-payload SHA256. Same identity+digest returns prior receipt; different digest returns `idempotency_conflict`. Bind caller identity/scope before looking up receipt. Scope excludes provider/session generation so replacement can resume the same logical request; current caller must still be authorized. Recipient is part of payload digest, so changing it with the same key conflicts. Never store raw secret input to compute this receipt; digest the validated/privacy-prepared semantic envelope. Version canonicalization rules with fixtures.

**Proposed product bounds, to validate with UX:** 64KiB text per message, 8 artifact refs, envelope depth8, page max100, 60-second default consumer lease, renewal within20 seconds, 30-second jittered poll. These are initial design values, not API/library facts or settled operator decisions. Expiry never accepts client clock as authority; server clamps/refuses to documented policy. Reject bounds, never clip accepted semantic payload.

**Typed results:** `ok`, `unsupported_capability`, `invalid_envelope`, `access_denied`, `unavailable`, `idempotency_conflict`, `stale_consumer`, `stale_claim`, `digest_mismatch`, `expired`, `outcome_unknown`, `cursor_reset_required`. Foreign/no-such private references get the same unavailable/access-denied answer. Errors contain no credential, DB detail or private neighbor identity.

**Read cursor:** opaque versioned token bound to estate, authorized participant/subscription, filter revision, reader epoch and last scanned committed seq. Filter change starts another cursor. Server scans bounded committed seq windows and returns `scanned_through` even when authorized results are empty; only durable handling advances consumer checkpoint. Notification order and inserted timestamps cannot advance it. Restore/read epoch mismatch returns cursor_reset_required and a bounded full-catchup strategy. Decide at ADR whether cursor tokens must hide estate-wide event counts; signing alone is integrity, not confidentiality.

**Acceptance fixtures:** old MCP list unchanged until COM negotiated/enrolled; enum/unknown-field/depth/size rejection before append; forged estate/sender/project/session denied; secret artifact reference denied; same command repeat stable receipt; changed recipient/body same key conflict; provider replacement same logical key returns original receipt under fresh valid authority; paginated interrupted catchup resumes; unsupported version typed refusal.

**Exact first task:** build pure envelope/canonical digest and scope-error fixtures, then prove two estates cannot forge sender/recipient at command admission before successful submission test. No UI or Telegram implementation in COM-01.

## COM-02 packet: board, mailbox and atomic intent

**Owner:** Fabric storage/main. **Prerequisites:** COM-01 fixtures/ADR and reserved migration; parent schema78/upgrade evidence. Do not turn chat into a task automatically; task_id linkage optional and validated against canonical owner.

**Proposed persistent domains (names require reservation review):**

- `project_comm_messages`: immutable accepted envelope, message UUID, estate, sender/recipient, participant policy snapshot, thread/parent, body/artifact refs, canonical digest, submitted seq. Participant edges may support sender history and explicit multi-reader threads. Mark private under TABLE_SCOPE unless dedicated view has a proved single-project predicate.
- `project_comm_requests`: request lifecycle projection (`queued`, `accepted`, `working`, terminal completed/failed/cancelled/expired); acceptance/result seq and latest causal references. Claim/attempt state is separate operational authority, not another request status source.
- `project_comm_commands`: durable idempotency receipt/digest/result for submit/reply/cancel; bounded, scoped lookup. It must survive reply loss and reconstruction policy must be stated.
- `project_comm_delivery_intents`: stable `(message_id, recipient_project, capability)` identity + eligible flag, submitted seq. Optional external mirror intent accompanies board commit, but Telegram target enrollment is not invented here.
- Future transport-specific `comm_outbox_attempts` and `comm_inbox_updates` carry delivery ambiguity/dedup under COM-08; do not encode Telegram receipt ids as canonical request status.

**Events proposed:** `project.communication.submitted@1`, `.replied@1`, `.cancelled@1`, `.expired@1`, `.accepted@1`, `.progressed@1`, `.completed@1`, `.failed@1`. Distinct prefixes/types for transport intents/receipts. One request has one accepted envelope; a reply is another immutable message referring to its parent and request. Original body remains read-only; cancellation/redaction is an appended policy event/tombstone.

**RPCs proposed:** `submit_project_communication`, `read_project_communications`, `read_project_communication_thread`, `reply_project_communication`, `cancel_project_communication`. Trusted main passes authenticated principal, estate/sender enrollment and authority revision, not raw values selected by MCP/renderer. Each RPC checks current grant/membership and referenced projects, uses estate lock first, canonical identity guard, dedup receipt, append_event/projector, and commits receipt+eligible intent atomically. Protect communication event types against generic append bypass using the existing transaction-bound authorization pattern (`append_event` baseline migration74:226–236). Revoke function execution from API roles except intended service-role command entry; projectors/authorization tables private and non-executable.

**Outbox rebuild rule:** message history may reconstruct, but replay must not re-enable a delivered or unknown external effect. Keep attempts/claim authority operational, fenced and excluded from history-only reconstruction. A restored estate's below-watermark intent is ineligible until new local consent creates a new live event. Existing same-estate projection rebuild preserves completed receipts or deterministically folds receipt events; test both from-empty projection and retained operational state. Do not simply insert pending outbox rows on every replay.

**Acceptance:** disposable PG with Supabase default privileges; no direct projection writes or projector RPC by API roles; foreign project IDs/participant enumeration denied; journal append+outbox injected failure rollback leaves neither; crash/lost HTTP response returns same submit receipt; 1000+ message cursor catches all authorized data through insert/replay; source restored pending history cannot acquire target authority or mirror old effects; expired/cancelled state cannot be completed; query failure returns unavailable instead of `[]`. Assert same state from replay, and unknown external outcome retained across process restart.

**Exact first task:** owned PG fixture with two estates and two projects each; refuse forged sender/read/parent linkage, then transactional submit+same-key recovery. Extend scope/read-schema/function-privileges suites and archive version declarations with the reserved migration.

## COM-03 packet: consumer slot, generations and write fences

**Owner:** Fabric admission/runtime. **Prerequisites:** COM-01 scope/identity contract, COM-02 durable intents; optional provider adapter contract. No launchd/process/PID discovery authority. Registration never launches a new agent implicitly.

**Proposed runtime tables:** `project_comm_responder_slots` keyed `(estate, project, capability, slot_key)`, current consumer instance, monotonic generation, authority revision; `project_comm_consumers` server-minted instance id, trusted managed session or external enrollment principal, provider provenance category, lease_until, revoked_at; `project_comm_claims` stable delivery id + owner instance + responder generation + monotonically increasing claim epoch/claim UUID, digest, lease, started/accepted/effect-unknown state. Many registered observers permitted; one current fenced owner per delivery. Slot policy determines capability worker multiplicity instead of assuming one process per whole project.

**RPCs proposed:** register/replace/renew consumer; claim/accept delivery; progress/reply/complete delivery; release safe unaccepted claim; explicit reconcile unknown effect. Current owner/grant/authority revision checked in the same transaction as each mutation; DB clock supplies lease expiry. Replacement CAS requires expected current generation/instance; increments generation even if same provider/name returns. Delivery claim attempt increments independently; same responder generation cannot revive an obsolete claim UUID. Mutations carry exact digest and both fences; server supplies trusted session/principal context.

**Safe takeover:** queued/unaccepted work with proved no external effect can be assigned to new generation. Accepted work is not automatically safe merely because old process vanished: require a checkpoint/effect contract or mark outcome_unknown and operator/new-owner reconciliation. A replacement does not erase historical acceptance. Client timeout after claim/ack/complete queries same durable command identity before retrying. Renewal with expired/revoked/stale instance cannot extend a new holder's lease.

**Effect scope:** generation fence protects Fabric-mediated state/effects. It cannot stop a stale agent using unrelated credentials outside Fabric. To promise 'revocation between claim and effect refuses', all protected side-effect gateways must consume a current fence; ensure COM adapter instructions/grants prohibit treating a claim as generic execution permission. An external API with no idempotency/fencing remains outcome_unknown after send ambiguity, just as current hub recovery does.

**Restore:** project consumer descriptors/provenance may be historical, but no active lease, verifier, claim or accepted-effect authority survives a foreign estate restore. Start a new reader/consumer epoch and require local enrollment. Journal projection uses event occurred_at for historical ordering; live expiry eligibility uses DB clock inside authoritative commands. Never compare replay history against current wall time.

**Discriminating acceptance sequence:** Claude consumer G1 claims D/C1, pauses; lease expires; Codex replaces with G2 and claims D/C2; old Claude resumes and attempts ack, reply, renew, progress, complete and mediated effect. Every G1/C1 mutation refused; D has exactly one current owner and no obsolete state commit. Continue past takeover, not merely assert G2 acquired. Variants: concurrent replacers, same-generation old claim UUID, forged provider label, duplicate ack before writer result, revoked enrollment between begin/effect, long sleep/clock skew, DB read failure, rollback after claim loss, restored source credential/cursor, external side effect unknown. Assertions include zero erroneous effects, stable receipts and reconstructable history.

**Exact first task:** write owned DB CAS/fence fixture with two real database connections and explicit transaction ordering; observe stale completion fail against naive lease-only candidate, then implement short transactional registration/claim fences. Keep existing task deliveries/handoff behavior unchanged.
