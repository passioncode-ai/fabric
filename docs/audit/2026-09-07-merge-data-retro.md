# Fabric: хранение, синхронизация, память и ретроспектива

Ограниченная независимая проверка, 2026-09-07. Бренд: **PassionCode.ai → Fabric**. Код проверен на `153b4f029e626230d465d5d21d02fb8c9de5fadf`. Изменены только файлы отчёта в `/tmp`; source, ADR, ledger и канонический план не редактировались. Это **предложение для объединённого плана**, а не молчаливое изменение ADR-0041.

Прочитаны ADR-0002/0014/0027/0041, `retro-and-signals`, storage-раздел `agent-visibility-and-runs`, M118/182/183/184/191/198 и execution briefs, соответствующие main/renderer/shared/SQL. Вложение `pasted-text.txt` использовано как прежний порядок слоёв, не как доказательство текущего shipped: в нём M191 стоит за M189/M190, хотя актуальный brief уже снял эту ложную зависимость. Полные suites, native app и реальные агенты не запускались. Единственный исполняемый probe здесь — чистая `redact()` на вымышленных данных, без сети и БД.

Основной вывод: основа хранения уже правильная — журнал и проекции в одной БД, память с происхождением и замещением, защищённая запись агентского текста, локальный spool для восстановления транскрипта. Но интерфейс не объясняет границы этих механизмов. Обещания «зеркало = перенос всего выбранного человеком», «пакет полностью восстановим по lockfile» и «нет ID = анонимно» шире того, что доказывает код. Последнее пока **дефект принятого дизайна, а не доказанная текущая отправка данных**: M183 и upstream не реализованы.

### Отказ, offline и конфликт сейчас

При недоступной БД append завершается ошибкой; клиент повторяет только PostgreSQL `55P03`, максимум три попытки по умолчанию. **Общего durable outbox для пользовательских изменений нет**. Потерянный ответ после commit создаёт неопределённость «записалось ли»: journal client не принимает универсальный idempotency key, автоматическое повторение бизнес-команды должно учитывать её конкретный контракт. Это не следует исправлять бесконечным retry. Источник: [journal:63](https://github.com/passioncode-ai/fabric/blob/153b4f029e626230d465d5d21d02fb8c9de5fadf/packages/journal/src/index.ts#L63), [journal:83](https://github.com/passioncode-ai/fabric/blob/153b4f029e626230d465d5d21d02fb8c9de5fadf/packages/journal/src/index.ts#L83).

Per-estate lock гарантирует порядок событий и транзакционность одного append, но **не** разрешает семантический конфликт двух операторов и не делает составную операцию из нескольких append атомарной. Для редактирования/импорта/feedback lifecycle нужны expected revision, operation key и определённый результат повторения. M152 already имеет отдельный риск fact+answer; см. PLAN11 предыдущего аудита. Не смешивать это с порядком journal.

Локальная БД может работать без Интернета, если сам локальный stack доступен. Это не обещает offline-режим всех агентов/providers. При remote URL и потере сети нет автоматического переключения на локальную реплику. Точное runtime-размещение БД, backup/retention и network perimeter в этом pass не проверялись; карта показывает конфигурацию кода, не доступность конкретного развёртывания.

## 3. Предлагаемый контракт M182/M183

### M182: типология и происхождение

Сохранить пять категорий ADR-0041; `kind` остаётся независимым измерением.

| category | Что означает | Локальный retro | Автоматический внешний кандидат |
|---|---|---|---|
| project | Предметная область, код/данные/клиенты конкретного проекта | Да, только в разрешённом scope | Никогда |
| agents | Поведение runner/model/agent | Да; не считать самоотчёт независимым подтверждением | Только структурный service signal после остальных gate |
| harness | Контекст, инструменты, protocol, permissions, runtime seam | Да | Только allowlisted diagnostic summary |
| fabric | Ошибки/пробелы самого продукта, UI, flows | Да | Только allowlisted diagnostic summary |
| process | Reviews, briefs, cadence, командные правила | Да, через процессные вопросы/решения | Никогда по автоматическому service allowlist |

Рекомендуемый внутренний контракт: `category` default project; `about` — нормализованный стабильный subject key из версионируемого каталога/пространства имён; `source` — реальные event/task/session/artifact references; `occurrence_key` — происхождение случая, не random ID нового чтения; `claim` — исходное утверждение с автором; `observed_at/recorded_at`, relevant harness/runner/compiler versions; статус достоверности как claimed/observed/checked. Не превращать доверенность в красивый числовой score без основания. Не добавлять новый Run: исполнение при необходимости связывается существующей парой `(task_id, session_id)` по ADR-0042.

Category задаёт тему, **не** privacy grade и **не** право на глобальную видимость. Агент может ошибочно назвать клиентский рассказ `fabric`; фильтр категории должен защищать минимум, не выдавать сертификат. `about` может сам содержать repo/client name; наружу по умолчанию не переносится. Для старых фактов backfill default project, без автоматического угадывания service category.

Acceptance M182:

1. Tool schema → registered event (`memory.project.recorded@1`, additive schema_rev) → projector → read API → UI/pack query понимают пять значений; неизвестное значение отвергается до успешного append. Старое событие без category воспроизводится project.
2. Два rebuild и миграционный upgrade дают один и тот же результат, включая category/about, actor/source и M198 config_revision, без исключения поля из equality.
3. `kind=trap,category=harness` не теряет ни одно измерение; `process` никогда не проходит allowlist внешнего DTO. Human/agent supersession guard сохраняется.
4. Retry одной операции с тем же origin/operation key не создаёт второй occurrence. Три отдельных подтверждённых случая дают count=3; три refresh одного источника дают 1. Самоотчёт без независимого источника маркируется соответственно.

### M183a: локальный сбор по умолчанию

Сохранить **default-on локальный сбор service insights** в пределах одного estate и разрешений читающего. Это полезный рабочий механизм: собственник видит ошибки Fabric из своих проектов без ручного копирования. Называть его «локальная база улучшений Fabric»/«общая база внутри estate», не «анонимная отправка».

Рекомендую два представления над одним journal-authority:

- **Приватная локальная проекция**: источник, estate/project scope, dedup/occurrence, related task и обработка удаления нужны для достоверности и восстановления. Доступ — только уполномоченному coordinator/operator; future team checks по CO-071. Наличие внутренней связи честно объяснить. Не давать обычному project agent сведения из соседнего проекта через память.
- **Внешний DTO/preview**: отдельная закрытая схема с `additionalProperties: false`; только отобранные безопасные поля. Это граница сериализации, а не второе место редактирования факта. Связи, feedback source IDs и raw about наружу не уходят.

Такой контракт требует **нового ADR**, уточняющего 0041: полезная локальная прослеживаемость и анонимность внешнего агрегата — разные задачи. Возможен иной механизм скрытой локальной provenance-таблицы вместо estate_id в `fabric_feedback`, но это всё равно связь; не выдавать отсутствие столбца в одной таблице за отсутствие возможности корреляции.

### M183b: внешний контур только при настоящем endpoint и договорённости о данных

До endpoint UI показывает «локально; внешняя отправка недоступна», и сетевой worker отсутствует/выключен независимо от local collection switch. До реальной реализации зафиксировать получателя, HTTPS endpoint, формат/версию, цели использования, срок хранения, IP/access logs, доступ команды получателя, ответы на delete и срок их исполнения. В этом аудите не изобретён ни один endpoint и ничего никуда не отправлено.

Первый автоматический формат ограничить, например: schema_version, category из трёх service values, диагностический code из каталога, крупная версия Fabric/harness/runner, coarse time bucket, счётчик distinct occurrences. Редкие сочетания полей сами могут быть узнаваемы: формат должен проходить adversarial fixtures, а центральные отчёты — минимальный порог агрегации. Не обещать математическую анонимность без отдельного доказанного механизма.

Произвольный `claim`, имя файла/basename, путь, source_ref, task text, prompt, transcript, hostname, адрес, credential, actor и стабильный install fingerprint **не относятся к default-on outbound allowlist**. Rich feedback возможен отдельным ручным действием после просмотра точного очищенного payload. Это дополнительная возможность, а не отмена локального сбора по умолчанию. M95 использовать первым слоем; после него privacy transform, allowlist serialization и конечная проверка фактических байтов. Ошибка schema/redaction/contract version блокирует отправку, локальный факт остаётся доступен.

Preview показывает: получатель, версия контракта, **точно те поля и значения**, которые будут отправлены, размер/счётчик, причины исключения/обобщения и остаточные ограничения. Не выводить raw secret в diff ради демонстрации redaction. Если generation/privacy contract поменялся между preview и send, пересчитать кандидат и потребовать актуальную ревизию для ручной отправки; старый preview не подтверждает новые байты.

### Удаление, outbox и opt-out

Удаление из локальной очереди — устойчивое решение `suppress(source/occurrence, reason, actor, revision)` в journal, с приватным source key. `fabric_feedback` и outbox — восстанавливаемые проекции этих событий. Предлагаемые названия здесь семантические, новые event IDs не резервировались. Простое SQL DELETE строки кеша запрещено как реализация пользовательского «удалить».

`source key`/HMAC для dedup остаётся локальным: hash сырого имени или claim не является анонимизацией и не отправляется как устойчивый fingerprint. Для удаления одной записи suppress exact source; «не предлагать эту группу снова» — отдельный group suppression с явным scope/сроком. Новый настоящий случай должен следовать выбранной политике, а не случайно исчезать вместе с прежним или возвращать уже удалённое.

Outbox state: candidate → eligible/pending → in-flight → acknowledged; отдельно suppressed/cancelled/failed/unknown. Receipt удалённого сервиса содержит idempotent request key и подтверждённый результат, но не становится новой предметной истиной вместо исходного insight. Batch manifest фиксирует schema/privacy revision и bytes hash. Crash после commit receipt/до ответа, retry и duplicate ACK не дают повторного внешнего эффекта. Rebuild **не отправляет HTTP** и не сбрасывает acknowledged/suppression в pending; worker работает по восстановленным состояниям и idempotency protocol.

| Действие/состояние | Что продукт может обещать |
|---|---|
| Выключить локальный сбор | Прекратить создавать новые локальные кандидаты; уже существующие остаются до отдельного удаления, либо пользователь явно выбирает иное. Сама проектная память не исчезает |
| Выключить внешнюю отправку | Запретить новые отправки и отменить pending; повторно проверить switch непосредственно перед началом запроса, не только при сборе |
| Запрос уже in-flight | Best-effort abort, затем статус «исход неизвестен» до receipt/query; нельзя обещать, что байты не покинули компьютер |
| Уже acknowledged | Показать дату/версию отправленного. Выключение не отзывает данные. Удаление у получателя — отдельный запрос с подтверждением и честным retention сроком |
| Включить снова | Возобновить для новых допустимых кандидатов. Исторический backfill после периода opt-out — только явное действие с preview; deleted/suppressed не воскресают |
| Удалить локальный feedback | Скрыть/удалить кандидат и поставить durable suppression. Это не обещание удаления исходного claim из append-only memory journal и всех backup |

У default-on local collection и outbound availability разные состояния; UI может объединять их на одной карточке, но не одним неоднозначным boolean. Политика недоступности сервера/истёкшего контракта — keep local, outbound blocked, reason visible. Для локального сбора без сетевого transport не вводить искусственное ожидание внешних юридических/инфраструктурных работ.

Acceptance M183, обязательные дополнения к текущему brief:

1. `project/process/unknown` не становятся outbound DTO даже при ручной подмене payload/API; service-категория с PII/free text не обходит allowlist. Fixtures: имя, email, IP, basename с клиентом, secret, Unicode/encoded value, nested fields/keys, редкая сумма/цитата. Не ограничиваться UUID regex.
2. При отсутствии endpoint/contract реальные outbound calls=0, local collection работает default-on. Project-scope agent не читает соседний project feedback; две estates изолированы.
3. Удалить pending, перезапустить, дважды rebuild, повторно ingest тот же source: строки на отправку нет. Re-enable не отменяет tombstone. Project fact остаётся согласно отдельному memory contract.
4. Opt-out before enqueue, between enqueue/send, in-flight, after ACK: четыре разные проверки и честные UI-состояния. Race удаления и sender решается revision/lease; ACK после opt-out обрабатывается как уже выполненная отправка, не теряется.
5. Lost ACK/retry/restart не дублируют request у получателя. Неопределённый исход не подписывается «не отправлено». Delivered deletion показывается выполненной только по server receipt; retention backup исключения явно названы.
6. Changing classifier/privacy schema не переносит подавленные источники заново; replay детерминирован, transport не вызывается из projector. Preview hash=sent bytes hash для актуальной ревизии.

## 4. CEO-ретро: работающий замкнутый цикл M184

Цель — не регулярно производить ещё текст, а уменьшать повторение подтверждённых проблем и менять один управляемый источник правил. Более сильный агент лучше диагностирует и предлагает; Fabric сохраняет источник, решение, владельца, проверку и результат между агентами и проектами. Это и есть полезная синергия, не конкуренция с собственной силой модели.

Предлагаемый lifecycle:

1. **Capture.** Наблюдение/самоотчёт поступает из task/session/tool/checker с источником, category/about, версиями, occurrence key. Source/actor доверенность не повышается из-за того, что CEO пересказал запись.
2. **Triage.** Скрипты группируют точные копии, связывают повторения, проверяют существование references. Category+about недостаточно для exact duplicate: нужны совпадение нормализованного утверждения, applicability и происхождения. Лучше объединять представление/aliases, сохраняя все distinct occurrences, чем безвозвратно схлопывать факты.
3. **Assess recurrence.** Порог ADR N≥3 срабатывает на три distinct occurrences в определённом окне и scope. Пример рекомендуемого первого контракта: последние 30 дней, одна category+canonical about+существенная версия поведения, только новые occurrences после уже разобранного episode. Число и окно — предложение, подлежит фиксации, не существующее правило ADR.
4. **Propose.** Один process question на одну группу/episode, со ссылками на случаи, числом attempted/observed/checked, ущербом, предлагаемым действием, ценой, владельцем и acceptance. Новые случаи обновляют доказательства существующего вопроса, не создают новый вопрос каждый tick. Решения пользователя, grants и обязательный floor не обходятся.
5. **Decide.** Оператор отвечает через существующую Board очередь M149–152. CEO автоматически решает только то, что разрешено отдельным trust/floor контрактом и имеет проверяемый basis; механический retro tick сам не становится полномочным судьёй. Decline/defer сопровождается причиной и сроком/условием пересмотра.
6. **Apply.** Принятое улучшение создаёт/связывает task и меняет конкретный canonical source: brief, project rule, harness protocol, eval, runbook или код Fabric. У источника есть owner/revision. Нет каскада одинаковых memory заметок и противоречащих инструкций в каждом проекте.
7. **Verify.** Независимый code check/fixture/eval подтверждает acceptance. Автор изменения/агентский самоотчёт не заменяет проверку; ссылка на checker evidence остаётся доступна. Модель может улучшить предложение и анализ, но не подменяет факт выполненной проверки.
8. **Observe outcome.** После применения считать только новые случаи в указанном периоде; показать baseline/после/число наблюдений и coverage. Ноль записей при неработающем сборе не означает, что проблема устранена. Повторение после fix открывает/возобновляет follow-up со ссылкой на прежнее решение.
9. **Supersede/retire.** Закрывать неверный/устаревший insight только с причиной и новой актуальной ссылкой. Dangling reference ≠ устаревшая мысль; permission denied/offline/unreadable ≠ удалённый файл. Механизм предлагает, человек подтверждает judgement, прошлое остаётся читаемым.

### Tick — детерминированная обработка, а не новый orchestrator

Использовать текущий injectable tick seam, но не наследовать `console.error` как единственную запись health. Сейчас `routineTick` имеет только process-local `ticking`, читает без проверки error и ловит общий сбой в console: [routineTick.ts:50](https://github.com/passioncode-ai/fabric/blob/153b4f029e626230d465d5d21d02fb8c9de5fadf/apps/desktop/src/main/routineTick.ts#L50), [routineTick.ts:167](https://github.com/passioncode-ai/fabric/blob/153b4f029e626230d465d5d21d02fb8c9de5fadf/apps/desktop/src/main/routineTick.ts#L167). M186 уже знает часть этой проблемы: [brief:500](https://github.com/passioncode-ai/fabric/blob/153b4f029e626230d465d5d21d02fb8c9de5fadf/docs/evidence/plans/2026-09-06-execution-briefs.md#L500).

Для ретро нужны durable cycle window/cursor, claim/lease по estate+cycle+window, start/end/error receipts и checkpoint только после успешного commit результатов. Retry после crash повторяет тот же набор действий идемпотентно. После недельного offline показываются пропущенные периоды, выполняется ограниченный catch-up; нельзя отмечать прошедшие недели как успешно отработавшие. Разумный first scope — один встроенный скриптовый tick; внешний manager M194 может инициировать/читать тот же механизм через общий контракт после core/checker/floor, не является prerequisite для ретро.

Одно событие, три browser refresh, два прохода rebuild, retry потерянного tool ответа и повторный scan одного transcript — **один occurrence**. Три разных source event записи также не автоматически три происшествия: если это три самоотчёта об одной task failure, группировка должна ссылаться на один объективный failure/operation. Если происхождение нельзя различить, UI говорит «три сообщения, distinct incidents не подтверждены», и автоматический threshold не выдаёт точную метрику без основания.

Acceptance M184:

- Одна категория/subject с разными противоположными claims не merge. Exact duplicate одного occurrence не повышает N. Три distinct подтверждённых failure keys создают ровно один process question; повторные ticks и новая доставка тех же данных не создают второй.
- Restart между proposal event и checkpoint даёт тот же question/episode. Два одновременно запущенных tick instance не задваивают эффекты. DB failure сохраняет cursor и visible last error.
- `process` проходит tool→journal→projector→priority→Board→answer→decision fact; категория process не отправляется внешнему получателю. Связь с M152 atomic/idempotent answer сохраняется.
- Deleted reference, forbidden reference и unreachable reference дают три разных результата. Только достоверно dangling reference создаёт proposal, не самовольное retirement. Human correction cannot be buried by agent.
- Accepted improvement имеет task/owner/acceptance и независимый receipt. Закрытие process question само по себе не помечает code fix проверенным. После новой версии и первого нового случая видна ссылка на прежнюю попытку исправления.
- Suppressed local feedback не возвращается при weekly mirror. Service collection off не мешает проектному retro и Board hygiene. Внешний transport недоступен — локальный ретро всё равно работает.

## 5. M191: интерфейс, который показывает действительность

M191 имеет цену небольшого reader и **не зависит от M152/M188/M189/M190**. Это уже записано в [execution brief:483](https://github.com/passioncode-ai/fabric/blob/153b4f029e626230d465d5d21d02fb8c9de5fadf/docs/evidence/plans/2026-09-06-execution-briefs.md#L483), но старый слой во вложении и [backlog:96](https://github.com/passioncode-ai/fabric/blob/153b4f029e626230d465d5d21d02fb8c9de5fadf/docs/evidence/backlog.md#L96) сохраняют последовательность M189→M190→M191. Нужно распространять снятую зависимость, не ждать другого графического экрана.

Первый экран памяти должен отвечать на четыре вопроса: **что хранится; откуда это пришло; что получит следующий агент; что сейчас не удалось прочитать/сохранить**. Внутренние названия таблиц можно оставить в деталях; основной пользовательский язык — память проекта, история работ, пакет следующего запуска, локальное зеркало, база улучшений Fabric.

Предлагаемые readers без нового knowledge store:

1. **Источники и состояние.** Current backend/estate, локально/remote-configured, last successful read, last known seq, independent per-store error; локальные files/preferences отдельно. Нет зелёного «всё синхронизировано», когда известен только последний feed event.
2. **Пакет следующего запуска.** Выбор task/agent/effective configuration; dry compile через тот же selector/compiler, факты с происхождением/порядком, transcript annotations, бюджет, reasons omitted и результаты чтения. Preview не запускает сессию, не выдаёт токен, не создаёт context.compiled event и не повышает счётчик использований памяти.
3. **История знания.** Fact → recorded-by/source → exact source event/session → superseding chain; current и historical отдельно. Решение человека отделено от утверждения агента. Этот trust split уже есть в pack [contextPack:202](https://github.com/passioncode-ai/fabric/blob/153b4f029e626230d465d5d21d02fb8c9de5fadf/apps/desktop/src/main/contextPack.ts#L202), **не планировать его повторно как новый M177**.
4. **Перенос и зеркало.** Путь, manifest охвата, последняя успешная запись, divergent/missing/unreadable, preview изменений и retry. Называть «экспорт объявленных настроек» до выполнения полного ADR-0002. «Отстаёт на N» — только при наличии осмысленного declared cursor; иначе «содержимое отличается».
5. **База улучшений.** Local collection состояние, categories/counts/причины, source в разрешённом scope, pending/suppressed. Внешний раздел появится с реальным contract, и отдельно показывает recipient/preview/delivery/history/retention.

При одинаковых неизменных входах preview bytes/hash должны совпасть с pack на запуске. При изменениях между preview и launch показать, что пакет изменился, или фиксировать input snapshot и явно запускать по нему; сравнение только результата двух последовательных запросов к изменяемой БД не доказывает этот контракт. Pack-выбор сейчас «сначала person, затем agent; внутри каждого current/newest», а не просто общий newest-first из design: [contextPack:149](https://github.com/passioncode-ai/fabric/blob/153b4f029e626230d465d5d21d02fb8c9de5fadf/apps/desktop/src/main/contextPack.ts#L149).

Budget UI должен различать omitted by budget и вне окна maxSessions. Сейчас query ограничен 12 sessions по умолчанию, а omitted считает только полученные кандидаты; старшие сессии вне query не входят в это число [contextPack:112](https://github.com/passioncode-ai/fabric/blob/153b4f029e626230d465d5d21d02fb8c9de5fadf/apps/desktop/src/main/contextPack.ts#L112), [contextPack:214](https://github.com/passioncode-ai/fabric/blob/153b4f029e626230d465d5d21d02fb8c9de5fadf/apps/desktop/src/main/contextPack.ts#L214). Поэтому «опущено 0» не означает «вся история передана». Для исторической byte parity отдельно закрыть DATA-09, не задерживая полезный preview будущего запуска.

Acceptance M191: five-state read fixtures (loading/empty/read/stale/failed или согласованный эквивалент); независимый отказ misses; exact preview↔compile parity на frozen fixture; concurrent source update invalidates preview revision; no session/token/journal side effects; superseded chain с missing source; operator-first selection; budget vs maxSessions omission; mirror removed/read-only/manual divergence; backend env remote при metadata local не маркируется локальным хранением.
