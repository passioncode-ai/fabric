# PassionCode.ai → Fabric: продукт и бренд

Имена подтверждены владельцем 2026-09-07: **PassionCode.ai** — главный бренд, **Fabric** — продукт. Иерархия и позиционирование ниже подготовлены для согласованного переноса в канонические документы и интерфейс; это не новая принятая ADR и не описание уже выпущенных возможностей. Подробный маршрут включён в [объединённый план](2026-09-07-merged-execution-plan.md), карточка S11.

## 1. Иерархия, которая выдержит несколько продуктов

```text
PassionCode.ai                         главный бренд
└── Fabric                        продукт
    ├── Project workspace         рабочая среда проекта
    ├── Command center            состояние, решения и контроль
    ├── IDE                       код, diff, терминал, проверка
    └── Fabric Core               внутреннее название технического ядра

Agent Contract / Agent Adapter    технические компоненты совместимости
Другие будущие продукты           получают собственные имена под PassionCode.ai
```

IDE и командный центр — режимы одного Fabric. Отдельные продукты оправданы, когда у них появятся самостоятельные пользователи, задача и жизненный цикл. Сейчас дробление на Fabric IDE, Fabric Monitor, Fabric Teams и Fabric Cloud породило бы несколько обещаний раньше, чем замкнут один рабочий цикл.

Для первого знакомства: **Fabric by PassionCode.ai**. В заголовке приложения: **Fabric**. В общих материалах: **PassionCode.ai / Fabric**. Написание главного бренда — именно **PassionCode.ai**, адрес — `passioncode.ai`. Переименовывать GitHub namespace, package IDs и appId ради визуальной иерархии не требуется.

Это меняет действующее решение: `CONTEXT.md:10`, `README.md:21`, `docs/adr/0018-passioncode-is-the-product-fabric-is-the-kernel.md`, `docs/brand/terminology.md:20` называют PassionCode.ai продуктом, Fabric ядром. Нужна новая ADR, которая заменяет именно семантику названий; старый документ остаётся историей. Проектная модель и граница ядра сохраняются. В `docs/ux/vision.md:14` уже сформулирована нужная основа: проект, его команда, полномочия, работа, доказательства и обучение переживают смену агента.

## 2. Позиционирование

**Предлагаемая категория:** рабочая среда для проектов, людей и агентов.

**Главное обещание:** вы понимаете состояние проекта и можете продолжить работу с любой совместимой командой агентов, сохранив решения, границы и доказательства результата.

В первой версии продаётся конкретная работа: открыть существующий проект, поручить изменение, увидеть выполненное, разрешить нужное и проверить результат. Понятия Estate, Provider, admission и effect ceiling остаются техническим языком настройки и документации. Их не нужно преподавать до первого полезного действия.

Первый сегмент — технический основатель или небольшая команда, уже работающая с агентами и несколькими репозиториями. Это предложение о фокусе, опирающееся на наблюдаемую P-01 и предложенные P-02/P-03 в `docs/ux/foundation.md:9`; спрос и готовность платить ещё не измерены. Provider builder, федерация организаций и крупная корпоративная платформа — последующие рынки, а не дополнительные условия запуска первой версии.

## 3. Формулировки для проверки на пользователях

Это черновики будущей поверхности. Они не утверждают, что все описанные возможности уже доступны.

**Вариант A, основной**

> Fabric
>
> Рабочая среда для проектов, людей и агентов.
>
> Держите задачи, решения и результаты проекта вместе. Подключайте агентов, проверяйте их работу и продолжайте с того места, где остановилась команда.

**Вариант B, для страницы продукта**

> Проект продолжается. Команда становится сильнее.
>
> Fabric связывает работу людей и агентов с состоянием проекта, его решениями и проверенными результатами.

A понятнее объясняет категорию; B сильнее выражает долговременную ценность, но требует конкретного примера рядом. Английская опорная строка: **The workspace for projects, people, and agents.**

«From vibe coding to passion coding» можно оставить названием редакционной идеи. Главный заголовок должен объяснять продукт и работу пользователя. Фраза «agent-agnostic operating system for AI-native teams» перегружена словами, которые приходится расшифровывать одновременно. Это редакционная оценка; доказательство — проверка понимания на новых пользователях, а не внутреннее голосование о красоте слогана.

До доступной установки основной CTA — «Посмотреть, как работает Fabric» с настоящим сценарием и явным статусом версии. После появления проверенного установщика — «Открыть первый проект». GitHub остаётся отдельным техническим маршрутом. Ни одна кнопка не должна обещать загрузку или ранний доступ, пока такой путь не работает.

## 4. Визуальное направление

Сохранить узнаваемый знак маракуйи и уже подготовленные экспорты (`assets/brand/brand-pack/manifest.json`). На живом сайте 2026-09-07 знак, тёмная подложка, жёлтый акцент и типографика образуют последовательный образ. Перерисовка логотипа сейчас не исправит продуктовые разрывы.

Развести два регистра одной марки:

| Поверхность | Что сохраняется | Как адаптируется |
|---|---|---|
| Сайт PassionCode.ai | знак, семейство шрифтов, узнаваемый акцент | больше воздуха; реальные продукты и примеры вместо карты технических репозиториев |
| Страница Fabric | тот же бренд | первый экран показывает один рабочий цикл и фрагмент интерфейса с настоящими состояниями |
| Приложение Fabric | семантические токены и существующие компоненты | спокойная плотная среда; нейтральные поверхности; акцент для главного действия |
| Будущие продукты | общий словесный знак и типографика | собственный продуктовый символ/акцент после появления самостоятельной задачи |

Для приложения оставить текущий Paperclip pack (`tokens.app.css:1`) и встроенную библиотеку компонентов. Миграция на другую библиотеку исключительно ради вкуса не обоснована. Исправить семантику интерактивных компонентов, контраст и общий контракт темы, затем оценивать композицию.

Цвет не равен статусу: «Нужно решение», «Выполняется», «Остановлено», «Проверено» должны читаться без знания палитры. Не делать весь активный интерфейс жёлтым, все проблемы красными, а все завершения зелёными: завершённая сессия ещё не означает проверенный результат. Разделить состояние исполнения, проверки и необходимость участия человека.

На текущем сайте измерено: при 1280×720 основной hero CTA занимает y=719.4…769.4 и почти целиком ниже первого экрана; верхняя ссылка GitHub доступна. На 390×844 основной CTA помещается, горизонтального переполнения нет. Следующая композиция должна проходить оба размера: полезное описание, основной маршрут и пример результата видны без конкуренции нескольких крупных акцентов.

## 5. Проверяемые критерии бренда

1. Новый читатель после первого экрана может назвать Fabric продуктом, PassionCode.ai главным брендом и привести один сценарий использования. Проверить на отдельных людях; пока это целевой критерий, не измеренный факт.
2. Любое обещание помечено как доступное, экспериментальное или запланированное и связано с проверяемой возможностью. Технический репозиторий не выдаётся за скачиваемый продукт.
3. Один термин имеет одну роль. В интерфейсе «проект», «задача», «запуск», «решение», «проверка»; в настройках можно раскрывать provider/binding, не перегружая рабочие экраны.
4. Живой пример «сигнал → задача → изменение → проверка → результат» занимает меньше объяснений, чем текущая онтология. Пользователь может открыть показанное доказательство.
5. RU/EN передают одинаковые действия и границы. Названия агентов приходят из реестра, поэтому Codex не превращается в «Terminal».

## 6. Карта переноса названия

В одной согласованной поставке: новая ADR → `CONTEXT.md` и vision → brand facts/terminology/channels → README и guides → desktop title/About/icon labels → i18n → public site и structured data → brand locks и narrative gate. `scripts/check-narrative.sh:8` сегодня закрепляет старую формулу; `docs/brand/channels.md` прямо запрещает называть Fabric пользовательским продуктом. Пока правила не изменены, косметическое переименование заставит проверки защищать старый бренд.

Не переименовывать старые ADR, события, идентификаторы tenants, appId и существующие пути данных. Их изменения требуют отдельной миграционной причины. Для адресов сайта сохранить прежние URL или оформить редиректы; структурированные Organization/Product/SoftwareApplication должны различать главный бренд и продукт и содержать только факты текущего выпуска.

Humanization: on — own pass; текст проверен на конкретность, сохранение фактов и различение предложения/реализации. Маркетинговый текст не опубликован.
