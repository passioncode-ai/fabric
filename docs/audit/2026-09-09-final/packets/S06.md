#### solution

##### choice
Question owns immutable revisioned subject/options; many-to-many blocking set is canonical. blocked_by remains only compatibility summary (earliest active blocker), never launch guard. Answer and decision fact are one typed command and transaction. Delivery uses committed continuation outbox; does not wait for full M188 steps.

##### states
- Question open(revision) → answered(resolution_id) | withdrawn(reason) | stale(reason). Terminal resolution cannot overwrite; ask a new question for a new subject or revised decision.
- Block relation active while its question open; resolution removes only that relation from active-set query. Task status remains its rung.
- Continuation pending → addressed → delivered_unconfirmed | accepted | expired/superseded/unknown; independent from answer committed.

##### transactions
- answerQuestion(scope,key,questionId,expectedRevision,answer,chosenOption,basis): lock question and sorted blocked tasks; validate scope, open status, about/subject revision, current option set, principal role and floor via S03.boundary. CEO/product-manager settlement checks current cite/trust/criticality in same command, never caller assertion.
- Allocate decision_id/resolution_id once; append memory.project.recorded@2 and question.answered@2 plus block resolution and continuation-request events in one transaction. Use actual memory event vocabulary, not nonexistent memory.remembered. Commit receipt returns both references and remaining blockers per task. Crash rolls back all; duplicate key returns both same IDs.
- Recompute active blockers by join questions.status=open; order asked_at then question id. Set blocked_by/blocked_since from earliest remaining, null only count=0. Wake/continuation outbox for newly unblocked task only after commit and only once per resolution/task; do not start task when another blocker exists.

##### schema

- continuations {continuation_id PK,source_resolution_id,task_id,source_task_run_id?,recipient_task_run_id?,delivery_id?,state}; UNIQUE(source_resolution_id,task_id)

##### commands
- QuestionAsk({taskId?,text,whyBlocked,kind,about,subjectRevision,options,blocks[]}) → question id/revision
- QuestionAnswer({questionId,expectedRevision,answer,chosenOption?,basisRefs?}) → {resolutionId,decisionId,remainingBlockers:[{taskId,count}],continuations[]}
- QuestionWithdraw({questionId,expectedRevision,reason}) → resolution receipt; does not invent a decision fact

#### invariants
- Answer→decision→unblock is one logical commit, delivery is a separate acknowledged effect.
- No answer to stale subject/options/revision, no second answer overwrite.
- No per-session question count cap; hygiene may group duplicate obligations but cannot delete them.

#### failure_cases
- Two questions on task, answer first → still blocked by second.
- Question resolved by colleague while operator edits → stale_revision with current state, no overwritten answer.
- Recipient execution ended after commit → continuation remains addressed to task/new admitted TaskRun, not last open terminal.

#### migration
- Backfill blocker estate/project from both parents and quarantine invalid legacy links without rewriting journal. Replace apply_questions with deterministic recomputation compatible with @1; add v2 branch for explicit resolution id.
- Keep legacy answered questions without decision_id as legacy_missing_decision, not fabricate an answer fact; UI indicates gap. New writes require atomic decision link.
- Revoke direct table DML and raw guarded question answer events after all callers switch. M152.commit builds on this; M152.continue additionally consumes S04/M103.
