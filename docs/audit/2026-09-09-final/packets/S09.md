#### solution
- Сохранить estate как tenant boundary и owner/member как начальную минимальную модель. Identity берётся из проверенной auth-сессии на server-side command boundary, actor_id из renderer не принимается. Owner управляет membership/agent binding/grants; member читает дозволенное и создаёт/ведёт проектные задачи, но не выдаёт себе полномочий.
- В v1 membership даёт estate-wide project visibility. Project-only/private memberships не имитировать фильтром renderer: это отдельная будущая capability; текущий owner/member интерфейс явно показывает estate scope.
- Onboarding минимален: создать/выбрать estate → подключить или создать project/repository → проверить readiness выбранного исполнителя → создать первую задачу → открыть результат и receipt. Полная организация/все настройки не обязательны. Return journey начинается с addressed Inbox и изменений после lastSeen.
- Revocation увеличивает membership revision и делает новые команды недопустимыми. Действующая команда повторно проверяет authority перед внешним dispatch; активная executor lease отменяется/ограничивается при отзыве. Уже выполненный эффект не стирается.

#### interfaces
- ActorContext {person_id,estate_id,membership_role,membership_revision,session_expiry}; создан доверенным verifier, не IPC payload.
- MembershipCommand {command_id,expected_revision,target_person_id,role:owner|member,action:invite|accept|revoke}; output {status:committed|conflict|refused,receipt_ref}. Invite: random single-use token hash only, expiry, intended identity, audited acceptance.
- OnboardingState {estate_id?,project_id?,repo_status:absent|checking|ready|error,runner_status:unknown|checking|ready|unavailable,first_task_id?,last_completed_step}; settings persisted atomically per user.

#### invariants
- Последнего owner нельзя отозвать; передача требует атомарного добавления нового owner.
- Повтор invite accept с тем же command_id возвращает прежний receipt, не повторную membership.
- Профиль человека не является источником authorization.
- Funnel events являются локальными/estate operational observations, а не автоматической отправкой analytics наружу.

#### failure_cases
- Revoke between read and write -> revision conflict; operation not executed.
- Member accesses foreign estate through guessed task ID -> uniform scoped not_found/refused without object disclosure.
- Two tabs accept invite -> one transaction wins, second idempotent result.
- Failed runner setup keeps project/repo and entered instruction; retry readiness, not recreate project.

#### migration
- Existing local owner is migrated only through verified account-link confirmation; never match people by display_name. Keep service identity separate from person membership.
- User-facing invite/send needs recipient and delivery choice in implementation run; do not send invitations as part of this documentation change.

#### tests
- Two synthetic authenticated identities: owner allowed grant, member denied same; after revoke old token denied even with cached UI.
- Last-owner concurrent revoke -> both cannot succeed.
- Onboarding fixture from empty and returning project; duplicate create click yields one project; result deep-link restored after restart.
