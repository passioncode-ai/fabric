#### solution

##### choice
FailureRecord normalizes kind, origin, evidence, certainty, scope and safe recovery. Preserve runtime termination separately from task-domain result. A successful test of impossibility can be a task result with outcome no; it is not an agent crash.

##### kinds
- runner-missing
- skill-failed-to-load
- harness-unreachable
- agent-crashed
- agent-wedged
- task-failed-honestly
- advisory-model-failed
- notifier-source-down
- unknown

##### classification
- runner-missing requires failed executable resolution/spawn ENOENT evidence; skill-failed requires loader/protocol reported error, not merely missing orientation.
- agent-crashed requires observed abnormal process/invocation termination; agent-wedged gap-only evidence carries certainty=suspected and presents suspicion. If source health unavailable, classify unknown/host observation condition.
- task-failed-honestly requires typed agent result with claim/proof/notVerified and target invocation; submits review. Exit0 alone produces no successful task result; exit!=0 alone does not describe whether domain work failed honestly.
- Retryability derives operation semantics and effect state: validation/policy/credentials terminal until changed input; transient infrastructure bounded; outcome_unknown reconcile_only. Recovery action is typed and server revalidates conditions on click.

##### transactions
- Record failure occurrence once by source observation id/attempt; append safe evidence ref and stage. Do not overwrite terminal receipt after new run. Later corrected diagnosis appends diagnosis.superseded linking previous record; old cause stays in history.
- executeRecovery({failureId,expectedRevision,action}) validates currently allowed action, then uses existing launch/command/cancel ports with idempotency. UI cannot invoke hidden retry that bypasses quota/fence.

#### invariants
- Every diagnosis names what observed it; unknown is an explicit valid result.
- Failure recovery does not erase past run/result.
- Business negative result and runtime crash have different receipts/actions.

#### failure_cases
- Toolcall silence → no automatic harness-unreachable kind.
- Provider timeout with possibly executed effect → reconcile_only, never retry_new_key.
- User clicks stale recovery after issue already resolved → no mutation and current receipt.

#### migration
- Add versioned failure event and typed DTO; keep existing reason strings as legacy_unclassified source evidence. Never infer precise kind from arbitrary human prose alone.
- Existing task.finished/abandoned retained historically; new runtime ended event no longer auto-equates to task done/cancelled.
- Map taxonomy names consistently in protocol, schema, UI and docs; agent-wedged suspected wording changes presentation, not evidence.
