### observed
Два тика реального createChainAdvance с fake store вызывают два новых запуска без taskId. Проход по каждому follows вместо группировки даёт частичный join. startExisting не подключён к этому пути.

### solution
Один общий admitExistingTask command для UI, chain, answer и routine; routine создаёт task один раз на cycle window, chain использует follower.id. TaskRun/session identity фиксируется до spawn либо связывается атомарной распиской; не обновлять только leases.

### steps
- Добавить регрессионные проверки двух тиков и A+B→C, включая незавершённого/failed родителя и конфликт имён payload.
- Группировать incoming follows, закреплять все predecessor result refs; получать один admission idempotency key для follower invocation.
- Вынести общий admission/dispatch из IPC handler; передавать реальный taskRun/session binding через PTY, delivery, tool trace и terminal close.
- Сохранять launch outbox и попытку; после crash/timeout сверять реальный процесс, uncertain не respawn автоматически.
- Подключить Run existing в TaskPage/Board и continuation; проверить отсутствие нового task.created при запуске follower.

### acceptance
- N повторов одного окна и два конкурентных host дают максимум один active TaskRun и один spawn.
- Все обязательные родители/outputs нужны одновременно; недоступное чтение не разрешает запуск.
- Два blockers: первый answer не запускает; последний answer продолжает ровно исходную задачу.
- Spawn failure/exit/cancel завершают правильный TaskRun; lease и deliveries относятся к тому же session.
