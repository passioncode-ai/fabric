Reviewer: fresh, independent (did not read the iteration-1 ledger or reports before writing these findings).
Candidate: `main` at `2927a087` (worktree `<worktrees>/hubv-read`, detached), change = `67a5dc42` + `2927a087`.
Method: the REAL `AgentAccessPanel`, `BoardScreen` → `ObligationActs` and `consentPrompt` mounted in a scratch Vite
harness (`harness/main.tsx` beside this file) with the app's token/style/launch CSS, `I18nProvider` (en/ru),

## Findings

(written incrementally; see the end for counts)

### UX-1 — blocking — the queue's Allow/Deny answer leaks into the NEXT access request opened in the same detail pane
- **Where:** `apps/desktop/src/renderer/src/launch/ObligationActs.tsx:124-154` (`AccessActs` keeps `state` = `'allowed'|'denied'` in local `useState`) rendered at `launch/BoardScreen.tsx:278` as `<ObligationActs item={chosen.entry} …/>` with **no `key`**. Choosing another row keeps the same component instance, so its state survives.
- **Evidence:** `pw/interact.mjs` case 1, real `BoardScreen` with two pending requests (Research desk, mailbot): click "Allow Research desk" → detail says *Allowed*; click row 02 → the mailbot detail says **"Allowed"** with no Deny/Allow, while the mock recorded only one call: `calls [["decide","req-1","allowed"]]`. Screenshot `harness/shots/17-board-second-row-after-allow-en.png`. The same holds after Deny ("Denied" on a request nobody denied), and for the `connectProblem` line.
- **Why blocking:** a consent surface states a decision that was never made; the operator moves on believing mailbot is allowed (or denied) and the request silently expires, or the act is unreachable from the queue until the pane remounts.
- **Fix:** key the acts by the request — `<ObligationActs key={chosen.entry.ref} …/>` (or key `AccessActs` by `access.requestId`), and re-read the board after a decision (`AccessActs` never calls the board's `reload`, so the row stays "Needs attention" in the list). Test: two access rows, decide the first, open the second, expect its own Deny/Allow.

### UX-2 — blocking — Reconnect: no "waiting" state, and an immediate false claim that Fabric stopped using the live key
- **Where:** `AgentAccessPanel.tsx:113` shows the waiting line only `&& !p.connection`, so a Reconnect in progress (`lastAttempt: {outcome:'waiting', reconnect:true}`, built in `main/index.ts` `hubOverview`) shows nothing; `AgentAccessPanel.tsx:121` passes `after: () => keyStays(p.name)` to Reconnect, so the moment the connect link is merely OPENED the panel says `access.products.keyStays` = "Fabric no longer uses the previous key. It stays valid in Fabric Inbox → Agent access until you revoke it there."
- **Evidence:** `harness/shots/03-reconnect-waiting-en-light.png` (connected + reconnect waiting: no waiting line, Reconnect still enabled); `pw/interact.mjs` case 4 → `AFTER RECONNECT CLICK: … Fabric no longer uses the previous key. It stays valid in Fabric Inbox → Agent access until you revoke it there.` (`harness/shots/20-after-reconnect-click-en.png`). ADR-0115 amendment 13 and SCN-133 say the opposite: until the product delivers a new key that is stored and recorded, *the previous connection stays live*; a Deny in the product, a vault failure or no answer keeps it.
- **Why blocking:** the sentence invites the operator to revoke, in Fabric Inbox, the very key Fabric is still using — which breaks every agent call through the hub — and the screen gives no sign that an answer is awaited in the product (SCR-76 `waiting` state is undrawn for Reconnect).
- **Fix:** show `access.products.waiting` whenever `lastAttempt.outcome === 'waiting'` (connected or not); say `keyStays` only after Disconnect, and after a Reconnect only once `lastAttempt.outcome === 'connected' && lastAttempt.reconnect`. Disable Reconnect/Connect while a waiting attempt is open (see UX-9). Test both.

### UX-3 — blocking — a long mailbox runs out of the card on both Allow surfaces; the operator cannot read the whole resource being granted
- **Where:** `.access-asks` (`styles.css:314`) and `.lp-facts-asks` (`launch/launch.css:418`) have no `overflow-wrap`; the address is one unbreakable token. (Grant rows are fine: `.row-main` has `overflow-wrap:anywhere`, `components.css:121`; the native prompt wraps.)
- **Evidence:** SCR-76 at 1280 px with `cloudflare:a.really.long.local.part.for.testing@subdomain.of.a.long.domain.example.com`: `pw/shoot.mjs` 21 → `"over": ["panel:561>325","access-card:544>291","access-asks:536>275"]`, screenshot `harness/shots/crop-21.png` (address cut at "…@subdomai" outside the card). Queue detail (SCR-41): case 24 → `li: {sw:437, cw:331}`, `harness/shots/crop-24.png` (cut at "…example.exam"). A realistic 50-character address (e.g. `weekly-digest@newsletters.example-company.com`) already exceeds the ~275 px column of the 22rem panel.
- **Why blocking:** ADR-0115 amendment 2 / 17 — the queue and Settings show "the same facts as the prompt before their Allow", byte-for-byte; here the tail (the domain) can be off-screen while Allow is one click away.
- **Fix:** `overflow-wrap:anywhere` on `.access-asks li`, `.lp-facts-asks li` (and `.access-card p` for ids/repositories). Test: render a 120-char address in both and assert `scrollWidth <= clientWidth`.

### UX-4 — non-blocking — `.lp-facts` override flattens every fact grid in the launch screens
- **Where:** `launch/launch.css:416` (added in `2927a087`) `.lp-facts{display:flex;flex-direction:column;…}` is unscoped and comes after the prototype's `.lp-facts{display:grid;grid-template-columns:repeat(3,…)}` (`launch.css:134`). Every `dl.lp-facts` — `BoardScreen.tsx:250, 309, 329` and `ReleasesScreen.tsx:130` — becomes a single stacked column.
- **Evidence:** case 13 computed style of the board's `<dl class="lp-facts">`: `"display":"flex","flexDirection":"column"` (State/Waiting stacked, `harness/shots/13-board-access-en-light.png`).
- **Fix:** give the access block its own class (e.g. `.lp-access-facts`) or scope the rule (`div.lp-facts`), and check the Board and Releases previews against the prototype.

### UX-5 — non-blocking — English machine text inside Russian sentences on the connect/unreadable lines
- **Where:** `sayConnectProblem` appends `problem.detail` into the localised sentence (`shared/accessWords.ts:71-74`); details come from `productConnect.ts:233, 251, 359, 380, 394` (OS error, Observatory's refusal, validation list, DB message); `AgentAccessPanel.tsx:52` shows `humaniseError(e).detail` (DB text) in `access.unreadable`; `hub.offDetail` shows `startHub`'s English reason.
- **Evidence (ru):** `05-failed-vault-ru-dark` → "…поэтому Fabric Inbox его отзывает. use_secret.py: project fabric has no vault (run vault.py init)"; case 18 → "Разрешено. Не удалось открыть Fabric Inbox. Установлено ли его приложение? No application knows how to open URL fabric-inbox://connect?… Подключите его…"; `10-unreadable-ru-light` → "Не удалось прочитать доступ агентов: relation "access_requests" does not exist."; `09-huboff-ru-dark` second line in English (mock text); the real reasons are Fabric-authored English instructions, not machine words — `main/hub.ts:53` "…Correct or remove it, then quit and reopen Fabric", `:61` "…Move that agent to another port (or choose a free one for Fabric with FABRIC_HUB_PORT), then quit and reopen Fabric", `:161` — and the port-claimed remedy ("move that agent") exists only in English while the localised line says only "free the port". SCR-76 allows the machine's reason only for hub-off, "as a second line"; SCN-132 step 3 says every word is in the operator's language.
- **Fix:** render `detail` as its own muted secondary line ("What Fabric saw: …"/«Что увидел Fabric: …», as hub-off does) instead of inline; drop the instruction tail from the hub-off reason.

### UX-6 — non-blocking — the late-record-not-withdrawn outcome contradicts itself and carries a Fabric-authored English instruction
- **Where:** `main/productConnect.ts:415` → `{ code: 'record-failed', detail: 'the late record could not be withdrawn; disconnect it in Settings → Agent access' }`.
- **Evidence:** `06-connected-latefailed-ru-light`: card says *подключён к …* and, under it, «Fabric не смог записать подключение, поэтому Fabric Inbox отзывает ключ. the late record could not be withdrawn; disconnect it in Settings → Agent access». The connection WAS recorded (it is live), the product has revoked its key, so the live connection is dead, and the instruction is English.
- **Fix:** a code of its own (e.g. `withdraw-failed`) with en/ru words: "Fabric recorded the key after Fabric Inbox stopped waiting and could not undo it; Fabric Inbox revoked the key, so this connection will not work — Disconnect, then Connect." Test in `accessWords.test.ts`'s ru scan.

### UX-7 — non-blocking (a11y) — focus is dropped to `<body>` on every act
- **Where:** `AgentAccessPanel.tsx:62-75` disables every button while `busy` and then re-reads; the focused button is disabled (focus fix-up) and the card it lived in is removed.
- **Evidence:** case 2: `focus before BUTTON Allow Research desk`, `focus while busy BODY`, `focus after allow BODY`, `focus after revoke BODY`. A keyboard/VoiceOver user lands at the top of the document after each Allow/Deny/Revoke/Clear.
- **Fix:** keep the acting button enabled-but-`aria-disabled` while busy, and after the re-read move focus to the next card's first control or to the section heading (make `h3`/`h4` `tabIndex={-1}`); same for `AccessActs` in the queue.

### UX-8 — non-blocking (a11y) — "Allow and connect Fabric Inbox" is announced as "Allow Research desk"
- **Where:** `AgentAccessPanel.tsx:204` and `ObligationActs.tsx:167`: `aria-label={t('access.allowFor', { name })}` replaces the visible text `sayAllow(t, r)`.
- **Evidence:** case 2 `BUTTONS`: `["Allow","Allow Research desk"]`; with an unconnected product the visible label is "Allow and connect Fabric Inbox"/«Разрешить и подключить Fabric Inbox» but the accessible name stays «Разрешить: Research desk» — the screen-reader user is not told that Allow also opens Fabric Inbox, and voice control ("click Allow and connect") fails (WCAG 2.5.3 label in name).
- **Fix:** accessible name = visible label + agent ("Allow and connect Fabric Inbox for Research desk"), e.g. a key `access.allowConnectFor`.

### UX-9 — non-blocking — Connect stays enabled while the product is already waiting
- **Where:** `AgentAccessPanel.tsx:124` disables Connect only on `busy`/`!listening`.
- **Evidence:** `04-notconnected-waiting-ru-light`: «Ждём вашего ответа в Fabric Inbox.» with a primary «Подключить» under it; a second click opens a second consent in Fabric Inbox (up to 3, then `busy`).
- **Fix:** while `lastAttempt.outcome === 'waiting'` show the waiting line with the button disabled (or labelled "Open Fabric Inbox again").

### UX-10 — non-blocking — narrow window: product acts overflow the card
- **Evidence:** 760 px wide, ru dark (`harness/shots/crop-22.png`): «Отключить» sticks out of the product card's right border; `.toolbar` (`components.css:126`) does not wrap outside `.panel-head`. Electron's main window sets no `minWidth` (`grep minWidth main/index.ts` → nothing).
- **Fix:** `.access-acts .toolbar{flex-wrap:wrap}`.

### UX-11 — non-blocking — copy
- Denied list reads as a fragment: "**Spammer** send mail in ceo@example.com" / «**Spammer** отправлять почту в …» (`AgentAccessPanel.tsx:170`) — needs "asked to"/«просил:».
- Inside Settings → Agent access, `access.allowedConnect` tells the operator to "open Agent access in settings" — the screen they are on.
- The native prompt quotes the reason with “…” in ru (`accessWords.ts:97`) while the panel and queue use «…» (`ru.ts:290`).
- The prompt says "Allow also opens Fabric Inbox" / «"Разрешить" также откроет…» while the button reads "Allow and connect Fabric Inbox".
- `keyStays` after Disconnect says "the previous key" for the key that was current.
- On macOS `dialog.showMessageBox` does not display `title`, so the question "Allow Research desk to use Fabric Inbox?" is never seen; the bold line is the statement `access.prompt.message`. Consider making `message` the question.

## What is sound (measured)
- Every consent sentence is phrased from `en.ts`/`ru.ts` (122 `access.*` keys in each, `grep -c`); en and ru render completely on the panel, queue row and native prompt (shots 01, 02, 04, 14; case 15 prompt in ru incl. «Разрешить и подключить Fabric Inbox»).
- The native prompt: Deny is `defaultId`/`cancelId` 0; shows registry name+id, installed-by, source, each ask line, the quoted reason cut at 300 with "…", the same-user floor, incremental/credential line, the year, and the not-connected line (cases 15, 16). Untrusted text is one line (`oneLine`) and interpolation is single-pass, so a `{name}` in a reason is not expanded (`translate.ts:19`).
- States drawn: loading (`11`), unreadable with Try again and never "no agent has access" (`10`), hub-off warning with Connect/Reconnect disabled and sessions unaffected (`09`), empty lists said in words incl. denials (`12`), not connected/waiting (`04`), failed with Try again (`05`), withdrawn + previousLost (`07`), declined (`08`), connected with server and localised date (`01`, `02`: `10/1/2026` / `01.10.2026`).
- Light and dark both legible; the warning ink border and the danger "Revoke all" read in both (01, 02, 05, 09).
- Buttons that act on an agent carry its name for a screen reader ("Revoke for Research desk: read mail in news@example.com", "Revoke all for mailbot", "Clear the denial for Spammer"); heading outline h2 → h3 sections → h4 cards (case 2).
- Queue: the access row is titled "<name> asks to use Fabric Inbox"/«… просит доступ к Fabric Inbox», ranked first, its detail shows the prompt's facts above Deny/Allow (13, 14); a refusal is said in the operator's language (case 19: «Не сделано: Запрос истёк до ответа; агент должен попросить снова.»).
- One side panel at a time (`sidePanel.ts`, App `panel` state).
