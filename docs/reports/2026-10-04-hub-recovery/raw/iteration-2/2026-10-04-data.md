## Findings

### DA-1 — BLOCKING — live grants and live credentials the operator cannot see or revoke (capped, oldest-first reads)

Evidence (`probe-pages.mjs`, real `AccessService`/`createAccessStore` over `psql-rest`, fully migrated schema):

- `normaliseAccessRequest` admits 32 capabilities × 64 resources (`apps/desktop/src/shared/access.ts:204`, `:215`);
  `decide` writes one grant per pair (`accessService.ts` `decide`, `grants = row.capabilities.flatMap(...)`). One
  request of 32 × 32, one Allow → **1024 live grants in the database**.
- `grantsOf` and `liveGrants` read `.limit(1000)` ordered by `decided_at` ascending (`accessStore.ts` `grantsOf`,
  `liveGrants`; PostgREST `max_rows = 1000` in `supabase/config.toml:18` caps it anyway). Measured:
  `grantsListedInStatus: 1000`, `liveGrantsOfBinding: 1000`, `grantsTheCallPathCannotSee: 24`,
  `overviewGrantsShown: 1000`.
- A granted pair outside the page is **refused at call** (`coverage` over `liveGrantsOf`): `REFUSED (your grant for
  tool_31 does not cover box08@example.com)`.
- **Revoke of that live grant is refused**: `revokeGrant` looks the id up in `liveGrants()` (`accessService.ts`
  `revokeGrant`) → `{ ok:false, code:'not-live' }`, while the database row is still live (`stillLiveAfterRevoke: t`).
- Bindings: `bindings()` reads 500, oldest first, revoked ones included (`accessStore.ts` `bindings`). After 500 older
  (revoked) bindings, a new agent completes consent and claims its credential (`newBindingLiveInDb: 1`) and the
  operator's list does **not** show it (`newBindingInOverview: false`, `overviewBindings: ["example-agent.default"]`)
  — Settings → Agent access offers no Revoke for a live credential.
- `liveGrants` has no expiry filter and expired grants are never revoked, so the oldest-first page fills with dead rows
  over time: the same loss happens without any single large request.

Why blocking: ADR-0115 §3 rests on "standing, narrow, **revocable**"; here a live grant/credential exists that the
operator is not shown and (for grants) cannot revoke, and the iteration-1 DA-5 fix ("filtered and counted by the
database, never a capped page filtered here") was applied to requests only.

Fix: read live state in the query — grants `revoked_at is null and expires_at > now`, bindings `revoked_at is null`
(and claimed or within the claim window), newest first, paged to completion or counted; `revokeGrant` reads the grant
by id (`eq('id', grantId)`), not out of a page; authorise `agent.call` with a covering query
(`binding_id, callee, capability, resource in (...)`) instead of a capped list; bound capabilities × resources per
request (e.g. ≤ 256 pairs) in the normaliser AND in `apply_hub_access`. Test: one Allow of 32 × 32 → every grant
listed, callable and revocable; 501 bindings → the newest listed.

### DA-2 — MEDIUM (non-blocking) — a restored pending request is still decidable, and the SOURCE's poll secret collects the credential in the target

Evidence (`estate-s.sql` → `restore_estate` into `fabric_dispatch_test_v2c`, then the target's own acts):

- Restored request `…013` comes back `pending`, `expires_at > now()`, `poll_verifier` = the source's
  (`source_poll_verifier_kept: t`).
- In the target, `append_event(T,'access.decided@1', allow, new_binding)` for it → **accepted (seq 17)**; the binding
  is above the watermark, so it is live; `access.credential.claimed@1` → **accepted (seq 18)**, binding live with a
  verifier. In the app, `AccessService.status` would mint that credential to whoever presents the poll secret minted
  in the SOURCE estate (`status`: door + `sameToken(verifierOf(pollSecret), row.poll_verifier)`).
- Window: the request's 10 minutes; the target's queue lists it (`overview` reads `pending` + `liveAt`) although the
  agent asked a different estate.

Migration 77 §2 says "an event at or below the watermark projects as history only", but the poll verifier is
authority (RFC 8628's device_code) and it crosses the boundary. Fix: at or below the watermark project
`access.requested@1` with `poll_verifier = null` and refuse an `access.decided@1` above the watermark for a request
at or below it ("restored request; the agent asks again here"). Test: restore an archive with a live pending
request → it cannot be decided and its status cannot be read with the source's secret.

### DA-3 — MEDIUM (non-blocking) — the agent.call idempotency memory keeps product answers whole, unbounded in size, and past revocation

Evidence (`node --expose-gc probe-memory.mjs`, real `createAgentCall`, the product answering a 4 MiB body):
`{"calls":64,"answerMiB":4,"heapGrowthMiBAfterCalls":512,"heapGrowthMiBAfterRevokeAndGc":512}`.

- `remembered` keeps each produced answer (the full envelope, output included) for 24 h, up to 256 keys **per
  binding**, with no byte bound (`hubCall.ts` `IDEMPOTENCY_TTL_MS`, `IDEMPOTENCY_MAX_PER_BINDING`), and the
  forwarder bounds time but not size (`productForwarder.ts`: `timeout`, no byte cap).
- Expiry is swept only when THAT binding calls again (`for (const [k, v] of mine) …` inside `agentCall`); a revoked
  binding never calls again, so its answers stay until the app quits (measured: unchanged after revoke + GC).
- One consented agent can therefore pin 256 × (answer size) in Electron's main process (64 calls already 512 MiB),
  and every past binding's memory accumulates.

Fix: remember only answers under a byte bound (or a hash and a re-fetch rule), cap total bytes across bindings, sweep
on a timer, drop a binding's memory on `access.binding.revoked@1`. Test: N large answers stay under the cap; a
revoked binding's memory is released.

### DA-4 — LOW — migration 74's one-spelling rule does not reach the hub keys the door now reads

Evidence (`fabric_dispatch_test_v2a`): `access.requested@1` with `binding_id = '{A0000000-0000-4000-8000-000000000021}'`
→ accepted (seq 7); `access.decided@1` with `request_id` upper-case, `binding_id` without hyphens and
`grants[0].id = 'A0000000-…-0000000000FF'` → accepted (seq 8). The projector stores canonical ids; the journal keeps
`{A0000000-…}` / `A0000000000040008000000000000021` / `A0000000-…FF`.

`refuse_noncanonical_identity` (`20261003000074_canonical_ids_at_the_door.sql:92`) checks only `id, project_id,
session_id, task_id, note_id, task_run_id, delivery_id`; migration 77's door reads `binding_id` and `grants[].id` and
the projector reads `request_id`, `grant_id` — so spans' `grant_ids`, an export or any journal reader comparing
strings can disagree with the projection, the exact failure 74 was written against. Not exploitable through the app
(the writer mints `randomUUID()`), hence low. Fix: extend the key list (and `grants[].id`) in a migration 78 and test.

### DA-5 — LOW — the hub's own refusals of an ask leave no trace

Evidence (`accessService.ts` `request`): the per-agent cap (`maxPendingPerAgent`), the global cap (`maxPending`), the
standing-denial answer and the "already with the operator" answer return without `ops.record` and without a journal
event (only the unknown-agent refusal is recorded, `hub.access.refused`). A loop that fills the 20-slot queue for
10 minutes — which blocks every other agent's first request — is invisible in Fabric's operations log. Fix: one
`ops.record({ op: 'hub.access.refused', detail: { code: 'per-agent-cap' | 'queue-full' | 'denied-standing' } })`
each; test that a capped ask is logged.

### DA-6 — LOW — hash-only storage is the writer's promise, not the schema's, for three hub events

Evidence (`fabric_dispatch_test_v2a`, estate `aaaaaaaa-…-0003`): accepted and journalled —
`access.requested@1` carrying `poll_secret: 'PLAINTEXT-POLL-SECRET'` (seq 1), `access.credential.claimed@1` carrying
`credential: 'PLAINTEXT-CREDENTIAL'` beside a valid verifier (seq 3), `product.connected@1` carrying
`client_secret: 'PLAINTEXT-PRODUCT-SECRET'` beside a valid `secret_ref` (seq 4): `journal holds plaintext | 3`.
The columns are safe (a raw credential as `verifier` is refused by `access_bindings_verifier_check`), but the journal
is append-only and travels in exports, so one writer slip is a permanent leak. Migration 77 closed exactly this class
for spans (key allowlist) and `secret_ref`, not for the three events that carry the hub's secrets' hashes. Today's
writer sends only documented keys (`accessService.ts`, `productConnect.ts`), hence low. Fix: a key allowlist in
`apply_hub_access` for `access.requested@1`, `access.credential.claimed@1`, `product.connected@1` (as for
`hub.call.forwarded@1`), with a test per event.
