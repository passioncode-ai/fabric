### PL-2 — The live-database upgrade order the plan cites is not in the runbook it cites, and the app does not give the command the runbook promises
- Severity: **high, release-blocking candidate** (0.3.1 is the first release a published-build user upgrades
  across a schema change: 0.3.0 requires exactly 75, 0.3.1 exactly 77).
- Evidence:
  - P-08 cites "(backup, rehearsal on a copy, `supabase migration up`; [release runbook](../../../../launch/release-mac.md))".
    `docs/launch/release-mac.md` (116 lines) has no dump, no rehearsal on a copy, no `supabase migration up`, no
    read check (`grep -n -iE 'dump|pg_dump|migration up|rehears.*copy'` → only the CI tag rehearsal, line 88).
  - `release-mac.md` §What the installed app needs: "A newer build whose schema is ahead of an existing database
    stops with the exact command to run in that stack folder". The code does not:
    `apps/desktop/src/main/schemaReadiness.ts#withSchemaReadiness` throws "The database schema is 75; this build
    requires 77–77. Follow the database upgrade plan, then retry…", and
    `apps/desktop/src/shared/startupFailure.ts` maps `FABRIC_SCHEMA_NOT_READY` to "Follow the details below, then
    retry." No command; and no document named "database upgrade plan" exists
    (`git grep -iE 'database upgrade plan'` → only the throw site).
  - The working copy of the stack does receive the new migrations (`bundledStack.ts`: copies changed migrations),
    so `supabase migration up --local` in `~/Library/Application Support/Fabric/stack` is the real step — it is
    simply written nowhere a user or the operator reads it for this release.
- Fix: a "Upgrading an existing database" section in `release-mac.md` (stop Fabric → install 0.3.1 → `pg_dump`
  → restore into a copy and `supabase migration up` there → `supabase migration up --local` in the stack folder →
  the read check, e.g. `select max(version)` = 77 and the journal count before/after), and the
  schema-behind message names that command and the section (with a test on the message). Or rule it with a
  CO row and say in CHANGELOG 0.3.1 that a 0.3.0 user must run the command.

### PL-3 — The release notes extractor publishes an "(unreleased)" section, and nothing refuses a release whose CHANGELOG was not renamed
- Severity: **medium**.
- Evidence: the shared publish workflow (`passioncode-ai/.github/.github/workflows/release-publish.yml@v1`,
  step "Release notes from the CHANGELOG") matches `^## <version>([ —-]|$)`, so `## 0.3.1 (unreleased)` matches
  and its body — "Not released yet: the version bump and the tag follow the third verification iteration…" —
  would become the 0.3.1 notes. `scripts/release-mac.mjs` / `scripts/lib/release-mac.mjs` contain no
  `CHANGELOG` check (`grep -iE 'changelog|unreleased'` → nothing). Precedent: v0.3.0 was published with the
  fallback body "Release v0.3.0." (`gh release view v0.3.0` → body starts "Release v0.3.0."), which is why
  2927a087 added a retroactive `## 0.3.0`.
- Fix: preflight (`release-mac.mjs --check-only`) refuses unless `CHANGELOG.md` has exactly one `## X.Y.Z`
  heading with nothing after the version, with a test; or the shared workflow excludes "(unreleased)".
