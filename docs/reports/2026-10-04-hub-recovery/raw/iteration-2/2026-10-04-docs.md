### DO-1 — MEDIUM — Reconnect tells the operator "Fabric no longer uses the previous key" before anything changed
- Evidence: `AgentAccessPanel.tsx:121` passes `after: () => keyStays(p.name)` to Reconnect; `act()` (`:60-72`) shows
  `after` as soon as `hub.connect(product,{reconnect:true})` returns ok — i.e. when `ProductConnector.begin` has only
  opened the link (`productConnect.ts:222-258`, outcome `waiting`). `en.ts:865` `access.products.keyStays` = "Fabric no
  longer uses the previous key. It stays valid in {name} → Agent access until you revoke it there." (`ru.ts:305` same).
  The code and every doc say the opposite: the previous connection stays LIVE until the new key is stored and recorded,
  and stays live for good if the product denies, fails, the vault refuses or the deadline passes
  (`productConnect.ts:26-31`; ADR-0115 amendment 13 "a failed or slow vault leaves the previous connection live";
  SCN-133 Errors & recovery; SCR-76 says only "a line that the previous key stays valid in the product").
- Fix: on Reconnect say the waiting line only; say keyStays after `lastAttempt.outcome === 'connected' && reconnect`
  (or word it "When Fabric Inbox delivers the new key, Fabric stops using the previous one; it stays valid there until
  you revoke it"). Disconnect keeps its line (there it is true). Add a panel test for the reconnect→denied path.

### DO-2 — MEDIUM — ADR-0115 amendment 19 (the agent-facing wire contract) misdescribes `agent.call`'s answer
- Evidence: amendment 19 table: `agent.call` → "the product's own answer, or a refusal"; "A refusal is `isError: true`
  with `{error: {code, message, data?}}`", and `product-error` is listed among refusal codes. Code: a forwarded call
  answers the fabric-interop result ENVELOPE (`hubCall.ts:104-133`, `:226-227`: `{id, contractVersion, outcome,
  done, proof, scope, notVerified, artifacts, output, usage, trace, createdAt, producer}`), the product's output in
  `output`. When the product itself answers `isError`, Fabric returns that envelope with `isError: true`,
  `outcome: 'failed'` and NO `error` object (`hubCall.ts:223-227`); `product-error` is the code only of a span
  (`:224`) or of a transport-side failure from `forwardToProduct` (`productForwarder.ts:59,63,142`). An agent following
  the ADR reads `isError` and looks for `error.code` that is not there. `hubCall.ts`'s own header item 7 states the
  envelope correctly — the ADR does not.
- Fix: amend the table: answer = the interop result envelope (`outcome: succeeded|failed`, product output in `output`);
  `isError: true` + envelope = the product answered with an error; `isError: true` + `{error:{code}}` = Fabric refused
  or could not reach it. Name 413 (body too large) beside 401/429/503 (`agentSurface.ts`).
