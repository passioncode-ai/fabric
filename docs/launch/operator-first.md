# R0: снять нагрузку с оператора

**Текущий приоритет:** связать первую версию в целые пользовательские пути, затем уменьшать визуальный шум. [Аудит путей](../ux/audits/2026-09-15-r0-operator.md) → [план исполнения](../ux/plans/2026-09-15-r0-operator.md) → [контракт общения и управления](../architecture/operator-interaction.md).

Статус: аудит и план по запросу оператора 2026-09-15, исходники `192cdcc29a9145d930bc696a9658f95987bceeb7` (wiki v63). Это новая детализация R0; исправления UI и подключение runtime ещё не выполнены. Старые планы и идеи сохраняются.

## Профессиональная постановка задачи

Спроектировать и проверить первую версию Fabric как рабочую среду управления несколькими проектами, в которой оператор быстро восстанавливает контекст, видит только требующие его участия вопросы, принимает обоснованные решения и возвращается к работе без ручного восстановления истории. Проверять не наличие экрана, а достижение результата: понятный вход → достаточный контекст → доступное действие → подтверждённый исход → согласованное состояние связанных экранов → возможность вернуться и понять произошедшее.

Fabric должен самостоятельно выполнять разрешённую рутинную работу, объяснять свои действия и поднимать исключения с готовыми вариантами. Текстовый и голосовой разговор — способы ввода информации и управления этой же системой. Реплики сохраняются и адресуются проектам, задачам и истории; разговор не становится отдельным хранилищем целей или вторым task manager.

## Что обнаружено

**REFINE:** выбранное направление сохраняем. Основной разрыв — между приоритетной оболочкой, подробными экранами и их состоянием. CEO на общем Home получает Atlas; его сохранённое поручение не видно на новой доске; из проекта можно попасть в общий пульс. Эти три пути воспроизведены в браузере. Голосового ввода в проверенных UI-модулях нет. Полная матрица с границами доказательств находится в аудите.

Минимализм не означает скрывать неопределённость или исход действия. Уменьшаем число конкурирующих элементов, повторов и подтверждений, сохраняя область работы, свежесть данных, главный вопрос, текущую фазу и следующий шаг.

## Объём первой версии

| Обязательный результат R0 | Граница |
|---|---|
| Персональный Fabric, создание и выбор проектов | Компактный профиль сверху, выбранный облик, простой порядок проектов; AI-рисование не блокирует запуск |
| Возврат и переключение контекста | Цель, изменения, последнее решение, сейчас, нужное участие и следующий шаг; сохранённые вкладки/черновики/место |
| Доска внимания | Ручные темы и исключения агентов; ответ/решение/проверка различимы; не дублирует весь backlog |
| Наблюдение за работой | Агент/задача/запуск/сессия различимы; статус и возраст наблюдения доступны; технические логи по раскрытию |
| Разговор с CEO: текст и голос | Один composer, запись по явному действию, редактируемая расшифровка, журнал, адресация, результат и источники |
| Базовая настройка команды и циклов | Роль, существующий исполнитель, полномочия, бюджет; готовые циклы с preview/сохранением/паузой; эквивалентная ручная форма |
| Самостоятельность в заданных границах | Детерминированные правила и разрешённые действия выполняются сами; исключения с основанием идут оператору |
| Рабочий цикл | Утренний разбор → работа → исключение/результат → решение/проверка → checkpoint → следующий обзор |
| Честное завершение и восстановление | Сохранено/отправлено/получено/выполнено/проверено различимы; частичные данные и неизвестный исход не маскируются |

**Изменение прежнего разреза:** текстовый CEO, обязательный голосовой ввод и журнал общения больше не целиком откладываются до R1. В R0 входит узкий управляемый путь поручения и настройки; полный автономный manager остаётся в R1. Это уточнение прямого запроса оператора, а не повышение готовности существующего кода. CO-158 остаётся единственным предшествующим пакетом conversational manager; новый план расширяет его, не строит конкурирующий runtime.

Раскрываемая справка о цели, связях и истории нужна R0. Полноценный редактируемый многоуровневый граф планирования остаётся R1. Full-duplex, озвученные ответы, always-listening, 24/7 host, генератор произвольных workflow, массовое создание новых providers и расширенная геймификация сохраняются в следующем горизонте. Исторический CO-038 содержит также outbound «voice» продуктовых аккаунтов; это другая функция, её политика не меняется требованием микрофонного ввода.

## Требования, по которым принимаем работу

| ID | Требование | Проверяемое свидетельство |
|---|---|---|
| OF-01 | Каждая возможность R0 достижима обычным путём пользователя | Матрица вход/действие/исход, без каталога макетов как скрытого перехода |
| OF-02 | Первый уровень показывает только необходимые для решения данные | Экранная спецификация L0/L1/L2 и наблюдение на согласованных размерах |
| OF-03 | Актуальный контекст и статус доступны без удержания в памяти | A→B→A; цель/фаза/возраст/вопрос/следующий шаг совпадают с источником |
| OF-04 | Доска содержит требующие человека обязательства | Дедупликация, причина эскалации, разрешение и квитанция обновляют связанные представления |
| OF-05 | Самостоятельность уменьшает ручной контроль | Разрешённая рутина без лишнего approval; нарушение границы даёт объяснимую эскалацию |
| OF-06 | Через Fabric можно поручить работу и настроить агента/цикл | Typed proposal либо разрешённая команда, та же форма/validator/receipt, что вручную |
| OF-07 | Голос — обязательный доступный ввод R0 | Запись/stop/текст/исправление/отправка и ошибки микрофона/распознавания |
| OF-08 | Весь состоявшийся разговор сохраняется с происхождением | Реплики пользователя и Fabric, версии текста, timestamps, delivery, refs; переживают restart |
| OF-09 | Связи разговора с задачами и timeline точны и исправимы | Двусторонний переход до реплики; исправление связи не переписывает историю |
| OF-10 | Настройка прогрессивна и управляема | Preset→preview→save→next due→run→pause; расширенные параметры по раскрытию |
| OF-11 | Каждый сбой имеет честный выход | State matrix: draft/retry/reconcile/no access/no model/unknown без двойных действий |
| OF-12 | План можно исполнять без этого чата | Пакеты с владельцем, файлами, зависимостями, результатом, положительной и отрицательной приёмкой |

## Как идём дальше

1. **OX-01 вместе с D01/P0:** единая область и адрес объекта, producer→reader→screen, список повторно используемых механизмов.
2. **OX-02/OX-03/OX-04:** модель взаимодействий и полный связный макет критического пути, затем компактная композиция.
3. **OX-05…OX-10:** журнал, текст/голос, атрибуция, агентные настройки и циклы поверх подтверждённых контрактов.
4. **OX-11/OX-12:** объяснимая автономность и сквозная приёмка на идентифицированной сборке.

В плане указаны настоящие зависимости; номер не задаёт искусственный waterfall. Технические записи и принципы в этом документе — проектные требования, не измеренные свойства пользователей. Скорость возврата и число нужных вмешательств проверяются отдельным pilot.
