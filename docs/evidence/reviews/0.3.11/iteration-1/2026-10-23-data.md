On the operator's database it returns 8 of 887 posts; with a busy journal it is often 1 or 0, and the feed then says it is empty while threads hold messages. The CHANGELOG promises "the newest posts of every thread first". | `renderer/src/launch/CommsFeed.tsx#CommsFeed` (`window.fabric.comms.list(null, Math.max(0, last - FEED), FEED)`); `supabase/migrations/20261005000081_project_board.sql` header ("A message's `seq` is its journal seq") and `board_messages` insert with `j.seq`; `20261011000094_project_board_operator_read.sql#board_list_operator` pages ascending `seq > p_after_seq`; psql: 8 rows with `seq > 18421 - 100` of 887. The test mocks dense seqs (`CommsFeed.test.tsx`, heads 40 and 42). | Without a migration: page backwards from the heads, e.g. take the threads with the highest `lastSeq` from `comms.heads()` and read each one's tail with `comms.list(thread, ...)`, or widen the cursor (double the gap) until 100 posts or seq 0, with a fixed call ceiling. ## Not findings

- **Schema unchanged at 95.** No file under `supabase/` changed between `v0.3.10` and the candidate; 95 migrations; `schemaContract.json` minimum and maximum 95; `check-migration-order.mjs` passes; the operator's database answers `schema_version()` 95. A 0.3.10 database opens under 0.3.11 without a step, and 0.3.11 writes no new table, column or row type, so 0.3.10 reads everything 0.3.11 writes to the database. Only the missing statement is a finding (DA-3).
- **Event types and feed sentences.** The release appends no new journal event type: the only new append path is the existing `session.oriented@1`; no `event_types` row or `event.<type>` sentence is needed. History's «Что делали агенты» renders the App's existing journal feed (`App.tsx`, `feed={feed}`), not a new read.
- **Analytics.** No analytics event added or changed (no `analytics` or `track` lines in the source diff).
- **Operations log.** One new op name, `agentSurface.working-language-read`, through `ops.failed`, recorded only when the settings read throws; `check-ops.mjs` passes.
- **IPC `work:board`.** Channel name, preload method, `FabricApi.work.board()` type, `MAIN_ONLY` window rule and main handler agree; `check-ipc-contract.mjs` passes (160 of 160, 170 of 170). It takes no argument (see DA-2 for why it may need one).
- **`readTaskBoard` bounds.** Every read is bounded: projects 500, queue 100, plus `readHome`'s existing bounds (stages 500, review 50, running 200, journal 3000, review ids 5000, done 20). It runs on scoped feed marks (`task`, `work`, `question`, ...), not per render.
- **CommsFeed bounds.** Two calls per read: `comms.heads()` (the board caps it, `truncated` flag) and one `comms.list` capped at 100 by both `commsOperatorRead.list` and `board_list_operator`. Its problem is what it reads (DA-1), not how much.
- **Settings patching.** `agentLanguage` is in `PATCH_KEYS`, a non-boolean is refused by `settingsPatch` (the read-back differs), and a 0.3.10 `settings.json` without the key reads as on, the documented default (ADR-0174 decision 2).
- **Hub contract for published clients.** `fabric-mcp` serves no whoami of its own (`main/fabricMcp.ts`, `WAITING_TOOL`), the comms (`com.*`) schemas are unchanged, tool count is unchanged at 43 (`check-surface-tools.mjs`); tool input schemas changed only in description text. The whoami change is additive (DA-4 is about the version label only).
- **CO-389 heal.** The statement-timeout match applies only to `stack-would-not-start` and `unknown` causes and is guarded by `pastRetryPoint` at the call site (`main/index.ts`, `!pastRetryPoint && ... startupHeals(failure)`), so a start that already wrote past its retry point still stops on the dialog; the test also pins that a plain error mentioning "statement" does not heal.
- **Working language values.** `settings.locale` is validated to `en` or `ru` (`validateSettings`), and `workingLanguage` maps anything else to English, so no unknown code reaches an agent.
