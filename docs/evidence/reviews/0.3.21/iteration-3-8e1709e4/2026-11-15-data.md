## Findings
| ID | Severity | What | Evidence | Proposed fix |
|---|---|---|---|---|
| DA-15 | blocking | A question asked with options can no longer be answered from the app. 0.3.21 makes `recommended` required on a question with options and stores it on the option (`recommended: true`). The Board and «Нужны вы» send the stored options back with every answer, and the answer command's strict option shape refuses the unknown key. So for every such question asked under 0.3.21, every way of answering is refused `unknown_field`: the recommended option, any other option, «Отдать агенту» and «Ответить своими словами». The same stored questions stay unanswerable after a downgrade to 0.3.20, which the runbook offers as «the 0.3.20 bundle alone». This breaks something that worked (answering a question) and makes the CHANGELOG's «a question is one press» false. No test reaches it: the renderer tests stub `window.fabric.questions.answer`, and `command-ingress-adapters.test.mjs` has no option with `recommended`. | `shared/questionAsk.ts:113` (`pick.recommended = true`); `agentSurface.ts:2733` (`options: asked.value.options` in the `question.asked@1` payload, kept by `prepareAgentPayload`, see the probe above); the migrations project `e.payload->'options'` unchanged (`20260908000036_question_ask_idempotency.sql:44`); `main/index.ts:4034` and `shared/board.ts:197` pass `q.options` through; `renderer/src/BoardPanel.tsx:166-175` sends `options: item.question!.options`; `shared/commandIngress.ts:250` `object({ id, label, consequence })`, strict at `commandIngress.ts:124` (`refuse('unknown_field')`); probe `probe-answer.mjs` above; CHANGELOG.md:50-58; `docs/launch/release-mac.md:334` | Accept the flag in the answer's option shape: `recommended: optional(boolean)` in `prepareAnswerComposition`. Also have `submitAnswer` send only `{id, label, consequence}`, which 0.3.20 accepts too, so a downgrade keeps working. Add a `command-ingress-adapters.test.mjs` case that answers a question whose option carries `recommended: true`, by option and by free text, and watch it fail on this candidate first. This needs a new candidate. |
| DA-16 | non-blocking | `fabric_board_search` cuts its task read at 500 by creation time, not by the last move the tool describes. The query orders by `started_at desc`, and `started_at` is the row's creation time (`not null default now()`, never updated for a task). On a project with more than 500 open and recent tasks, the oldest-created tasks are dropped first. Those include a long-running task that moved today and is held now, which is exactly the «who works on what» hit the tool exists for. Its live claim is still read, but a claim makes no document of its own, so the held work drops out of the answer. `capped: ["tasks"]` is said, so nothing is claimed falsely. | `workTools.ts:420` (`.order('started_at', { ascending: false }).limit(max)`); `supabase/migrations/20260831000004_tasks.sql:19` (`started_at timestamptz not null default now()`); `boardSearchRead.ts:206-224` (task documents come only from `taskRows`); the tool's `days` description «by the last move or message» (`workTools.ts:407`) | Order by `moved_at desc nulls last` (then `started_at`), or read the live-claimed task ids first and the rest after them. Say in spec §3 which tasks a full read keeps. CO-578 can carry it. |

## Checked and sound
- **V3-73 is fixed.** The surface test's written list now names `fabric_board_search` between `fabric_agents_list` and `fabric_effect_report`, which is where the sorted tool list puts it (`test/agent-surface.test.mjs:140`). `surfaceTools.ts` names it too. I did not run that suite, because it needs the stack.
- **Run four's rulings (V3-59 to V3-68) are sound as non-blocking.**
  - DA-14 and ER-23 (generic query tails) reduce precision only: the full-path document still ranks first, and `similar_work` is a hint, never a refusal.
  - UX-21 to UX-23, DO-35 and DO-36 are wording.
  - One note: DA-15 needs a new candidate anyway, so the reason «the gate refuses source after `verifiedCommit`» no longer holds for this release. CO-578's small fixes could ride that candidate instead of waiting for `main`.
- **Project scoping holds.**
  - Tasks, notes and released claims are read through the project-scoped store. `createScopedStore` adds `estate_id` and `project_id` to `project_tasks`, `task_notes` and `work_claims` (`scope.ts:116,148,150`; `agentSurface.ts:1232`).
  - Live claims come from `readWork` on the same store. When that read is full, it is named `live claims` in `capped` and hits are marked `holder_unknown`.
  - The board is read through `this.board.list(this.boardCaller(scope))`, the session's own reader door, with the principal closed over the scope (`agentSurface.ts:3239-3240,3298-3310`).
  - A board-surface session gets only the board's tools, so it cannot reach `fabric_board_search` (`agentSurface.ts:1559-1563`).
  - Another project's text reaches the answer only as messages in threads this project takes part in, and as the directory's names and capabilities.
- **Window ladder.**
  - It reads at most 15 `com.list` pages (1 day, 7 days and the asked days, or 1 day, 6 hours and 1 hour), plus 5 directory pages.
  - When a wider window fails, the window read whole is kept and named `failedPast`.
  - When a narrower read fails, what the wider one read is kept and named `capped`.
  - `board_narrowed` has two forms that never both apply (`>= days` against `< days`), and the note drops «a wider days» when the board was narrowed or capped (`boardSearchRead.ts:109-131,281-292`).
- **Text, word and query caps** match spec §3a: 6 000 characters a document, 64 a word, 12 query words, 300 characters a query, 8 tails a path and 240-character snippets. Each query word appears once in `matched`, `searched` and `not_searched`.
- **Sweep receipt.**
  - `work.swept@1` names `threads` as capped when either thread read stopped at its bound: the open-first read (10 pages) or the newest read (3 pages) (`abandonedSweepRun.ts:791`).
  - That matches migration 124's note («which reads stopped at their bounds») and 0.3.20's meaning, where the newest 300 already stopped there on a busy board.
  - A capped thread read blinds no kind, as before. `request-no-folder` is in `ABANDONED_KINDS`, so the receipt's `found` rule accepts it.
- **Dispatcher.**
  - A no-folder request is held in memory (`noFolder`). It goes to the operator only 30 minutes after filing, and only with the switch on (`boardDispatch.ts:157`).
  - It writes no record to `board-dispatches.json`, and an earlier record keeps its outcome (`boardDispatchRun.ts:1069-1072`).
  - An inbox item stays skipped (`:1061-1062`).
  - `aliasProposed` proposes once per process, never waits on the answer, and goes only to the operator's local Observatory.
  - `readOpenRequests` logs a capped thread read once per change.
- **The question card** shows `entry.why` (the asker's own words) as React text under «Подробнее», and the board's «blocks N» count as a separate line (`BoardScreen.tsx:494-521`).
- **Upgrade path.** There is no migration since `0d729bbe`. The CHANGELOG's «Upgrading» paragraph (lines 12 to 13) and the runbook (schema 102, `release-mac.md:334,418`) are true for the schema. Going back to 0.3.20 is a bundle swap only, but DA-15 also holds there for questions stored under 0.3.21.
