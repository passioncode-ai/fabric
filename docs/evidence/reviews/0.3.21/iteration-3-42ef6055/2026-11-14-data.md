## Findings
| ID | Severity | What | Evidence | Proposed fix |
|---|---|---|---|---|
| DA-13 | blocking | Run two's ER-15 fix reads a path as its tails after each `/`, with no bound. That makes the size of each document's index grow with the square of the number of `/` in one joined run, so the spec's cost claim «Its cost is linear in what it reads» is false. A run of n segments adds n tails of about half the run's length each. A 6 000-character run of one-letter segments (the `TEXT_MAX` bound) yields 3 000 terms totalling 9 000 000 characters; the same 6 000 characters as words yield 4 500. Board messages are written by other projects, so another project can post such text in a thread this project takes part in, and every search call pays for it on each such message (the board part reads up to 500). At a fixed read length this measured 3.3 times the time and 3 times the RSS at 500 documents, and 3.5 times and 4.5 times at the 2 000-document bound. `TEXT_MAX` keeps it bounded, so it is not a stall like ER-1, but the shipped spec sentence no longer holds. | `apps/desktop/src/shared/boardSearch.ts:104-106` (`for (let i = id.indexOf('/'); ...) out.push(id.slice(i + 1))`, no bound); `docs/evidence/specs/2026-11-14-board-search.md:96` («Its cost is linear in what it reads»); probes `scale.mjs` and `tails.mjs` above | Bound the tails. Either keep only the last few segments (for example the tails after the last 8 `/`, which covers any repository path), or stop once the tails' characters pass a small multiple of the run's length. Add a test that a 6 000-character `a/b/c/...` run yields a bounded number of term characters; the spec sentence then holds again. `verifiedCandidateProblem` does not admit `docs/evidence/specs/` after `verifiedCommit` (`scripts/lib/release-mac.mjs:154-166`), so either fix needs a candidate before the release commit. |
