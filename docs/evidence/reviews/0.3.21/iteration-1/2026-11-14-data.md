## Checked and sound
- Scoping: `fabric_board_search` reads through the session's `createScopedStore` (`agentSurface.ts:1550-1554`), whose `select` adds `estate_id` and `project_id` equality filters for `project_tasks`, `task_notes` and `work_claims` (`scope.ts:116, 148, 150`; `scopedStore.ts` `select`). PostgREST ANDs `.or(...)` with those filters at the top level, so the `or` widens only within the project. No other project's tasks, notes or claims can be read; `similar_work` uses the same project's `readWork` snapshot.
- The board is read through the session's own reader door: `this.board.list(this.boardCaller(scope))` and `this.board.directory(...)` (`agentSurface.ts:3238-3239`). The caller is built from the credential (`boardCaller` 3297-3309). `board_list_reader` checks `board_is_project` and thread participation (`20261026000125:31-38`). `directory` refuses viewers and asserted principals. Reading marks nothing read (`since` only, no `unread`). Board sessions get no work tools at all (`agentSurface.ts:1559-1563`).
- Nothing leaks beyond what the session could already list: message bodies come only from threads the project takes part in; the sender's `principal` is not copied into the answer; directory entries carry only name and capabilities, as `com.directory` does. The tool writes nothing and logs no query text. `checkReference(query)` refuses a secret-bearing query.
- Columns used exist: `project_tasks.moved_at` (`20260905000019:22`), `brief_*` (`20260905000016:57-59`), status values (`20260905000016:76`), `work_claims.agent/released_at/released_how` (`20261011000095:47-56`). The fields of `board_message_json` match the reader (`request.state/target/capability`, `sender.project`, `body.text`, `at`).
- Bounds are real and named: tasks `limit(500)` newest started first, `capped` at 500; notes `limit(1000)` newest first (the gateway's `max_rows` is 1000); board 5 pages of 100 per window; directory 5 pages. Each part fails on its own into `degraded`, and when every part fails the answer says "Nothing could be read" (test "a part that fails is named in degraded ...").
- Dispatcher in-memory state: the `noFolder` set is pruned against the requests read every pass, exactly like `pastDue` (`boardDispatchRun.ts:908-909`); entries move between the sets, and the set is bounded by the requests read. `lastWorkAt` lives on the `live` session entry and goes with it; `lastLaunchFailure` and `threadsCapped` are single values logged once per change. A no-folder hand-over writes no record and changes no existing record (`boardDispatchRun.ts:1063-1068`), so `board-dispatches.json` is unaffected.
- The work signal: `isWorkCall` counts only `tools/call`. fabric-mcp's keep-alive is an MCP `ping` (`fabricMcp.ts:48, 623-640`), so it no longer counts as work (test `work-signal`).
- CO-572: `readRequestThreadIds` dedupes by id, has bounds of 10 + 3 pages and reports `capped`; the board supports `openOnly` (`commsOperatorRead.ts:185`, `board_request_open`).
- Question `recommended`: the flag is stored inside the `options` jsonb, which the projector copies from the payload, so it survives; the free `recommended` id is only compared against option ids, never stored on its own.
- CO-570: the handler path is returned to the caller, not journalled. CO-575 and CO-573 (10) touch no stored data.
