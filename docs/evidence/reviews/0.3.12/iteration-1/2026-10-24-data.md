## Not findings

- **The schema step is shaped like the chain.** `project.profiled@1` has its `event_types` row (`projects = true`) and a feed sentence in both locales (`i18n/en.ts:1382`, `ru.ts:2228`). `project_relations` carries the composite foreign key `(estate_id, project_id) -> projects (estate_id, id)` on migration 42's `projects_estate_identity`, RLS on, a member read policy, select granted to `authenticated`, everything revoked from `anon` (probe: anon insert f). `apply_project_profile` and `apply_projections` are revoked from `public`, `anon`, `authenticated` and `service_role` (the db test asserts it). The dispatcher differs from migration 116's by exactly the one added line; the archive function differs from migration 120's by exactly `'96'::jsonb`, and the TypeScript side admits 96 (`ceoPrivateArchive.ts:25`).
- **Upgrade and fresh install.** A fresh chain reaches 96 and the five db tests pass, including a rebuild from the journal that gives the same profile. On a seeded schema-95 database, migration 123 applies, `schema_version()` reads 96 and existing projects keep null profile columns; no existing event is reinterpreted. The ledger hash matches the file; `schemaContract.json` is 96..96; the CHANGELOG and `release-mac.md:310` say 0.3.11 cannot open 96 and the rollback is the backup. Migration 123 does not apply twice (the policy already exists), like migrations 95 and 113; the runner records each version once, so this is not a defect.
- **No cross-estate write.** A profile naming another estate's project is refused by `refuse_foreign_identity` before the projector; the projector also filters `estate_id`; the hub tool writes only `scope.projectId`, and its zod bounds (600, 160, 80, 20 plan items, 50 relations) sit inside the ingress limits, which also redact every text. The reads through `store` carry the estate filter (`check-scope.mjs`), and the wall's direct read names `estate_id`.
- **CO-370 and CO-373 left in place.** The migration does not touch `board_epoch_gate`, `board_list` or `board_waiting_operator` (grep count 0), and no other file under `supabase/` changed; both rows stay with 0.3.13's schema step as the triage records.
- **The reads added in wave 1 and 3 are bounded and honest.** `readWork` and `readWhereWork` filter by project in the query when given one and flag `capped` at their limits; `readTaskBoard`'s cancelled read (50) reports `capped` and a failed read in its own column; the queue orders by `seq` (0.3.11 DA-7). The `tasks.detail` blockers read is estate-scoped and resolves titles through the chunked `selectIn`; a failed read omits `blockedBy` rather than saying nothing blocks. The board's asker read goes through `selectIn` on the questions' own session ids.
- **People from Git store nothing.** `gitPeople.ts` runs one `git log` per repository (365 days, 2000 commits, 5 s, 4 MB buffer), keeps the result in memory for ten minutes and returns failed folders in `unread`; no address reaches the database or a file.
- **`boardFilters` and `machineTrust` validation.** Both are patch keys and are validated on read: a project id must be 36 characters of hex and dashes, an agent name 1 to 64 of a safe set, trust only `mine` or `organization`, anything else reads as no filter or not trusted.
- **`board_threads_operator` is unbounded**, but it is migration 120's and already read by Comms every 2.5 s; the graph adds a read on journal moves while it shows. Not new in this release.
- **The directory now shows a repository folder name** for two Projects of one name (CO-369), inside one estate's board; intended by the row, and only the folder's last segment.
