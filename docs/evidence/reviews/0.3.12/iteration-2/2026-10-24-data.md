## Rollout: does the step take schema 95 with 0.3.11 installed to 96

Yes, on the evidence available without touching the working stack. The live database is exactly the 95-file chain (1 760 schema facts identical), so migration 123 meets what it was tested against. The stack folder holds the candidate's 95 earlier files and the same `config.toml`, so after Rollout step 3 copies the one file (whose sha256 equals the ledger's) `supabase migration up --local` has exactly one pending version, `20261023000123`, which sorts after the newest applied `20261021000120`; `schema_version()` counts the CLI's `schema_migrations` rows, so it reads 96. The CLI connects as `postgres`, which is not a superuser on this stack and owns every public object; the migration applied as such a non-superuser owner on a copy holding the live journal and its projections (4.9 ms, every table keeps its rows). On 0.3.12's first start `materializeStack` rewrites only files whose bytes differ, so the copied file stays and nothing is removed. The one way the step can be undone before step 7 is a start of 0.3.11 between steps 3 and 7: its `materializeStack` removes migration 123 from the folder (a migration its bundle does not carry), and 0.3.11 refuses a schema-96 database; Rollout step 2's broker check and the person quitting Fabric already cover this. Rehearsal step 5 needs the tag `v0.3.12` in the local checkout (`rehearse-upgrade.mjs#candidate` reads it through `git rev-parse` and `git archive`), so it runs after the tag is fetched; step 0's disk floor of 8 GB is met today (13 GiB free on the data volume).

## Not findings

- **Rebuild equals live.** `append_event` takes the estate's advisory lock, assigns `seq`, inserts and runs `apply_projections` in one transaction, so projection order is seq order; `rebuild_estate_projections` replays in seq order. `apply_project_profile` depends only on the event and the row (`occurred_at`, `actor`, payload), so it is deterministic. Measured twice: a copy holding the live journal rebuilt to every projection the live database holds (only command-written tables differ), and a fresh chain at 96 replaying the copy's journal, profile probes included, gave an identical profile and relations listing.
- **The schema step on an existing install.** The live database at 95 is byte-for-byte the chain's schema (functions, columns, indexes, policies, grants, event types), so the migration's `alter table projects add column if not exists` and `create table if not exists` meet what they expect. It applied in 4.9 ms on 72 projects and 21 794 events, as a superuser and as a non-superuser owner; it rewrites no stored row. It cannot run twice (the policy exists), which the runner never asks of it.
- **Grants and RLS.** `project_relations` has RLS on, a member read policy, select for `authenticated`, nothing for `anon`; the projector functions are revoked from every API role (the db test asserts it, and passes). The `service_role` write grant is iteration 1's DA-7, ruled CO-418.
- **No leak across estates or projects.** The hub tool writes only `scope.projectId` and reads the business with `estate_id`; the store adds the estate (and project) filter to `project_relations` (`shared/scope.ts:113`, `check-scope.mjs` 17 raw queries narrowed); the graph's thread read names `ACTIVE_ESTATE`. A business comparison is case-insensitive in both the tool and the wall (`businessesJoined` lower-cases).
- **No second writer path for profiles.** `project.profiled@1` is appended only by the hub tool and `projectsSetBusiness` (grep); imports accept only `project.created@1`, `project.settings.updated@1` and `agent.registered@1` (`commandIngress.ts:252`); `append_event` is executable by `service_role` only.
- **The analytics read's cost.** A sequential scan of the estate journal, 8.25 ms at 21 798 events; the page re-reads on task, work and question journal families (`App.tsx:1060`), not on every event. At today's rate (2 936 events a day) the scan grows about tenfold a year; the journal index is already ruled CO-418 (V1-31).
- **Timestamp ordering in `withCloses`.** `localeCompare` sorts a whole-second timestamp after a fractional one in the same second; PostgreSQL prints microseconds, so this needs two events of one task inside one second with one at exactly `.000000`. Not worth a row.
- **The onboarding task id** is derived from the project id alone; `project_tasks` creation is `on conflict (id) do nothing`, and there is one estate. Not a defect today.
- **Settings file size.** 5 000 marks are about 235 KB; `localStore.ts` has no size cap on read, so a full file is read, not reset.
- **The use record of the credential sweep** stores nothing durable and is bounded by the live bindings (7 on the live database, all live; 5 claims journaled).
