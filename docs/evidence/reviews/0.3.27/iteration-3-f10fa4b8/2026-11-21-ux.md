| UX-60 | Non-blocking | **During a runner switch, `ceo_reply` tells the voice to have the owner start the CEO.** The UX-54 fix treats "no live console" as "not running" in every state. During a fallback the state is `starting` and the session id is null. So `ceo_reply` says "tell the owner to start the CEO from its window; do not ask again", even though Fabric is starting the next runner by itself. While it starts, the popup shows «Запускается» and a Stop button, with no start button (`CeoPopup.tsx`, lines 106 and 133). This also hits an ask still waiting in the queue: at 755687ab that case said correctly "still waits in the queue… try ceo_reply in a while". Because of "do not ask again", the voice may stop reading for an answer that does come. `ceo_reply` is new in 0.3.27, so 0.3.26 is not affected. | `main/ceoVoiceTools.ts#ceoReply` (the `ceoLastActivity() === null` return now comes first). `main/index.ts` (`ceoLastActivity` is null while `agent.sessionId()` is null). `main/ceoAgent.ts#restart` sets `sessionId = null; state = 'starting'`. Probe (an ask queued as `not-delivered`, then a limit, `ceo_reply` called while hermes opens): candidate `{"state":"starting","reply":{"ok":false,"reason":"the CEO console is not running…","next":"tell the owner to start the CEO from its window; do not ask again"}}`; 755687ab `{"state":"starting","reply":{"ok":false,"state":"queued",…,"next":"do not ask again; tell the owner it waits, and try ceo_reply in a while"}}`. The same probe with an ask that was already typed gives the new "start it" wording on the candidate too. | Give the voice tools the CEO's state. Say "start it" only when the state is `stopped`, `failed`, `idle` or `ended`. While it is `starting`, say "the CEO is switching or starting: tell the owner it waits, and call ceo_reply again in a while". Add a test with the state `starting`. |
| UX-61 | Non-blocking | **After the queue's write of a voice ask breaks off, `ceo_reply` never reads the CEO's answer for the rest of the call.** `askUnknown` returns before the transcript is read, so every call answers `state: unknown`. If the line went in and the CEO answered, the voice still cannot read the answer out. When `ask_ceo`'s own direct write breaks off, it tells the voice to read `ceo_reply`, and the answer is then read normally. The two cases of the same uncertainty end differently. | `main/ceoVoiceTools.ts#ceoReply` (the `deps.askUnknown?.()` return comes before the read loop). `main/index.ts#runVoiceTool` (a `delivery-unknown` ask is marked with `wroteAt` and no `unknown`, so the transcript is read). | Say "unknown" once, or put it beside the result, then read the transcript from `wroteAt` as for a written ask. Return `answered` when the CEO did answer. |

At 755687ab such a retype was dropped when the restart did not end with a running CEO. CO-615 (1) already covers waiting lines that are not listed and have no age.
