| DA-38 | Non-blocking | **Kept-aside queue files are never removed and keep the owner's text with no time limit.** Each start that finds a `pending.json` that does not parse renames it to `pending.json.corrupt-<time>`. Nothing ever removes these files: not the CEO's start, and not the inbox cleanup, which reads only `inbox/`. There is no limit on how many build up. Each one holds the owner's messages word for word, up to about 50 lines of 8000 characters. The record `ceo.agent.queue-read-failed` gives only the error class. It does not name the kept file, and it does not say when the rename itself failed. If the rename fails, the next save writes over the broken file after all. The docs say the file "is kept aside" but not for how long. | `apps/desktop/src/main/ceoAgent.ts:157` (`renameSync(queueFile, \`${queueFile}.corrupt-${Date.now()}\`)`, its failure only `void e2`). `ceoAgent.ts#pruneInbox` reads only `inbox`. Probe: three starts on a broken file, then a CEO start, printed `{"count":3,"modes":["600","600","600"],"holdsText":true,"afterStart":3}`. | Remove `pending.json.corrupt-*` older than `INBOX_KEEP_MS` in the start's cleanup, and keep at most a few. Record `{kept_aside: true \| false}` with the read failure. Name the retention in the AGENTS.md row and the CHANGELOG line. |
| DA-39 | Non-blocking | **A queue file that parses but has the wrong shape is lost without a trace.** A `pending.json` that is valid JSON but not an array (for example an object or `null`) loads as an empty queue. So does an entry without a string `line` and a numeric `at`, which is dropped. In both cases nothing is recorded and nothing is kept aside. The next save writes over the file. This is the case a downgrade or a future format change would hit. The ER-41 comment says the file is "never overwritten by the next save without a trace". That is true only for a file that does not parse at all. | `ceoAgent.ts:161` (`Array.isArray(raw) ? raw.filter(...) : []`, no record). Probe, with delivery failing, then one new send: body `{"line":"one order","at":1}` gave `records:0, keptAside:0, fileNow:[{"line":"new",...}]`. Body `[{"line":"ok","at":1},{"text":"lost order","at":2}]` gave `records:0`, and the second entry was gone. | Treat a file of the wrong shape like one that does not parse: keep it aside and record it. Record how many entries were dropped as invalid. |
| DA-40 | Non-blocking | **A message refused because the queue is full still leaves its attachments in the inbox for 30 days.** `send` saves the attachments (up to 10 files of 25 MB each) before it checks whether the queue is full. The window then says "The message was not kept", but its files stay in `ceo/inbox/` until the 30-day cleanup at a later CEO start. Each new try against a full queue saves another copy. | `ceoAgent.ts#send`: `saveAttachments(attachments)` runs first, and the `queue-full` return comes after it in both branches (`enqueue(...)` returns null). `en.ts` `ceoAgent.composer.queueFull`. `INBOX_KEEP_MS` is 30 days. | Check `queued.length >= CEO_QUEUE_MAX` before saving the attachments, or remove the saved paths when the send is refused. |
| DA-41 | Non-blocking | **Two messages sent close together, with the queue empty, can still be typed out of order.** Message C goes the direct path and is still waiting for the prompt. Message D is sent a moment later and also goes direct, because the queue is still empty. If C's readiness deadline ends before the prompt shows, but D's own deadline does not, D is written first. C is then queued and `drain` types it after D. The window is short, the gap between the two sends against C's deadline, so this is a residual case of DA-31. SCN-189's "goes behind them" covers only messages already in the queue. | `ceoAgent.ts#send`: `if (queued.length > 0)` sees an empty queue while C is in flight. `deliveryQueue.ts`: each item has its own deadline from when it was pushed. Probe, where C's delivery fails after 30 ms and D's is written at 40 ms: `{"r1":{"ok":true,"queued":true},"r2":{"ok":true},"typed":["D second","C first"]}`. | Count a direct send in flight as waiting: while one is in flight, a new send goes into the queue behind it. Or put a failed direct line at the head of the queue and drain before reporting the later one as sent. |
