### ER-12 (non-blocking): stage reports of earlier ids unordered and unbounded; claims cap unsaid

What is wrong: `withIdentity` reads `agent_stages` for the earlier session ids with `selectIn(..., 'session_id', earlier)`, no `order`, no `limit`. `selectIn` chunks by 100 ids and each chunk answers at most the gateway's 1 000 rows, silently (`scopedStore.ts#selectIn`: `rows.push(...data)` with no count check). Stage reports are written on every milestone, so an agent with many earlier ids can exceed that, and the 1 000 kept are arbitrary, not the newest. `joinByRuntime` then picks "the newest stage report across its ids" from a set that may not hold it, and the agent's «Сейчас» line shows an older step as current. The claims read does pass `order`/`limit: CLAIM_ROWS`, but unlike enrolments (`enrolCapped`) its cap is never compared and never said (`identityUnread` is not set when 1 000 claims come back). The sibling read of the home (`workRead.ts`, the 500-row `agent_stages` read) is ordered `reported_at desc`, so this is the only unordered one.

Evidence: `apps/desktop/src/main/agentIdentity.ts#withIdentity` (the `Promise.all` of `agent_stages`, `session_heartbeats`, `work_claims`; only `work_claims` carries an order); `scopedStore.ts#selectIn` body.

Fix: pass `{ column: 'reported_at', ascending: false, limit: STAGE_ROWS }` for stages and compare each chunk's count to its limit as enrolments do; set `identityUnread` when the claims read is full. Add a test with a fake store that returns 1 000 stale rows.

### ER-13 (non-blocking): turns read walks the journal on a quiet machine

What is wrong: `withWork` reads `type = 'session.turn.observed@1' and occurred_at >= now-1h`, `order seq desc limit 500`. No index serves `type` or `occurred_at` on `journal` (only the primary key and partial indexes on other types/paths, see "What I ran"). When fewer than 500 turns fall in the hour, which is every quiet hour, the database walks the journal backward to the start before it can stop, because the `occurred_at` bound does not end the scan. It runs inside `work.home`, which the renderer re-runs on every `session`, `task`, `agent` and `work` mark and every 15 s. The rhythm reader already solved this exact problem (`windowStartSeq` then `gte('seq', startSeq)`), and CO-477 names the enrolment lookup and `comms.waiting` but not this read. Consequence is the one ER-7 and CO-477 already describe: a 15 s `dbDeadline` failure turns into `turnsUnread: true` and the strip says «прочитано не всё», on exactly the machines that have large journals.

Evidence: `apps/desktop/src/main/agentWork.ts#withWork` (no `seq` bound); `grep -rn "create index" supabase/migrations/*.sql | grep journal` lists no index that covers `session.turn.observed@1`; `main/workRhythm.ts#windowStartSeq` for the working pattern.

Fix: bound the read with the first `seq` at or after the window's start (one small query, or reuse the rhythm's), or add a partial index `on journal (estate_id, seq desc) where type = 'session.turn.observed@1'`; add the read to CO-477.

### ER-14 (non-blocking): the ER-11 test does not test what its title and the ledger say

What is wrong: `test/work-rhythm.test.mjs` «ER-11: a reading that fails rejects every caller sharing it, and the next call reads again» makes `store.select` throw, then asserts `r.unread.length > 0` and that the next call reads again. The reader never rejects (every sub-read is caught into `unread`), so the rejection path of the shared `flight` (a `composeRhythm` throw, which would reject every caller) is not exercised, and the title states the opposite of the assertion. The same test runs with `minIntervalMs: 0`, so the behaviour that a fully failed reading is itself kept for `MIN_INTERVAL_MS` (15 s) before the next real read is not covered either. The ledger row V2-11 cites this title as evidence for "failure paths".

Evidence: `apps/desktop/test/work-rhythm.test.mjs` test ER-11 (assertions on `r.unread` and `again.days`); `main/workRhythm.ts#createRhythmReader.read`.

Fix: rename the test to what it proves ("a read whose store throws is said unread, and the next call reads again"), and add one case with the default interval showing the failed reading answered again for 15 s, and one where `composeRhythm` throws, showing both callers reject and `flight` clears.

### ER-15 (non-blocking): one rejected nicety drops the whole waiting list

What is wrong: in `withWaitingList` the comment says the subjects are "a nicety: a thread page that does not answer leaves the subjects the requests themselves carry", and a thread page with `ok: false` is handled that way. A thread page or responders call that rejects (instead of answering `ok: false`) rejects the `Promise.all`, lands in the outer `catch`, and the home loses the list and shows only the count. The behaviour is safe (the count is untouched, logged as `comms.waiting-list-unread`) but narrower than the comment promises.

Evidence: `apps/desktop/src/main/commsWaitingList.ts#withWaitingList`: `Promise.all([q..., deps.responders(), deps.threads()])` with no per-call catch.

Fix: `deps.threads().catch(() => ({ ok: false } as ...))` for the subjects, or amend the comment to say any rejection drops the list.
