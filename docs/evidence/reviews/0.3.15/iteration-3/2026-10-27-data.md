### DA-15 (non-blocking): a connected agent holding an old claim disappears from its own task

- What is wrong. `shared/agentWork.ts#workOf` counts a held task as work only while a signal (the claim time among them)
  is within `TASK_WORK_MS` (60 min). An agent that keeps its claim for longer and sends only keep-alive pings is therefore
  `atWork: false` and, not being stale (pings keep it fresh), not quiet either. `shared/homeProjects.ts#groupInWork` with
  `atWorkOnly` drops it from the cards (`onWorkRow` keeps only at work, or stale with a task), counts it in
  `connectedIdle`, and its running task, which the home still lists as `inWork` with `live: true`, is no longer held by
  any card agent, so it renders as `launch.home.inWork.orphan` («Task with no agent:»). The hover on the folded line
  (`launch.home.inWork.connectedIdleWhy`) says "none holds a task or reported work in the last 15 minutes", which is false
  for this agent. The rail drops it the same way (`railAgents` filters on `onWorkRow`). A long task is the normal case
  for a coding agent that waits on a long background step, so this is not a corner.
- Evidence. Probe `scratch-data/p1.mjs` (one non-stale agent, claim 2 h old, no signals, home view with the matching
  `inWork` item):
  `{"agents":0,"connectedIdle":1,"noTask":0,"noTaskSessions":[]} false` then
  `{"cards":[{"agents":0,"orphans":1}],"idle":1}`. The agent holds the task by a live claim and the home says nobody does.
- Fix. In `onWorkRow` (and so in the rail and the card fold) keep a non-stale agent that holds a task of its own
  (`!a.task.fromEarlierSession`) as a quiet row, as is done for a stale one, or count the held task as work while its
  claim is open and the agent is not stale; at minimum change the hover and the orphan wording so they do not claim
  that no agent holds it. The strip's number can stay as it is.

### DA-16 (non-blocking): the release note and the DA-13 disposition are false for the left column

- What is wrong. `CHANGELOG.md` (0.3.15): "An agent gone quiet that holds no task is in none of Главная's numbers; it stays
  in the left column and on Агенты." The ledger row V2-18 repeats it. `shared/railAgents.ts#railAgents` filters with
  `onWorkRow`, which is false for a quiet agent with no task, so it is not in the left column; only Агенты lists it. The
  `railAgents` header comment says so itself ("an agent merely connected is not here ... an agent at work, and a quiet one
  that still holds its task, are").
- Evidence. Probe `scratch-data/p3.mjs` over three agents (quiet no task, quiet with task, connected not stale):
  `[ 'quiet-task:quiet' ]`. Only the quiet agent with a task survives.
- Severity note. It is a sentence in the release notes, not a behaviour regression (0.3.14 listed every agent in the
  left column, so an agent has gone from visible to listed only on Агенты). I kept it non-blocking because the release
  commit can correct the sentence; if the lead reads "ships something false" strictly, treat it as the one item to fix
  before tagging.
- Fix. Change the CHANGELOG sentence (and V2-18) to "it is on Агенты only", or keep a quiet no-task agent in the rail
  (`onWorkRow` plus a rail-specific allowance) if the left column is meant to show it.

### DA-17 (non-blocking): the identity join does not reach the agent's page

- What is wrong. `main/agentIdentity.ts` joins an agent's earlier session ids (aliases) for the home reading, which makes
  «Сейчас» show the carried task and stage. `main/workRead.ts#readSessionTasks` then reads claims
  (`.eq('owner_session', sessionId)`), launched tasks, questions (`.eq('asked_by_id', sessionId)`), and the page's history
  (`shared/sessionHistory.ts`, one session id) for the current id only; `LiveAgent.aliases` is used in exactly one place,
  `main/agentWork.ts` (grep over `src`: `shared/agentIdentity.ts`, `shared/homeLive.ts`, `main/agentWork.ts` only). For a
  re-enrolled agent, the very case D5 and D6 set out to fix, the page's head says it works on the carried task while its
  «Задачи» list, «Вопросы этого агента», milestones and endings are empty or start at the new id, and a question the
  agent asked under its earlier id is not shown to the person at all on its page (it is still on Главная's «Нужны вы»).
  `held` on the page uses `current.claimedAt` from that tasks read, so a carried task shows no «держит N» although
  `agent.task.heldSince` is known; `AgentPage.tsx#heldTime` ignores it.
- Evidence. `grep -rn "aliases" apps/desktop/src --include=*.ts --include=*.tsx` shows the only reader outside the join
  is `main/agentWork.ts`; `AgentPage.tsx` line `const heldTime = current && current.via === 'claim' ...` where `current` is
  found in `tasksView.tasks`, which carries the current id's claims only.
- Fix. Pass the aliases into `work.session` (`readSessionTasks(store, [id, ...aliases])`, `selectIn` over
  `owner_session`/`asked_by_id`/history `session_id`), and fall back to `agent.task.heldSince` for the held time. Or say on
  the page that earlier sessions' tasks are not listed. Needs live data only to see how often it bites.

### DA-18 (non-blocking): two ways a display name can be wrong or duplicated

- What is wrong. `shared/projectDisplayName.ts#resolveDisplayName` matches a descriptor by the project's own name AND by
  the basename of every repository path it holds, then picks one by `rank` and id. A project with several repositories
  therefore takes the name of whichever sub-repository has a descriptor first, and a second project whose single
  repository is that folder takes the same name. Nothing disambiguates equal names on the rail, the cards, the top bar or
  the console tabs (the slug is only a hover).
- Evidence. Probe `scratch-data/p2.mjs`: projects `passioncode` (repos `fabric`, `switchboard`, `passioncode`) and
  `fabric` (repo `fabric`), descriptors `fabric` and `switchboard`: result
  `{"a":{"name":"Fabric",...},"b":{"name":"Fabric",...}}`; the umbrella project prints as «Fabric».
- Fix. Prefer a descriptor matched by the project's own name over one matched by a repository folder; when two projects
  resolve to one display name, keep the slug-derived name for the later one (or append the slug). Cannot size without the
  live `project_repos` rows.

### DA-19 (non-blocking): two counts that can disagree with the board or the chart in bounded cases

- Waiting list. `shared/commsWaitingList.ts` keeps a request when no ACTIVE responder holds its project and capability, but
  the board's `board_responder_live` (migration 124) also treats a capability the target project LISTS as answered.
  The list cannot read that, so when candidates outnumber the count it is flagged `listComplete: false`, yet the
  oldest five candidates are still printed as «Запросы без ответа» with "не взял", and some of them may be requests the
  count excludes. Said honestly only by the extra count sentence.
- Strip versus chart. `main/homeStrip.ts#readHandedInToday` reads every `task.moved@1` and `task.closed@1` of the day,
  newest first, capped at the gateway's 1 000 rows (`capped` shows «N+»), then filters in memory; `main/workRhythm.ts#marks`
  filters moves to review and closes as done in the database. On a day with more than 1 000 task moves (claims, returns
  to backlog and the sweep's moves are all `task.moved@1`) the strip prints a floor while the chart for today is exact, so
  the two «one definition» numbers differ. Pulse and the strip are not capped the same way either.
- Fix. Give `readHandedInToday` the same database filters as the rhythm's marks (`payload->>to = review`; closes with
  `payload->>outcome = done`); drop or mark the list's lines when `listComplete` is false and listed capabilities
  are possible. Both need live volumes to size; neither shows a wrong number on a quiet estate.

### DA-20 (non-blocking): «console printed» includes typing

- What is wrong. `main/index.ts#heldSessions` takes `outputAt` from `ptys.list().lastActivityAt`, and `main/pty.ts` sets
  `lastActivityAt` on output (`onData`), but also in `write()` (typed input and delivered text) and on exit. A person
  typing into an idle Fabric console, or Fabric delivering a message into it, makes the agent «at work» for 15 minutes and
  moves its work time, while `HeldSession.outputAt` and `shared/agentWork.ts` both say it is when the console printed.
- Evidence. `main/pty.ts` `write(sessionId, data)` sets `s.lastActivityAt = Date.now()` before `s.pty.write(data)`;
  `DeliveryQueue`'s callback does the same.
- Fix. Keep a separate `lastOutputAt` in the PTY session set only in `onData`, or reword the doc and CHANGELOG
  ("its console had activity"). Low impact: typing usually precedes real work.

## Things I checked and found correct

- Rhythm window: local-day boundaries use `new Date(y, m, d - i)` so 23 and 25 hour days are right; the day count starts
  at the first `seq` with `occurred_at >= window start`, which is a lower bound for every in-window event; finished days
  are cached by zone and date and today is always asked again; a failed day is `null`, never zero; a capped marks read
  makes the days before the latest cut unknown and the totals `N+`.
- The database filters are real PostgREST forms on the scoped Supabase client (`not.in` with quoted values, `payload->>to`,
  `actor->>kind`, `head` + `count: exact`); the `actor` column is the journal's jsonb.
- `handedInTask` agrees with the strip, Pulse and `task.moved@1` / `task.closed@1` payload keys (`task_id`, `to`, `outcome`).
- Turn rows carry the Fabric `session_id` (`shared/commandIngress.ts`), so `withWork`'s alias map joins them correctly;
  a full 500-row read is said as partial (`turnsUnread`).
- `joinByRuntime`: one task to one live agent (newest claim wins), another project's claims and stage reports are skipped,
  a released-on-purpose claim is never carried; `taken` stops a task shown twice.
- Counts: the strip's «работают» is `atWork.agents`, the cards' count adds the quiet holders and the head says how many are
  quiet; `connectedIdle` is computed by the same rule in `withWorkSignals` and `groupInWork`.
