### DA-1 (non-blocking) Pulse is not on the rhythm's read

Evidence: `renderer/src/launch/PulseScreen.tsx` computes `rhythmDays(feed, now, period)` and `rhythmTotals(scoped, now, period)`
from the `feed` prop, which is the newest 500 events (`FEED_WINDOW`; `shared/homeView.ts`, whose own header now says
«Пульс still reads the feed»). `useRhythm` is called only in `EstateHome.tsx`. Home gap D1 proposed that the same read serve
`PulseScreen.tsx` (`gaps/2026-10-27-home.md` row D1), and `CHANGELOG.md` `## 0.3.15` says results and decisions «are counted
the same way on Главная, Pulse and the chart». The definitions are shared (`handedInTask`, `isPersonDecision`), but the
data is not: on a journal of 2 500 events a day, 500 events cover a few hours, so Pulse shows every day but the newest as unknown
(the D1 symptom) and totals near zero, while Главная shows 28 days. Both screens carry the title «Ритм работы» and the
same 28-day label. Pulse is behind Настройки → Ещё, so impact is limited.
Fix: have `PulseScreen` take `useRhythm` (its per-project filter needs a project argument on `work.rhythm`, or hide the
per-project chart until it has one), or state in the changelog that only the definitions are shared and that Pulse is
unchanged, and mark its days with the reading's scope.

### DA-2 (non-blocking) `task.heldSince` is not when the task was taken

Evidence: `shared/homeLive.ts#composeHome#currentTask`: for a claim it is `claim.since` (the claim time, correct); for a
task Fabric launched in the session it is `launched.updated_at`; for a task named by a stage report it is
`named.reported_at`. `updated_at` moves on every edit of the task (a note, a brief, a move) and `reported_at` on every new
stage report. The row prints `lh-arow-held` «держит {time}» from it (`HomeInWork.tsx#heldFor`). `shared/agentWork.ts#workOf`
also uses `heldSince` as a work signal, so an edit by anyone counts as work time and moves the card up. Fix: for a launched
task use the attach event (`task.session.attached@1`, already read for the agent page, `attachedAt`) or `started_at`; for a stage-named
task use the oldest stage report that names the task in this session, or leave `heldSince` null and print nothing.

### DA-3 (non-blocking) Open task plus a keep-alive equals «at work»

Evidence: `shared/agentWork.ts#workOf`: `atWork: (!!a.task && !a.stale) || fresh`. `stale` is the ten-minute sign
window that fabric-mcp's two-minute ping keeps satisfied. So an agent with any open claim, launched task, stage-named
running task, or (new in 0.3.15) a task carried over by `joinByRuntime` (`fromEarlierSession`) is at work for hours or days
while its window sits open, which is exactly the 0.3.14 symptom (37 «working» for one open claim) for every claim holder.
`joinByRuntime` runs before `withWork` in `main/index.ts` (workHome handler), so the carried-over task counts. The
doc comment says «holds a task (and still signs)», so this is as designed, but the number then means «has a task», not
«works». Fix: for the task rule require a work signal newer than a bound (for example 60 minutes) or a heartbeat in a working
phase; keep «holds a task» as a separate fact (it already is: `noTask`).

### DA-4 (non-blocking) Costs of the new reads on a large journal

`journal` has no index on `type` or `occurred_at` (indexes: primary key `(estate_id, seq)`, partial ones on
`payload->>'session_id'`, `owner`, `actor->>'id'`, `project_id`, a few by type and request id; no migration changed in
0.3.15). Each of these is a primary-key range scan with a filter, so cost is linear in the journal:

| read | shape | when | cost |
|---|---|---|---|
| `main/agentWork.ts#withWork` turns | `type=session.turn.observed@1 and occurred_at>=now-15min order by seq desc limit 500` | every home reading (15 s and on every mark) | scans backwards through the whole journal unless 500 matches are found, which never happens in a 15-minute window |
| `main/agentIdentity.ts#withIdentity` enrolments | `type=session.enrolled@1 and payload->>runtime_session_id in (100 ids) order by seq desc limit 1000`, once per 100 runtimes | every home reading | whole-journal scan per chunk: no index on `runtime_session_id` (`journal_by_session_id` is on `session_id`) |
| `main/workRhythm.ts#windowStartSeq` | `occurred_at>=window start order by seq asc limit 1` | every rhythm reading | scans forward over every event older than 28 days, once |
| `main/workRhythm.ts#marks` | `type in (...) and occurred_at>=... order by seq desc limit 1000` | every rhythm reading | scans backwards over the whole journal: with fewer than 1 000 matches it never stops |
| `main/workRhythm.ts#countDay` today | `seq>=startSeq and occurred_at in day and type not in (4 ticks)`, `count exact, head` | each reading for today; first reading for all 28 days, 4 at a time | each scans from `startSeq` to the end: about 28 days of events per query, so the first reading is about 28 x 28 days / 2 row visits; later readings one 28-day scan |
| `main/commsWaitingList.ts` submitted | `type=comms.message_submitted@1 and kind=request and occurred_at>=30d order by seq desc limit 1000` | only when something waits (15 now) | whole-journal scan; transitions are served by `board_transitions_by_request` |

Measured on the local journal (32 516 events, 15 days): 6 to 14 ms each, so about 50 ms of database time per reading. At 300 000
events that is about 10 times more per read (roughly 60 to 140 ms each, and the three marks-style reads full scans),
at 1 000 000 events about 30 times. This matches the 0.3.14 `readHandedInToday` shape (also a full backward scan), so it
is a continuation rather than a regression, but 0.3.15 adds four such scans to the reading. Day counts are
kept per finished day (`settled`), which is good; the first reading after start is the heavy one.
Fix: a partial index `journal (estate_id, seq desc) where type in (...)` or `(estate_id, type, seq desc)` for the
types read here, and `(estate_id, (payload->>'runtime_session_id'), seq desc) where type='session.enrolled@1'`; or bound
the scans by seq (start from `max(seq)` minus a window, as `windowStartSeq` does for the counts). Until then the
`seq >= startSeq` bound that `countDay` already uses is the right shape to add to `marks` and the turns read.

### DA-5 (non-blocking) No minimum interval for the rhythm reading

Evidence: `EstateHome.tsx`: `useRhythm(markOf(marks, ['work','task','agent','session','question','proposal','access','policy','grant']))`;
`useRhythm` reads on every change of the mark, one in flight and one more queued (`flight.dirty`). `session.turn.observed@1`
is a `session` event (6 856 of 32 516 events here) and `work.renewed@1` a `work` one, so with several agents the reading
runs back to back, each with the scans in DA-4, even though the chart only changes by whole events. `useHome` has a 15-second
timer; the rhythm has none and no debounce. Fix: a trailing debounce of 15 to 30 seconds in `useRhythm`, or a reader-side
cache of the answer for the same period (the reader already keeps settled days).

### DA-6 (non-blocking) Identity join: what it can merge and what it misses

Evidence: `shared/agentIdentity.ts#joinByRuntime` joins by runtime session id alone. It cannot merge two Claude Code
agents (the id is Claude's own session id; 298 distinct ids, 1 118 enrolments, at most 19 per id here). Two gaps:
(a) the join ignores the project: one runtime id in the local journal is enrolled in two projects
(`select ... group by runtime_session_id having count(distinct project_id) > 1` returns 1); the live agent of project B then
takes the stage report, heartbeat and running task of its project A session, and the task carries `projectId` of A while the
row sits under B. `siblings` should be filtered to the live session's project (the `session.enrolled@1` event has `project_id`).
(b) a `/clear` gives a new runtime id (`fabricMcp.ts` header: «an enrollment after a /clear names the new id»), so the
history under the old id is not joined: the agent shows «Задачи не взял» again (not a bug, a different conversation, but the
reading says nothing). Also Codex and Kimi enroll with no runtime id (`fabricMcp.ts#runtimeSessionIdOf` returns null;
135 of 1 118 enrolments here), so D5 and D6 still hold for them; the home gap and changelog say «an agent»
without that exception. Duplicate rows for one agent during the ten minutes before the old session goes stale are not merged either.
Fix: add the project to the filter, and name the exception in the changelog and `agentIdentity.ts` header.

### DA-7 (non-blocking) Stage stamping outranks the grace rule when it is wrong

Evidence: `shared/agentTrail.ts#taskTrail`: `text(p.task_id) ?? heldAt(e.occurred_at)`; the stamped id always wins.
`main/agentSurface.ts` (stage report handler): for a launched session `scope.taskId` is stamped, for an enrolled one
`stageTaskOf` returns the single live claim of the project. An agent that reports «starting B» while it still holds A
(release comes later) is stamped A forever, and a launched session that later claims B is stamped with its launch task.
`STAGE_BEFORE_CLAIM_MS` fixes only unstamped reports (no claim, or older rows). The code honours the contract of
`spawnParentOf`, so this is the known limit of «one live claim means this task». Fix: when the stage text is reported within
`STAGE_BEFORE_CLAIM_MS` before a later claim of another task and the stamped task was released, prefer the later claim in
`taskTrail`; or do not stamp and resolve only at read time with the holds, which are the better evidence.

### DA-8 (non-blocking) The marks bound is spent on moves that are not results

Evidence: `main/workRhythm.ts#marks` reads `task.moved@1` of every kind of move plus the decision types in one 1 000-row
read. Of 322 `task.moved@1` events in 15 days, 135 are to review; the rest (running, backlog) take bound without counting.
At about 20 moves a day the 28-day bound is reached near day 28 on a busier week and the totals become `N+` and the
oldest days unknown. `payload->>to` and `payload->>outcome` are in the payload and cannot use an index, but they can filter
before the limit: `.eq('payload->>to','review')` for moves, `.eq('payload->>outcome','done')` for closes. The behaviour on a
full read is correct (`marksCapped`, older days null, `+` shown); this only moves the point where it starts. Note that
`access.decided@1` by `agent` actors (54 of 87 here) are excluded correctly by `isPersonDecision` but still use read rows.
Fix: split the marks read into results (filtered) and decisions (filtered by `actor->>kind='person'`), each with its own bound.

### DA-9 (non-blocking) The display name is not on every screen

Evidence: `shared/projectDisplayName.ts` says every place in the shell that prints a project asks here. Still
printing the stored name: `PulseScreen.tsx` (`nameOf`), `HistoryScreen.tsx` (two), `CommsScreen.tsx`, `ReleasesScreen.tsx`,
`Feed.tsx`, `HomeParts.tsx:302`, `GraphScreen.tsx`. The same project reads «Research Agent» on the rail and `research-agent`
on Pulse, Comms and History. `resolveDisplayName` also matches by `repoKey` to a descriptor: two projects that share one
repository remote (or whose folder equals a generic descriptor id) get the same name and cannot be told apart in the
rail; the slug is kept as a hover only. `humaniseSlug` uses `w[0].toUpperCase()`, which splits a word starting with an
astral character (an emoji folder name); harmless otherwise. Names for projects beyond the first 500
(`projectNames.ts` `PROJECTS = 500`) silently fall back to the slug. Fix: route those `nameOf` callers through
`projectDisplayName(p, home.view?.displayNames)`; on a descriptor match shared by two projects keep the slug as a suffix.

### DA-10 (non-blocking) Two «at work» counts

Evidence: the strip counts `view.atWork.agents` (`live.filter(atWork)`); the cards head uses `agentsAtWork = live.filter(onWorkRow)`
(at work, or stale with a task) and `agentsQuiet = stale && onWorkRow`. An agent that is stale (ten minutes without a sign)
and has a stage report inside 15 minutes is both at work and quiet, so strip N differs from head N minus quiet. A stale agent
with a task and no fresh signal is on a card but not in the strip. UX-21 says the head and the strip add up. Fix: define
the strip as `onWorkRow` count, or count quiet-at-work agents on one side only. `connectedIdle` itself is consistent: both
`withWorkSignals` and `groupInWork` count `!atWork && !stale`.

### Checked, no defect

- 28-day rhythm: one count per local day (`rhythmWindow` on the local clock, DST days 23 or 25 hours; `localMidnight` is the
  same start as `rhythmWindow`'s last day), machine ticks excluded in the database (`not.in` with quoted values), a failed day
  null not zero, finished days kept for the process, a capped marks read marks the days it may have cut as unknown (the
  day that contains the oldest mark is also unknown, which is the safe side).
- Result definition: `handedInTask` is the single definition used by the strip (`countHandedIn`), the rhythm and Pulse's
  feed fallback; payload keys match production (`task_id`, `to`; 17 moved to review today, 17 distinct).
  Decisions: `isPersonDecision` counts only `person` and `operator` actors; production has `access.decided@1` by `agent` 54
  (the operator's standing rule, excluded) and by `person` 33, so Главная's decisions equal 34 over 15 days; `system` hub
  actors are excluded. No `policy.decided@1` or `grant.issued@1` by a person exists (policy decisions are written with the
  requesting agent as actor), so those types add nothing today.
- Waiting list vs count: `composeWaitingList` uses the same terminal states as `board_request_open`, the `request_id`,
  `to`, `message_id`, `thread_id`, `request.target_project_id` and `capability` keys exist in the migrations, expiry and
  answers are `comms.request_transitioned@1` events, so the journal derivation agrees with the count here (15 and 15);
  the list is oldest first, cut at 10, and `listComplete` is false whenever candidates differ from the count (including a
  listed capability the screen cannot read) or the read was capped, in which case the count sentence is shown.
- No migration changed; every new read goes through the scoped store and keeps `estate_id` in the filter, so the primary key
  serves the scan.
