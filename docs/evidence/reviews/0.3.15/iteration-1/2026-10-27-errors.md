## Findings

| id | severity | summary |
|---|---|---|
| ER-1 | non-blocking | A re-enrolled agent with a long-released claim on a still-running task is counted "at work", and two live sessions of one runtime show the same task |
| ER-2 | non-blocking | The rhythm read is not throttled: every `session` event restarts a 3-query read including a 1 000-row payload fetch |
| ER-3 | non-blocking | The rhythm's marks read is unfiltered (every `task.moved@1`), so the 28-day totals will usually be a capped floor with most days unknown |
| ER-4 | non-blocking | The rhythm has no day-rollover refresh, and a failed re-read keeps the old chart with the reason only in a tooltip |
| ER-5 | non-blocking | A failed turns read is shown as "connected, idle" (only logged); turns are not joined across an agent's session ids |
| ER-6 | non-blocking | Display-name read: silent caps, no stale fallback (names flip to raw slugs on a transient failure), and a serial wait inside `projects.list` |

### ER-1 (non-blocking): identity join recreates the "everyone is at work" inflation for re-enrolled agents

Evidence: `shared/agentIdentity.ts#joinByRuntime` takes, for an agent with no task, the newest claim under any sibling session id whose task is `running`, with no condition on `released_at` or `released_how`. `shared/agentWork.ts#workOf` then returns `atWork: (!!a.task && !a.stale) || fresh`, with no check of `task.fromEarlierSession`. Probe: view with one live agent, heartbeat `idle`, one claim under `old` released 25 days earlier, task `running`:

```
atWork true task true true { agents: 1, connectedIdle: 0, noTask: 0, noTaskSessions: [] }
```

Second probe: two live sessions with the same `runtimeOf` value and the same old claim both get `t1` (`[ 't1', 't1' ]`); the `heldNow` guard only covers a task held by a live agent that already has `a.task`, not two agents resolved in the same pass. The sweep returns most such tasks to backlog, so the window is narrow, but within it D3 (a ping is never work) is violated by the new join itself.

Fix: join only claims with `released_at === null` or released with `how` in a lapse set within `AT_WORK_MS`; in `workOf` do not let `fromEarlierSession` alone make an agent at work; resolve the join so one task is assigned to at most one live agent (newest `claimed_at` session wins).

### ER-2 (non-blocking): unthrottled rhythm reads

Evidence: `EstateHome.tsx` calls `useRhythm(markOf(marks, ['work','task','agent','session',...]))`; `HomeParts.tsx#useRhythm` reruns on every mark change, with only an in-flight guard and one "dirty" re-run. `main/workRhythm.ts#read` always issues `windowStartSeq`, `marks` (up to `GATEWAY_ROWS` = 1 000 rows with `payload`) and today's count, even when nothing changed. With several agents each turn is a `session` event, so the read chains back to back. `useHome` has the same pattern but ships far lighter rows.

Fix: a minimum interval (for example 15 s) in `useRhythm`, or a main-side coalescing (return the previous result when younger than N s and `inFlight` shared between callers; main also has no in-flight sharing between two windows).

### ER-3 (non-blocking): unfiltered marks read caps early

Evidence: `main/workRhythm.ts#marks` reads `.in('type', [RESULT_TYPES, DECISION_TYPES])` newest first, limit 1 000. `task.moved@1` fires on every move (to running, backlog, review) and decision types written by agents or the system (`grant.issued@1`, `access.decided@1` by standing rule) are also fetched, then discarded client-side by `isPersonDecision`. On a busy estate 1 000 rows will cover days, not 28; `composeRhythm` then marks older days unknown and shows "N+". Honest, but the goal "results and decisions over 28 days" is met only in part.

Fix: filter in the query: `task.moved@1` with `payload->>to = review`, `task.closed@1` with `payload->>outcome = done`, decision types with `actor->>kind in (person, operator)`; or count each per day like events.

### ER-4 (non-blocking): rollover and stale-on-failure

Evidence: `useRhythm` has no timer (compare `useHome`'s `REFRESH_MS` tick), so on an idle machine past local midnight the chart still ends on yesterday and highlights it as today until the next event. After a failed re-read `setReading((r) => ({ rhythm: r.rhythm, problem }))` keeps the previous chart; `HomeParts.tsx#rhythmOf` puts the problem only into `why`, which is a `title` hover on the totals.

Fix: add a tick at least at midnight and every minute; show a visible "not current" marker when `problem` is set.

### ER-5 (non-blocking): turns read failure and identity

Evidence: `main/agentWork.ts#withWork` logs `work.turns-unread` and continues with no turns, so an agent whose only recent signal was a turn reads as `connectedIdle`, shown as fact in `atWork.connectedIdle`; the view carries no "turns unread" field (compare `goalsUnread`). Turns are keyed by the current Fabric session id (`payload.session_id`), and `withIdentity` does not join them across sibling ids, so a re-enrolled agent that only finished turns under its previous id is not at work. A 500-row cap on turns is logged as `work.turns-capped` only.

Fix: add `turnsUnread` to `HomeView` and show "a dash" for the counts; join turns through `siblings`.

### ER-6 (non-blocking): project display names

Evidence: `main/projectNames.ts#readNow` reads `projects` with `limit(500)` and no order, then `selectIn('project_repos', ..., 'project_id', ids)` in chunks of 100 with a silent 1 000-row cap per chunk (`scopedStore.ts#selectIn` with no `order`); a chunk with more than 1 000 repository rows loses some silently and the name falls to the humanised slug. On failure `read()` throws and the callers (`index.ts` projectsList, `withDisplayNames`) fall back to stored slugs even when a good reading exists from seconds before (`kept` is not used past the TTL), so names flip between "Research Agent" and `research-agent`. `projectsList` awaits this read after its own read, so an unresponsive database adds up to a second 15 s deadline.

Fix: return the stale `kept` on failure (marked stale), compare chunk size to the cap and fail visibly, run the names read in parallel with the list.

### Checked and found sound

- `main/workRhythm.ts`: bounded (28 count requests, 4 at once, today re-read, finished days cached by zone and date), a failed day is `null` with a reason, never zero; `startSeq` null path correct; window math correct across DST (25 h day) and a +14 h zone.
- `commsWaitingList.ts`: any failed read returns the board's count reply unchanged and logs; `listComplete` is false when capped or when candidates differ from the count.
- `readSessionTasks`: the new question and runner reads are settled with handlers before the main reads can throw (no unhandled rejection); a failed questions read is said (`questionsUnread`).
- `agentSurface.ts` stage reports: the extra claims read is caught; an unreadable or ambiguous claim leaves the report unnamed but recorded.
- Renderer `HomeBoardWaiting` handles a failed or missing read as `FailureNote`.

## Verdict

Blocking findings open: none. Six non-blocking findings (ER-1 to ER-6); ER-1 is the one most worth fixing in this release because it reintroduces, for re-enrolled agents, the inflation D3 set out to remove.
