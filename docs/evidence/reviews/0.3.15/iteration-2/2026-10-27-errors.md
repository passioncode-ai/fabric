### ER-7 (non-blocking): a failed identity read is shown as truth

`main/agentIdentity.ts#withIdentity` catches every failure, logs `work.identity-unread` and returns the view unchanged. Unlike `withWork` (`atWork.turnsUnread`) and `withBranches`, it sets no flag. The view that comes back is exactly the 0.3.14 bug the join was written to remove (home gaps D5, D6): each re-enrolled agent has no task, no stage report, `aliases` absent. `withWork` then counts it into `atWork.noTask` («Работают без задачи») and, because `aliases` is missing, ignores its turns under earlier ids, so a working agent can read as «connected, idle». The renderer cannot tell a read that failed from an agent that holds nothing.

Evidence: `withIdentity` catch block (`ops.failed('work.identity-unread', e, { note: 'each agent shows only what its current session id holds' })`, then `return view`); `HomeView` carries `atWork.turnsUnread` only; the file header says "never a wrong task", which holds, but a wrong «no task» is the same class of false statement. The read is the heaviest of the chain (journal by JSON path, see ER-10), so a 15 s deadline failure is the realistic way to hit it.

Fix: add `identityUnread: true` (with the reason) to the view when the catch runs; `HomeInWork`/`HomeStats` then say «не прочитано» on the «без задачи» count and the quiet-agent line, as `turnsUnread` does.

### ER-8 (non-blocking): wrong attribution across ids

1. `shared/agentIdentity.ts#joinByRuntime` guards the claim carry with `c.project_id !== a.projectId` (DA-6) but not the stage and heartbeat carry. `StageRow` carries `project_id` and `main/agentIdentity.ts` selects it, yet `stagesBy` is keyed by session id only: the same coding-agent session enrolled earlier in another project lends its newest stage report («doing») to this project's agent.
2. `carried()` accepts `released_at === null` with no age bound. A claim left open by an earlier session that has not yet been swept (the sweep runs every third cycle pass and releases only after two sightings) is carried for as long as it stays open.
3. `readSessionTasks` (`main/workRead.ts`) reads `questions.asked_by_id = sessionId` and claims by `owner_session = sessionId` for the live id only, while the home now joins across ids. An agent page for a re-enrolled agent shows the carried task (`fromEarlierSession`) but not its open questions asked under the earlier id, and says «no questions» (`questionsNone`) as a read result.

Fix: filter carried stages by `project_id === a.projectId`; bound an unreleased carried claim by `claimed_at` (or by the earlier session's last sign); read `asked_by_id in (live id + aliases)` in `readSessionTasks`, or label the list «this session only».

### ER-9 (non-blocking): the capped-marks check uses the union's oldest row

`shared/workRhythm.ts#composeRhythm` computes one `oldestMark` over every mark row and treats a day as known when `d.from >= oldestMark`. `main/workRhythm.ts#marks` merges three reads of at most 1 000 rows each and reports only `capped = parts.some(...)`. When one read is capped (cut at day N) and another holds older rows, `oldestMark` is older than the capped read's cut and the days between show a known 0 instead of unknown. Probe (`scratch-errors/probe1.mjs`): moves to review on days 1 and 2 ago (capped read), one close 20 days ago; result `2026-10-05..07: null, 2026-10-08..24: 0`, so 17 days read zero though the capped read could have lost marks there. Reaching 1 000 rows in one read inside 28 days is unlikely today, which is why this is non-blocking; the bug is in the exact rule the field exists for (never zero for an unknown).

Fix: return `cutAt` per capped read from `marks()` (the oldest `occurred_at` of each full read) and use the newest of them as the bound.

### ER-10 (non-blocking): caps said only in the log, and an unindexed lookup

- `main/agentWork.ts`: `rows.length >= TURN_ROWS` logs `work.turns-capped` info only. Agents whose newest turn is past the 500th row are judged idle with no `turnsUnread`.
- `main/agentIdentity.ts`: `selectIn('journal', ..., ENROLMENT_ROWS)` per chunk of 100 runtime ids; a full chunk is neither compared to its limit nor logged, so an agent's older sibling ids can silently drop and its stage report or task is lost again.
- The enrolment lookup filters `payload->>runtime_session_id` plus `type`, ordered by `seq` desc. No journal index covers that path (`grep "create index.*on journal" supabase/migrations`: `journal_by_session_id` is on `payload->>'session_id'`; none on `runtime_session_id`). It runs on the home reading (15 s refresh plus every mark), so on a large journal it is a backward walk of the primary key until 1 000 matches or the whole table, ended only by the 15 s `dbDeadline`, which lands in ER-7.
- `main/commsWaitingList.ts` runs a 1 000 row read, a thread page and up to 10 transition chunks on every `comms.waiting` call (home every 60 s and on each comms mark), with no throttle like the rhythm's; `selectIn` has no limit on the transitions, so a gateway cap of 1 000 rows per chunk is silent. It degrades honestly (`listComplete`), so only cost is at issue.

Fix: say a capped turns/enrolment read (flag the view, as for `turnsUnread`); add a partial index `on journal (estate_id, (payload->>'runtime_session_id')) where type = 'session.enrolled@1'` (migration), or keep the runtime id in a small table; coalesce `comms.waiting` as the rhythm reader does.

### ER-11 (non-blocking): the failure paths have no test

`test/work-rhythm.test.mjs` ER-2 test covers coalescing and the interval, not (a) the shared reading rejecting (every sharer rejects, `flight` cleared, `last` unchanged, a later call retries), (b) a reading younger than the interval across local midnight (`sameLocalDay`), (c) `readNow` partially failing and being cached for 15 s with its `unread`. `test/agent-identity.test.mjs` tests `joinByRuntime` only, never `withIdentity`'s catch (ER-7); nothing tests `withWork`'s turns failure beyond the flag, or `executorsCached` resetting on rejection (`main/index.ts#executorsCached`: `rows.catch(() => { executorsKept = null })` also resets a newer entry; a timed-out `--version` is cached as `unresponsive` for 10 minutes). Add tests for these.
