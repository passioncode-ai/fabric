## Findings

| ID | Severity | What | Evidence | Proposed fix |
|---|---|---|---|---|
| DA-1 | blocking | The new capacity gate holds every board dispatch whenever `used >= cap`, ignoring Switchboard's board share. Switchboard admits a board start at a full pool while `board_used < board_share` (the share exists exactly so board runs go on when interactive sessions fill the cap), and reports it as `board_admitted`. Fabric reads only `used` and `cap`, so at a full pool with board slots free it opens and starts nothing that 0.3.22 would have started and Switchboard would have admitted. A working path regresses, and the CHANGELOG line «at the cap it opens no workflow and starts nothing» states a rule Switchboard does not have. | `apps/desktop/src/main/boardDispatchWiring.ts:572-576` keeps only `{used, cap}`; `apps/desktop/src/main/boardDispatchRun.ts:1134-1140` `atCapacity = capacity.used >= capacity.cap`, then `return`; Switchboard `crates/fabric-sessions-core/src/capacity.rs:291-302` (`admits`: `start == Start::Board && board_used < share` at a full pool) and `:314-326` (`board_admitted`, `board_share`, `board_used` in the view); live `switchboard_capacity` on this Mac: `cap 40, board_share 10, board_admitted true`. The new test `board-dispatch-run.test.mjs` «at Switchboard's session cap no run starts» covers only `used >= cap` with no share. | Read `board_admitted` when Switchboard names it and hold only when it is `false`; with an older Switchboard that has no such field, fall back to `used >= cap`. Add a test: `used 40, cap 40, board_used 1, board_share 10` starts a run. |
| DA-2 | non-blocking | At the cap the pass `return`s before the request loop, so nothing but the launch is skipped too: a request with no folder is not given to the operator after 30 min, `emptyRuns` past the bound is not given to the operator, the live-session and past-due bookkeeping is not refreshed, for as long as the pool is full. And records already `starting` are asked again above the gate, so at the cap they still reach Switchboard and are refused `at_capacity` (mapped to `failed-to-start` with its back-off). | `apps/desktop/src/main/boardDispatchRun.ts:1119` (starting records retried before the gate), `:1140` (`if (atCapacity) return`), loop from `:1145`; `apps/desktop/src/shared/boardDispatch.ts` `refusalCheck` has no `at_capacity` case (default `failed-to-start`). | Compute the hold once and apply it only where a run would start: skip `start(r)` for `starting` records and `continue` at `decision.path === 'launch'`, leaving every other path of the loop running. Map `at_capacity` to a wait check rather than `failed-to-start`. |
| DA-3 | non-blocking | A PM reply whose answer block does not parse is now taken as a note: it is marked handled with `posted: true` and never judged again, and the PM side is told nothing. In 0.3.22 the same reply got «не применено: <причина>» back. Any malformed attempt (a trailing comma, a fence tagged `JSON` or untagged, a body the board redacted) is silently dropped, the PM agent believes it answered, and the person's decision is lost until the request ends and the re-ask fires. | `apps/desktop/src/main/peopleAskRun.ts:208-216` (`!hasAnswerBlock(body)` sets `handled[m.id] = { result: '', posted: true }`); `apps/desktop/src/shared/peopleAsk.ts:191-209` (`blocks` keeps only fences tagged `json` whose content parses, so `hasAnswerBlock` is false for any malformed block); a redacted message reads as `''` (`peopleAskRun.ts:208`). | Treat a reply as an answer attempt when its text names `fabric-people-answer/1` or holds any fenced block, and run it through `parseAnswer` so a malformed one gets its «не применено» reason; keep the silent note path for replies with neither. Say a redacted reply in the thread rather than dropping it. |
| DA-4 | non-blocking | The disk floor is enforced only by the runtime watch. The launch's own start (`startStack` in `index.ts`) runs `supabase start` with no disk check, so a Fabric started or restarted on a disk under 1 GB starts the database writing (WAL recovery, migrations) before the watch stops it. `stoppedForDisk` is in memory, so after a restart under 3.5 GB the 3.5 GB hysteresis is gone and the stack starts at any free space above 1 GB. ## Checked and sound

- People-ask re-ask: the first ask keeps the 0.3.22 key `people-ask:<item>:<revision>` and a second gets `:2`, both
  inside the board's key pattern (`peopleAsk.test.ts`); a re-ask that is skipped leaves the closed record to be asked on
  a later pass; an unsent second ask keeps `attempt 2` and so its key; `handled` is carried into the new record, so an
  answer is never judged twice; `pending` keeps a request with an unjudged answer from being closed as undecided;
  `isAskRecord` tolerates the new optional fields, so a downgrade reads the file; at most two requests per item and
  revision.
- Withdrawn line: posted under its own idempotency key `people-ask-withdrawn:<requestId>` beside the cancel, its text
  carries only the item id, revision and Fabric's own reason sentence; failures go to the ops log without the body.
- Control timeout: matched as a fixed sentence and replaced by Fabric's own note, so no Switchboard stderr reaches the
  log (DA-5 of 0.3.16 kept); a start that timed out stays `starting` with the same dispatch id, workflow and hand-over,
  which Switchboard dedupes per workflow (`boardDispatchRun.ts#start`).
- Live-session window: a left task (`RESUME_CAPABILITY`) stays with the live session; a request or inbox item goes to
  a run after the grace plus 10 min (`boardDispatch.ts:162`, tested both sides of the bound).
- The cycle's move: `board-dispatches.json`, `resume-since.json`, `people-asks.json`, `people-ask-routes.json`, the
  digest token and `digests/` resolve to the same files under `userData` as in v0.3.22; the people-ask doors, item read
  and access read are the same calls given through `BoardDecisions`; `cycle.ran@1` is unchanged.
- `projectReads.ts` and `createAssignDeps` are line for line the v0.3.22 queries (`maybeSingle`, ordering, `limit 50`,
  the same journal events and actor); `index.ts` still builds them per call over the current `store`, so a Retry's new
  store is used.
- `setLocalStoreDir` is called at `index.ts` module scope before any store is read, and no module that makes a store at
  import reads it at import; a read before the folder is named throws `LocalStoreDirUnset` by name, never reads empty.
- `board-main`: nothing in the window spawns it (its only reference is the bundle entry); its ops log is under
  `<userData>/board/logs`, apart from the window's; it does not start the cycle, so it writes none of the dispatcher's or
  people-ask's files; a second hub cannot take the window's port, and `startHub` then publishes no `hub.json`; its test
  runs with a temporary HOME and port.
- Login-item re-registration runs only in the process that won the single-instance lock, never in launchd's own copy,
  only for a packaged macOS start with the switch on, and only when `launchctl print` names a different bundle version;
  the ops line carries two version strings.
- Disk stop: `supabase stop` without `--no-backup` keeps the volumes; `stoppedByHeal` makes the watch read the missing
  containers as Fabric's own to start once space is back, and a run of `startStackOnce` clears it; the ops lines carry
  free gigabytes and the last two lines of an error cut to 300 characters, the same shape as `stack.recover`'s.
- «Новая сессия»: `checkLaunch` is a read; a failed read is shown as unread, nothing starts until the person chooses.
