## Findings
| ID | Severity | What | Evidence | Proposed fix |

| DA-1 | blocking (a shipped claim is false) | The release notes say «a restore refuses an archive whose board file is gone or differs, naming the file» (CO-315). The check exists only in `createBackups().verify`, which has no production caller. The only restore a person can run is `privateHistory.restore`. That path never reads `board.sha256` and does not copy it into the operation's folder. So an exported archive whose `board.json` was lost restores with `board_history: 'missing'`, which is exactly the CO-315 defect: the person is told the texts were never in the archive. A `board.json` swapped for another file that is self-consistent and bound to the same archive is accepted as well. This was already true at a0a89d1, where the check also lived only in `backup.ts`; iteration 1 did not see it. | `CHANGELOG.md:62-63`; `main/index.ts:1504, 4417`; `main/privateHistory.ts:133-137, 182, 240`; `docs/launch/harness-r0/restore-authority.md:235-237`; the probe output above (`verify` says `truncated`, the wired restore says `ok` and `missing`) | In `privateHistory.readArchive`, read `board.sha256`. If it is present and `board.json` is absent, refuse `invalid_archive`/`truncated`. If it is present and does not match, refuse `integrity_mismatch`. Copy `board.sha256` into the operation's folder and check it again at the `board` stage. Add a `private-history-service` case that deletes `board.json` and expects a refusal, and watch it fail first. The other option is to narrow the release note to what is actually wired and leave CO-315 open. |
