## Findings

### DO-1 · non-blocking · The runbook says the installed app's main process runs on a measured runtime on Intel; by the code's own definition it does not, on either architecture

- **Evidence.** `docs/launch/release-mac.md:14-15`: "On Intel the app's main process runs on a measured runtime
  (Electron 44.0.0 darwin-x64)". The tuple in `apps/desktop/src/main/runtimeAdmission.ts:51-52` keys on
  `codeSha256` `d2a5a75b…ef6c`, the SHA-256 of the **npm** darwin-x64 `Electron Framework`, which `checks.md:797-798`
  records as thin (`lipo -archs` → `x86_64`). `runtimeTuple()` hashes the running app's own framework
  (`runtimeAdmission.ts:61-66`, `86`); in the released universal app that file is the one `@electron/universal`
  joined from both architectures and electron-builder then re-signed (`macPackager.js#doUniversalPack`:
  `makeUniversalApp`, then `doSignAfterPack`), so its bytes cannot equal a thin file's and `isMeasuredRuntime()`
  (`:94-97`) is false in the installed app on Intel and on Apple silicon alike. `checks.md:822-823` says so itself:
  "NOT_RUN: the packaged, hardened universal app on an Intel Mac (as N1 for arm64)". The only consumer of the
  admission, `ownedBackendProcessRegistry.ts:102`, is never instantiated by the app (`git grep
  "createOwnedBackendProcessRegistry("` finds only its definition).
- **Why it matters.** The section is *What the installed app needs*. It tells a reader the Intel app runs on an
  admitted runtime. What was measured is a development runtime under Rosetta. Nothing changes at run time, because
  the gate is not wired, but the runbook claims more than its own receipt.
- **Smallest fix.** "Electron 44.0.0's npm darwin-x64 build was measured under Rosetta and admitted for the
  owned-process adapters (receipt); the packaged universal app's runtime is not a measured tuple (N1, NOT_RUN), and
  the app has not yet run on an Intel Mac."

### DO-2 · non-blocking · The release gate refuses this ledger as it stands, and *Release close* does not list two of the things it needs

- **Evidence.** My probe of `releaseGateProblems` on the candidate's ledger:
  `iteration 1 must end with its one line "Exit for iteration 1: … Blocking findings open: none."`, the same for
  iterations 2 and 3, and `the release gate requires reviewReceipts schema fabric-release-reviews/1`. The ledger's
  §Iteration 1 (lines 85-125) and §Iteration 2 (126-156) end with their tables and have no exit line. 0.3.3's ledger
  has one per iteration (`2026-10-08-release-033-verification.md:140, 195, 262`). There is no 0.3.4 receipt JSON:
  `docs/evidence/reviews/0.3.4/iteration-{1,2}/` hold only the `.md` reports, where 0.3.3 has `<level>.json` beside
  each. *Release close* item 1 (lines 52-55) names `release-gate.json` with "three receipt groups", but not the exit
  lines or the fifteen receipt files those groups must point to (runbook lines 69-80).
- **Why it matters.** The ledger and P-15 present iterations 1 and 2 as closed, but the gate's own machinery reads
  them as open. On this checklist the release commit would first be refused at `preflight`. All of these files may
  change after `verifiedCommit` (runbook lines 81-83), so this does not block the candidate.
- **Smallest fix.** Add the two exit lines now, and the third with iteration 3's disposition. *Release close* item 1
  should also name "an `Exit for iteration N` line per iteration and the fifteen receipts
  `docs/evidence/reviews/0.3.4/iteration-N/<level>.json`".
