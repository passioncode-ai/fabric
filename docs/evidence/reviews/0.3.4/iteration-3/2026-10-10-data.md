## Findings

### DA-1 — non-blocking — The journal read can never return more than 1000 rows, so "a longer journal is seen, and refused" is false, and a used estate behind 999 hub requests is granted

**Evidence.**
- **What the code expects.** `seedRepair.ts:25-30` says: "one more is read so that a longer journal is seen, and refused rather than called untouched". It sets `EVENT_READ_LIMIT = 1000`. The read at `:100-101` asks for `.limit(EVENT_READ_LIMIT + 1)`, which is 1001 rows. The check at `:60` refuses when `events.length > 1000`.
- **What the gateway allows.** The gateway answers at most `max_rows` rows: `supabase/config.toml:18` sets `max_rows = 1000`, and the bundled stack ships that file (`electron-builder.yml`, `extraResources` filter `config.toml`). The repository has already measured this itself: `scopedStore.ts:99-101` says "The gateway answers at most `max_rows` rows (1000 …) however many match, and says nothing about the rest".
- **Measured** on a disposable stack through the shipped `seedRepairDb` and supabase-js:
  - "requested limit 1001 rows returned 1000".
  - On a legacy database with 999 unattended requests followed by a person-created project (journal 1001 rows, `projects` 1), `seedOnlyProblem` gave `null`.
  - `repairSeedOnlyEstate` returned `{"repaired":true}`, and `resolve_subject` then said `owner`.
- **The `> EVENT_READ_LIMIT` branch is unreachable in production.** The tests cannot see this:
  - `seed-repair.test.mjs:28` feeds the pure function 1001 events. The real reader never returns that many.
  - The recording client (`:86-106`) fakes the rows.
  - The `legacy` tier reads with SQL directly (`first-install-db.test.mjs:70-71`), bypassing the gateway.
  - Planting `EVENT_READ_LIMIT = 5000` leaves `seed-repair.test.mjs` green (exit 0).
- **This came in with iteration 2's own fix.** V2-6 raised the limit from 50 to 1000, which is exactly the gateway's cap. V2-6 therefore does not fully hold.

**Why it matters.** The release makes three statements about this bound, and none of them holds at it:
- CHANGELOG.md:22: "A database anyone has used is never changed this way."
- ADR-0131 §2 (line 39): "within `EVENT_READ_LIMIT` (1000) events in all".
- The code comment quoted above.

Past 1000 events the decision is made on a prefix. Whatever lies beyond row 1000 is never read.

**Why it is not blocking.** Reaching it takes two things:
- 999 or more unanswered hub requests. That means a 0.3.1–0.3.3 error dialog left open for hours with agents asking. It is plausible on a Mac with many agents.
- *Then* a non-hub event, while the operator is not a member and no membership decision is on record. No shipped path writes that. A person's write needs identity in the app (the guarded journal), and 0.3.4 runs the gate before the hub. Only a service-role script could do it, as `walk-estate.sql` does.

The second condition is what makes the case unreachable through the product.

**Smallest fix I would accept.**
- Put `EVENT_READ_LIMIT + 1` within the cap, for example `EVENT_READ_LIMIT = 999`. Alternatively, read the exact journal count separately (`count: 'exact', head: true`, as `decisions` already does) and refuse when it exceeds the rows read.
- Add a check that the bound fits the gateway: a test that reads `max_rows` from `supabase/config.toml` and asserts `EVENT_READ_LIMIT + 1 <= max_rows`. Watch it fail with the current 1000.
- Make ADR-0131 §2 state the bound that actually holds.

### DA-2 — non-blocking — `rehearse-upgrade --make-fixture N` no longer builds an older release's database: it seeds with the 0.3.4 seed

**Evidence.**
- `rehearse-upgrade.mjs:166` builds its "synthetic dump shaped like an older release" (header, line 18) with `startStack(dir, { migrationCount: count, seed: true })`.
- `test-stack.mjs:167` copies the seed from `REPO_ROOT`, which is the candidate's.
- For any N ≥ 70 (for example `--make-fixture 75`, the "0.3.0-shaped dump" that `release-mac.md:244` cites), migration 70's projector (`:211-218`) grants `owner_person_id` to `…000a`, a person migration 58 inserted.
- So the fixture's org #1 now opens. No 0.3.0 install ever made that shape: every one was `…0002`-owned and `not_a_member` (ADR-0131 Context).
- The rehearsal judges schema version and row counts only, so its own verdict is unaffected. But the repository's only tool that models an older release's database has quietly stopped modelling CO-241's shape.
- No committed test runs the path the CHANGELOG "Upgrading" paragraph and ADR §5 promise: a 69/75/78 database → upgrade to 79 → repaired at start. Its evidence is iteration 1's probe receipt (`docs/evidence/reviews/0.3.4/iteration-1/2026-10-10-data.md`, `upgrade.mjs` for 0.3.0 only).

**Why it matters.** Anyone who rehearses the documented upgrade for a 0.3.0/0.3.1/0.2.0 database with `--make-fixture` gets a database that already opens. It would hide a regression in exactly the path 0.3.4 tells those users to take.

**Smallest fix I would accept.** Either option is enough:
- `--make-fixture` applies the seed of the release it shapes: the seed at `--ref`, or `apps/desktop/test/fixtures/legacy-seed-0.3.3.sql` for counts ≤ 79, since the seed was byte-identical from `v0.2.0-rc.1` to `v0.3.3`.
- Or the runbook and the script header say the fixture carries the current seed and is not a CO-241 rehearsal.
