## Findings

### ER-1 — non-blocking. The repair's "a longer journal is seen, and refused" never fires: the gateway caps the read at 1000 rows, the limit the repair asks for

- **Evidence.**
  - `seedRepair.ts:30` sets `EVENT_READ_LIMIT = 1000`. `seedRepair.ts:101` reads
    `.limit(EVENT_READ_LIMIT + 1)`, i.e. 1001 rows, through PostgREST.
  - `supabase/config.toml:18` sets `max_rows = 1000`. PostgREST documents `db-max-rows` as "a hard limit on the
    number of rows PostgREST will fetch" (docs.postgrest.org v14, Configuration).
  - The codebase itself measured that cap and depends on it:
    - `scopedStore.ts:99`: "The gateway answers at most `max_rows` rows (1000, `supabase/config.toml`) however many
      match … MEASURED in the 2026-10-03 release review".
    - `accessStore.ts:93`.
    - CHANGELOG 0.3.2 "no longer cut at 1000 rows".
  - So `events.length` is at most 1000. The guard `events.length > EVENT_READ_LIMIT` (`seedRepair.ts:60`) can never
    be true against the real stack.
  - A journal of 1001 or more events whose first 1000 have the seed's shape is judged on those 1000 alone, and is
    granted.
  - In iteration 2 the limit was 50, which is why the earlier note "`max_rows = 1000` is above the 51-row read" held
    then. V2-6 raised the limit to 1000, onto the cap.
  - The unit case `seed-repair.test.mjs:28` hands `seedOnlyProblem` 1001 synthetic events, a list the real read
    cannot return. The recording client (`:86–106`) holds only that `.limit(1001)` is *requested*. No tier reads
    through PostgREST.
- **Why it matters.** This is the one code path that makes Fabric an owner without anybody deciding it. ADR-0131 §2
  states its bound as "within `EVENT_READ_LIMIT` (1000) events in all", and the code comment says a longer journal is
  "seen, and refused rather than called untouched". In the candidate both statements are false.
- **Why it is not blocking.** In every database I can reach, the events past the 1000th are also hub requests:
  - a failed start never holds `OPERATOR_ACTOR`, so no decision can be journalled;
  - `hub.call.forwarded@1` needs a binding, and a binding needs a decision.

  So today's outcome is the same as with a working guard. The guard exists for the case nobody foresaw.
- **Smallest fix I would accept.** One of:
  - `EVENT_READ_LIMIT = 999`, so the read of `limit + 1` fits under `max_rows`;
  - or a separate `select('seq', { count: 'exact', head: true })` compared with the limit.

  Either way, add a test that reads `max_rows` from `supabase/config.toml` and asserts `EVENT_READ_LIMIT + 1 <= max_rows`.
  The test should be watched failing at 1000.

### ER-2 — non-blocking. The release preflight would refuse the 0.3.4 ledger as it stands, for a requirement the *Release close* list does not name

  artifacts that do not exist yet, it reports:

  - the same for iteration 2;
  - `iteration 1 … receipt is absent … docs/evidence/reviews/0.3.4/iteration-1/<level>.json` for all five levels,

- **Why it matters.** *Release close* item 1 names "three receipt groups" but not the exit lines. A release commit
  built from that list would be refused by `release-mac.mjs` preflight. That is a closed failure, not a dangerous

### ER-3 — non-blocking. "On Intel the app's main process runs on a measured runtime" is not true of the app that ships

- **Evidence.** `docs/launch/release-mac.md:14–15` says, under *What the installed app needs*: "On Intel the app's
  main process runs on a measured runtime (Electron 44.0.0 darwin-x64)". The facts in the code:
  - The new tuple (`runtimeAdmission.ts`, region `measured-runtimes`) is the SHA-256 of npm's **thin** x86_64
    `Electron Framework` (`d2a5a75b…`).
  - `runtimeTuple()` hashes `Contents/Frameworks/Electron Framework.framework/Versions/A/Electron Framework` of the
    running app (`codeBinary`).
  - In the shipped app that file is lipo-joined by `@electron/universal`, so it starts with a fat header, not a thin
    Mach-O magic. It is also re-signed, as the file's own comment says ("the packaged, hardened app is re-signed and
    is measured separately (N1)").
  - So it matches no tuple on either architecture.
  - Today nothing in the shipped app consults admission. `ownedBackendProcessRegistry.ts` is imported only as types
    (`git grep` finds no runtime import in `index.ts` or anywhere else). So nothing breaks.
- **Why it matters.** The release notes and runbook present the x64 measurement as the Intel app's runtime. A reader
  will take Intel admission as done for the shipped app. In fact it covers only the npm Electron under Rosetta, and
  the packaged universal app is unmeasured on both architectures, as the arm64 app always was. The CHANGELOG's
  wording, "Its Intel runtime was measured under Rosetta", is accurate only if it is read as the npm runtime.
- **Smallest fix.** One clause in the runbook line:
  "the npm Electron 44.0.0 darwin-x64 runtime is measured; the packaged universal app, like the arm64 one, is not
  (N1)".

## Looked and found nothing

- **A failed read, a refused grant, a throw in the repair.** Each returns its reason. Nothing is granted unless all
  three reads answered and the shape holds (`seedRepair.ts:77–94`; run 1 covers: connection refused, timeout,
  permission denied, door conflict, a thrown read). If the second `identity.establish()` rejected, the throw would
  skip `ops.record`. But supabase-js returns transport errors as `{ error }` rather than throwing, and the startup
  failure log and `startup.bootstrap` would still record it.
- **The boundary sentence.** Every refusal is thrown as `identity could not be established: <says>`, and the
  repair's reason is appended only when the repair ran and the second read also refused (`index.ts:666–667`).
  `startup-failure.log` and the dialog's details carry the whole message (`explainAndQuit`).
- **Partly seeded database.** Both seeds are a single `do $$` block, so a seed is applied entirely or not at all.
  With no estate, bootstrap founds one with an owner and skips the repair (`estate` falsy). With no creation event,
  the estate is refused (`seedOnlyProblem`). The new seed is idempotent (run 2 `fresh` case 4). Migrations 68–81
  write no membership or journal rows at top level. Only `event_types` inserts and one `access_requests` update in
  080, so a 0.2.0/0.3.0/0.3.1 database brought to 79 keeps the shape.
- **What older failed starts could write.** Only `access.requested@1` by `system/fabric-hub`
  (`accessService.ts:202`). Every other hub event needs an operator decision or a binding. `unattended()` admits
  exactly that.
- **The reads themselves.** `service_role` has `select` on `journal` (`migration_one.sql:296`), on `memberships`
  (`:290`) and on `membership_commands` (`…052:113`). A `head: true` count error gives `data: null`, which is
  refused.
- **Slow database.** The gate adds up to four reads and one RPC with no deadline before any window exists. This is
  the same class as the pre-existing `estates` read and the identity read: unbounded, nothing new. Iteration 2 noted
  the same.
- **Universal build failure modes.**
  - In the per-architecture pack, `afterPack` runs on the x64 and arm64 temp apps and again on the joined app
    (`app-builder-lib` `doUniversalPack`, `emitAfterPack` with `arch` 4). `@electron/universal` skips a Mach-O that
    is universal in both apps (`index.js:120–125`), so the joined prebuilds are not re-lipo'd and do not trip its
    "same in both builds" error (`:130–133`).
  - Refusals: a missing darwin prebuild is refused (run 3, second test); a lipo failure throws with stderr; a
    prebuild that did not become universal throws; foreign prebuilds throw.
  - A thin or unreadable Mach-O in the joined app throws in `afterPack`, and again in the receipt
    (`release-mac.mjs:148`). A main binary that is not universal fails the receipt (`:146`).
  - The only production native dependency is node-pty (`package.json` dependencies), and it has no `build/` to
    shadow the prebuilds.
- **Release workflow paths.** For `universal`, `artifactName` gives `Fabric-0.3.4-universal.dmg`, which is what
  `release.yml:96` copies. A missing file fails `cp`, and `if-no-files-found: error` catches it as well. Both
  `release-mac.mjs` paths read `dist/mac-universal/`. One small transition gap: a stale local `dist/mac-arm64` from a
  0.3.3 debug build is deleted without the `lsregister -u` step. On CI the runner is fresh, so this matters only on a
  developer Mac. Too small to raise.
