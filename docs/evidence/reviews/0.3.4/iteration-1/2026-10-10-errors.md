## Findings

### ER-1 — non-blocking — When the repair does not apply, the person is told "could not work out why", and the reason is nowhere they will look

- Evidence: `apps/desktop/src/main/index.ts:878-890` — the repair's `why` goes only to `ops.record` (`detail: { why }`);
  the thrown error is the unchanged boundary sentence `identity could not be established: ${established.says}`.
  Run 8: that sentence classifies as `cause: "unknown"` → dialog "Fabric could not start, and could not work out why."
  with only Copy/Quit (past the retry point, `index.ts:649`). `startup-failure.log` is written from the same
  failure (`explainAndQuit`), so it carries no `why` either.
- Why it matters: every residual case ADR-0131 §3 deliberately leaves alone (history after creation, a named owner,
  another member, a failed read, a conflict) now looks to the person exactly like the 0.3.0–0.3.3 bug the release
  claims to fix, and the dialog says the app does not know why when it knows precisely. The boundary is right to
  refuse; it is wrong to refuse mutely.
- Smallest fix I would accept: keep the boundary sentence as the prefix and append the repair's reason when a repair
  was attempted, e.g. `identity could not be established: <says> (the 0.3.0–0.3.3 seed repair did not apply: <why>)`;
  optionally a `classifyStartupFailure` case for `identity could not be established` with a remedy that names the
  operations log and CO-241. Pin it in a test of the thrown text.

### ER-2 — non-blocking — A failed repair is logged below a successful one

- Evidence: `index.ts:884` `level: repair.repaired ? 'warn' : 'info'` overrides the outcome-derived level
  (`shared/opsLog.ts:60` `LEVEL_FOR = { ok: 'info', unknown: 'warn', failed: 'error' }`, whose comment warns that
  naming a level as well "is answering the same question twice and eventually differently"). So `connection refused`,
  `permission denied` and a thrown read (all `outcome: 'failed'`) are recorded at `info`; Diagnostics reads with a level
  floor (`ops.ts` `read({ level })`, `atLeast`), so a `warn` floor shows the success and hides every failure.
- Why it matters: the one place the reason survives (ER-1) is filtered out by the obvious filter.
- Smallest fix: drop the explicit `level` (let `failed` be `error`), or keep `info` only for the shape refusals
  (`seedOnlyProblem` answers) and `error` for read/grant/throw failures.

### ER-3 — non-blocking — The repair runs after the hub opens, so any hub write into the default estate turns a repairable database into a permanently refused one

- Evidence: `index.ts:722` `startHub(...)` (and `pastRetryPoint = true` at 649) runs before the repair at 878-887.
  `accessService.ts:202` journals `access.requested@1` with `HUB_ACTOR = { kind: 'system', id: 'fabric-hub' }`
  (`accessService.ts:80`) into `ACTIVE_ESTATE` on an agent's `fabric.access.request`, with no identity check (the
  journal is guarded only at `index.ts` after identity). `seedRepair.ts:41` then answers "the estate has history after
  its creation" on every later start. The same window existed in every failed 0.3.0–0.3.3 start: the hub was up
  behind the error dialog until quit.
- Why it matters: (a) on a Mac with registered agents (PassionCode's own products register in the hub), a 0.3.3
  database may already carry such an event, and 0.3.4 will refuse it with ER-1's mute dialog; (b) the ledger's release
  close item 3 requires the **operator's** database — reset 2026-10-08, then started repeatedly by the lifecycle broker
  on 0.3.2/0.3.3 — to be repaired, and nothing in the ledger records that its `org #1` journal is still exactly the
  seed's one event. I could not check it (out of bounds for this review). If it is not, the release-close check fails
  after the tag.
- Smallest fix I would accept: before tagging, record in the ledger the `org #1` journal shape of the pre-0.3.4 dump
  (restore `pre-0.3.4-seed-repair-2026-10-10.dump` into an owned cluster; `select seq, type, actor from journal where
  estate_id = '…0001' order by seq`). In code, the clean fix is to run `identity.establish()` + the repair before
  `pastRetryPoint = true` / `startHub` (it needs only `db` and the estate), which also makes an identity failure
  retryable; if that is deferred, a carry-over row naming the window.

### ER-4 — non-blocking — A conflict leaves startup refused although the operator is now a member; the bootstrap seam has no test

- Evidence: `index.ts:887` re-reads identity only `if (repair.repaired)`. A grant answered `conflict`
  (`change_membership` compare-and-set, `20260909000052_membership_authority.sql:162-166`) means someone else's grant
  landed between the read and the write — on this shape, the same grant — yet the start throws "that person is not a
  member of this estate". Two processes can reach this: the single-instance lock (`index.ts:4451`) is per userData
  directory, the dev build (`package.json` name `@fabric/desktop`, no `productName`, no `setPath`) and the packaged app
  (`productName: Fabric`) use different ones, and both open the same `fabric` stack. Reopening heals it (the next
  `establish()` succeeds). No test drives `bootstrapReady`'s branch (`why === 'not_a_member' && ACTIVE_ESTATE ===
  DEFAULT_ESTATE`), the re-read or the record: `seed-repair.test.mjs` covers `repairSeedOnlyEstate` with a fake, and
  `first-install-db.test.mjs` re-implements the reads in SQL rather than calling `seedRepairDb` through PostgREST.
- Why it matters: rare, but it is exactly the "two Fabric processes starting at once" path, and it answers with a
  false sentence (the person *is* a member by then).
- Smallest fix: call `identity.establish()` again after any repair attempt (it is a read; on a refusal it answers the
  same), and a test of that seam with a fake identity/db.

### ER-5 — non-blocking — The thin-Mach-O guard fails open on a Mach-O lipo cannot read and on 64-bit fat headers

- Evidence: `scripts/lib/universal-mac.mjs:32-33` — `slices()` returns `null` when `lipo -archs` fails, and
  `thinMachO` (:44-45) treats `null` as "not a Mach-O". Run 7: a file with magic `cffaedfe` + garbage →
  `slices(corrupt) => null`, `thinMachO(odd) => []`. `MACH_O` (:17) lacks `0xcafebabf` (FAT_MAGIC_64), so a 64-bit fat
  file is skipped too.
- Why it matters: `after-pack-universal.mjs:17-19` and the receipt's `checks.universal` (`release-mac.mjs`) state
  "every Mach-O carries arm64 and x86_64"; a file the check could not read is counted as passing. Low likelihood
  (codesign would probably reject a corrupt Mach-O), hence non-blocking.
- Smallest fix: in `thinMachO`, report a file with Mach-O magic whose `lipo` fails as `path [unreadable]`; add
  `0xcafebabf`.

### ER-6 — non-blocking — The release workflow still describes an Apple-silicon-only DMG

- Evidence: `.github/workflows/release.yml:1` "The release: Fabric for macOS as one DMG for Apple silicon", while
  line 96 copies `Fabric-$version-universal.dmg` and `electron-builder.release.yml` builds `universal`.
- Why it matters: the workflow's header is what an approver reads in the protected `release` environment; it now
  misstates what is being signed.
- Smallest fix: "one universal DMG (Apple silicon and Intel)".

- **Repeated starts** — once granted, the shape answers "already a member" and the door answers `conflict`

- **Slow database** — the repair adds three round trips without a deadline, the same class as the existing

- **Universal build failure modes** (run 7, real node-pty 1.1.0): thin before → four thin files listed; after

  signing (`app-builder-lib/out/macPackager.js:209-213`) and removes the per-arch temp apps (:198-199);
  `Arch.universal` is `4` (`builder-util/out/arch.js:16`), as `after-pack-universal.mjs:17` assumes.

- **Runtime admission** — the new x64 tuple admits only the npm Electron framework; the packaged, re-signed framework
