## Findings

### UX-1 — blocking — When the repair does not apply, the startup dialog says Fabric "could not work out why"; it knows why, and it gives the person nothing to do

- **Evidence.** If the repair refuses, `index.ts:890` throws
  `identity could not be established: that person is not a member of this estate`. `classifyStartupFailure` has no
  case for that message, so the dialog uses `cause: 'unknown'` (`startupFailure.ts:171–176`). Measured with the
  candidate's own functions:
  ```
  {"cause":"unknown","title":"Fabric could not start, and could not work out why."}
  The machine’s own words are below. Copy them — an unrecognised failure is worth reporting, …
  Fabric had already opened its agent surface when this happened, so retrying in place is not safe; reopen the app instead.
  What the machine said:
  identity could not be established: that person is not a member of this estate
  buttons [ 'Copy the details', 'Quit' ]
  ```
  The translated dialog reads the same: en.ts:921–922 and ru.ts:300–301 ("Fabric не запустился и не смог понять
  почему"). `pastRetryPoint = true` (index.ts:649) is set before the identity read, so the person gets no Retry and is
  told to "reopen the app instead" (en.ts:897 / ru.ts:276). Reopening runs the same refusal again. The repair
  computes a reason (`seedRepair.ts#seedOnlyProblem`, for example "the estate has history after its creation"). That
  reason goes only to the operations log, at level `info` (index.ts:884), and never reaches the dialog or
  `startup-failure.log`.
- **Why it matters.** This is the failure 0.3.4 exists to fix, and ADR-0131 §3 keeps it as the outcome for every
  database outside the repaired shape. The title is false: the cause is known and classified. The remedy, "an
  unrecognised failure is worth reporting", gives no place to report it. "Reopen the app" gives the same result
  every time. Before 0.3.4, this unhelpful dialog is part of why every fresh install failed with nothing anyone
  could act on.
- **Smallest fix I would accept.** Add an `identity-refused` cause to `classifyStartupFailure`, matched on
  `^identity could not be established`. Give it an en/ru title and remedy (`startup.identity-refused.*`) that say
  what is true: Fabric's own person is not a member of the Estate it opened, and Fabric does not make itself an
  owner of an Estate somebody has used. The remedy names the next step: report it, with the log path, or open a
  different Estate. Append the repair's `why` to the thrown message so it lands in the dialog's "What the machine
  said" and in `startup-failure.log`. Add one `startupFailure.test.ts` case on the exact string.

### UX-2 — blocking — "An install that could not start, starts" is false for 0.3.0 and 0.3.1 installs: their database is refused for its schema before the repair can run

- **Evidence.** CHANGELOG.md:11 and :20–22 ("Every fresh install of 0.3.0 to 0.3.3 …", "An install that could not
  start, starts … makes you its owner on the next start"). release-mac.md:168 and ADR-0131 make the same claim about
  databases from 0.3.0–0.3.3. Migration counts: v0.3.0 has 75, v0.3.1 has 78, v0.3.2 and v0.3.3 have 79. The build
  accepts only schema 79–79 (`shared/schemaContract.json`). The schema check runs before `bootstrapReady`
  (index.ts:608, `withSchemaReadiness(…, bootstrapReady)`), and Fabric never migrates on its own (schemaReadiness.ts:31,
  :84–85). Measured (`ux-scratch/legacy030.mjs`): the database a fresh 0.3.0 install made is
  `schema_version 75`, `resolve_subject → not_a_member`. A person who failed on 0.3.0 or 0.3.1 and installs 0.3.4
  therefore gets "Fabric could not verify database compatibility". They are told to stop all writers, make a
  verified backup and follow the upgrade runbook, all for a database that holds nothing. The same run shows that
  after the upgrade (76–81) the shape still holds (1 event, members `…0002:owner`), so the repair would then apply.
  But neither the notes nor the dialog tell them to upgrade. The 0.3.4 notes also lack the **Upgrading.** line that
  0.3.3's notes had. By reading only (not measured): `v0.2.0-rc.1` already has the `…0002` seed, migration 58, the
  fatal throw (`identity could not be established`) and the bundled stack (`electron-builder.yml`
  `extraResources … stack/supabase`). So 0.2.0 most likely failed the same way, and the "0.3.0 to 0.3.3" range is
  incomplete at that end too.
- **Why it matters.** These are release notes a user acts on, and the website will point at 0.3.4 *because* earlier
  versions cannot start (ledger, Release close item 4). Half of the named versions do not get the promised result,
  and the dialog they get asks for an upgrade procedure meant for a database with real data in it.
- **Smallest fix I would accept.** Narrow the claim in CHANGELOG, ADR-0131 and release-mac.md:168: a 0.3.2/0.3.3
  database (schema 79) is repaired at start; a 0.3.0/0.3.1 database (schema 75/78) is first refused for its schema
  and is repaired once upgraded to 79. Add an **Upgrading** line saying so, with the exact step. Because a database
  that never started holds nothing, also name the shorter way: discard and recreate it, with the exact command for
  the bundled stack folder. Settle 0.2.0 by measurement or by naming it. A `legacy` case for schema 75 in
  `first-install-db.test.mjs` would turn my scratch measurement into a receipt.

### UX-3 — non-blocking — A repaired database keeps the old seed's `…0002` as a second owner; nothing shows it, the notes do not mention it, and no open row tracks it

- **Evidence.** `seedOnlyProblem` accepts `…0002` as a member (seedRepair.ts:47), and the repair grants only; it does
  not revoke. After the repair the measured members are `…0002:owner` + `…000a:owner` (legacy run, and ADR-0131
  Consequences, line 55). I found no members, persons or person-name surface in the renderer (see "What a person
  sees"), so a person cannot see or remove it. The release note says "makes you its owner" (CHANGELOG.md:20–22),
  not "an owner beside an unused one". CO-241 is marked *resolved*, and this leftover appears only inside its
  resolution text ("Left as it is … removing it is a membership revoke the operator decides"). It is not a row of
  its own, against AGENTS.md rule 2 (a deferral gets a row).
- **Why it matters.** Today there is no visible effect. When Estates gain people (invitations, the owner/member
  labels in SCN on invitations, "a last-owner change is refused"), every repaired install will show an owner called
  "Operator" that nobody is.
- **Smallest fix.** Open a CO row for the `…0002` membership in repaired databases (decide revoke or keep, latest
  before any person or member surface ships). Add one clause to the release note.

### UX-4 — non-blocking — On a repaired install, Profile says Fabric has been "Running for N days" since the day the failed install was made

- **Evidence.** Tenure is the first journal event's `occurred_at` (index.ts estate summary, `tenureFrom` in
  `shared/tenure.ts`; shown by `ProfileSection.tsx` as `profile.tenure`, "Running for {days} days, since {since}",
  en.ts:566). In a repaired database that event is the old seed's `estate.created@1`, written when the 0.3.x install
  first started and failed. The repair journals nothing (`legacy`: "nothing journalled by the repair"). The
  operator's own database, reset 2026-10-08, would show about two days of "running" for a Fabric that never opened
  a window.
- **Why it matters.** `tenure.ts` exists so that an unstarted estate is not shown as a running one ("NOTHING
  RECORDED IS NOT ZERO DAYS"), and this is that error in a different form. It is minor and appears on one screen.
- **Smallest fix.** Accept it and say so in the CO row from UX-3, or count tenure from the first event after the
  creation in an estate whose creation is `system/seed`.

### UX-5 — non-blocking — The 0.3.4 "Changed" note is written for the builder, and it claims more about Intel than was measured

- **Evidence.** CHANGELOG.md:11 and :26–36. The headline "Fabric … runs natively on Intel Macs too" rests on
  measurements under Rosetta on an arm64 Mac, of an *unsigned* universal build. The receipt it links says "NOT_RUN:
  the packaged, hardened universal app on an Intel Mac" (`docs/launch/harness-r0/checks.md:821`). "Electron 44.0.0's
  darwin-x64 main process is now a measured runtime" describes the npm Electron: the tuple hashes the `Electron
  Framework` bytes (`runtimeAdmission.ts#codeBinary`), and runtimeAdmission.ts:35 says the packaged app "is re-signed
  and is measured separately (N1)". The DMG's framework is joined and re-signed, so the new x64 tuple cannot match in
  the app a user installs. On Intel the shipped app behaves as on arm64, not as the sentence suggests. On voice and
  terminology: node-pty "prebuilds", `lipo`, "Mach-O without both slices", receipt `checks.universal`, "registry 17
  groups, native view host 14 groups", CO-237/CO-238 are the insider shorthand voice.md lists as its failure mode
  ("every unfamiliar term introduced"). The Fixed bullets say "its estate" / "first estate" in lowercase, while the
  terminology table spells the term *Estate* and the app shows this one as "My workspace".
- **Why it matters.** These notes are published as the GitHub release text (CHANGELOG.md:3–6). An Intel user reads
  that the app was proven native on their machine, and it was not run on one.
- **Smallest fix.** One user-facing bullet: one DMG for Apple silicon and Intel Macs, with the Intel half measured
  under Rosetta and not yet run on an Intel Mac. Move the build mechanics into release-mac.md, which already has them
  under "Universal macOS". Use "Estate" or "your workspace" consistently.

### UX-6 — non-blocking — The scenario layer still describes startup as a build/schema check only; the identity step, the repair and its refusal are not in scenarios, flows or screens

- **Evidence.** The diff changes no file under `docs/ux/` (the `git diff --stat` list). SCN-095 Preconditions
  (scenarios.md:2463), FLW-55 "Before entry" and its diagram (flows.md:1700, :1709) and SCR-36 "Startup boundary"
  (screens.md:777) name only build identity and schema as startup outcomes. None of them mentions establishing
  identity, the seed repair, or the native dialog shown when identity is refused (UX-1). SCN-126 / FLW-69 are still
  true for both paths checked (entry: "first launch of an estate with no project").
- **Why it matters.** 0.3.4 changes a user-visible startup outcome: a database that was refused now opens, and the
  remaining refusals keep the dialog. The repository rule is scenarios → flows → screens in the same change (AGENTS.md
  iteration contract), and `docs/ux/scenarios.md` owns that truth.
- **Smallest fix.** One amendment line on SCN-095 Preconditions and on FLW-55 "Before entry": after the schema check,
  identity is established; a database only the old seed has touched is granted to the local operator (ADR-0131);
  anything else ends at the native startup dialog with the identity cause from UX-1.

### UX-7 — non-blocking — The receipt the 0.3.4 notes link to still calls universal macOS "0.3.5"

- **Evidence.** `docs/launch/harness-r0/checks.md:793` "For the universal release (PR #27, 0.3.5; …)", the anchor
