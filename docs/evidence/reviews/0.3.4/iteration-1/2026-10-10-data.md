## Findings

### DA-1 — blocking — A 0.3.1–0.3.3 database whose failed start let the hub write is never repaired, and 0.3.4 opens the hub before the repair too

**Evidence.**
- 0.3.1, 0.3.2 and 0.3.3 all open the hub before identity: `startHub` at `index.ts` lines 594/706/721 and
  `identity.establish()` at 709/860/877 (`git show <tag>:apps/desktop/src/main/index.ts | grep -n …`). On the identity
  failure the startup dialog loops (`index.ts:4608-4635` in the candidate). Nothing withdraws `hub.json` until quit
  (`withdrawHub` is called only from `quit.onQuit`). So for as long as the error is on screen, a registered agent can
  call `fabric.access.request`. `AccessService.request` then appends `access.requested@1` as `{kind:'system', id:'fabric-hub'}`
  (`accessService.ts:80`, `:202`). That append is unguarded, because system actors pass (`identity.ts#guarded`) and no
  operator is needed.
- Measured (`data-work/probe.mjs hub`): on the legacy-seeded database, that event is accepted by `append_event`. The
  journal goes to 2 events and `seedOnlyProblem` answers `the estate has history after its creation`. The app then fails
  as before with "identity could not be established: that person is not a member of this estate". The repair's reason
  goes only to the operations log (`identity.seed-repair`, `level: 'info'`, `index.ts:885`). The person sees the old
  sentence and has no documented way out (the runbook and the ADR name none).
- The candidate keeps the same order: `startHub` at `index.ts:722`, the repair at `:881`. A 0.3.4 first start on such a
  database can still lose this race inside its own startup window.
- The release close depends on this case. Ledger step 3: "started … on the operator's database, which it must repair".
  That database has failed under 0.3.2 and 0.3.3 since 2026-10-09 00:48 UTC, on the Mac with the most hub-registered
  agents. I was not permitted to read its dump, so whether it has a second event is unmeasured.

**Why it matters.** The CHANGELOG says "If an earlier version set up a database it then refused, this one finds it
untouched and makes you its owner". That is false for a shape the 0.3.1–0.3.3 code itself produces, and the affected
person stays exactly where CO-241 left them. The `legacy` fixture models a database nobody ever opened. It does not
model one that a failed start left behind.

**Smallest fix I would accept.**
- In `seedOnlyProblem`, also admit events after the creation when every one is system-actored by `fabric-hub` with an
  `access.*` type. That is what a failed start can write. Keep refusing any person-actored event and any other type.
- Move the repair ahead of `startHub`, right after the estate read, so 0.3.4 cannot make the race itself.
- Add a `legacy` case to `first-install-db.test.mjs` with one `access.requested@1` row, watched failing without the change.
- Before release-close step 3, measure the operator's dump read-only in a disposable cluster: the org #1 journal count
  and its types.

### DA-2 — non-blocking — A revoked operator membership is silently granted again

**Evidence.** `data-work/probe.mjs revoke` ran grant → `committed` and a revoke of `…000a` → `committed` (`…0002` keeps
the estate owned). Then `seedOnlyProblem` gave `null`, and a second `change_membership(…, 'grant', 0, …)` gave
`committed`. Membership changes are not journalled (migration 52 writes only `membership_commands`), and a revoke
deletes the row, so revision 0 matches again. `membership_commands` held 3 rows for the estate, and the repair never
reads them.

**Why it matters.** ADR-0131 §3 says every shape that is "somebody's decision … is left alone". A revoke is such a
decision, and the repair undoes it on the next start. No product path revokes today (`change_membership` is called only
by `seedRepair.ts` and tests), so this needs a hand-made SQL revoke. Hence non-blocking.

**Smallest fix.** Refuse when `membership_commands` has any row for the estate (the record of a decision), with a unit
case and a `legacy` DB case.

### DA-3 — non-blocking — The real database reads and the startup wiring are untested: a regression that grants a used estate passes every tier

**Evidence.** No test imports `seedRepairDb` or exercises `bootstrapReady`'s repair block. `grep -rn seedRepairDb
apps/desktop/test scripts` finds only a comment (`first-install-db.test.mjs:68`). The `legacy` case re-implements the
reads in SQL (`limit 2`) and calls `change_membership` itself.

I planted `.limit(2)` → `.limit(1)` and `p_expected_revision: 0` → `null` in a copy of `seedRepair.ts`.
`seed-repair.test.mjs` stayed green (exit 0), and `first-install-db` cannot see either plant. `limit(1)` hides all
history, so the repair would grant any default estate that was seeded by the old seed. A null revision drops the
compare-and-set. Deleting the block from `index.ts:879-889` also fails no test.

**Why it matters.** The safety argument of ADR-0131 rests on "two events are enough to know it has history" and on the
compare-and-set. Neither is held by a test at the layer that ships.

**Smallest fix.** A full-tier test against the disposable stack (it has PostgREST) that runs `repairSeedOnlyEstate(seedRepairDb(client), …)`.
It should show that a two-event estate is refused, and that the grant's RPC binds with `p_expected_revision` 0. Add a
source check (like the existing gates) that `bootstrapReady` calls the repair on `not_a_member` before it throws.

### DA-4 — non-blocking — The x86_64 receipt names the wrong release

**Evidence.** `docs/launch/harness-r0/checks.md:793`: "For the universal release (PR #27, 0.3.5; …)". The CHANGELOG, the
ledger and ADR-0131 all say universal macOS ships in 0.3.4, and 0.3.5 is the Windows/Linux port.

**Why it matters.** This is the receipt the `runtimeAdmission.ts` x64 tuple and `executorAuth.ts` cite. A reader
checking which release admitted the x64 runtime is told the wrong one.

**Smallest fix.** Change it to "0.3.4". This is a dated receipt, so add an amendment line rather than rewriting the
measurement.
