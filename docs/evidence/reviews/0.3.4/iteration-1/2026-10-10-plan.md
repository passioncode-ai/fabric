## Findings

### PL-1 — **blocking** — When 0.3.4 is published, the website will keep serving 0.3.3, which cannot start, and the runbook describes a site mechanism that no longer exists

**Evidence.**
- The site no longer picks Fabric's build from a hand-edited pointer. It uses the always-current resolver (roadmap
  RM-15, site `docs/DEPLOYMENT.md#always-current-versions`). Its policy file
  `releases/products.json` on the site's `main` says:
  `"fabric": { …, "channel": "prerelease", "assets": { "macos": "Fabric-{version}-arm64.dmg" } }`.
  The same document says: "A release is eligible only when every required asset is attached". In `worker/releases.js`
  (`fetchSnapshot` → `pickRelease`), a release that lacks the asset is skipped, so the newest eligible release wins.
- From 0.3.4 the release carries only `Fabric-0.3.4-universal.dmg`
  (`.github/workflows/release.yml:96`, `apps/desktop/electron-builder.release.yml:8` `${arch}`, `scripts/release-mac.mjs:143`).
  0.3.4 will therefore be **ineligible**, and the site will keep offering `v0.3.3`.
- What the site serves today: `curl -sI https://passioncode.ai/fabric/download/macos` returns
  `302 location: https://github.com/passioncode-ai/fabric/releases/download/v0.3.3/Fabric-0.3.3-arm64.dmg`.
  The page says "Early preview 0.3.3 · macOS on Apple silicon", "Apple silicon (arm64) · macOS 13 or later" and
  "Intel Macs are not supported in this preview". The resolver moved the site to 0.3.3 by itself: site commit
  `d19bd337` (2026-10-09 23:23Z), "Sync pages to the published releases". No site PR was involved.
  The knowledge base says the same: `knowledge/products.md:38` reads "the site follows the newest release automatically".
- The candidate's runbook step 9 (`docs/launch/release-mac.md:121-131`) still says the site "serves
  `/fabric/download/macos` from its `fabric/release.json`", and that a site PR sets `downloads.macos` to the
  `-universal.dmg` URL. The 0.3.4 ledger's *Release close* item 4
  (`2026-10-10-release-034-verification.md:56-57`) relies on that step: "The website's release PR (runbook step 9) …
  so the site points at 0.3.4". Neither mentions `releases/products.json` or the asset pattern. Neither mentions the
  page's Apple-silicon-only copy.

**Why it matters.** 0.3.4 exists so that a new install starts. The release close, followed as written, publishes
0.3.4 while passioncode.ai goes on handing new users 0.3.3. The resolver is built never to offer a release without
the policy's asset, so nothing would show the problem. The bad link stays live until somebody reads the site's policy.

**Smallest fix I would accept.**
- Rewrite runbook step 9 for the resolver: the site's PR changes `releases/products.json` `fabric.assets.macos` to
  `Fabric-{version}-universal.dmg` (merged once v0.3.4 is published, or with a floor of 0.3.4), plus the page's
  platform copy (Apple silicon *and* Intel), the screenshots and the facts row.
- Name that change in close item 4.
- Make the receipt the live `/fabric/download/macos` redirect naming `v0.3.4/Fabric-0.3.4-universal.dmg`.
