## Findings

### DO-1 · non-blocking · 0.2.0 had the same defect, but every document says "0.3.0–0.3.3"

- **Evidence.** v0.2.0 (`docs/releases/fabric-0.2.0-mac.json`, commit `f3569996`) has all of the following:
  - migration 58, identical to v0.3.3's (`git diff --quiet f3569996 v0.3.3 -- …000058…` → identical);
  - the identical seed;
  - the same fatal refusal (`git show f3569996:apps/desktop/src/main/index.ts`, lines 567–569);
  - the stack, with `seed.sql`, bundled in the app (`f3569996:apps/desktop/electron-builder.yml:26–32`).

  An owned cluster on 0.2.0's 69-migration chain plus that seed answers `resolve_subject` → `not_a_member` (table above).

  The range "0.3.0–0.3.3" is stated as the whole affected set in CHANGELOG.md:11, ADR-0131:3/9, `seedRepair.ts:3`, CO-241, ledger lines 6–7 and 56 ("0.3.0 to 0.3.3 cannot start on a new Mac"), the MERGES entry and the map entry. Meanwhile `fabric-v0.2.0` is still a published prerelease (release-mac.md:157–161), and `docs/brand/facts.md:17` still names 0.2.0 as the downloadable preview.
- **Why it matters.** The release notes and the ADR give an incomplete count of the broken releases. Anyone deciding what to withdraw or what to tell users, such as the website item in the ledger's release close, will leave 0.2.0 out.
- **Smallest fix.** Write "every release since migration 58 — 0.2.0 and 0.3.0–0.3.3" (with this measurement as the receipt) in CHANGELOG, ADR-0131 Context, CO-241, the ledger and `seedRepair.ts`. Add one line saying a 0.2.0 database (schema 69) takes the upgrade procedure first. The repair itself is shape-based and needs no change.

### DO-8 · non-blocking · CHANGELOG Intel claims beyond their receipts

- **Evidence.**
  - CHANGELOG.md:31–32 says "Measured on an unsigned universal build: node-pty spawns on the x86_64 slice (Rosetta) and on arm64". `git grep` finds that measurement only in the CHANGELOG. Its only record is the commit message of `9a753865`. checks.md's Intel section has no row for it, and it lists as NOT_RUN "the packaged, hardened universal app on an Intel Mac".
  - The headline, "runs natively on Intel Macs too" (CHANGELOG.md:11), rests on runs under Rosetta on an arm64 Mac. The ledger's release close has no Intel check.
  - Related: the registry's 17 groups ran with an arm64 backend Node (checks.md:796–797; `lipo -archs` of that Homebrew node → `arm64`).
- **Why it matters.** Release notes are published as true (AGENTS.md rule 3). One measurement has no tracked receipt, and the headline goes further than what was run.
- **Smallest fix.** Add the universal-build node-pty run to checks.md, with its command and exit code. Qualify the CHANGELOG ("measured under Rosetta on Apple silicon; not yet run on an Intel Mac"), or add an Intel smoke to the release close.

### DO-9 · non-blocking · No gate runs the universal-mac test

- **Evidence.** `release-mac.md:34–35` says "Tested by `scripts/test/universal-mac.test.mjs`". `git grep -n "universal-mac.test"` finds only that line: no `ci.sh` step, workflow or package script runs it. `ci.sh:379` runs only `release-mac.test.mjs`.
- **Why it matters.** The library that produces `checks.universal` and joins node-pty is tested only by hand. A regression would first show up in the protected release run.
- **Smallest fix.** Add the test to the `node --test` line in `ci.sh` fast. It already skips where `lipo` is missing.

### DO-12 · non-blocking · "The sign-in readers know the x64 builds" names versions older than the pinned ones
