## Findings

### DO-1 · blocking · The runbook and the startup dialog name a stack folder the installed app does not use, on the upgrade path the 0.3.4 notes send users down

- **Evidence.**
  - The app materializes its stack at `path.join(app.getPath('userData'), 'stack')` (`apps/desktop/src/main/env.ts:41`).
    Nothing sets the name or the path (`grep setName|setPath|app.name =` in `src/main` → nothing). Electron takes the
    name from `package.json` `productName`, falling back to `name`. The installed app's `package.json`, read out of
    `/Applications/Fabric.app/…/app.asar`, has `productName= undefined name= @fabric/desktop`. `productName: Fabric`
    exists only in `electron-builder.yml:2`, which names the bundle, not `userData`. So the installed app's stack is
    `~/Library/Application Support/@fabric/desktop/stack`. Both
    `docs/evidence/specs/2026-09-29-agent-registry-brief.md:114` ("the dev package name, not 'Fabric'") and the
    0.3.4 runbook's own new sentence agree (`release-mac.md:181`: `cd "$HOME/Library/Application Support/@fabric/desktop/stack" && supabase stop --no-backup`).
    On this Mac, the `Fabric` folder holds only `backups`, which the runbook's own `mkdir` creates.
  - Yet the same runbook says `~/Library/Application Support/Fabric/stack` at `release-mac.md:21` ("keeps a working
    copy in …") and at `:255`, step 4 of the same *Upgrading* section: `cd "$HOME/Library/Application Support/Fabric/stack"`
    then `supabase migration up --local`.
  - The startup dialog says the same wrong folder: `schemaReadiness.ts#stackPath`
    (`'~/Library/Application Support/Fabric/stack'`, used in `schemaBehindRecovery`), `startupFailure.ts`
    (schema-missing and database-unreachable remedies), and `en.ts`/`ru.ts` `startup.schema-missing.remedy` and
    `startup.database-unreachable.remedy`.
- **Why it matters.** CHANGELOG 0.3.4 **Upgrading** tells anyone with a 0.3.0, 0.3.1 or 0.2.0 database to "upgrade it
  to 79 … and the next start repairs it", through that section. On 0.3.4's first start they see the schema-behind
  dialog, and it points at the wrong folder; step 4's `cd` then fails. The section now names two different homes for
  one database, within one paragraph, beside an irreversible command ("there is no undo"). A reader cannot tell which
  is right. The defect predates 0.3.4, but 0.3.4 is the release whose promise rests on this path.
- **Smallest fix.** In `release-mac.md`, write `~/Library/Application Support/@fabric/desktop/stack` at :21 and :255,
  with one clause saying why (the app's userData follows its package name). Correct the same path in
  `schemaReadiness.ts#stackPath`, the two `startupFailure.ts` remedies and the two en/ru keys, with `docs/brand/strings.md`.
  Or, if the code strings wait, open a CO row for them in this change. Do not "fix" it by adding `productName`: that
  would move every existing user's data folder.

### DO-2 · non-blocking · "Before the retry point, so a read that failed may be retried" is not what the code does: the refusal comes after the retry point, with no Retry, and the hub is open behind it

- **Evidence.** ADR-0131 §Decision 3 and the comment in region `seed-repair-wiring` (`index.ts#bootstrapReady`) say
  the repair runs "before the retry point, so a read that failed may be retried". In `bootstrapReady`, the order is:
  1. the region, which records a failed repair in `seedRepairWhy`;
  2. `pastRetryPoint = true`;
  3. the hub is built and `await startHub(…)` runs;
  4. `const established = await identity.establish()`, which throws `identity could not be established … did not apply: <why>`.

  The dialog is `startupDialog(failure, { retryable: !pastRetryPoint, … })`, and nothing resets `pastRetryPoint`
  (`grep pastRetryPoint` → three hits). So a repair whose journal read failed ends in a dialog with no Retry. On any
  identity refusal, 0.3.4 still opens the hub and leaves it open behind the error until quit. ADR §Context presents
  that as 0.3.1–0.3.3 behaviour ("opened the agent hub before identity and kept it open behind the error").
- **Why it matters.** The ADR's Decision states a property the release does not have. The reader of the ADR (and the
  ER/DA levels) will assume a transient failure is retryable in place, and that the hub-behind-the-error window is
  closed.
- **Smallest fix.** Either move the final `establish()` and its throw into the region, before `pastRetryPoint = true`,
  for the default-estate path. That makes the refusal retryable and keeps the hub closed on it. Or delete "so a read
  that failed may be retried" from ADR §3 and the comment, and say that quitting and reopening retries, and that the
  hub still opens before the final identity check.

### DO-3 · non-blocking · The `identity-refused` remedy is false when the identity read itself failed

- **Evidence.** `classifyStartupFailure` matches any `^identity could not be established\b`
  (`startupFailure.ts`, the `identity-refused` case). `shared/identity.ts#subjectOf` produces that prefix for an RPC
  error too (`why: 'unavailable'`, "identity could not be resolved: …"). Measured: that message classifies as
  `identity-refused`, with "this database does not name that owner. Fabric takes an Estate for itself only when nothing
  has happened in it yet …" (run table). ADR §4 lists "a read that failed" among the cases that get this cause.
  "Fabric has changed nothing in the Estate" is also false in the rare case of a repair that committed, followed by a
  final read that failed: `seedRepairWhy` stays null and the same remedy shows.
- **Why it matters.** A database that did not answer is told it has the wrong owner, and the person is asked to report
  it instead of retrying or checking the stack.
- **Smallest fix.** Classify as `identity-refused` only `not_a_member`-shaped refusals (or those carrying the repair's
  reason). Send `unavailable` to `database-unreachable`/`unknown`. Alternatively, word the remedy for both cases. Add
  one case to `startupFailure.test.ts`.
