## Findings

### ER-1: non-blocking. A database that stops answering at the identity read is now told "this database does not name that owner" (a regression from 0.3.3)

- Evidence: `shared/startupFailure.ts:98` matches `/^identity could not be established\b/` *before* the
  database-unreachable case (`:173`). `subjectOf` turns every transport or PostgREST error into
  `identity could not be resolved: <message>` (`shared/identity.ts:70`, why `unavailable`), and bootstrap prefixes it
  (`index.ts:899-901`). Run 8, candidate:
  - `identity could not be established: identity could not be resolved: TypeError: fetch failed` →
    `cause: "identity-refused"`, title "Fabric does not have access to the Estate it opened.", buttons
    `["Copy the details","Quit"]`.
  - `…: canceling statement due to statement timeout` (a slow database) → `identity-refused`.
  - `…: the identity command returned no verdict` → `identity-refused`.

  Run 9, `v0.3.3`: the same `fetch failed` message → `cause: "database-unreachable"`.
- Why it matters: the remedy (`startupFailure.ts:103`, en/ru `startup.identity-refused.remedy`) says "this database
  does not name that owner … Fabric takes an Estate for itself only when nothing has happened in it yet; the details
  below say what it found instead. Copy them and report them." For a stack that stopped or timed out, all of that is
  false. 0.3.3 gave the right answer here ("The database is not answering … Run `supabase start` … and retry").
  When the earlier read (`before`, `index.ts:653`) answered `unavailable`, the repair is not attempted and
  `seedRepairWhy` stays null. In that case the details "say what it found" about nothing: they hold the bare 0.3.3
  sentence. The same is true for a chosen, non-default estate. The CHANGELOG line "When Fabric still cannot open the
  Estate, it says why" covers only the case where the repair actually ran. No test pins the order:
  `startupFailure.test.ts` "names the identity refusal…" checks only a `not_a_member` message.
- Smallest fix I would accept: name `identity-refused` only for a refusal (`why` `not_a_member` / `no_such_person`).
  Either throw that case with a code (`FABRIC_IDENTITY_REFUSED`) and classify by code, or move the identity branch
  after the database-unreachable branch and make it skip `identity could not be resolved:` messages. Add a test
  asserting that `identity could not be established: identity could not be resolved: TypeError: fetch failed`
  classifies as `database-unreachable`.

### ER-2: non-blocking. ADR-0131 §3 says a failed read "may be retried", but the fatal identity check still sits past the retry point and after the hub opens

- Evidence: the repair records a failed read and carries on (`index.ts:655-660`: `seedRepairWhy = repair.why`, no
  throw). Then `pastRetryPoint = true` (`:669`) and `startHub(...)` (`:742`) run. The refusal is thrown only at
  `:898-901`. So `explainAndQuit` builds the dialog with `retryable: !pastRetryPoint` = false (`:4620`): Copy/Quit
  only, plus "retrying in place is not safe; reopen the app instead". Two places claim otherwise: ADR-0131 §3 (line 45,
  "It runs before the retry point … and a read that failed may be retried") and the region comment (`index.ts:649`,
  "before the retry point, so a read that failed may be tried again"). The dialog then waits indefinitely
  (`while (!quit.quitting)`), with the hub listening behind it.
- Why it matters:
  1. The stated recovery for a transient read failure does not exist in place.
  2. Behind every refused 0.3.4 start, the hub still accepts `fabric.access.request` into the estate it just refused,
     and journals `access.requested@1` (`accessService.ts:202`). The remedy says at the same moment that "Fabric has
     changed nothing in the Estate".
  3. Those events count toward `EVENT_READ_LIMIT = 50` (`seedRepair.ts:26,56`). With at most 3 pending requests per
     agent (`accessService.ts:189`) and a 10-minute TTL (`shared/access.ts:19`), one agent that asks again after
     each expiry adds about 18 events an hour. A dialog left open about 3 hours after one transient read failure
     makes a repairable database "has more events than the repair reads" permanently. This is the DA-1 window that
     iteration 1 closed for the repair's own read; it stays open for the refusal.
- Smallest fix I would accept: throw the identity refusal before `pastRetryPoint = true`. Inside the seed-repair
  region, after any repair attempt, read `identity.establish()` again and throw with the repair's reason if it is not
  `ok`. Then a refusal is retryable, the hub never opens for a start that will refuse, and §3 is true. If that is
  deferred, the ADR §3 sentence and the `index.ts:649` comment must stop claiming retry, and a carry-over row must name
  the remaining hub window.

### ER-3: non-blocking. Two starts racing on the same database log a successful start as a failed repair at `error`

- Evidence: `change_membership`'s compare-and-set answers `conflict` when another start's grant landed first
  (`…052:162-166`; `first-install-db.test.mjs` `legacy` "a grant against a membership that moved is refused"). The
  wiring records `outcome: 'failed', level: 'error', detail: { why: 'the membership door said conflict: …' }`
  (`index.ts:656-658`). The read again at `:898` then succeeds and the app opens. The dev build and the packaged app
  use different userData folders, so the per-userData single-instance lock (`index.ts:4462`) does not stop them from
  sharing the `fabric` stack. This is the case iteration 1's ER-4 described.
- Why it matters: Diagnostics, read at an `error` floor, shows `identity.seed-repair failed` on a start that holds
  identity. The first thing a person sees there contradicts what happened. It is low-impact: the start itself is right.
- Smallest fix: record the outcome after the read again. If the operator is then a member and the repair answered
  `conflict`, record `ok` (or `unknown`) with "granted by another start". Or record a `conflict` answer at `warn`.

## Looked and found nothing

- **Failed read, refused grant, thrown call in the repair.** Each returns its reason, and nothing is granted when any
  read fails or the shape does not hold (`seedRepair.ts:73-90`; run 1 cases: connection refused, timeout, permission
  denied, conflict, a thrown read). Startup still refuses with the boundary sentence as the prefix
  (`index.ts:899-901`). The thrown message keeps `identity could not be established: <says>` and appends
  ` — the repair … did not apply: <why>`.
- **The reads as they go to PostgREST.** `journal` has `estate_id`, `seq`, `type`, `actor jsonb`, `payload jsonb`
  (`migration_one.sql:110-121`). `membership_commands` grants `select` to `service_role` (`…052:114`). A `head: true`
  count error yields `data: null` and a refusal (`seedRepair.ts:100-101,79`). `max_rows = 1000` is above the 51-row
  read.
- **Concurrency on the grant.** `change_membership` locks the estate's memberships `for update` and compares the
  target's revision (`…052:155-166`). A decision recorded by another start between the read and the grant is caught
  by the same compare-and-set, because any grant the other start made is the operator's own membership. The grant
  journals nothing (run 2, `legacy`).
- **Partly seeded database.** Both seeds are one `do $$` block (atomic). A database with no estate is founded by
  bootstrap with an owner, and the repair is skipped (`estate` null, `index.ts:652`). The new seed's person row
  matches migration 58's (`seed.sql`, `if not exists`). The seed re-run is idempotent (run 2, `fresh` case 4).
- **What an older failed start could write before identity.** `v0.2.0-rc.1` and `v0.3.0` open no hub. `v0.3.1` and
  `v0.3.3` open it (`startHub` before `identity.establish()`, 594/709 and 721/877). There is no other journal append
  between them and the identity read. `access.decided@1` needs `OPERATOR_ACTOR`, which a failed start never had. So
  `unattended()` (`seedRepair.ts:33-35`) admits exactly what could be written.
- **Slow database.** The repair adds one identity read, three reads and one RPC without a deadline. This is the same
  class as the existing `estates` read and identity read; no window is shown during `bootstrapReady` (the splash ends
  with the stack start, `index.ts:556-557`). It was not raised in iteration 1 either; no new failure class.
- **Universal build failure modes.** A missing darwin prebuild throws (run 3, second test). A lipo failure throws
  with lipo's stderr (`universal-mac.mjs:21-24`). A result that is not universal throws (`:75`). Foreign prebuilds
  throw in `afterPack` (`after-pack-universal.mjs:14-15`). A thin or unreadable Mach-O in the joined app throws
  (`:18-21`) and again in the receipt (`release-mac.mjs:146`). A main binary that is not universal fails the receipt
  (`:144`). The installed node-pty has no `build/Release` (it loads `build/Release` before `prebuilds/`,
  `lib/utils.js:19`), so no thin compiled copy shadows the joined prebuilds. If one appeared it would be thin and be
  refused, so the check fails closed.
- **Release workflow paths.** A missing `Fabric-$version-universal.dmg` fails `cp` (`release.yml:96`) and
  `if-no-files-found: error`. `artifactName` `${productName}-${version}-${arch}.${ext}`
  (`electron-builder.release.yml:8`) gives that name for `universal`. `release-mac.mjs` reads `dist/mac-universal/`
  for both the cleanup and the receipt (`:98,118`). The Ubuntu preflight imports `universal-mac.mjs`, whose top level
  calls no lipo.
- **Runtime admission and sign-in readers on x64.** The new tuple admits only the npm Electron 44.0.0 darwin-x64 main
  process. The sign-in readers accept `x64` for the exact measured versions only (`executorAuth.ts:18,51`). Runs 5 and
  6 pass.
