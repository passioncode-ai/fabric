## Findings

### UX-1 — blocking — The upgrade route the 0.3.4 notes send 0.2.0/0.3.0/0.3.1 installs down names a stack folder that does not exist on an installed Fabric

- **Evidence.** CHANGELOG.md, **Upgrading**, says that a 0.3.0/0.3.1 (75/78) or 0.2.0 (69) database "is refused for
  its schema first: upgrade it to 79 … and the next start repairs it". The dialog that person gets (rendered with
  the candidate's code) says:
  ```
  TITLE: Fabric could not verify database compatibility
  … Follow https://github.com/passioncode-ai/Fabric/blob/main/docs/launch/release-mac.md#upgrading-an-existing-database
  before running supabase migration up --local in ~/Library/Application Support/Fabric/stack, then retry.
  ```
  That path comes from `schemaReadiness.ts:30` (`stackPath`), used at :85. The same folder appears in the
  `schema-missing` and `database-unreachable` remedies (`startupFailure.ts:164`, `:178`; `en.ts:920`, `:922`;
  `ru.ts:299`, `:301`) and in the runbook (`release-mac.md:21`, and the procedure's `cd` at `:255`). An installed
  Fabric does not keep its stack there:
  - The packaged app's name is `@fabric/desktop` with no `productName`. `apps/desktop/package.json:2`, and the
    installed app's own `app.asar` `package.json` → `{'name': '@fabric/desktop', 'productName': None}`.
  - No `app.setName`/`setPath('userData')` exists in `src/main`. So `userData` is
    `~/Library/Application Support/@fabric/desktop`, and the bundled stack is materialized there
    (`env.ts#bundledStackRoot`: `path.join(app.getPath('userData'), 'stack')`, packaged only).
  - On this Mac, `…/@fabric/desktop/stack` exists and holds the installed 0.3.3's `startup-failure.log`
    (2026-10-10 01:23, the CO-228/CO-241 failure). `…/Fabric/stack` is absent; `…/Fabric/` holds only the
    hand-made `backups/`.

  The candidate's own runbook disagrees with itself. Its new "shorter way" (`release-mac.md:181`) uses
  `…/@fabric/desktop/stack`, and the procedure it sits in uses `…/Fabric/stack` (`:255`).
- **Why it matters.** This is the remedy for a population the release notes speak to directly, and the person is
  told to act on it. As written it fails at the `cd` ("no such file or directory"). The failure is safe, but the
  person cannot act on it. The same wrong folder is in the `database-unreachable` dialog, which its own comment calls
  "the commonest failure there is". This was not introduced by 0.3.4: the folder name dates from the bundled stack
  (2026-09-29). 0.3.4 is the release that sends people down this route.
- **Smallest fix I would accept.** Name the folder an installed Fabric actually uses,
  `~/Library/Application Support/@fabric/desktop/stack`, in `schemaReadiness.ts#stackPath`, `startupFailure.ts`
  (both remedies), `en.ts`/`ru.ts`, `docs/brand/strings.md` and `release-mac.md:21`/`:255`. Add one test that ties
  the string to `apps/desktop/package.json`'s `name`. Do **not** fix it by adding a `productName`: that would move
  `userData` and leave every existing install's settings, logs, active-estate choice and stack copy behind.

### UX-2 — non-blocking — The `identity-refused` dialog is worded for one case but matches every identity failure: for a chosen Estate it promises a reason it does not carry, and a database outage now reads as an access refusal

- **Evidence.** The cause is matched on the prefix alone, `/^identity could not be established\b/`
  (`startupFailure.ts:98`), and it is checked *before* the database cases (`:173`). Bootstrap appends the repair's
  reason only for the default Estate when `before.why === 'not_a_member'` (`index.ts`, region `seed-repair-wiring`).
  Rendered (en; ru is the same in substance):
  - **B: an Estate chosen through `active-estate.json`** (restore). The remedy says "the details below say what it
    found instead". The details are only `identity could not be established: that person is not a member of this
    estate`. The one thing the person could do, remove `active-estate.json` to open the default Estate (the remedy
    the `active-estate-unreadable` cause already gives, `en.ts:904`), is not offered.
  - **C: `resolve_subject` itself failed** (`shared/identity.ts#subjectOf` → `identity could not be resolved: …`).
    For example, with `TypeError: fetch failed` the dialog now says "this database does not name that owner … Fabric
    takes an Estate for itself only when nothing has happened in it yet". Measured: the same message classified
    `database-unreachable` on v0.3.3 and `identity-refused` on the candidate (`c033.mts`). That is a regression in
    the wording for an outage.
  - In every case, "Copy them and report them" names no place to report, and the dialog's own
    `startup.notRetryable` line (`en.ts:897`) says "reopen the app instead". Reopening runs into the same refusal.

  The CHANGELOG line "The startup window names the refusal and what Fabric found" (CHANGELOG.md:24–25) is true only
  for case A (the default Estate, repair refused).
- **Why it matters.** The brief asks whether this sentence is honest and actionable. It is honest for case A, the
  main one. For B it promises a detail that is absent and leaves out the step that works. For C it blames the
  database's membership for a connection failure, which is the misdiagnosis the classifier exists to prevent.
- **Smallest fix I would accept.**
  - Throw a coded error from bootstrap (for example `FABRIC_IDENTITY_REFUSED`, with `why`) only for
    `not_a_member`/`no_such_person`, so that `unavailable` falls through to the database cases.
  - For a recorded (non-default) Estate, append "the Estate recorded in active-estate.json" and say that removing
    it opens the default Estate.
  - Say "copy them and report them at <the repository's issues URL>", or drop "report".
  - Add a `startupFailure.test.ts` case for C.

### UX-3 — non-blocking — The identity refusal still comes after the agent surface is open: while the failure dialog is up, an agent's request can raise a notification that opens a main window with no IPC, and it falsifies "Fabric has changed nothing in the Estate"

- **Evidence.** The repair moved before the hub, but the refusal did not. The repair block and its identity read run
  before the retry point (`index.ts`, region `seed-repair-wiring`). `pastRetryPoint = true` and
  `startHub(…)` (`index.ts:742`) follow, and the throw `identity could not be established` comes last (`index.ts:898`).
  Nothing withdraws the hub on a startup failure: `withdrawHub` runs only in `quit.onQuit`, `index.ts:745–748`.
  While the dialog is shown:
  - A registered agent's `fabric.access.request` is journalled into the Estate (`accessService.ts:202`,
    `access.requested@1` as `system/fabric-hub`; iteration 1 DA-1 and ER-3 measured this happening during failed
    starts on this Mac).
  - With no main window, `ConsentPresenter.present` shows a macOS notification (`consentPresenter.ts:93`).
  - Clicking it calls `bringForward` → `openWindow` (`consentPresenter.ts:104–107`) → `if (mainWindow === null)
    createWindow()` (`index.ts:707`). Unlike `app.on('activate')` (`index.ts:4703`, `if (!windowReady) …`), this has
    no `windowReady` guard. `registerIpc(meta)` (`index.ts:4507`) never ran, so that window's renderer has no IPC
    handlers.
  - An Allow would be decided with `OPERATOR_ACTOR` still unset (`index.ts:346`, assigned only at `:902`).

  The new remedy ends "Fabric has changed nothing in the Estate" (`en.ts:906`, `ru.ts:285`, `startupFailure.ts`),
  and the request write makes that false while the dialog is on screen. SCR-36's startup boundary still says
  "recovery/agent services have not started in this attempt. Retry rechecks the schema" (`screens.md:777`). Its 0.3.4
  amendment does not say that an identity refusal is different: the surface is open and there is no Retry.
  Not observed on screen (NOT_RUN above). This is traced through the code.
- **Why it matters.** A person who has just been told Fabric could not start is then asked by Fabric to allow an
  agent. Answering opens a broken window. It happens exactly on the Macs where agents are registered, which includes
  the operator's own.
- **Smallest fix I would accept.** Refuse at the read that already happens before the retry point: when `before` is
  not ok and the repair did not apply, throw there. The dialog then offers Retry and the hub never opens behind a
  refusal. This also removes the "reopen the app instead" line from UX-2. Failing that, guard `openWindow` with
  `windowReady`, withdraw the hub when startup fails, and amend SCR-36 to match.

### UX-4 — non-blocking — The notes say the old first owner "stays listed beside you" and "is not a person"; no screen lists it, and it is a person record

- **Evidence.** CHANGELOG.md:23: "The old first owner stays listed beside you; it is not a person and acts for no
  one." CO-242 says "no screen shows members today", and the renderer has no members surface (see the paths
  above). The old seed inserted it as a person: `persons (id, display_name, auth_user) values (operator, 'Operator',
  null)` (`git show v0.3.3:supabase/seed.sql`, line 12), and it holds the `owner` membership after the repair
  (`legacy` run).
- **Why it matters.** A reader of the release notes will look for a list that does not exist. "Not a person"
  contradicts the record a future member surface will show, labelled "Operator" (CO-242's own concern).
- **Smallest fix I would accept.** "The old first owner stays in the database as a second owner. No screen shows it
  and nobody signs in as it; what happens to it is decided before any member screen ships."
