## Findings

### PL-1 — **blocking** — The candidate silently reverts `main`'s workspace pin: the gitlink goes back to 0.3.3's snapshot while the receipt names `main`'s

**Evidence.**
- The merge `11a7dc6c`, "Merge origin/main (workspace pin) into the 0.3.4 branch", has parents `f18354be` and
  `6fdf8fcc`, and its base is `9ef939e6`. The base and `f18354be` both pin `a5dd292f`. `6fdf8fcc`, which is
  `origin/main` today, pins `5a0ddc57`. Only one side changed the gitlink, so a plain merge takes `5a0ddc57`. The
  result pins `a5dd292f`: `git diff 6fdf8fcc 11a7dc6c -- workspace` → `-5a0ddc57… +a5dd292f…`, which is a manual
  revert. `git diff --stat origin/main a0ab055c -- workspace` → `1 file changed`.
- The merge kept `main`'s receipt. `docs/workspace-receipt.json` says
  `"workspace_commit": "5a0ddc5781815114717e8a7e67ebceb4ebeea6af"`, but `git ls-files --stage workspace` →
  `a5dd292f…`. That is exactly the condition `workspace-snapshot.mjs#checkReceipt` refuses ("Workspace gitlink and
  receipt disagree").
- The release gate does not catch it. `release-mac.mjs#publicationPinProblem` checks the pin only for changes
  *after* `verifiedCommit`, and here the disagreement is inside the candidate itself, so the release commit and the
  tag would carry it.
- The landing is a fast-forward (Release close item 1). It would move `main`'s pin back over three publications
  (`189bec0`, `971f92b`, `5a0ddc5`) and over fabric-workspace PRs #86, #88, #89, #90 and #91. At `a5dd292f`,
  `knowledge/platforms.md` does not exist (`git show a5dd292f:knowledge/platforms.md` → no output). That page is the
  knowledge base's only record of the operator's 2026-10-10 calls ("universal from 0.3.4 … operator decision
  2026-10-10 | 0.3.5 (CO-238)", `platforms.md:16` at `5a0ddc5`).
- The records say the opposite. Map entry `iteration-2026-10-10-release-034-main-merge` (`map.html:190`) says main
  "with the scheduled workspace publication (`6fdf8fcc`)" was merged in and "the code did not change". `MERGES.md:8`
  says "origin/main merged in (`6fdf8fcc`, …)".

**Why it matters.** The parent repository's pin is a production publication pin. The release would ship a receipt
that does not describe its own gitlink, and, until someone republishes, the knowledge base pinned to `main` would
lose the page that records the 0.3.4/0.3.5 decision. The records claim the opposite, so nothing points a reader at
it.

**Smallest fix.** Set the next candidate's `workspace` gitlink to `5a0ddc57`, or to whatever `main` has published by
then, so that `git ls-files --stage workspace` equals the receipt's `workspace_commit`. Re-run `workspace.mjs
check` after publication. Optionally, make the fast tier fail when the gitlink and the receipt disagree.
