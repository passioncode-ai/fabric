## Findings

### DA-1 — non-blocking — The repair has an undocumented ceiling of 49 unattended hub requests, and a failed 0.3.1–0.3.3 start can pass it in hours

**Evidence.**
- `seedRepair.ts:56` refuses when the read returns more than `EVENT_READ_LIMIT` (50) rows. The read is
  `.limit(EVENT_READ_LIMIT + 1)` (`:97`) and includes the creation event. So the most it accepts is the creation plus
  **49** hub requests.
  - Probe `hub`: 49 accepted, and at 50 → `the estate has more events than the repair reads`.
  - The doc comment at `seedRepair.ts:25` says the opposite ("How many events *after* the creation the repair reads").
- The 0.3.3 failure dialog loops while the hub stays open (`v0.3.3` `index.ts` 4594–4625; `withdrawHub` only on quit). The
  hub caps requests at 3 pending per agent and 20 in all (`accessService.ts:190`, `:194`), and each expires after 10
  minutes (`shared/access.ts:19`). An agent that keeps asking therefore writes up to 18 events an hour. Several agents
  together can write up to 120 an hour.
  - One persistent agent crosses 49 in under 3 hours of an open error dialog.
  - Several agents at the global cap cross it in about 25 minutes.
- The CHANGELOG says such an install "starts" and that untouched means "at most an agent asking for access while the
  start was failing" (`CHANGELOG.md:20-21`). Neither it nor ADR-0131 §2 ("within `EVENT_READ_LIMIT` events in all") says
  that more such requests, which grant nothing, leave the install refused.
- The ledger's *Release close* item 3 reads the operator's dump for "the `org #1` journal's count and types". It does
  not say the count must be ≤ 50 for the repair to apply. That database failed under 0.3.2/0.3.3 since 2026-10-09 00:48
  UTC, on the Mac with the most registered agents.

**Why it matters.** A database the ADR itself calls untouched (only unanswered requests) is refused, depending on how long
an earlier error dialog sat open. The person then gets `identity-refused` and is told to report it. They have no way out.

**Smallest fix I would accept.** Make the decision independent of how many unattended requests there are. For example:
- read the first event (`limit 1`);
- read separately the events that are *not* `access.requested@1` by `system/fabric-hub`, with `limit 1`;
- keep the membership and decision checks.

A `legacy` case would cover it: 60 hub requests → granted, watched failing on the current code. If the cap stays
instead:
- correct the `:25` comment;
- state the bound in the CHANGELOG and ADR §2;
- make *Release close* item 3 compare the dump's count with it explicitly.

### DA-2 — non-blocking — "A read that failed may be retried" is false: a failed repair read ends past the retry point, with advice to report instead of reopen

**Evidence.**
- What the documents promise:
  - ADR-0131 §3 (line 45) says the repair runs "before the retry point … so … a read that failed may be retried".
  - The wiring comment says the same (`index.ts:649`, "before the retry point, so a read that failed may be tried
    again").
- What the code does:
  - `repairSeedOnlyEstate` never throws. A failed journal, members or decisions read returns
    `{ repaired: false, why: "…could not be read…" }` (`seedRepair.ts`), and `bootstrapReady` only stores it in
    `seedRepairWhy` (`index.ts:660`).
  - Startup then sets `pastRetryPoint = true` (`:669`), opens the hub and throws at `:899–901`.
  - The dialog is built with `retryable: !pastRetryPoint` (`index.ts:4620`), so it offers no Retry. It adds
    `startup.notRetryable` ("reopen the app instead").
- The `identity-refused` remedy says something else again: "Fabric takes an Estate for itself only when nothing has
  happened in it yet … Copy them and report them" (`shared/startupFailure.ts:102`). For a transient read failure on a
  repairable database, the right action is to reopen, because the next start repeats the repair.
- The wiring test asserts the order ("the repair runs before the point after which retrying is unsafe"). The order
  holds, but no test checks the retry property the ADR derives from it.

**Why it matters.** It is the one recoverable failure of the repair. The documents say it is retried in place, but in fact
the person gets mixed advice and is pointed at reporting rather than reopening. It is low frequency: the identity read
just succeeded on the same connection.

**Smallest fix I would accept.** Either option is enough:
- When the repair failed on a read or the transport (not on a shape refusal), throw before `pastRetryPoint = true` with a
  retryable cause, so the dialog offers Retry. Add a wiring case for it.
- Or correct ADR §3 and the `index.ts:649` comment to "repeated on the next start", and have the `identity-refused` detail
  say "reopen Fabric" when the reason is a failed read.
