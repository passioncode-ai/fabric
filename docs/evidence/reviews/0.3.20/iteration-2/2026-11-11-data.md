## Findings
| ID | Severity | What | Evidence | Proposed fix |
|---|---|---|---|---|
| DA-10 | blocking | A run on another machine whose request and thread come to more than 4 000 characters can never open its workflow: Fabric puts up to 12 000 characters in the packet's `notes`, and Observatory refuses a `notes` longer than 4 000. The open fails, is retried with the doubling back-off, recomputes the same (or a longer) text, and fails again; the request never starts, neither there nor here (the refusal is not one of the `REMOTE_REFUSALS` that run it here), and reaches «На проверке» only once its deadline has passed. In 0.3.19 the same request opened and started. Board requests with replies pass 4 000 characters easily. The spec's "at most `THREAD_TEXT_MAX` characters" and the CHANGELOG's "A board run on another machine can do its work" are false for them. | `boardDispatchWiring.ts:185` `THREAD_TEXT_MAX = 12_000`; `boardDispatchRun.ts:569` `...(remote?.text ? { notes: remote.text } : {})`; Observatory `store/workflow.py:358` `_string(raw.get("notes"), "body.notes", 4000)`, applied in `checkpoint_write` (`:832` `redactor.scrub(checkpoint_body(body))`). probe2: `remoteLong REFUSED InvalidInput body.notes is 5,216 characters; the limit is 4,000`. `boardDispatchRun.ts` open catch: `board.dispatch.started failed`, `openFailed`, `retryOpen.set`, `continue`. The test `requestThreadText: ... cut to its bound` asserts only `<= THREAD_TEXT_MAX + 10`, never Observatory's bound. | Cut the text to Observatory's limit with a margin (for example `THREAD_TEXT_MAX = 3_900`; JS `length` counts UTF-16 units, which is never less than Python's `len`, so a JS cut at or under 4 000 is safe), keep the request first and say what was cut; add a test that feeds the opening packet's `notes` length to the 4 000 bound; correct spec §3.7. |
| DA-11 | non-blocking | A remote run's retried open no longer sends the packet it first sent: `retryOpen` keeps the dispatch id, end and open time but not the target or the thread text, so a retry reads the thread again (and the target). When a message arrives in the thread in between, or the first read failed and the second works, the body differs under the same idempotency key, Observatory answers `IdempotencyConflict`, and once the end nears a fresh dispatch id opens a second workflow while the first stays open with a lease nobody holds: the ER-9 / ER-16 defect, back for remote runs. Narrow (needs a lost Observatory answer). | `boardDispatchRun.ts:985` `retryOpen.set(req.id, { dispatchId, endsAt, openAt, ...inbox })`; `:965` and `:966` recompute `target` and `remote` every pass; comment at `:984` "the packet first sent under this dispatch id is kept through every retry". | DA-12 | non-blocking | The thread text puts project ids and the request id as bare UUIDs, which Observatory's redaction replaces: every message reads `from project [redacted]`, so the remote run cannot tell who said what, and the fallback line `(the request <uuid> was not on the thread's first page)` loses its id. | `boardDispatchWiring.ts#requestThreadText` `from project ${m.sender.project}` and `(the request ${req.id} ...)`; `memory_redact.py` `KEEP` keeps only `fabric-project:`, `board-request:` (and others) prefixed UUIDs; probe2 notes: `request (the request) from project [redacted]:`. The run's own goal already uses the `board-request:` form for this reason (`boardDispatchRun.ts` comment "Observatory redacts a bare UUID in text"). | Write `fabric-project:<uuid>` (kept by `KEEP`) or the project's display name, and `board-request:<uuid>` in the fallback line; add the redactor's effect to the test (or assert the reference forms). |
| DA-13 | non-blocking | "The newest messages" are the newest of the thread's oldest 100: `requestThreadText` reads one page after seq 0, which the board answers oldest first. In a thread longer than 100 messages the remote run gets old context, misses the latest replies, and may be told the request is not on the page although it exists further on. | `boardDispatchWiring.ts:193` `comms.list(estateId, req.thread, 0, 100)`; `commsOperatorRead.ts#list` "One page of a thread ... after `afterSeq`, oldest first", limit capped at 100; JSDoc says "one page of the thread" while spec §3.7 says "the request first, then the newest messages". | Page to the end (the reply carries `lastSeq` and `more`) or read the request with its own read and the last page of the thread; or state "the first 100 messages" in §3.7. |
