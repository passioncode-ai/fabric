## Judged on the brief's questions

- **`fabric.project.resolve` answers only with a live `project.resolve` or `session.enroll` grant:** holds. The handler reads `liveGrantsOf(binding)` (not revoked, not expired, from the store) on every call and refuses `access-required` with the ask it needs; a store failure goes through `guard` to `hub-unavailable` with `ops.failed`, never to an answer (`hubTools.ts:109-118,230-240`; `board-surface.test.mjs` shows nothing is resolved without the grant). «Отключить» revokes every live binding of the agent, the `project.resolve` one included (`keptOut.ts:76-88`, `index.ts:3833-3838`). No consumer of 0.3.7 is cut off: Observatory had no binding (ledger, thread `617c8cbe`) and Switchboard has no registry entry (CO-360); an enrolled coding agent still resolves.
- **The access lane refuses a disconnected agent:** holds, before any write (`accessService.ts:266-271`); a binding may ask only for its own agent (`:380-381`); `folder` is refused; the resource is exactly `projects` and `askLines` cannot be reached with it from a product callee, whose resources must be mailboxes (`access.ts:256-260`). ER-4 and ER-5 for what remains; the per-ask binding is CO-363.
- **Backoff and cooldown:** `failed` grows from 3 s to a minute and a whoami resets the count (`fabricMcp.ts:236-243,620-633`); a 503 is a cooldown only with Retry-After, bounded to 5 minutes with jitter, and only for the hub that answered it (`fabricMcp.ts:181-183,269-289`; `fabric-mcp.test.mjs:811-829`). ER-1, ER-2 and ER-3 for the edges.
- **Refusal levels by code (CO-335):** consistent across every tool that can answer a typed refusal: the hub's and the forwarder's failure codes stay `failed` at error, `outcome-unknown` and the board's `not_available` are `unknown` at warn, the rest `ok` at warn with `error_code`; the board and the guard log their own `ops.failed` beside the trace line, so a real failure is never only a warn (`toolOutcome.ts:175-185`, `boardService.ts:266-278`, `hubTools.ts:116`). The code is read only from a strict pattern; nothing a product wrote reaches the log through it. The hub answers JSON (`enableJsonResponse: true`), so `bodyFromEnds` sees it.
- **The decimal 3 GB line and its one number:** holds. `LOW_DISK_BYTES` is `3e9`; `freeDiskGb` is the one formatter for the dialog, the copied details and the log; `statfsSync` runs once per failure before the dialog loop and a failure leaves no line; the five causes match SCN-161 (`startupFailure.ts:251-270`, `index.ts:5194-5203,5253`).
- **The session cap stays 8:** `sessionEnroll.ts:69`, the file unchanged against `v0.3.7`.
- **Wave 4 renumbered to 0.3.9:** outside this level; the living registers I read say 0.3.9 (`docs/evidence/backlog.md:129`), and `check-plan-ids.mjs` and `check-docs.sh` exit 0.
