### DO-1

added since v0.3.15 prints 0»; V1-33 (DO-13) «fixed: as DA-1»; the map entry `iteration-2026-11-05-release-0316-i1`
says the operator's quotes were retold. ADR-0096 §5: «From here on, operator statements are recorded as paraphrases.»

  quotes a whole passage) and `docs/adr/README.md:147`, `:148`;
- `docs/evidence/specs/2026-11-04-on-demand-sessions.md:60`;
- `docs/evidence/specs/2026-08-16-software-fabric-carryover.md:500`, `:502`, `:504`, `:509`, `:510`, `:511`, `:520`;

### DO-2

**Claim.** CHANGELOG `## Unreleased`, CO-294 (lines 85 and 86): «It never changes the docker context itself»; AGENTS.md
Lifecycle, «Local Supabase stack» row: «it never changes the docker context (`src/main/dockerLaunch.ts`, CO-294 …)»;
`docs/ux/scenarios.md:4022` (CO-294 amendment): «Fabric never changes the machine's docker context»; the region header of
`apps/desktop/src/main/dockerLaunch.ts` says the same.

**Evidence.** `apps/desktop/src/main/dockerLaunch.ts#dockerAppFor`: with Colima installed it returns
`{ name: 'Colima', command: colima.bin, args: ['start'] }` (or `['start', '--profile', p]`), the profile taken from the
socket the CLI uses or, failing that, from the first docker context whose engine is Colima's (`findColima`). So a Mac
whose current context is OrbStack's or Docker Desktop's, with Colima installed and a Colima context present, gets
`colima start`, which activates Colima's context by default. CO-508 (carry-over register, open, decide by 2026-11-21)
records exactly this: «`colima start` makes its own docker context active by default (`--activate`), so «it never
changes the docker context» (CO-294) is not true on a Mac that uses another context». Iteration 1 ruled ER-8 to CO-508
(V1-17), but the shipped sentences were left as they were.

**Fix.** Pass `--activate=false` to `colima start` (with a test on `dockerAppFor`'s args), or rewrite the three
sentences to say that starting Colima makes Colima's context the active one. Either closes CO-508's first half.

### DO-5

The 0.3.16 wave row of `docs/evidence/specs/2026-11-04-on-demand-sessions.md` §9 (V1-31's fix) lists what is not built,
but these statements of the spec are still worded as current and are not in that list:

- §3.1: «The hub's dispatcher runs on every `comms` journal event of kind `request` and on the cycle». It runs on the
  cycle only (`main/index.ts`, `void dispatcher.onPass()` in `runCycle`).
- §3.4: the take-back hand-over's reason is `crash` «when Switchboard reports the run failed»; the code always sends
  `restart` (`main/boardDispatchRun.ts`, `open` and `closeWorkflow`). The constraints carry «the operator's mandate as
  the request carries it (DEC-0125)»; the packet's four constraints carry no mandate.
- §3.6: «The dispatcher follows the request (`com.get`)»; it reads states from its one board read per pass
  (`boardDispatchWiring.ts#readOpenRequests`, `requestState`). A run past its limit «ends `timed-out`»: the record has
  no such outcome (`DispatchRecord.outcome`); a stopped run is `finished` or `exited-without-answer`.
- §3.3: the switch is named «Запускать агентов по запросам доски»; the product's label is «Запускать агента на запрос
  доски, который некому взять» (`i18n/ru.ts`, `settings.dispatch`). «per project per day» is a rolling 24 hours in the
  code (`DAY_MS`), while `shared/boardDispatch.ts:26` says «per UTC day».
- §2: the CO-494 grant is «recorded as the operator's act with his words as the reason» and given «on its declared
  capabilities»; ADR-0186 decision 1 and `accessService.ts` record it as the asking agent's act, for any project and up
  to eight capabilities (the narrowing is CO-506).
- §6: «The run has the machine's default permissions»; see DO-6.

**Fix.** Add these to the wave row's «Not in 0.3.16», or correct the sentences (the label, the rolling day, the actor).

### DO-6

**Evidence.** `boardDispatchWiring.ts#wireBoardDispatch`, `launch`: every dispatch passes `--permissions all`, which the
spec §3.5 says runs Claude Code with `--dangerously-skip-permissions` and Codex with
`--dangerously-bypass-approvals-and-sandbox`. Settings' permission choice (`agentPermissions`, `'fewer-prompts' |
'manual'`) is not read. The spec is split: §2 says «in this version a started session runs with «all on»», §6 says «the
machine's default permissions». The CHANGELOG bullet and the switch's help text (`settings.dispatchHelp`, ru and en) say
the run «stops before any step that touches production» (an instruction in the packet) but not that it runs with every
permission on, and the switch is on by default.

**Fix.** Say it where the person decides: one clause in the CHANGELOG bullet and in `settings.dispatchHelp` (through
the text checker), and make §6 agree with §2.

### DO-7

**Claim.** CHANGELOG `## Unreleased`, CO-458 (`:41`): «the request is answered when that task is done».

**Evidence.** `main/crossProjectAssign.ts#answerAssigned` is called only from `onDoneInReview`, which
`main/workTools.ts` fires when an agent's `fabric_work_release` with `done` moves B's task to review (`main/index.ts:1127`).

an agent releases B's task done … задача на проверке».

**Fix.** «the request is answered when B's agent hands the task in (it reaches review)».
