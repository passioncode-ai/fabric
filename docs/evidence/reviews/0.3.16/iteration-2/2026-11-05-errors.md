### ER-1

A run that ended while its request is not in this pass's read is never judged.

Evidence. `boardDispatchRun.ts#createBoardDispatch` (`watch`): after Switchboard says `ended`, `const state = await
deps.requestState(r.requestId); if (state === null) continue` leaves the record `running` with no bound (the iteration-1
ER-6 fix). `boardDispatchWiring.ts#wireBoardDispatch` answers `requestState` from `lastStates`, which holds only the
requests of `readOpenRequests`: threads active in the last 7 days, at most 3 pages of 100 threads, 5 pages of messages
each. The ER-3 escape (`UNKNOWN_AFTER_END_MS`) applies only when Switchboard says `unknown`, not when the request cannot
be read. A request dispatched near the end of its default 7-day life (for example after a live session held the project
for days, which ER-5 of iteration 1 now makes the norm) whose run wrote nothing in the thread falls out of the window as
the run ends; so does one beyond the 300-thread cut. The record is persisted, so a restart keeps it.

Probe P3b (two such runs, then another project's request, 7 simulated days):
`P3b after 7 days: launches 2 states p-a:running,p-b:running last decision for c deferred-cap`.
With the default `maxOnMachine: 2` nothing is dispatched again on this machine, and nothing tells the operator.

Proposed fix. In `watch`, when Switchboard says `ended` and the state stays unread past `endsAt + UNKNOWN_AFTER_END_MS`,
end the record with outcome `unknown` (not an empty run), as ER-3 does; or read the request's state by id
(`comms.facts`) instead of from the windowed read. Test: the P3b scenario frees both places.

### ER-2

Two empty runs reach «На проверке» only in some states.

Evidence. `shared/boardDispatch.ts#decideDispatch` checks `emptyRuns >= EMPTY_RUNS_TO_OPERATOR` only after
`candidate()` (which is false for `outcome_unknown`, for `claimed` with a live attempt, and within 5 minutes of the
deadline), after `liveResponder` and after `liveSession`. The sweep shows a request only when it is `queued` and still,
or marked `toOperator` (`shared/abandonedSweep.ts#findAbandoned`). A dispatched second run that takes over a dead
`in_progress` holder with `com.responder_replace` turns the request `outcome_unknown` (board semantics:
"in_progress ones become outcome_unknown"), and `board_tick` never expires it (it expires `queued` and `claimed` only,
`20261021000120_board_core_holds.sql#board_tick`). The release notes say: "after two runs that left the request
unsettled it starts no more, closes the request's workflow and shows the request in «На проверке»". The decision's own
comment says a request in a project with a live session is, unanswered, "the operator's in «На проверке»", which is
false for an `accepted` request left by an empty run (only `queued` is shown).

Probe P7 (in_progress, run 1 empty, run 2 leaves `outcome_unknown`, 60 more passes):
`P7 launches 2 emptyRuns 2 toOperator 0 closed false`.

Proposed fix. In `decideDispatch`, right after `inFlight`, return `to-operator` when `emptyRuns >=
EMPTY_RUNS_TO_OPERATOR` and the state is not settled, whatever the candidate, responder or session; and let the sweep
show an `accepted` request whose holder lapsed after a dispatched run. Test: P7 ends with `toOperator` holding the
request and the workflow closed.

### ER-3

A failed close leaves the request unmarked.

Evidence. `boardDispatchRun.ts` pass, `to-operator` branch: on a `closeWorkflow` failure the code logs
`board.dispatch.closed failed` and `continue`s before `last.outcome = 'to-operator'`, so `toOperator()` does not hold the
request and the sweep does not show it. The comment there says "the request still goes to the operator, closing is
tried again", which the code does not do. Each pass (every minute) tries the close again and writes one warn line.

Probe P4 (the close write refused): `P4 launches 2 toOperator 0 closed failures in 10 passes 10`.

Proposed fix. Mark and save `outcome: 'to-operator'` first, keep a separate `closed: boolean`, and retry the close with a
back-off. Test: a refused close still puts the request in `toOperator()`.

### ER-4

A start that timed out but ran leaves a superseded lease in memory.

Evidence. `boardDispatchRun.ts#createBoardDispatch` keeps Fabric's lease in `leases` until a start answers a launch id
or the workflow is closed. A start whose CLI call timed out (60 s, `boardDispatchWiring.ts`, `CLI_DEADLINE_MS`) may still have
started the run (nothing in Fabric rules out that Switchboard's `dispatch_start` completes after the CLI's deadline), and
a run that accepted the hand-over supersedes Fabric's lease. If that run ends before the retry, Switchboard answers `handoff_refused` (the
hand-over is no longer waiting); after three timeouts the record is `failed-to-start`. Either way the next dispatch
takes `open()`'s `leases.has(prior.workflowId)` branch and writes `run-ends-at` with the stale lease, which Observatory
refuses ("the previous executor's writes are refused"); `open` throws, nothing is kept, and the next pass does the same,
until the app restarts and `leases` is empty. The run that did start has no launch id, so it is not counted in
`runningOnMachine`: the machine cap can be exceeded by one per such record. This machine's own gate notes record load
averages of 40 to 106, the condition under which three consecutive 60 s timeouts happen.

Probe P1 (attempt 1 times out, the retry is `handoff_refused`, the request then `accepted` with nobody on it, 30 passes):
`P1 failed starts over 30 passes: 30 notes: [ 'run-ends-at was not written: stale-lease' ]` and
`P1 launches after the refusal: 0 records: 1 toOperator: 0`.

Proposed fix. Drop the kept lease when a start ends `handoff_refused` or after any attempt that did not answer (the run
may hold the workflow), so the next run takes it back (§3.4); and when a write under the kept lease is refused, fall
back to the take-back instead of throwing. Ask Switchboard for the launch by dispatch id before recording
`failed-to-start`. Test: P1 starts a second run through the take-back.

### ER-5

The workflow is opened before its record.

Evidence. `boardDispatchRun.ts` pass: `open()` writes the workflow (`observatory_checkpoint_write` with
`idempotencyKey: dispatch-${dispatchId}-open`, a fresh `randomUUID()` each pass) and offers it; the record is pushed only
after `open()` returns and `firstLine` passes, and `if (deps.quitting?.()) return` sits between them. A failing offer, a
`firstLine` throw or a quit at that point leaves an open workflow with no record, so the next pass (no `prior`) opens
another.

Probe P8 (the offer refused, 60 passes): `P8 workflows opened in 60 passes: 60 records 0 launches 0`.

Proposed fix. Derive the open key from the request (`dispatch-${req.id}-open-${n}`, `n` the number of records for it) so
a retry gets the same workflow back, or save a record `opening` with the workflow id right after the first write. Test:
P8 opens one workflow.

### ER-6

The switch does not stop a recorded start.

Evidence. `boardDispatchRun.ts` pass: `if (!on && !live) return`; with a `starting` record `live` is true, and the
`starting` loop runs before `if (!on) return`, so `start()` asks Switchboard again with the switch off. If the first ask
did not start anything, this starts a run after the person turned the switch off. The release notes say "With the
switch off the board is not read"; the lifecycle row names the switch as what stops it; the release's own owed check
says "with the switch off nothing starts".

Probe P2 (first ask unanswered, switch turned off, next pass): `P2 launches with the switch off: 1 state: running`.

Proposed fix. With the switch off, do not call `dispatch` for a `starting` record: end it `failed-to-start` (or ask
Switchboard read-only whether the dispatch id started), and correct the notes to "with the switch off and nothing in
flight". Test: P2 makes no second launch.

### ER-7

The back-off and the daily cap count the wrong things.

Evidence. `boardDispatchRun.ts` pass: `now - last.startedAt < REFUSAL_BACKOFF_MS`, where `startedAt` is when the record
was created, not when Switchboard refused or the third attempt failed. `dispatchesToday` counts every record of the
project in a rolling 24 h (the comment in `shared/boardDispatch.ts#DispatchLimits` says "per UTC day"), refused and
failed-to-start included, though nothing ran.

Probe P5: a refusal on the second attempt, 5 minutes after the record: `P5 minutes from the refusal to the next ask: 5`;
a steady `ceiling_reached`: `P5 asks in 24 h of a ceiling refusal: 20` with the last decision `skipped-daily-cap`.
The notes promise "a refusal waits 10 minutes".

Proposed fix. Keep `endedAt` on the record and measure the back-off from it; count only records that got a launch id
toward the daily cap, and name the window as rolling. Test: P5 waits 10 minutes and keeps dispatching after a
day of refusals.

### ER-8

The 500-record trim can forget the operator's request.

Evidence. `boardDispatchRun.ts` pass end: `if (records.length > 500) records = records.slice(-500)`. Records of every
refusal and failed start are kept (up to 20 per project per day, ER-7), so on a busy estate a week holds more than 500;
the trim then drops the oldest, including a `to-operator` record (or the last record carrying `emptyRuns`) of a request
that is still open for its seven days. `toOperator()` loses it and `decideDispatch` sees `emptyRuns: 0`.

Probe P6 (two empty runs, to-operator, then 500 newer records): `P6 toOperator after trim: false new launches: 1`.

Proposed fix. Never trim records of a request that is unsettled and `to-operator`, `starting` or `running`; trim
settled requests by age. Test: P6 keeps the request with the operator.
