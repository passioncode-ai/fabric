### ER-1

**What.** `boardDispatchRun.ts#createBoardDispatch` (`pass`, lines 192-207) opens the workflow, writes `run-ends-at`,
offers the hand-over, then calls `deps.launch`. On `{ refused }` it says the check and `continue`s (line 196-199); on a
throw it logs `board.dispatch.started failed` (line 204-207). Neither path writes a record, so the next pass finds no
`last`, `inFlight` false, `runningOnMachine`/`runningInProject`/`dispatchesToday` not counting it, and goes through
`open()` again with a fresh `randomUUID()` dispatch id, so every Observatory idempotency key
(`dispatch-${dispatchId}-open|offer`) is new.

`boardDispatchWiring.ts#wireBoardDispatch` `launch` (lines 115-130) maps EVERY failure of the CLI, including its 60 s
`execFile` timeout (`CLI_DEADLINE_MS`, line 18) and a `JSON.parse` failure of a successful answer, to
`{ refused: 'failed' }` (`refusalCheck` gives `failed-to-start`). Switchboard's contract (`fabric-switchboard`
`docs/CLI.md` line 117): the owner starts and reaps the run ("the owner is its parent", `dispatch.rs#watch`), and "a
second `dispatch` for the same workflow while one runs answers the same `launch_id`". Fabric's retry uses a new workflow,
so that guard never applies. Spec §3.5 also says a `failed-to-start` outcome is recorded and "the dispatcher ... does
not retry it unchanged"; it is retried unchanged every pass.

**Probe** (`dispatch-probe.mjs`, `dispatch-probe.out`):

```
P1 (launch answers refused 'failed' after the owner started the agent), 10 passes:
  "agentsActuallyStarted": 10, "recordsKept": 0, "workflowsOpened": 10
P2 (standing refusal ceiling_reached), 60 passes:
  "workflowsOpened": 60, "handoffsOffered": 60
```

In the real flow the duplicates last until the first agent claims the request (a `claude -p` that boots, enrolls,
accepts the hand-over and claims: minutes); a live session does not stop them after the grace (ER-5), and the
per-project cap does not, because nothing was recorded. In the same pass a second request for the same project also
launches. A standing refusal (`ceiling_reached`, `spend_unknown`, `permission_mode`, `agent_not_installed`, and on
Windows `handoff_refused` always, `docs/CLI.md` line 117) creates 1 440 open workflows and offered hand-overs a day per
waiting request in Observatory, none ever closed.

**Fix.** Before `open()`, write a `starting` record for the request (dispatch id, workflow id once known) and save it;
reuse that workflow and dispatch id on later passes so Observatory's and Switchboard's idempotency hold. Treat a CLI
timeout or unparseable answer as `unknown` (ask `sessions --history` filtered by `launched_by.dispatch.id`, or keep the
record `starting` until its `endsAt`), never as "nothing started". Count refusals and failures toward
`dispatchesToday` and back off a standing refusal (the spec's "not retried unchanged").

### ER-2

**What.** The record is pushed and saved only after `deps.launch` resolves (`boardDispatchRun.ts` lines 200-202). The
cycle gates only the start of a pass (`index.ts:2909`, `if (!quit.quitting) void dispatcher.onPass()`); a pass already
running never checks `quit.quitting` and keeps calling Switchboard while Fabric quits. The quit deadline is 10 s
(`AGENTS.md` lifecycle table, `src/main/quit.ts`), the CLI's 60 s. A quit, crash or forced kill between the owner
starting the run and the save leaves `board-dispatches.json` without it, and the restart's `load()` sees nothing.

**Probe** (`dispatch-probe.mjs` P4): launch in flight, "restart" (a new `createBoardDispatch` over the same file):
`"recordsOnDiskAtQuit": 0, "agentsStartedForOneRequest": 2`. The CHANGELOG (`## Unreleased`, CO-409 bullet): "What was
started is kept in `board-dispatches.json` ... so a restart never starts a second run." False for this window. A
`save()` that throws after a launch (disk full) is also logged `board.dispatch.started failed` although the run started.

**Fix.** The same `starting` record as ER-1, saved before the launch; stop a pass at `quit.quitting` before `open()` and
before `launch`.

### ER-3

**What.** `watch()` (`boardDispatchRun.ts` lines 78-92) ends a record only on `runState === 'ended'`. `runState`
(`boardDispatchWiring.ts` lines 131-142) answers `unknown` when `switchboard` is not found, when the CLI fails, and when
Switchboard's own state is `unknown` (`launch.rs#home_state`: `session_running` returned an error). Nothing ages a
record out by its `endsAt`. A record stuck `running` counts toward `runningOnMachine` and `inFlight` forever and is
persisted, so it survives restarts.

**Probe** (`dispatch-probe.mjs` P3), three requests in three projects, `runState` always `unknown`, three days of hourly
passes: `"launched": 2, "stillRunning": 2, "oldestEndsAt": "2026-11-05T11:00:00.000Z", "nowAt": "2026-11-08T10:00:00.000Z",
"thirdRequestEverStarted": false, "lastDecisionForThird": "deferred-cap"`. `said()` logs `deferred-cap` once, so the
operator sees one line and then silence.

**Fix.** End a record as `unknown` (and stop it with `switchboard dispatch stop --launch-id`) once `now` is past its
`endsAt` plus the 120 s silence and a cycle; count such ends as empty runs; say a run Switchboard cannot report in
«На проверке» rather than only in the log.

### ER-4

**What.** CHANGELOG (`## Unreleased`, CO-409): "two runs that left the request unsettled go to the operator in «На
проверке»". `decideDispatch` returns `{ path: 'to-operator' }` (`shared/boardDispatch.ts` lines 106-107, 113), and the
dispatcher only logs it (`boardDispatchRun.ts` `said`, then `continue` at line 184). The comment at
`boardDispatchRun.ts` lines 5-7 relies on the sweep, but `findAbandoned` shows a board request only when it is `queued`
(`shared/abandonedSweep.ts` lines 203-207: "a claimed or accepted one is being worked"). A run that took the request
and died leaves it `accepted` or `in_progress` (spec §3.6), exactly the case the rule is for. Nothing in the renderer or
attention reads `board.dispatch.*` or the records (`grep -rn "board\.dispatch\|board-dispatches\|to-operator"
apps/desktop/src` outside the three dispatcher files: only the wiring import and the file path in `index.ts`). Spec §3.6
also says Fabric takes the workflow back and closes it (`close: true`, `status: blocked`); no code does.

**Probe** (`to-operator-probe.mjs`): with two empty runs, the decision is `to-operator` in every state; the sweep's
findings are `["request-unmoved"]` for `queued` and `[]` for `claimed`, `accepted` and `in_progress`.

**Fix.** Put a `to-operator` decision in the operator's queue itself (an attention row keyed by the request, like
`risenRows`), and close the workflow as the spec says; or narrow the CHANGELOG to queued requests.

### ER-5

**What.** CHANGELOG (`## Unreleased`, CO-409): "A request nobody takes for two minutes, in a project with no live
session, gets a workflow ...". `decideDispatch` (`shared/boardDispatch.ts` lines 110-112) treats a live session only
inside the grace: `if (input.liveSession && waited < GRACE_MS) return { path: 'live-session' }`; past it the request is
launched. The spec says this on purpose (§3.2: "A live session that does not take the slot within G is treated as
absent and the request is dispatched"), so the shipped note contradicts the code. The consequence is not cosmetic: the
started run works in the project's folder (`folderOf`, the primary repository path, `boardDispatchWiring.ts` lines
102-106) with `--permissions all` (`--dangerously-skip-permissions`, line 120), beside the person's live session in the
same working tree.

**Probe** (`to-operator-probe.mjs`): `liveSessionPastGrace: "launch"`.

**Fix.** Decide which is true. Either keep the code and correct the note (and say that the run shares the folder), or
make `liveSession` stop the dispatch (or hand it to that session, §3.2's nudge) as the note promises. Given two agents
in one working tree, the operator should choose.

### ER-6

**What.** In `pass()` `watch()` runs before `readRequests()` (`boardDispatchRun.ts` lines 158-161), and
`requestState` is `lastStates.get(requestId) ?? null` (`boardDispatchWiring.ts` line 143), the map the previous pass
read. A run that completes the request and exits between two passes is judged against the earlier `accepted` /
`in_progress` state and ends `exited-without-answer`, `emptyRuns + 1` (`boardDispatchRun.ts` lines 84-87). After a
restart `lastStates` is empty, so every run that ended is judged `exited-without-answer`. A finished run is the common
case (an agent exits seconds after `com.complete`), so the `finished` outcome and the empty-run count are unreliable;
no relaunch follows only because the next read sees the request settled.

**Fix.** In `watch()`, read the ended run's request now (`comms.facts` or `com.get` for that id), or run `watch()`
after `readRequests()`; with no state read, record `unknown`, never "without answer".

### ER-7

**What.** `pass()` calls `readRequests()` unconditionally (`boardDispatchRun.ts` line 161); the switch is consulted only
inside `decideDispatch`. `readOpenRequests` (`boardDispatchWiring.ts` lines 22-57) reads up to 3 thread pages, up to 5
message pages for every request thread active in the last week, and the facts per 100 requests, every 60 s, with the
switch off and even when no project has a folder. The sweep reads the same board every third pass
(`shared/abandonedSweep.ts#SWEEP_EVERY_TICKS` = 3, `abandonedSweepRun.ts#readBoardRequests`), so the dispatcher triples
the board load. With the board door down, each pass throws and logs `board.dispatch.pass failed` (warn) every minute.
`decided` (`boardDispatchRun.ts` line 70) also keeps one entry per request id seen for the life of the process.

**Fix.** Return before any read when the switch is off (still `watch()` running records); share the sweep's board read
or read only `queued`/`claimed`/`accepted`/`in_progress` requests; drop `decided` entries for requests no longer read.

### ER-8

**What.** `dockerLaunch.ts#dockerAppFor` (lines 67-71): with `colima` on PATH or in Homebrew, the profile is taken from
the socket, else from the first Colima docker context, and `colima start` is returned whatever socket Fabric waits for.
`colima start` activates its context by default (`colima start --help`: `--activate ... (default true)`, colima 0.10.3
on this Mac). CHANGELOG (CO-294): "It never changes the docker context itself"; the module's own reason (lines 3-5) is
that "OrbStack started again switched the whole machine's context to itself and sent other projects' scripts to an empty
engine". When the active context is Docker Desktop or `default` (`/var/run/docker.sock`), Fabric starts Colima, which
switches the machine's context to `colima` and still does not bring up the engine Fabric was waiting for.

**Probe** (`docker-probe.mjs`): Colima installed with a `default` context, sockets
`~/.docker/run/docker.sock`, `/var/run/docker.sock`, `~/.orbstack/run/docker.sock`: each returns
`{ "name": "Colima", "command": "/opt/homebrew/bin/colima", "args": ["start"] }`. The test
`docker-launch.test.mjs` "with Colima installed and its context known, Colima is started ... whatever socket was named"
pins this. On the operator's Mac the active context is `colima` (`docker context ls`), so it is harmless there.

**Fix.** Pass `--activate=false`; start Colima only when the socket Fabric waits for is Colima's (or the active context
is Colima's), and start nothing otherwise.

### ER-9

**What.** `opsDigestRun.ts#createOpsDigestRun` `closeHours` (lines 86-104): after the first closed hour of a gap longer
than 24 h it jumps `bucket` to the current hour (line 103) and the loop ends without folding the day it left, so that
day's `daily-YYYY-MM.jsonl` line is never written and its hours stay in `today` in memory. `observe` drops every record
with `at < bucket` (line 113), so a clock set back (a wrong clock corrected) drops all counts until it catches up.
Nothing prunes `userData/digests`; `AGENTS.md` says "Nothing is pruned yet: a month's files are a few hundred
kilobytes", but an hourly line carries every op seen in the hour (the live log shows up to 70 distinct ops an hour,
median 28, about 65 bytes each), about 1 to 3 MB a month, and the sink counts sampled successes that the log does not
write, so the digest can hold more ops than the log shows.

**Probe** (`digest-probe.mjs`): hours of 5 Nov closed, then a tick on 8 Nov: `"hourlyFrom"` ends at
`2026-11-05T13:00:00.000Z`, `"dailyDays": []`. After a clock set back three hours, 20 failures recorded: the latest
digest's `"ops": []`.

**Fix.** Before jumping, fold and write the daily digest of each day the gap leaves; treat a record before `bucket` as
belonging to the open hour (or reset `bucket` when the clock goes back by more than an hour); keep the digests within a
budget or a number of months, and correct the size in `AGENTS.md`.

### ER-10

**What.** `index.ts#applyLoginItem` (lines 652-657) records `app.started` (CO-365, commit `4faa9a76`: "every start
records how it began, so a reboot is checked in the log"). It is called at `whenReady` (`index.ts:5517`) before
`startOrExplain()` (`index.ts:5535`) runs `bootstrap()`, whose `useOps(createOps(...))` (`index.ts:828`) installs the
only sink. Before that, `ops.record` is `sink?.record(input)` with `sink === null` (`opsSink.ts` lines 10-12, 17, 26-35),
a no-op. The commit's test (`test/background-launch.test.mjs`) matches the source text with a regex, so it cannot see
the order. The same applies to `applyLoginItem`'s own `app.login-item` warning at start. `git tag --contains 4faa9a76`
prints nothing, so this is new in 0.3.16.

**Fix.** Keep the start record's values in a variable and write `app.started` right after `useOps` in `bootstrap`, or
have `opsSink` buffer records made before bootstrap; test it by reading the log after a start, not the source.

### ER-11

**What.** `shared/abandonedSweep.ts#CLOSED_TASK_STATES` (line 56) includes `review` and `backlog`, and `findAbandoned`
lets go of any claim whose task is in one of them, before any other judgement (lines 176-181); `abandonedSweepRun.ts`
releases it the same sweep. The claim tool's description (`main/workTools.ts:370`) says "A claim moves its task from
backlog to running ...; a task in another column stays where it is", so a claim on a task in review is a supported act
(a session fixing review findings, a verifier), and it is now released within 3 minutes, every time it is made again.
The claim is inserted before its task is moved (`workTools.ts#moveClaimedTaskToRunning`, called after the claim), so a
sweep between the two, or a move that failed, also lets go of a claim on a `backlog` task.

**Probe** (`claim-closed-probe.mjs`): a claim made 60 s ago, renewed 10 s ago, its session signed 10 s ago:
`{"review":["claim-closed"],"backlog":["claim-closed"],"running":[]}`.

**Fix.** Release only for `done` and `cancelled`, and for `review`/`backlog` only when the task moved there after the
claim was made (compare `moved_at` with `claimed_at`).
