### DA-2

Evidence. `main/boardDispatchRun.ts:189` takes a fresh `randomUUID()` dispatch id each pass; with no record for the request, `open()` takes the `!prior` branch (`:116-123`) and writes `observatory_checkpoint_write` with `idempotencyKey: dispatch-${dispatchId}-open`, then `observatory_handoff_create` with `offerTtlSeconds: 3600` (`:139-142`). A refusal (`:196-199`) or a throw after the workflow opened (`:204-207`) pushes no record and saves nothing, so the next pass repeats it. Probe `dispatch-refused.mts`: `5 workflows opened over 5 passes; records saved: 0`. The `said()` dedupe (`:71-76`) keys on the decision, which flips between `launch` and `wait:deferred-cap` each pass, so the operations log gets two lines a minute for the request. `refusalCheck` maps `ceiling_reached`, `spend_unknown` (a spending ceiling reached) and `no_agent` to waits that recur for hours. The existing test (`test/board-dispatch-run.test.mjs:113`) runs one pass only.

Proposed fix: record a refused or failed start (state `refused`, the workflow id and the check) and reuse its workflow through the `prior` path on the next try, or open the workflow only after Switchboard accepts; back off a refused request (for example until the cap's next change or the next hour); dedupe the log line by request and check; add a multi-pass test.

### DA-3

Evidence. Spec §7 (`docs/evidence/specs/2026-11-04-on-demand-sessions.md:282`): "Fabric journal events (each with `event_types` rows and a feed sentence `event.<type>` in `i18n/en.ts`)", and §3.6 (`:215`): "The dispatch's outcome is the hub's journal entry". `grep -rn 'board.dispatch' supabase apps/desktop/src/renderer/src/i18n/en.ts` prints nothing; the dispatcher only calls `deps.log` (the operations log, `main/index.ts:2865`), which keeps 7 days (`AGENTS.md` ops-log paragraph). For the two-empty-runs and past-deadline cases `decideDispatch` answers `to-operator` (`shared/boardDispatch.ts:106-113`) and `boardDispatchRun.ts:184` only logs it; §3.6 says Fabric "takes the workflow back the same way to close it (`close: true`, `status: blocked`)", which no code does, so those workflows stay open in Observatory. No new journal type was added in this range, so no `event_types` row is missing today.

Proposed fix: add the three `board.dispatch.*@1` types in a migration with their `event_types` rows and `event.<type>` sentences, append them beside the ops records (no request text, as §7 lists), and close the workflow on `to-operator`; or amend the spec to say the journal events and the close are a later wave.

### DA-4

Evidence. `main/crossProjectAssign.ts:48-62`: the board submit carries `idempotency.key: assign:${key}`, but `fileTask` (`main/index.ts#assignDeps`, `id = randomUUID()`) and both `note` calls are not keyed. `renderer/src/launch/CrossProjectConsole.tsx:106-110` deliberately retries with the same key ("a retry after a lost answer is the same request"). Probe `assign-retry.mts`: one note write failing once, then the retry: `tasks filed in B for one request: 2`; the first task has no "Board request:" mark, so `answerAssigned` (`:66-68`) never answers the request for it. The module header (`:8-9`) says "nothing half-done is left".

Proposed fix: derive the task id and note ids from the key (UUID v5 of `assign:${key}`, or look up a task already carrying the mark for that request id before filing), and write the mark in the same event as the task (`task.created@1` payload) so a task never exists without it.

### DA-5

### DA-6

Evidence. `AGENTS.md:147`: "Nothing is pruned yet: a month's files are a few hundred kilobytes". Probe `digest-size.mts` over the operator's own operations log with the real `foldHour`: average 1 754 B a line, 308 hours, about 1 233 KB of `hourly-YYYY-MM.jsonl` per 30 days (max line 6 424 B), with no retention in `main/opsDigestRun.ts`. `grep -n -i dispatch AGENTS.md` prints nothing: the lifecycle table (LC-09) has no row for the 60 s dispatcher (`main/index.ts:2909`), `userData/board-dispatches.json` (`main/index.ts:2863`, kept to 500 records, `boardDispatchRun.ts:210`) or the Observatory stdio child it keeps open for the app's life (`main/observatoryMemory.ts`). The files themselves are fine on data grounds: `board-dispatches.json` is written 0600 to a `.tmp` and renamed (`boardDispatchWiring.ts:150-154`) and holds ids and times only; digests are appended 0600 inside the 0700 userData folder and hold operation names and counts only.

Proposed fix: correct the size to the measured order (about 1 MB a month) or add a retention (for example keep 12 months); add the dispatcher's row to the lifecycle table with its file, bound and child process.

### DA-7

Evidence. `main/boardDispatchWiring.ts:59-63` rejects with `String(err || e.message).slice(0, 300)`; with empty stderr Node's message is `Command failed: <file> <args>` (probe: `"Command failed: /usr/bin/false --json dispatch --dir /Users/example/DATA/proj\n"`). `defaultProvider` (`:107-113`) lets that error reach `boardDispatchRun.ts:217-219`, which writes `note: e.message.slice(0, 200)` to the operations log; `observatoryMemory.ts:84` puts up to 300 characters of Observatory's refusal body in the error too. The log stays on the machine and the digest keeps no detail, so this is local only.

Proposed fix: log a fixed code (`switchboard-failed`, `observatory-refused`) and the exit status, never the message, as the digest already does with `path.basename(file)` (`main/index.ts:825`).
