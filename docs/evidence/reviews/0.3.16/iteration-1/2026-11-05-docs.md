### DO-1

**Claim.** `CHANGELOG.md:22-23`: «Fabric watches the run to its end; two runs that left the request unsettled go to the
operator in «На проверке».» The same in the design map entry `iteration-2026-11-05-board-dispatch`
(`docs/reports/map.html:190`, «после двух таких запрос показывается оператору»), the spec §2.4, §3.6 and §10.

**Code.** `apps/desktop/src/shared/boardDispatch.ts:107` and `:113` return `{ path: 'to-operator' }`;
`apps/desktop/src/main/boardDispatchRun.ts:183-184` does `said(req.id, decision)` (one `board.dispatch.decided` ops line)
and `if (decision.path !== 'launch') continue`. Nothing else handles `to-operator` (`grep -rn "to-operator" apps/desktop/src`
finds only those two lines and the type). The queue's source for board requests is the sweep, which only reports
`if (r.state === 'queued' && still >= STILL_MS)` (`apps/desktop/src/shared/abandonedSweep.ts:205`, `STILL_MS` 3 min). A
dispatched run normally claims and accepts the request; after two such runs the request is `claimed`, `accepted` or
`in_progress` and never reaches «На проверке». Neither does an `accepted` request past its deadline (the other
`to-operator` path). A `queued` request is shown after 3 minutes whatever the dispatcher did, so the "two runs" rule
adds nothing there either.

**Fix.** Either make `to-operator` produce a row of «На проверке» (as `risenRows` does for the digest) and close the
workflow as §3.6 says, or rewrite the note: «after two runs that left the request unsettled Fabric starts no more for it;
a request still queued shows in «На проверке»». Same correction in the map entry and spec §2.4, §10.

### DO-2

**Claim.** `CHANGELOG.md:20`: «A request nobody takes for two minutes, in a project with no live session, gets a
workflow ...». The Settings help text says the same (`apps/desktop/src/renderer/src/i18n/en.ts:980` «When a project gets
a request and has no session, Fabric starts the default agent»; `ru.ts:297` «а его сессии нет»), and the map entry
(«и в проекте нет живой сессии»).

**Code.** `apps/desktop/src/shared/boardDispatch.ts:111`: `if (input.liveSession && waited < GRACE_MS) return { path: 'live-session' }`.
Past `GRACE_MS` (2 min) a live session no longer stops anything; the next lines return `launch` when the switch, folder
and caps allow. The spec agrees with the code (§3.2: «A live session that does not take the slot within G is treated as
absent and the request is dispatched»). So a project with a person's live session also gets a second agent started
with `--permissions all` (`boardDispatchWiring.ts`, `launch`) two minutes after a request arrives.

**Fix.** Say what happens: «A request nobody takes within two minutes (a live session of the project gets those two
minutes to take it) gets a workflow ...», in the release note, both Settings help strings (through the text checker) and the map
entry.

### DO-3

**What runs.** `apps/desktop/src/main/index.ts` region `board-dispatch-cycle` wires `wireBoardDispatch`, and `runCycle`
calls `void dispatcher.onPass()` every 60 s. Each pass reads up to 3 pages of 100 request threads of the last 7 days
and up to 5 pages of 100 messages per thread, the responders and the request facts
(`boardDispatchWiring.ts#readOpenRequests`); runs `switchboard --json agents status`, `dispatch` and `sessions show`
with a 60 s deadline (`CLI_DEADLINE_MS`); keeps one Observatory Python stdio child from first use until quit
(`observatoryMemory.ts#createObservatoryClient`, closed by `quit.onQuit`); writes `userData/board-dispatches.json`
(mode 0600, the newest 500 records); and starts coding-agent runs through Switchboard. It is on by default
(`shared/appSettings.ts`: `dispatchBoardRequests: raw.dispatchBoardRequests !== false`) and has no platform gate.

**The table.** `AGENTS.md` lifecycle table (lines 144-170) has no row for it (`grep -n "dispatch" AGENTS.md` finds only
the home row's `READ_GAP_MS` sentence); the "PTY sessions and coding-agent runners" row (`AGENTS.md:145`) names only
«the person or a routine / chain step» as starters; and the Windows and Linux paragraph (`AGENTS.md:187-197`) still ends
«Nothing else runs in the background», which is false on both since this release.

**Fix.** Add an LC-09 row: started by the main process with the cycle, the switch «Запускать агента на запрос доски,
который некому взять» (on by default); cadence 60 s, one pass at a time, the reads and their bounds above; the
Observatory child kept until quit; `userData/board-dispatches.json`; runs started through Switchboard, at most 2 on the
machine and 1 per project, 20 per project per day, each limited to 60 min or the board's deadline; stopped by the switch
(new dispatches) and quitting. Name the dispatcher in the runners row and in the Windows and Linux paragraph.
