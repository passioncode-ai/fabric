### PL-1

**What.** `scripts/release-mac.mjs` runs `workspacePinProblem` on the tag commit after the gate and refuses on any
difference between the `workspace` gitlink and `docs/workspace-receipt.json`. At the candidate and at `origin/main`
the probe answers «HEAD pins workspace 48dda197de8d but its receipt names 77e81ea1b75e». The gitlink went back in
`891b58f1` (2026-11-03, a docs commit about CO-409); `56288d65` (2026-11-02) had pinned 77e81ea1. Iteration 1 found this
(PL-9, V1-50) and the ledger disposed it «not a defect: the scheduled publication pins the newest snapshot after the
release commit lands». That premise does not hold today: `sync-status.json` reads 30 consecutive failures since
2026-11-03T00:42Z, because `origin/main`'s `ci.sh fast` fails in `build-mockup-coverage.mjs` on SRC-02's pinned hash of
`docs/evidence/backlog.md` (probe: mismatch on `origin/main`, match on the candidate). And even once the candidate lands
and the publication works again, the publication commit comes after the release commit, while the runbook (steps 1 to
3) tags the release commit and runs the preflight on it.

**Proposed disposition.** Re-dispose V1-50 as fixed in the release commit: set the gitlink to 77e81ea1 (the receipt's
commit), which `publicationPinProblem` admits after `verifiedCommit` (both sides a gitlink, receipt unchanged), or tag
only a commit after the first successful scheduled publication on `main`. Either way, run
`node scripts/release-mac.mjs --check-only` on the commit to be tagged before pushing the tag, and write the result in
the ledger. The ledger may change after `verifiedCommit`; the gitlink may change only in that exact shape.

### PL-2

**What.** `CHANGELOG.md` `## Unreleased`, the dispatcher bullet:

- «With the switch off nothing starts and the board is not read.» `boardDispatchRun.ts` `pass`: `if (!on && !live)
  return`, then `readRequests()` and `watch(now)`: with the switch off, a run already in flight (any record not
  `ended`) is still watched and the board still read every minute until it ends (up to its 60-minute limit). `AGENTS.md`
  says it right: «with the switch off and nothing in flight it reads nothing».
- «Not in this release: the journal events, the live session's wake and runs on Windows (CO-409).» Nothing in
  `boardDispatchRun.ts`, `boardDispatchWiring.ts` or `boardDispatch.ts` tests the platform; on Windows with Switchboard
  and a default agent a run starts. `AGENTS.md` (the Windows and Linux paragraph) says «a run it starts on Windows or
  Linux is not verified in 0.3.16 (CO-409)», which is the truth.

Lesser, same bullet family: «The board rule every session gets…» says «A session carrying out a board request … stops
before any step that touches production» as behaviour; V2-1 corrected the same claim in the switch's help to «its
instructions tell it to stop».

**Proposed disposition.** Fixed in the release commit (`CHANGELOG.md` may change after `verifiedCommit`): «With the switch
off nothing new starts; a run already started is watched until it ends», «runs on Windows and Linux are not verified»,
and «the rule tells such a session to stop before…».
