## Findings

| Id | Severity | Summary |
|---|---|---|
| ER-1 | blocking | The close of a to-operator request is retried every minute forever on a permanent error, one warn line each time, across restarts |
| ER-2 | blocking | A run Switchboard reports `unknown` never counts as empty, so the two-run stop never fires and up to 20 full-permission runs a day per project go on |
| ER-3 | non-blocking | A workflow the run closed itself makes every later take-back fail; the request retries every 10 minutes and never reaches the operator |
| ER-4 | non-blocking | A `starting` record with the switch off never ends and keeps the board read every minute; on again, it starts a run with no fresh decision |
| ER-5 | non-blocking | Lease handling after a start that did run: the take-back can steal a live run's lease, and it is tried before the 120 s silence the spec names |
| ER-6 | non-blocking | A persistent Switchboard refusal is retried every 10 minutes for the request's life, each time writing a checkpoint, a hand-over pack and a record |
| ER-7 | non-blocking | An accepted request past its deadline that Fabric never dispatched goes `to-operator` as a log line only |
| ER-8 | non-blocking | The records file is checked for two fields only; a malformed record holds a place forever; a record never saved is still started |
| ER-9 | non-blocking | Observatory workflows are left open with no record on a quit between open and record and on a lost first-checkpoint answer |
| ER-10 | non-blocking | `noteOf` keeps paths after `:`, `~`, `[`, `,` and in `file://` URLs |
| ER-11 | non-blocking | `callOpName` counts empty names (`mcp.`) and raw unknown tool names, so the digest's op set is unbounded |

### ER-1

**What.** `boardDispatchRun.ts#createBoardDispatch`, `pass`: every pass, for each record with `outcome === 'to-operator'
&& !closed`, `closeWorkflow` is called; on any throw it logs `board.dispatch.closed` `failed` and tries again next
pass. There is no attempt count, no back-off, no once-per-state log, and to-operator records are never trimmed
(`kept`), so the loop has no end. Two realistic triggers make the error permanent:

1. The close was written but its answer was lost (the client's 60 s call timeout on a loaded machine, or the
   Observatory child restarted). Fabric did not hold the lease, so the retry takes the workflow back first with the
   same key `dispatch-<id>-close-back`; Observatory's `handoff_create` raises `WorkflowClosed` before its idempotent
   replay (`store/workflow.py#handoff_create`: the `wf["status"] != "open"` check precedes `_atomic`), so the retry
   can never succeed.
2. The second empty run closed the workflow itself (its body says "Write the final checkpoint, then end", and the
   tool's own `close` is described as "the final checkpoint").

**Evidence.** P2: after the lost close, 1 440 `board.dispatch.closed` failures in a day and 1 443 `handoff_create`
calls; `closed` stays `false`. The record survives a restart (`load` keeps it), so the loop resumes after every start
while the switch is on. The first hour also raises a `failures-rose` row in «На проверке» (60 failed against 0,
`shared/opsDigest.ts#foldHour`).

**Fix.** Treat a closed workflow as closed: when `closeWorkflow` meets `WorkflowClosed` (or `observatory_checkpoint_latest`
reports the workflow closed), set `closed = true`. Bound the rest: count attempts on the record, back off (doubling
from 1 min to a cap such as 6 h), and log only on the first failure and on a change of note. Add a test with a
stand-in that closes on the first call and throws on the answer.

### ER-2

**What.** `watch`: when `runState` answers `unknown`, past `endsAt + UNKNOWN_AFTER_END_MS` the record ends with
outcome `unknown` and `emptyRuns` is not incremented. `runState` answers `unknown` whenever `switchboard sessions show`
fails (exit, 60 s timeout, unparsable JSON) or reports a state outside `starting|running|ended` (Switchboard's own
`unknown`, `launches.rs#with_state`). The request is then still a candidate, the next run starts, and the two-run stop
(`EMPTY_RUNS_TO_OPERATOR`) never fires. Only `maxPerProjectPerDay` (20) bounds it, for every unsettled request, for
its whole 7-day life, each run with `--permissions all`.

**Evidence.** P3: three days, 60 runs, all `unknown`, `emptyRuns` never above 0, `toOperator()` empty. The CHANGELOG
says "after two runs that left the request unsettled it starts no more"; under this degraded Switchboard that is
false, and the cost is real agent spend.

**Fix.** When a run is ended as `unknown`, read the request's state from this pass (`requestState`, which `watch`
already has); when it is readable and not settled, count the run as empty (or count `unknown` endings toward the stop
separately, e.g. two `unknown` endings also give the request to the operator). Test it with the P3 stand-in.

### ER-3

**What.** `open` for a later run takes the workflow back with `observatory_handoff_create` (no lease, reason `restart`).
When the earlier run closed the workflow, Observatory answers `WorkflowClosed`; `open` throws, the failure is logged
and `openFailedAt` waits 10 minutes, then the same again, for as long as the request is a candidate. The run is
counted as one empty run only, so the request never reaches `EMPTY_RUNS_TO_OPERATOR` and is never shown to the
operator by the dispatcher (the sweep shows it only while it is `queued` and still for `STILL_MS`; a `claimed` or
`accepted` one is not shown).

**Evidence.** P1: one launch, then 144 `board.dispatch.started` failures in a day, `toOperator()` empty, the record
`exited-without-answer` with `emptyRuns: 1`.

**Fix.** On `WorkflowClosed` at take-back, give the request to the operator at once (mark the last record
`to-operator`, `closed: true`), or open a fresh workflow for the next run; and make the dispatched body say that a run
which leaves the request unsettled must not close the workflow (spec §3.4).

### ER-4

**What.** A start that got no answer stays `starting` and is re-asked only while the switch is on (`pass`, the
`starting` loop guarded by `on`). With the switch off, `live` is true for ever, so the board is read every minute and
the record never ends. When the switch comes back on, the record is re-asked with no fresh decision: no request state,
no live-session or deadline check, and `timeoutMinutes` falls to 1 once `endsAt` has passed, with a hand-over whose
one-hour offer has lapsed. The same lack of a fresh decision applies with the switch on between attempts.

**Evidence.** P4: 1 440 board reads in a day with the switch off; two days later, with the request `answered`, a run
is started (`timeoutMinutes: 1`). The CHANGELOG says "With the switch off nothing starts and the board is not read".

**Fix.** With the switch off, end a `starting` record as `failed-to-start` (or `unknown`) once past its `endsAt`; before
re-asking, skip and end the record when the request is settled, gone from the read, past `endsAt`, or now has a live
responder or session.

### ER-5

**What.** After a start that did run but whose answer was lost three times (`START_ATTEMPTS`, each a 60 s CLI
timeout), the record ends `failed-to-start` with `launchId: null`, so the live run is not watched or counted. Ten
minutes later `open` finds Fabric's held lease superseded (the run accepted the hand-over), drops it and takes the
workflow back without a lease; Observatory allows that once the run has been silent 120 s, so Fabric accepts the
workflow away from a live run, then Switchboard answers `running` for the existing launch (`docs/CLI.md`, `dispatch`).
The run loses its lease mid-work. Separately, after every ordinary empty run the take-back is tried in the same pass
that saw the run end, before the "newest checkpoint is at least 120 s old" the spec names (§3.4), so Observatory
refuses it (`_handoff_authority`), a failure is logged, and the next run waits the 10-minute open back-off.

**Evidence.** Code reading: `start` deletes the lease only on a `launchId`; `open`'s held-lease branch catches the
write failure and falls through to take-back; `pass` calls `watch` then decides in the same pass.

**Fix.** Before a take-back, ask Switchboard whether a run of the workflow lives (re-ask `dispatch` with the old
dispatch id, or read the launch by `launched_by.dispatch.id`) and adopt it; wait for the workflow's newest checkpoint
to be 120 s old (`observatory_checkpoint_latest`) instead of taking the refusal as a failure.

### ER-6

**What.** A refusal ends the record and waits a fixed `REFUSAL_BACKOFF_MS` (10 min); the next try is a new dispatch:
a checkpoint write under the held lease, a new hand-over pack (`handoff_create`), a new record, a Switchboard call.
Refusals that will not clear by themselves (`not_in_group`, `agent_not_installed`, `permission_mode`) are retried the
same way for the request's whole life. After 500 ended records the trim drops the oldest, which can take a request's
whole history (its `emptyRuns` and the started runs the 24-hour cap counts).

**Evidence.** `probe-refusal.mjs`: one day of `not_in_group`, 144 Switchboard calls, 144 checkpoint writes, 144
hand-over packs, 144 records; over the 7-day window that is about 1 000 per request.

**Fix.** Double the back-off per identical consecutive refusal (cap a few hours) and reuse the open offer while it is
unexpired instead of making a new pack; treat a refusal that names configuration as `skip` until the settings or the
folder's group change.

### ER-7

**What.** `decideDispatch` returns `to-operator` for an `accepted` or `in_progress` request past its deadline with no
live holder. The dispatcher records it only when it has a `last` record for the request; otherwise it is the
`board.dispatch.decided` log line alone, and the sweep (`abandonedSweep.ts#findAbandoned`) shows only `queued`
requests or `toOperator` ones, so the request is never shown. Spec §3.6 says such a request "is shown to the operator".

**Evidence.** `probe-deadline.mjs`: decision logged once, `toOperator()` empty, no record.

**Fix.** Keep a to-operator mark per request id independent of records (a small set saved beside the records), or
have the sweep show an `accepted`/`in_progress` request past its deadline with no live holder.

### ER-8

**What.** `boardDispatchWiring.ts#wireBoardDispatch` `load` keeps any object with a string `requestId` and a string
`state`. A record `running` without `launchId`, or with any other state string, is never ended by `watch` (it skips a
record with no `launchId`), counts as active for the machine and project caps, and keeps the board read with the switch
off. `emptyRuns` absent becomes `NaN` on increment. Separately, when the save right after `records.push(r)` throws (a
full disk; this Mac had under 8 GB free on 2026-11-05), the pass aborts, but on the next pass the `starting` loop asks
Switchboard for that record, which was never written, so the "written before Switchboard is asked" guarantee does not
hold on the retry, and a restart then starts a second run.

**Evidence.** P5: the restored record holds the project (`deferred-project-busy` for 120 passes) and 10 board reads in
10 passes with the switch off.

**Fix.** Validate every field (`state` in the three values, `launchId` a string when `running`, numbers finite, ids
well formed) and end or drop what fails, saying so once; mark a record `saved` only after its save succeeds and start
only saved records.

### ER-9

**What.** `pass` returns on `quitting` after `open` succeeded and before the record is pushed, leaving an open
workflow and a live offer with no record; after the restart the request has no `last`, so a new workflow is opened.
The first checkpoint is written with the key `dispatch-<dispatchId>-open`, and `dispatchId` is new on every try, so a
lost answer also leaves an orphan open workflow. A quit that lands between two of `open`'s sequential Observatory
calls lets the next call start a new Observatory child after `close()` (`createObservatoryClient` reconnects on demand).

**Fix.** On quitting after `open`, push and save the record as `starting` without calling Switchboard; key the first
checkpoint on the request (for example `dispatch-open-<requestId>-<emptyRuns>`) so a retry replays it; refuse new calls
in the client once `close()` ran.

### ER-10

**What.** `boardDispatchRun.ts#noteOf` replaces an absolute path only after start of text, a space, a quote, `(` or
`=`. Paths after `:`, `~`, `[`, `,` and inside `file://` URLs reach the operations log.

**Evidence.** P6: `see file:///Users/example/DATA/a`, `under ~/DATA/secret-proj/a`, `cwd:/Users/example/a`,
`[/Users/example/a]` and `at <anonymous>,/Users/example/a` come back unchanged.

**Fix.** Match `(?:file:\/\/)?(?:~|[A-Za-z]:)?[\\/]` after any non-word character (or anywhere), and add these shapes
to the test.

### ER-11

**What.** `shared/toolOutcome.ts#callOpName` accepts the empty name: `tools/call` with `name: ""` (and a request with
`method: ""`) is counted as `mcp.`, and `a..b` as `tool.a..b`. Any tool name that fits the pattern is counted as
itself, whether or not the tool exists, so a client calling many invented names grows every hourly digest's op set
without bound (`opsDigest.ts#countInto`).

**Evidence.** `probe-opname.mjs`.

**Fix.** Require non-empty segments (`^[a-z][a-z0-9_]*(?:[.:/-][a-z0-9_]+)*$`) and count a tool name outside the
hub's registered tool list as `tool.other`.

### ER-12

**What.** `opsDigestRun.ts#createOpsDigestRun` `backfill` reads each month's hourly file once to list the days, then
calls `hoursOf(day)` for each missing day, which reads and parses the whole month file again. It runs synchronously in
`createOpsDigestRun`, before `useOps(createOps(...))`, on the main process at start.

**Evidence.** `probe-backfill.mjs`: 35 missing days, 39 reads of a 5.3 MB file, 1 267 ms on this loaded Mac (about a
third at the ADR's 1 to 3 MB a month).

**Fix.** Parse each month's hourly file once into a map by day and fold from it; or defer the fold to the first cycle
tick.
