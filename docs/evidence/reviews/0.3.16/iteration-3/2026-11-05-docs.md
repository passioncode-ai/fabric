### DO-2

**Claim.** CHANGELOG `## Unreleased`, CO-409 bullet: «With the switch off nothing starts and the board is not read.»
AGENTS.md dispatcher row, «Stopped by»: «quitting …; the switch in Settings». Spec §6: «The operator's switch stops new
dispatches at once; runs in flight finish or reach their time limit.»

**Evidence.** `main/boardDispatchRun.ts#createBoardDispatch`, `pass`: `if (!on && !live) return` with
`live = records.some((r) => r.state !== 'ended')`; with any record not ended, `deps.readRequests()` (the board's threads,
messages and request facts, `boardDispatchWiring.ts#readOpenRequests`) runs on every pass. A record left `starting` (a
`switchboard dispatch` that gave no answer, fewer than `START_ATTEMPTS` asks) is only asked again when the switch is on
(`for (const r of on ? … : [])`, iteration 2's ER-6 fix), and `watch` only ends `running` records, so with the switch off
it is never ended. Probe `switchoff.mjs`: one pass with the switch on (the start answers nothing, the record is
`starting`), then 120 passes with it off: `reads 121`, the record still `starting`. The board is read every minute for
as long as Fabric runs with the switch off, and the record never reaches a time limit. A `running` record also keeps
the reads until its run ends (up to its 60 min limit plus `UNKNOWN_AFTER_END_MS`), which the notes do not say either.

**Fix.** Notes: «With the switch off nothing new starts; Fabric keeps reading the board only to follow a run it already
started, until that run ends.» Code (for the errors level): with the switch off, end a `starting` record as
`failed-to-start` (or keep asking Switchboard about it), so the reads stop; a test that turns the switch off with a
`starting` record and counts reads.

### DO-3

**Claim.** AGENTS.md, Lifecycle, «The board dispatcher» row: «keeps `userData/board-dispatches.json` (0600, written
before each start, at most 500 records)».

**Evidence.** `boardDispatchRun.ts`, end of `pass`: `kept = r.state !== 'ended' || r.outcome === 'to-operator'`; only
the other records are trimmed to the newest 500 (iteration 2's ER-8/DA-2 fix, V2-15). Records given to the operator are
never dropped, so the file grows by one per request given up on, without bound. Probe `bound.mjs`: 300 records given to
the operator plus 600 finished; after one pass `records kept after the trim: 800 saved: 800`.

**Fix.** «at most the newest 500 ended records, plus every record in flight and every one that gave its request to the
operator (never trimmed)»; and either bound the given-up records (for example once their request is settled or past
its deadline) or name the growth in CO-509.
