### DA-2

Evidence. `apps/desktop/src/main/boardDispatchRun.ts:375-383` now keeps every record in flight and every `to-operator` record, and of the rest the newest 500. A request's empty-run count lives only in its records: a new record copies it from the request's last one (`:370`, `emptyRuns: last?.emptyRuns ?? 0`) and the decision reads it from the last (`:314`, `:335`). A request whose newest record is an ended `exited-without-answer` with `emptyRuns 1` is neither in flight nor `to-operator`, so it is trimmed like any other once 500 newer ended records exist. Refusals produce them: since iteration 2 (ER-7, DA-3) refusals no longer count against the daily cap, so each refused request writes a record every `REFUSAL_BACKOFF_MS` (10 min), 144 a day, for the 7 days a request lives (`boardDispatchWiring.ts`, `WINDOW_MS`). One such request trims a 500-record window in about 3.5 days, six in about 14 hours.

A request that waits meanwhile writes nothing: a live session in its project keeps it waiting (`decideDispatch`, ER-5), and so does a live responder. Probe `evict-empty.mts`: A's only record is trimmed after 13.8 h; when the session leaves, A is started as a new request and runs twice more before it goes to the operator: `A launches in all 3`. Each further wait of that kind can reset the count again. The same trimming drops started runs younger than 24 hours, so `dispatchesToday` (`:334`) can undercount the 20-a-day cap under the same load.

`CHANGELOG.md` `## Unreleased`: "after two runs that left the request unsettled it starts no more". Each run has every permission (`--permissions all`). Separately, `to-operator` records are never trimmed, also after their request has left the board, so the file grows by one record per such request for the life of the install, and `AGENTS.md:163` («at most 500 records») is no longer true.

Why blocking: a shipped claim is false under a reachable condition (refusing projects plus a waiting request), with an extra run of an agent holding every permission; it is the iteration-2 DA-2 mechanism through a record the fix does not keep.

Proposed fix: never trim the newest record of a request whose `emptyRuns > 0` while that request is still read from the board (or keep a small per-request map `{emptyRuns, toOperator, lastEndedAt}` beside the history and trim only the history); drop `to-operator` records whose request is no longer read and is past its deadline; count started runs for the daily cap from that map or from records kept for 24 h; say «at most 500 ended records, plus those in flight and those given to the operator» in `AGENTS.md:163`. Add the probe's scenario to `test/board-dispatch-run.test.mjs`.

### DA-3

Evidence. `main/index.ts#bootstrap` creates the digest run (`createOpsDigestRun`, whose constructor runs `backfill`) before `useOps(createOps(...))`; before `useOps` the sink is a silent no-op (`main/opsSink.ts`, "BEFORE BOOTSTRAP it is a no-op"). `opsDigestRun.ts#write` sets `failedOnce = true` before calling `onWriteFailed`, and only a successful write clears it. So when the start fold's write fails (disk full, an unwritable folder), the failure goes to the no-op sink and every later failed write is treated as already said. Probe `digest-silent.mts`: five closed hours, every write failing, zero lines said. The header of `opsDigestRun.ts` says "A write that fails is said once in the ops log". Data loss here is only the digest lines, which the next start's fold rebuilds when the folder is writable again; the defect is that nobody is told.

Proposed fix: run `backfill` after `useOps` (expose it as `run.fold()` called from `bootstrap`), or have `write` leave `failedOnce` false while no sink is installed. A test: a fold whose write fails, then a closed hour whose write fails, must say one line.

### DA-4

Evidence. `boardDispatchRun.ts:87-91`: the path is matched only after start of text, whitespace, a quote, `(` or `=`. Probe `noteof.mts`: `not-found: path:/Users/example/DATA/secret-project`, `at [/Users/example/DATA/p]`, `folder,/Users/example/DATA/p` and `file:///Users/example/DATA/…` pass unchanged. What reaches `noteOf` today is mostly `JSON.stringify` of an Observatory body (`observatoryMemory.ts`, a path there follows a quote and is caught) and Switchboard failures, which `boardDispatchWiring.ts` now reduces to a refusal code or an exit code, so the leak needs an error text of an unusual shape; the operations log stays on the machine. Iteration 1's DA-7 asked for no paths at all.

Proposed fix: match an absolute path after any non-word character (`(^|[^\w.-])(?:[A-Za-z]:)?[\\/]`), or log a fixed code and the tool name instead of the message, as iteration 2 proposed.

### DA-5

Evidence. `boardDispatchRun.ts:282-285`: with the switch off the pass returns early only when no record is in flight; otherwise it reads the board's requests (`readOpenRequests`: up to 3 pages of threads and 5 pages of messages each) every minute until the runs end. `CHANGELOG.md` `## Unreleased` says "With the switch off nothing starts and the board is not read"; `AGENTS.md:163` says "with the switch off and nothing in flight it reads nothing", which is what the code does.

Proposed fix: the CHANGELOG sentence as in `AGENTS.md`: "With the switch off nothing starts; the board is read only while a run started earlier is still in flight."
