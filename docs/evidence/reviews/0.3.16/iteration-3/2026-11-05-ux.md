### UX-1

The permissions panel in Settings → «Запуск агентов» opens with its lede, unchanged since v0.3.15:

- ru `settings.permissions.lede` (`i18n/ru.ts:281`): «Один выбор для всех агентов, которых запускает Fabric. …»
- en `settings.permissions.lede` (`i18n/en.ts:964`): "One choice for every agent Fabric starts. …"

The same panel (`launch/SettingsScreen.tsx#AgentPermissionsSetting`) now carries the dispatch switch, on by default (`shared/appSettings.ts`, `dispatchBoardRequests !== false`), whose agent is started by Fabric with `'--permissions', 'all'` (`main/boardDispatchWiring.ts:125`) whatever `agentPermissions` says; nothing in `main/boardDispatchRun.ts` or `main/boardDispatchWiring.ts` reads `agentPermissions` (grep prints nothing). The on-demand spec §3.5 says `--permissions all` runs Claude Code with `--dangerously-skip-permissions` and Codex with `--dangerously-bypass-approvals-and-sandbox`. So a person who picks «Проверять вручную» ("The agent asks before it acts") reads that this choice covers every agent Fabric starts, while an unattended agent with no approvals and no sandbox is started in their project folders by default. The dispatch help two lines lower says «со всеми разрешениями», so the panel now contradicts itself, and the radio choice, which is where a person decides, states the false half. This release made a shipped statement false (it was true in 0.3.15), on a security-relevant setting.

Proposed fix (either):
- words only: the lede says what is now true, for example ru «Один выбор для консолей и агентов, которых вы запускаете. Агент, которого Fabric запускает на запрос доски, всегда работает со всеми разрешениями (ниже).» and the same in en; check both with the text checker;
- or behaviour: with «Проверять вручную» chosen, the dispatch switch is off by default (or says it starts nothing), and the help says so.

### UX-2

CO-460 moved «Отметить прочитанным» from Главная's folded journal to История's «Что делали агенты» (`launch/HistoryScreen.tsx`). On Главная the feed had no filters, so the count and the mark covered exactly the rows on screen, the rule the old code states as "marking read cannot swallow rows the operator never saw (AX-07)" (v0.3.15 `EstateHome.tsx`, the journal panel's comment). История has «Кто» and «Проект» filters, remembered across visits (`rememberedFilters`), and the list receives the filtered events (`HistoryScreen.tsx:234`), but the count and the mark use the unfiltered feed: `unread` is `(feed ?? []).filter(e => e.seq > cursor)` (`HistoryScreen.tsx:114`) and the button calls `onRead(highestSeq)` of the whole feed (`HistoryScreen.tsx:230`). The probe above shows it: with one row visible the button reads "Mark 5 as read" and marks through seq 5, four rows the person never saw.

Proposed fix: compute the count and the highest seq from the same filtered list the section renders, or hide the button while a filter is on; add the probe's case to `HistoryScreen.test.tsx`.

### UX-3

After two runs Fabric started end without settling a request, the sweep puts it in «На проверке» as kind `request-unmoved` (`shared/abandonedSweep.ts:214`, `r.toOperator`). The screens name a sweep row only by its kind (`attentionTitle.ts#detailOf`, `t(\`attention.swept.${kind}\`)`), so the person reads «Запрос на доске, который никто не взял в работу» / "A board request nobody has picked up" (`i18n/ru.ts:484`, `i18n/en.ts:1166`). For this row that is false: two agents took it and ended. The person cannot tell it from an ordinary unanswered request, and is not told that Fabric will start no more runs for it, which the CHANGELOG bullet and the sweep's own `nextStep` say ("Two runs Fabric started for this board request ended without settling it: it waits for the operator, and Fabric starts no more for it").

Proposed fix: a kind of its own for this row (for example `request-to-operator`, agent-only kinds unchanged) with ru «Два запущенных агента не закрыли запрос: Fabric больше не запускает агентов на него, решите сами» and en "Two agents Fabric started left this request open: Fabric starts no more for it, it is yours"; a case in `attentionTitle.test.ts`.

### UX-4

Iteration 2's UX-3 fix changed `rail.agentTitle` to «{project} · {runner}», so the rail, its tooltip, the console button and an agent screen's top bar lead with the project, as the CHANGELOG says the screens now name an agent. The console keeps the old order:

- the top bar of an open console: `consoles.sessionTitle` «Сессия · {runner} · {project}» (`i18n/ru.ts:3176`, used at `App.tsx:1012`);
- a detached session window's back link: `session.back` «← {runner} · {project}» (`i18n/ru.ts:2463`, `SessionWindow.tsx:133`);
- while the console's own tab reads `consoles.tabTitle` «{name} · {runner}» (`launch/ConsoleTabs.tsx:39`).

One open console shows «AdOps · Claude Code» on its tab and «Сессия · Claude Code · AdOps» in the bar above it.

Proposed fix: «Сессия · {project} · {runner}» and «← {project} · {runner}» in ru and en (the parity comment above `placeTitle` in `App.tsx` updated with them).

### UX-5

«Поручить агенту B в Fabric» (CO-458) writes fixed Russian into what the person reads: A's task note «Поручено {B}: «…» (задача …, запрос …).» (`main/crossProjectAssign.ts:61`), the board answer «{B} сделал: «…». Задача … на проверке.» (`:78`) and A's task note «{B} сделал: «…» (задача …).» (`:82`). The sibling route on the same panel, «Открыть консоль», writes its note through the interface's language (`t('xp.note')`, `launch/CrossProjectConsole.tsx`, ru «Консоль открыта в {project}: {what}», en "Console opened in {project}: {what}"). A person using Fabric in English sees Russian notes on their task page after an assignment. The refusal reasons the panel shows under «Не поручено.» are English in a Russian interface ("the task is already in that project", "the board did not say its epoch, so nothing was sent", `crossProjectAssign.ts`), which is the detail slot's convention, so only the notes are the defect here.

Proposed fix: write the notes in the person's language (the renderer passes its locale, or main reads `settings.locale`, as the agents' rules read `agentLanguage`), with ru and en keys; the board answer in the agents' working language.

### UX-6

On the Agent access page the whole page content is `<aside className="ceo-panel ceo-page" aria-label="Доступ агентов">` (`AgentAccessPanel.tsx:165`), rendered inside the page's `<main className="content">` (`App.tsx:1122`, `:1173`). A screen reader's landmark list then offers the place's main region and, inside it, a "complementary" region that is in fact the page itself; the same element as a side panel was rightly an `aside`. The heading still takes focus on arrival from the rail (`LaunchShell.tsx`, the focus effect), so the page is usable; the landmark role is wrong.

Proposed fix: render the `page` form as a `section` (or `div`) with the same label, keep `aside` for the side panel.
