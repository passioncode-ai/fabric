## Checked and holding

- **Migration order.** The 5 files apply in order on a 79 database (owned-cluster probe and the real-dump receipt). The ledger gate passes.
- **`schema_version()` vs `schemaContract.json`.** `schema_version()` counts applied rows, 84 after the chain. The contract is `{minimum: 84, maximum: 84}`, and `scripts/build-manifest.mjs` takes `schemaMin`/`schemaMax` from the contract. Startup refuses 79 as `behind` and 85 as `ahead` (tests above).
- **Private archive admits 66–84 in both languages.** SQL: `…095` `ceo_private_archive_canonical` lists 66–84, and the probe shows 65 and 85 refused. TS: `PRIVATE_ARCHIVE_LIMITS.sourceSchemas` is 66–84, the type is derived from it (DA-8 fix holds), and admission is checked at `ceoPrivateArchive.ts:118`. Export writes `schema_version()` (= 84).
- **Thin dispatcher.** `apply_projections` in 81 → 91 → 95 only gains lines: `apply_grants`, then `apply_task_sources` and `apply_work_claims`, after `apply_operating_surfaces`. No body was rewritten.
- **New tables match migration 4's shape.** With Supabase defaults in force:
  - RLS is on, and each table has a member read policy for `authenticated`.
  - `select` is granted to `authenticated` and `service_role`. Insert, update, delete and truncate are false for every API role, and anon has nothing.
  - The projectors (`apply_work_claims`, `apply_task_sources`, `apply_grants`, `apply_projections`) are executable by no API role.
  - `board_*_operator` and `reserve_effect` are executable by `service_role` only. There is one `reserve_effect` overload.
- **event_types and feed sentences.** 106 rows, with each `projects` flag matching a projector (`grants-journal-db` A7-020 PASS). An `event.<type>` sentence exists in en and ru for each new type.
- **Grant replay idempotency.**
  - Issue is `on conflict (id) do nothing` with a cross-estate guard; consume is `coalesce`; events at or below a restore boundary are skipped. The `grants-journal-db` rebuild test passes.
  - Observation, not a defect: on an upgraded database, a rebuild now applies pre-91 `grant.consumed@1` events, which carried `grant_id` in 0.3.4 (`git show v0.3.4:…/policy.ts`). A legacy grant whose 0.3.4 table update failed silently turns into spent, which is the journal's truth (probe: `consumed_at` went from `-` to set).
- **Analytics counts.** These are live `access_grants` reads in the active estate; an unreadable count is omitted. Nothing new beyond iteration 1's notes (`limit(10_000)`).
- **Work views' `console` field.** `index.ts#heldSessions` sets `console: true` only for a running PTY, and `workRead.ts#claimView` reads it from `consolesOf(sessions)`. Enrolled and hub sessions are `false`. Correct.
