| ID | Blocking? | Finding | Evidence | Suggested fix |
|---|---|---|---|---|
| ER-1 | **Yes**: the release cannot run | `release.yml` is not valid YAML, so GitHub rejects the workflow and a pushed `v0.3.5` tag starts nothing. The `run:` of the step "An unsigned Windows release says so in its notes (PL-10)" is a plain scalar containing `: ` (`{ version: v, …`). | The `yaml.safe_load` row above (exit 1, line 160 col 186); `.github/workflows/release.yml:160`. Add a gate that parses every workflow, e.g. the python one-liner in `scripts/ci.sh fast`, so this cannot ship again. |
| ER-2 | **Yes**: the person is misled toward a migration | Iteration-1's ER-9 fix holds only for a client that throws, and the real one never does. postgrest-js resolves a transport failure as `{ error: { message: 'TypeError: fetch failed' … }, status: 0 }` (its `res.catch`, `shouldThrowOnError` false). So `withSchemaReadiness` always reads an unreachable database as `backend-error`. The dialog then says "The database is running but answered the schema check with an error, so it may be older than this build. Make a verified backup, then follow 'Upgrading an existing database'…". That sends the operator to a migration procedure when the stack is stopped, `SUPABASE_URL` points nowhere, or Docker died after `supabase start`. The `transport` remedy cannot be reached. | The schema-probe row above; `schemaReadiness.ts#withSchemaReadiness` (`response.error != null` → `backend-error`); `index.ts` `readSchema: (signal) => db.rpc('schema_version').abortSignal(signal)`; postgrest-js `dist/index.cjs:394-430`; `en.ts:917`. The test models transport as a throw (`schema-readiness.test.mjs:88`), which the real client never does. | Classify by the answer's shape. `status === 0`, or an error whose message starts with `FetchError:`, `TypeError:` or `AbortError:`, is `transport` (or `timeout` for `AbortError`). Only an HTTP answer with a PostgREST error is `backend-error`. Add a test that drives the real client against a closed port. |
| ER-3 | **Yes**: the loop guard is bypassed and claims are orphaned | fabric-mcp treats the surface's own refusals as a broken connection. `classifyFailure` maps only 401/403/404 to "nothing ran"; 429 (call budget), 413 (body too large), 408 and 400 (batch) become `{drop: true, mayHaveRun: true}`. Three things follow. (a) The agent is told "The connection to Fabric broke … The outcome is unknown — check its effect", although the surface refused before any tool ran. (b) The proxy drops a healthy session and enrolls again. The old bearer is `claimed`, so no spare exists and a new session is minted with a fresh budget, so 120 calls/min becomes unbounded for an enrolled agent, plus one `session.enrolled@1` per minute in a loop. (c) The old session is never revoked: it keeps its claims, and the agent's new session cannot release them (`fabric_work_release` → `not-yours`) until they lapse. | The 429-probe row above; `fabricMcp.ts#classifyFailure` (region `fabric-mcp-failures`); `agentSurface.ts#handle` (429/413/408/400 are refused before `handleRequest`); `sessionEnroll.ts` (spare reuse only for `unclaimed`). | Treat 4xx refusals other than 401/403/404 as `{drop: false, mayHaveRun: false}`, pass the surface's reason and `Retry-After` to the agent, and keep the session. If the proxy ever does re-enroll, revoke or reuse the old session so its claims follow it. |
| ER-4 | **Yes**: a working agent loses its claims and is told something untrue | The per-binding cap (8) ends the oldest-minted session, not the least recently active one. An enrolled session never ends when its coding agent exits: fabric-mcp's `client.close()` sends no DELETE, the surface 404s non-POST anyway, and only the hook pack's `observe end` ends one. So in one Fabric run, a long-running live session plus 8 short ones that already exited means the next start evicts the live one. Its claims are released (`session-ended`). Its next call answers "Fabric restarted or closed this session before X reached it … Nothing of this call was done", which is false. It re-enrolls under a new session id and does not know its claim is gone, so another agent can now take the same task. This only needs nine starts of one runner (e.g. claude-code) during one Fabric run, which a heavy operator reaches in a day. | The evict-probe row above; `sessionEnroll.ts` region `session-enroll-bound` (`live.slice(0, live.length - cap + 1)` over `liveOf`, sorted by `mintedAt`); SDK `client/streamableHttp.js#close` (no DELETE); `agentSurface.ts#handle` (`req.method !== 'POST'` → 404); `fabricMcp.ts#call` (the 401 sentence). | Evict by last sign of life (`live.lastCallAt`), not by mint time. End a session whose MCP client left: accept DELETE with the session's bearer and mcp-session-id, and have fabric-mcp call `terminateSession()` on stdin end. Tell an evicted agent "evicted, your claims were released" instead of "Fabric restarted". |
| ER-5 | No | Each `--rejoin-only` (the session hooks, per turn) mints another bearer for the same session, and nothing bounds or sweeps them. A claimed one keeps its `StreamableHTTPServerTransport` and a full `McpServer` until the whole session is revoked. An unclaimed one (a hook process that died before initialize) stays in `states` forever: it is dropped only if someone presents it after the claim window, which nobody will. Memory grows by one server per turn for the life of a long session. | The rejoin-probe row above (51 credentials for one session); `sessionEnroll.ts` region `session-rejoin` (mint, no `sessions.add`); `agentSurface.ts#mint` and `#drop` (the only drop of an unclaimed credential is at `handle`, line ~657). | Keep at most one rejoin bearer per session (reuse an unclaimed one, revoke the previous on a new rejoin). Sweep expired unclaimed states on a timer or in `mint`. |
| ER-6 | No | A Windows Stop runs `taskkill` synchronously on the main thread: `execFileSync`, 5 s timeout, up to two steps, per session. Quitting with several sessions blocks the main thread, and with it the in-process quit deadline and every window, for up to 10 s per session. The outside reaper then ends Fabric at 15 s instead of a drained quit. This is the same class as A6-009, which moved `which` off the main thread. | `pty.ts#signalProcess` (`stopWindowsTree(…, (how) => { execFileSync(how.file, how.args, { timeout: 5000 … }) } …)`); `quit.ts` (deadline is a timer). | Use async `execFile` with the same steps, or run the stops in parallel with an overall bound below `QUIT_DEADLINE_MS`. |

## Boundaries checked and found sound

- The door token can only ask. `enrollSession(null, …)` returns `needs-grant` (or `no-session` for a rejoin) and never a session. The door's tools are request, status and enroll (`hubTools.ts#HUB_TOOLS`).
- A link's parameters are a claim. A link only routes to a view, a project named by name matches only when exactly one project has that name, and nothing starts or acts.
- A binding is checked again after mint (`stillLive`). A revoked binding or grant ends its enrolled sessions (`onBindingRevoked`, `onGrantRevoked` → `EnrolledSessions`).
- The new IPC channels are main-window only.
- The product connect refusal on Windows comes before the consent page opens (`vault-unavailable`, worded en/ru).
- The quit drain is bounded (surface stop ≤3 s for releases, quit deadline 10 s, outside guard 15 s).
- `fabric-mcp` logs go to stderr only and never include a credential.
