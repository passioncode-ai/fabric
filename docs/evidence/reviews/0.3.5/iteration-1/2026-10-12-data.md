## Results by area

- **Order.** The migrations sort, and were merged, in the order 82 < 90 < 91 < 94 < 95. Every redefinition starts from the
  latest earlier body (diffs above). `schema_version()` counts the applied rows: 79 files at v0.3.4 and 84 now; the contract is `84/84`,
  and `build-manifest.mjs:83` requires maximum = file count.
- **Startup refusal.** 79 is refused as `behind`, with the runbook remedy; 85 is refused as `ahead`; only 84 starts (probe above).
- **Private archive.** SQL 95 admits source schemas `66…84` (95:259); TS `PRIVATE_ARCHIVE_LIMITS.sourceSchemas` lists the
  same set, `[66 … 84]` (`ceoPrivateArchive.ts:25`). The export reads `schema_version()`, so an archive exported at 84
  imports at 84. One type-level gap: DA-8.
- **Event register and feed.** Each new type has its row, a `projects` flag that matches the projector bodies, and an
  `event.<type>` sentence in `en.ts`:

  | Type | Row | `projects` | Sentence in `en.ts` |
  |---|---|---|---|
  | `hub.call.refusals.summarized@1` | 82:160 | false | :22 |
  | `session.enrolled@1` | 90:7 | false | :1213 |
  | `task.source.linked@1` | 95:35 | true; named in `apply_task_sources` | :1205 |
  | `work.handover.requested@1` | 95:36 | true; named in `apply_work_claims` | :1206 |
  | `session.turn.observed@1` | 95:37 | false | :1207 |

  The ingress side is covered too: `commandIngress.ts:175-181` (payload schemas) and `desktopIngress.ts` (owners).
- **Grants and RLS.**
  - `work_claims` and `task_sources` follow migration 4's shape: RLS enabled, a `member_estates()` read policy, and
    `select` granted to `authenticated` and `service_role` (95:92-98).
  - Writes to both tables are revoked from every API role (95:99). The same is done for `grants` (91:115).
  - Nothing in the app writes `grants` directly any more. Its only writers are the `grant.issued@1` / `grant.consumed@1` appends in `policy.ts`.
- **Grant idempotency on replay.** Issuing a grant uses `on conflict (id) do nothing` and a cross-estate guard. Consumption
  uses `coalesce(consumed_at, …)`, so a replay changes nothing. Events below the restore boundary are skipped. A pre-91
  `grant.issued@1` that names no grant projects nothing.
- **Claim idempotency on replay** (claim id, idempotency key, the one-live index). In a fresh-estate rebuild (restore), the
  result is fully determined by the events in order: the claim reads the lease row the lease projector has just written,
  judged by the event's own clock. Replaying on top of existing rows (`rebuild_estate_projections` does not truncate) is a
  no-op for `work_claims`, because every update is guarded by `released_at is null` and inserts use `on conflict`. No test
  covers either case: DA-4.
- **Analytics counts** (`index.ts:960-981`). They read live `access_grants` (`revoked_at is null`, `expires_at > now`) in the active
  estate. Grants brought in by a restore carry `revoked_at` and are excluded. Callee `fabric` counts as an enrolled coding agent
  (`analytics.ts:129`; the only `callee: 'fabric'` writer is `fabricMcp.ts:307`). An unreadable count is left out, never
  sent as zero. No defect. Two small points, not raised as findings:
  - `limit(10_000)` would truncate silently.
  - `agents_with_access` also counts grants whose credential was never claimed.
