## Checked and holding

- **Migration order on 79.**
  - All five filenames sort after `20261005000081_project_board.sql`, the newest file of v0.3.4 (`git show v0.3.4:supabase/migrations` lists 79 files, including 76/77/80/81).
  - The ledger gate passes, and the real-dump rehearsal applied them 79 → 84.
- **Projector per-concern functions.**
  - `apply_projections` gains `apply_grants` (91), then `apply_task_sources` and `apply_work_claims` (95), placed after `apply_operating_surfaces` because the claim projector reads the lease that projector just wrote.
  - No other projector body is rewritten. 82 replaces `apply_hub_access` with 80's body minus the six write rules, which move to `refuse_hub_write_rules`. That function is called from `append_event` (at `now()`) and from `restore_estate_events` (at the event's own `occurred_at`).
  - A restore is never stricter than the append that wrote the event: the stored `occurred_at` is at or after the append's `now()`. So no journal accepted at the door is refused on restore.
- **Grants and RLS of the new tables.**
  - `work_claims` and `task_sources` have RLS on, a member read policy for `authenticated`, and `select` granted to `authenticated` and `service_role`. Insert, update, delete and truncate are revoked from every API role. `anon` gets nothing, because default privileges (`…026`) grant only `authenticated`/`service_role`.
  - The projectors and `refuse_hub_write_rules` are executable by no API role.
  - `board_*_operator` and the 7-argument `reserve_effect` are executable by `service_role` only.
  - The `grants` table has no remaining TS or SQL writer outside `apply_grants`: `policy.ts` only reads it now.
- **event_types and feed sentences.**
  - The five new types are `hub.call.refusals.summarized@1`, `session.enrolled@1`, `task.source.linked@1`, `work.handover.requested@1` and `session.turn.observed@1`.
  - Their `projects` flags match the projector bodies: true only for `task.source.linked@1` and `work.handover.requested@1`.
  - 91 corrects seven stale flags. The rehearsal counts 101 → 106.
  - Each type has an `event.<type>` sentence in both `en.ts` and `ru.ts`.
- **Replay idempotency.**
  - `apply_grants`: issue is `on conflict (id) do nothing` with a cross-estate guard; spend is `coalesce`; events at or below a restore boundary are skipped; pre-91 `grant.issued@1` (no `grant_id`) projects nothing.

  - `apply_work_claims` replays correctly from empty, in order. The in-place-replay defect (V2-32) is reachable only by `rebuild_estate_projections`. I re-derived that boundary:
    - the main process calls no such RPC (`dbDeadline.ts#LONG_RPCS` only names it for a deadline);
    - `restore_estate_internal` and `restore_estate_verified` both refuse a non-empty target, so every restore replays from empty;
    - the only caller of `rebuild_estate_projections` is `scripts/probe-fresh-vs-upgraded.mjs`.
