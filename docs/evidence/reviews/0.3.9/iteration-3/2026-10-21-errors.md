## Findings

| ID | Blocking | Finding | Evidence | Fix |
|---|---|---|---|---|
| ER-1 | No | **The runtime stack watch can start `supabase start` after the quit has begun.** `stop()` only stops scheduling: a tick whose database read is in flight when the quit runs goes on to `recoveryDue` and `tryRecover`, neither of which checks `running`. `recoverStack` then sets `stopRequested = false`, undoing the `stopStartingStack()` the quit ran just before (it is registered earlier, so it runs first), and spawns `supabase start`, a child that is not killed when Fabric exits. It needs the stack down with a try due at the moment of the quit, which is the moment a person is most likely to quit (the chain schedules its read exactly at `nextRecoveryAt`, and a hung database holds the read for up to 6 s). The outcome is benign for data (the stack keeps running between launches by design) but contradicts AGENTS.md's row, "Stopped by: quitting", and leaves an unattended CLI run behind the quit. | `apps/desktop/src/main/stackWatch.ts:158` to `:159` (`tryRecover`, no `running` check), `:219` to `:238` (`tick` calls `tryRecover`); `apps/desktop/src/main/env.ts:153` (`stopRequested = false` in `recoverStack`); `apps/desktop/src/main/index.ts:1465` (`quit.onQuit(stopStartingStack)`), `:5344` (`quit.onQuit(() => stackWatch?.stop())`); `AGENTS.md:153`; scratch `after-stop.mjs`: `recoveriesAfterStop: 1` | Return from `tryRecover` (and from `tick` after its read) when `!running`; give `recoverStack` a `stopped` that also reads `quit.quitting`, so a quit is never undone by a later reset; a test that stops the watch while a read is in flight and asserts no `recover` call |
| ER-2 | No | **On Windows, fabric-mcp names `cmd.exe`, not the coding agent, as `agentPid`, so the /clear rename (TR-1) cannot match there.** `fabric-mcp.cmd` runs `Fabric.exe` as a child of `cmd.exe` (no exec on Windows), so `process.ppid` is the `cmd.exe` that runs the script; a hook's rejoin names the agent's own pid from Claude Code's session file (`claudePidOfSession`). `ofAgentPid` compares the two and never matches, so after a /clear on Windows the hooks' turns and end find no session (exit 3) while the agent's fabric-mcp keeps the session; History misses those turns.
