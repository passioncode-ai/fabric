## The question the plan sent here: can 0.3.8 run on schema 95?

**It cannot start on it; it keeps running on it.** Precisely:

1. **Start: refused.** v0.3.8's compiled contract is `minimum: 94, maximum: 94` (`git show v0.3.8:apps/desktop/src/shared/schemaContract.json`); `withSchemaReadiness` throws `ahead` ("The database schema is 95; this build supports 94-94 ...") before any domain service starts (`v0.3.8:apps/desktop/src/main/schemaReadiness.ts`, the `response.data > contract.maximum` branch). The CHANGELOG's "0.3.8 cannot open a schema-95 database" is true.
2. **Running: not re-checked.** v0.3.8 calls `withSchemaReadiness` once, in `bootstrap` (`v0.3.8:apps/desktop/src/main/index.ts:778`); no other caller. The only later schema read is `metaInfo` (`index.ts:1669`), which feeds `compatibilityOf`: Settings, Diagnostics then shows `database_ahead: this estate is at schema 95 and this build knows up to 94; this build cannot open it safely` (`v0.3.8:DiagnosticsSection.tsx:67-71`). `mayWrite` is read by nothing that gates writes (only `conversationRegistry.ts`'s own `mayWrite`, a different function).
3. **Every RPC 0.3.8 calls still resolves with the same arguments, return type and grants.** Diff of `proname(args) -> result acl` over `public` on the copy before and after migration 120: only additions (`apply_comms_reads_many`, `board_cursor_key`, `board_list_reader`, `board_read_ack_many`, `board_request_default_ttl`, `board_request_open`, `board_responder_possible`, `board_waiting_operator`); the eight replaced functions keep signature and ACL.
4. **Its tick runs the new tick.** v0.3.8's `tickBoard` (`boardService.ts:575`) reads only `ok`, `expired`, `rotated`, `retired`, `receipts_compacted`, `outbox_compacted`; the new `answered` key is ignored. So within a minute of the migration the running 0.3.8 answers the queued requests itself.
5. **`answered` reaches 0.3.8 only on reads, and nothing there validates it.** v0.3.8's closed `requestState` enum (`boardService.ts:147`) is used only in `commsReceiptSchema`, the write receipts; no write path returns an answered request (a target's reply returns `{message, thread, at}`; `board_claim` of an answered request refuses "This request is answered; it cannot be claimed"; `board_cancel` moves answered to cancelled). Comms in 0.3.8 shows the raw words `answered` and `target-reply` (`v0.3.8:CommsParts.tsx:30-33`, `contractWord` falls back to the value). `COMMS_TRANSITIONS` (no `answer` op in 0.3.8) is read only by tests.
6. **A migration under the running 0.3.8 is safe for the database.** The file takes `ACCESS EXCLUSIVE` on `board_requests` (the constraint swap) and a share lock on `board_messages` (the index) for milliseconds on 580 messages; the tick it races has `lock_timeout = '3s'`; it applies in one transaction (exit 0).

So the plan's step 3, "migrates the live database to 95 while 0.3.8 runs", does not need to change for 0.3.8's sake. It does need to say how the migration is applied (PL-1).
