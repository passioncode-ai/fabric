## 0.3.8 against schema 95 (the check the plan assigns to iteration 3)

A static check of every 0.3.8 path that reads what migration 95 changes; no run on a copy at this level. It holds: 0.3.8's `com.list` and `com.get` pass messages through unvalidated (`boardService.ts` :490 to :521), so `answered` reaches agents as 0.3.9 would send it; `board_insert_message` returns the same `{message, thread, at}` receipt (migration :88), so 0.3.8's strict `commsReceiptSchema` still passes for submit, reply and cancel; `tickBoard` reads named keys and ignores the new `answered` (:573 to :581); the operator reads accept any state string (`commsOperatorRead.ts` :126); the changed SQL functions keep their signatures; `commsTransition.ts` is used by tests only. Visible in the window, none harmful: Diagnostics says `database_ahead`, "this build cannot open it safely" (`buildManifest.ts#compatibilityOf`); the request timeline shows the raw word `answered` (`CommsParts.tsx#contractWord` falls back to the value); a private archive export refuses source schema 95 (`ceoPrivateArchive.ts` :25). 0.3.8 re-reads the schema only at start, so it keeps running; it cannot start again on 95.

## What exactly needs a person

One act, today: step 4's quit and open. The broker reports `startedBy: "other"` for the running Fabric and refuses to stop an app it did not start; the operator's rules forbid an agent quitting an enrolled app directly. So the person quits Fabric and opens it, and must not do so before the agent says the migration is done (a quit and open between step 2 and step 3 starts 0.3.9 on schema 94, which does not heal: the startup dialog and a hub refusing every agent). Optional and separate: a real reboot to verify the login item (CO-365). Nothing else: the tag push, the backup, the rehearsal, the install and the migration are agent work.
