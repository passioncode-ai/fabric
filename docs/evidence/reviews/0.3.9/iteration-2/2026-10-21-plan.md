## Does the candidate deliver the operator's priority

In code, yes. The hub is up before the database and while it is lost (`hubStandby.ts`, `stackWatch.ts`, a handover on the same sockets after `pastRetryPoint`, so it cannot be handed over twice), a stopped or still-running stack is not started in a loop (one `supabase start` per try, 10 s growing to 2 min from the end of a try, a hold when the database container is gone or running), a session keeps its identity across `/clear` and signs every 2 minutes, a claim and a release move the task, a reply answers a request and nothing stays queued for ever. Migration 120 applies on the full chain and its targets match the live schema-94 database. What does not hold is around the code: how the operator's running 0.3.8 actually reaches 0.3.9 (PL-1), a number about the operator's data that has moved (PL-2), and the release-close obligations to other projects, which have no written home (PL-3, PL-4).

## Upgrade from 0.3.8 at schema 94, and the window

0.3.9 admits 95 only; against 94 it classifies `schema-not-ready` behind, which `startupHeals` excludes, so it shows the startup dialog while the standby answers every agent `stack-unavailable` ("Fabric could not start ...", Retry-After 60) until the person quits. The running Fabric was started neither by the broker nor by the person through it (`startedBy: "other"`), and the broker stops only apps it started, so the stop is the person's quit. Between installing the bundle and that quit, the 0.3.9 `fabric-mcp` meets the 0.3.8 hub and enrolls without `agentPid` (iteration 1 PL-2, fixed and tested against a strict 0.3.8 schema on the same SDK). After the quit, the database must be migrated before Fabric opens again; if the person reopens first (what "the person's own quit and open" in the plan describes), 0.3.9 refuses, and the hub stays in refusal until the migration and a second open. See PL-1.

## Release readiness

The gate is ruled to the release commit (V1-45), and `release-mac.mjs#verifiedCandidateProblem` admits exactly what that commit needs after the verified commit: `apps/desktop/package.json` (version only), `CHANGELOG.md`, `release-gate.json`, the ledger, `docs/MERGES.md`, the map and the review receipts. Still 0.3.8 at this candidate: `apps/desktop/package.json:3`, `release-gate.json` (version, ledger, `verifiedCommit`); heading `## Unreleased`. The ledger's title names 0.3.9 alone and iteration 1 names its candidate in full, as the gate reads them. Anything else the release commit touches (backlog rows, the carry-over register, the plan README) fails the gate: those edits belong in the iteration-3 candidate or after the release.

## What needs a person

The quit of the running Fabric (broker cannot stop an app it did not start), and not opening it again until the database is at 95; restarting each coding agent so its `fabric-mcp` carries the session fixes (the plan names this); the reboot that proves the login item (CO-365, named). Moving the eight long-done backlog tasks and accepting the review tasks (TR-3's one-off, TR-15) stay the operator's moves; only TR-15 is named.
