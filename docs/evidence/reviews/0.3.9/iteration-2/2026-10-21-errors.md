## Findings

| ID | Blocking | Finding | Evidence | Fix |
|---|---|---|---|---|
| ER-1 | No | **The runtime stack watch can run two (or more) timer chains at once, for the rest of the run.** A recovery's `finally` clears `timer` and schedules a read in 1 s. When it ends while a timer tick is still reading (a database read takes up to 6 s when the stack is hung), `timer` is the handle of the timer that already fired, so `clearTimeout` removes nothing, and the in-flight tick then schedules its own next read: two chains. Each later recovery that ends during a read adds one more; nothing removes them until quit. During a long outage with tries every 2 min the chains accumulate, and each one reads the database every 30 s (and, while down, publishes to the window and sets the hub's refusal) after the stack is back. No restart loop results (`recovering` and `trying` still allow one try at a time); the cost is growing read load. The probe drives the real watch and ends with two pending watch timers. | `apps/desktop/src/main/stackWatch.ts:189` to `:191` (`if (timer) clearTimeout(timer)`, `schedule(1_000)`), `:227` (`void tick().finally(() => schedule())`); scratch `chains.test.mjs`: `2 !== 1`. The suite's `stack-watch.test.mjs` drives `tick()` directly and never calls `start()`, so the chain is untested. | Keep one chain: a generation counter checked in the timer callback, or reschedule only from the chain (have the recovery's end set a "read soon" flag the chain honours, or skip `schedule()` in the tick's `finally` when a newer timer exists); a test that calls `start()` with fake timers and asserts one pending watch timer after a recovery that ends during a read. |
| ER-2 | No | **An agent that exits during or just after a stack outage leaves its session, claims and running tasks behind.** While the stack is lost the hub answers every POST 503 with Retry-After (up to 120 s), so fabric-mcp's two-minute ping sets the transport's cooldown. The transport refuses EVERY request in that window before sending it, DELETE included, so when the agent exits, `leave()` never reaches the hub (the surface lets a DELETE through in this mode precisely so a leave still lands, but the client never sends it). The hooks' end is then the only way the session ends, and 0.3.9's `endRefusal` refuses it as `agent-still-connected` whenever the agent's own fabric-mcp signed within 5 minutes, judged by recency, not by whether the agent process (whose pid the hub now holds) is alive. Result: the session stays listed, its claims stay until they lapse (30 min), and the tasks those claims moved to running are never taken back to backlog, which only a release does. fabric-mcp also has no SIGTERM or SIGHUP handler, so one killed by signal (a closed terminal) sends no DELETE either. In 0.3.8 the hooks' end ended such a session. | `apps/desktop/src/main/fabricMcpClient.ts:186` (`if (remaining > 0) throw new FabricRateLimitError(remaining)`, before every fetch); SDK `terminateSession` uses the same `this._fetch`; `apps/desktop/src/main/agentSurface.ts:778` to `:779` (DELETE allowed while unavailable), `:2778` to `:2781` (`ownClientLive` by `lastOwnCallAt`), `:269` (`OWN_CLIENT_LIVE_MS`); `apps/desktop/src/main/workTools.ts:119` (`if (input.rejoin && input.ownClientLive)`); `apps/desktop/src/main/fabricMcpMain.ts:85` (only stdin `end` leaves); `apps/desktop/src/main/workRelease.ts:92` (tasks return only on release); scratch `delete-gate.test.mjs`: the hub saw `[ 'POST' ]`. | Let the DELETE bypass the client cooldown (it is the one request the hub accepts while unavailable); judge `agent-still-connected` by the agent's pid being alive (`process.kill(agentPid, 0)` on the hub's machine) when it is known, falling back to recency only without a pid; leave on SIGTERM, SIGHUP and SIGINT with the same bounded `proxy.close()`. A test: ping refused 503, then stdin end, expects the hub to see the DELETE and the session to end with its tasks back in backlog. |
| ER-3 | No | **When rotation keeps failing, the operations log grows past its budget without bound and writes a false `ops.gap` for nearly every record.** `write` appends the line, then `rotate` renames the file; a rename that throws lands in the same `catch` as a failed append, so `lost++` counts a record that IS on disk and sets `size = null`. The next write re-reads the size (still over the segment), writes an `ops.gap` marker for the "lost" record, its own line, fails the rename again, and so on: no segment is ever closed, nothing is pruned, and every record adds a gap line. A persistent rename failure is realistic on Windows (EBUSY or EPERM while another process holds the file open, such as an editor, a log tailer or a scanner). The probe (append allowed, rename refused) wrote 61 908 bytes against a 4 096-byte budget, 200 of 200 records present and 191 gap markers reporting losses that did not happen. The comment and the docs promise the budget is a hard ceiling because a full disk is ST-1's outage. | `apps/desktop/src/main/ops.ts:228` (`if (size >= segmentBytes) rotate(at)` inside the append's `try`), `:234` (`lost++`), `:160` (`renameSync`), `:32` ("never passes this: a hard ceiling"); scratch `rotate-fail.mjs` output above. | Catch the rotation separately from the append: a written record is never counted lost; a failed rotation is recorded once (a single `ops.rotate-failed` line per streak) and retried with backoff; when the current file passes the whole budget and cannot be rotated, stop appending (count into `lost`) rather than grow; a test with a directory that refuses renames. |
