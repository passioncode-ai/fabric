## Does the release answer the operator's priority

Yes, in its code. Each of the four core parts has a change and a test that I ran green: the hub answers before and while the stack is lost (`hubStandby.ts`, `stackWatch.ts`, ST-1 to ST-4), a session keeps its identity and signs while it works (TR-1, TR-2, TR-4, TR-5), tasks move with claims and the agents list is whole (TR-3, TR-6, TR-7), and requests are answered, expire and reach the home (BD-1 to BD-5). The board suite passes on the full migration chain, and migration 120's `create or replace` targets have the same signatures on the live schema-94 database, so it applies structurally there. What does not hold is around the code: the way the operator's installed 0.3.8 gets to 0.3.9 (PL-1, PL-2, PL-9), and the bookkeeping of what is not done (PL-3 to PL-5).

## Upgrade path for the installed 0.3.8 at schema 94

0.3.9 admits schema 95 only (`schemaContract.json`). On its first start against the live database (94) it classifies `schema-not-ready` behind, which `startupHeals` excludes (`shared/stackWatch.ts:60` to `:63`), so it shows the startup dialog and quits; the hub standby answers `stack-unavailable` until then. The step is the runbook's: stop Fabric, verified backup, rehearsal, `supabase migration up --local` from Fabric's stack folder, start 0.3.9. 0.3.8 cannot open 95 afterwards. Who does what: the migration is agent work, but stopping the operator-opened Fabric is not (the broker answers `in_use_by_person`; the 0.3.8 Release close records the running process is still 0.3.7). Between the bundle install and that restart, the new bundle's `fabric-mcp` meets the old hub (PL-2).

## What needs a person

The quit and reopen of Fabric (broker `in_use_by_person`), which gates the migration; restarting each running coding agent so its `fabric-mcp` carries TR-1, TR-2, TR-4 and TR-5 (41 Claude Code sessions at the audit, plus the Hermes of TR-8); moving the eight long-done backlog tasks and accepting the five review tasks (TR-3 one-off, TR-15: done and cancelled are the operator's moves); and the reboot that proves the login item (ST-7, CO-365). None is named in the plan (PL-9). The tag push is the release decision and needs no reviewer.
