## Findings

| ID | Blocking | Finding | Evidence | Fix |
|---|---|---|---|---|
| ER-1 | Yes | **On Windows and Linux a start that waited quits at the moment it succeeds.** `startOrExplain` calls `startupWaitDone('started')`, which destroys the wait window, before `createWindow()`. The wait window is then the only window (the splash is suppressed while it shows), so `destroy()` emits `window-all-closed` synchronously, and Fabric's handler calls `app.quit()` on every platform but macOS. The same happens on the failure path: `startupWaitDone('failed')` destroys the window before `explainAndQuit` shows the dialog, so the quit begins under the Retry dialog. The CHANGELOG's first line ("Fabric no longer quits when Docker or the database is not ready at start") is false there for a foreground start. The splash had the same exposure before 0.3.9 (`index.ts:736`); the wait window is new. macOS is unaffected. | `apps/desktop/src/main/index.ts:5308` (`startupWaitDone('started')`), `:5254` (`startupWaitWindow.destroy()`), `:5345` (`createWindow()` after it), `:5361` (`startupWaitDone('failed')` before `explainAndQuit`), `:5512` (`window-all-closed` handler); `apps/desktop/src/main/quit.ts:137` (`platform !== 'darwin'` quits); scratch Electron probe output above. | Create the main window (or show the dialog) before destroying the wait window, or make `windowAllClosed` ignore the event while startup has not finished (`!windowReady`) and quit is not under way; add a source-pinned test beside `startup-wait.test.mjs` and fix the splash path the same way. |
| ER-2 | No | **Requests that reach the hub during the socket handover get no answer at all.** `startHub` evaluates `handOver()` (which removes the standby's request handler) as the argument of `surface.start`, and `start` then awaits `primeCredentialVerifiers()` (a database read with a 5 s deadline, serialised on the operator lane) before it attaches its own handler. A request accepted in that window is dispatched to a server with no `request` listener: nothing ever answers it, and it is not re-dispatched when the handler arrives. The caller waits for its own timeout (the MCP SDK's 60 s in fabric-mcp). At startup after a long Docker wait many fabric-mcp clients retry together on Retry-After, so several can fall into it. | `apps/desktop/src/main/hub.ts:304`; `apps/desktop/src/main/agentSurface.ts:455` (prime awaited first), `:474` (handler attached after); scratch `handover-gap.test.mjs`: `during: hung` (no answer in 4 s), a later request answered. | Prime before calling `handOver()` (or attach the surface's handler first and prime after); a test that sends a request while a slow prime is pending and expects an answer. |
| ER-3 | No | **The runtime watch restarts a stack the operator stopped, and against a running but unanswering stack its recovery is futile churn.** `recover` runs `supabase start` whenever two reads fail, with no check of why. After a deliberate `supabase stop` (still the documented way to stop the stack) Fabric starts it again within about 70 s, every time. When the containers are up but the database does not answer (the ST-2 cases the audit measured), `supabase start` answers "supabase start is already running", which `startWithRetry` treats as transient: four CLI runs 10 s apart per try, every try up to 2 min apart, while recovery actually comes from Docker's restart policy, as before. | `apps/desktop/src/main/stackWatch.ts:143`; `apps/desktop/src/main/index.ts:5285`; `apps/desktop/src/shared/stackStartRetry.ts:16`; `AGENTS.md:152` (Stopped by: "`supabase stop`, by the operator"; the new watch row says nothing about it). | Recover only when Docker reports the project's containers exited, not absent (an absent stack was stopped on purpose: say so on the notice and do not start it), and skip `supabase start` while the containers run; or document that Fabric overrides `supabase stop` while it runs. |
| ER-4 | No | **A slow but working database puts the whole hub into refusal.** The watch counts a read over 3 s as a failure and two in a row as a lost stack, then every POST to the hub is answered 503 `stack-unavailable`, including calls that would have succeeded. The hub's own credential deadline is 5 s, and the stability audit measured 5 to 9 s answers on this machine (ST-10). Before 0.3.9 those calls were slow; now they are refused for at least the next watch tick. | `apps/desktop/src/shared/stackWatch.ts:20` (`STACK_READ_DEADLINE_MS = 3_000`), `:22`; `apps/desktop/src/main/agentSurface.ts:770`; `apps/desktop/src/main/accessStore.ts:26` (`HUB_DB_DEADLINE_MS = 5000`); stability audit ST-10. | Give the watch's read at least the hub's deadline, or treat a timeout as "slow" (record, do not refuse) and refuse only on a connection failure or a failed Docker ping. |
| ER-5 | No | **A hub that does not take over the standby leaves hub.json naming a closed port until the next start.** If `startHub` skips or fails the takeover (the port is claimed by an agent registered between the two registry reads, or the handover throws), index.ts stops the standby and sets `hubStandby = null`, but hub.json and the door token stay, naming this live pid. The standby's quit handler is guarded by `hubStandby === opened`, so it no longer withdraws them, and the failed `startHub` publishes nothing. Agents then find a live hub.json and a refused connection instead of `not-running`. A handover that throws also leaves the standby's sockets listening with no handler (they are no longer the standby's to stop). Rare, but the state persists for the whole run. | `apps/desktop/src/main/hub.ts:302` (takeover condition), `:304`; `apps/desktop/src/main/index.ts:782` (quit guard), `:1109`, `:1110`. | When the hub does not open over the standby, `closeHubStandby` (stop and withdraw) instead of `stop()` alone; close the adopted sockets if `surface.start` throws after `handOver()`. |
