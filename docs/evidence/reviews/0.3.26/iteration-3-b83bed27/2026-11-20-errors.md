## Verdict

**Not releasable at the errors level: one blocking finding, ER-26.**

The run-three change to ER-23 moved the queue from a ref to React state. That introduced a stale closure. When a continue press succeeds, a continue link that arrived during the press is dropped. Run two's ER-18 behaviour showed that link after the answer, and this candidate no longer does.

The ask itself still tells the person that "Another continue link waits for this one's answer". The ledger rows V3-ER-18 and V3-ER-23 say the link is "shown after the answer". Both claims are false on the success path.

A scratch test that uses the real `ContinueSessionAsk` and App's exact queue logic fails at the candidate. The same test with a ref-mirrored queue passes. The fix is one line plus the App-level test that CO-604 (31) set aside.

Everything else holds:
- **ER-24 and ER-25** are fixed and tested.
- **ER-23's clearing half** works as described.
- **Tests:** all named tests pass and both typecheck projects exit 0.
- **One non-blocking residual, ER-27:** an edge case of ER-24's restored path.

## Checked and fine

- **No act can hit the wrong process.**
  - The ER-24 change lets a press reach main only for a row the ask reads as ended or Claude-file-backed.
  - Main's `find` re-reads the live Claude files: `owned` returns null, and `unknown-owner` still refuses.
  - A Switchboard-only id is never in the live disk list, so it reaches `resumeEnded`. That path signals nothing: it starts `claude --resume` after `runningClaudeIds` refuses a Fabric-held id.
  - One residual depends on Switchboard's contract. A `running` row with `pid: null` would read as ended, and a press would start a second process on that session. The spec says a null pid means the process is gone, and the case with a live pid is ruled as CO-604 (25).
- **ER-23's clearing.** When not busy, `applyLink` clears the queue before replacing or nulling the ask, so a queued link cannot resurface after an unrelated ask. While busy, a non-continue link leaves the ask and the queue untouched. The same session's link is ignored. A third link replaces the queued one, so the newest wins, as it does when nothing is busy.
- **onBusy.** The closure is stale but harmless. It writes `continueAsk.session` of its own keyed instance, and every settle path calls `onBusy(false)`.
- **The UX-36 read-only ask** offers only Cancel, which is not disabled because no press can start.
- **`linkOriginOf` on an array** returns `{}`, a link with no app, as in run two. Only an `AGENT_ID`-valid `from` reaches the journal.
- **i18n.** `links.continue.queued` and the new `links.continue.from` are in both en and ru.
