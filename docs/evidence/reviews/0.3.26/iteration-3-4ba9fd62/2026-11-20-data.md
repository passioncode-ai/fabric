# Fabric 0.3.26 release review, iteration 3: data
Level data, candidate 4ba9fd6214dd80526eeba127b5c2fcb0a962647c, baseline 53e8c3e2, reviewer Claude Opus 5.5 (1M context), read-only.

## Verdict

There is one blocking finding, **DA-19**. The contract's `from` grammar allows an instance suffix such as `observatory.default`, which SL-1 itself gives as an example. Fabric's main process and its ask both drop such a value. For those links:

- The `from` is neither shown nor recorded.
- When the session is running, the launch journal records the false reason «Перенесена в Fabric из терминала вне Fabric» with `via: 'screen'`.

The CHANGELOG says "the app it came from (`from`) is recorded in the launch journal". That is false for a valid input. The fix is one line in two places.

The redaction fixes hold:

- DA-13: turns are redacted whole, then cut. I confirmed that the old order kept the `sk-ant-` prefix and the new order does not.
- DA-14: there is now an exported, tested composed reader.
- DA-16: there is a single-flight guard.
- DA-18: an unreadable history gets its own reason.
- DA-17 is ruled in CO-604 (20).

DA-15 is fixed only in part. That gap produced DA-19 to DA-22. There are 4 new non-blocking findings.

| DA-19 | Blocking | A `from` with an instance suffix is valid under the contract but is dropped by Fabric. DEC-0189 SL-1 gives the grammar `^[a-z][a-z0-9-]{1,62}(\.[a-z][a-z0-9-]{0,31})?$` and the example `observatory.default`, and the vendored parser accepts it. Fabric's checks reject the dot: the IPC handler and `linkReason` use `/^[a-z][a-z0-9-]{0,94}$/`, and the ask's `appName` uses `/^[a-z][a-z0-9-]{0,62}$/`. With `from` turned into `undefined`, three things go wrong. The ask does not show the app, against SL-1's "shows". The journal does not record it, against SL-1's "records" and the CHANGELOG claim. A running session's continue is journaled `via: 'screen'` with the reason «Перенесена в Fabric из терминала вне Fabric», which is a false record on disk. The test «the link's app reaches the console» covers only `machineSessions.ts` and never these regexes. | Scratch run: `parseFabricLink('fabric://session/continue?session=…&from=observatory.default')` returns `ok: true, from: "observatory.default"`, and both Fabric regexes return `false`. Add a test that sends `from=observatory.default` through the IPC validation and reads `via: 'link'` and the app in the journal reason. |

A `session/continue` link without `from` (allowed, since `from` is optional) that continues a running session is journaled `via: 'screen'`, «из терминала вне Fabric». ## Checked and fine

- **Redaction order and reach.** The text is redacted whole before the cut, for both the panel (`turns: redactedTurns`) and the CEO's `read`. Only text turns and tool names are included; tool results become `[tool result]`. The CEO's console screen and `last_line` are still redacted (`ceoTools.ts` `screen`, `consoleRow`).
- **The CEO read is bounded.** It now uses `readTail(file, READ_TAIL_BYTES)` (2 MB through a handle) instead of `readFileSync`. `readTail` uses `bytesRead` (ER-17), so a file that shrinks mid-read leaves no junk text.
- **Single flight.** `continuing` covers both the running and ended paths and is released in `finally`. `close` refuses while a continue runs.
- **Unknown owner (ER-14).** With no process table, nothing is signalled and the list still shows the session (test passes).
- **The ask's screen data.** It shows the folder basename (full path only as a fallback), the agent and the state. `refused` reaches only a tooltip and is translated through `machineWhy`, with unknown codes shown as `machineSessions.why.other`. `stopped-not-continued` no longer prints the id and folder in the sentence.
- **The `from` value.** It is validated before IPC and again in main, never logged with the link URL (`link.open` records only `notice` and `from`), and only ever text in the reason. Downgrade: older journal readers map an unknown `via` through `oneOf`, so the row stays with no `via`.
- **Vendored contract.** `shared/contract/{fabricLinks,secretShape}.ts` are unchanged since iteration 2, which checked them against `4c978495`.
