# Fabric 0.3.26 release review, iteration 2: plan

Level plan, candidate 30552b73e58571047945ef0eafb6c63d44fcb42a, baseline 53e8c3e2, reviewer Claude Opus 5.5 (1M context), read-only.

## Verdict

**Not ready to release. 1 blocking finding (PL-15), 7 non-blocking (PL-16 to PL-22).**

Iteration 1's plan findings mostly hold:

- All three blocking ones are fixed: PL-1 (the count claim), PL-2 (deferrals with no carry-over rows) and PL-3 (CO-601).
- Every ruled finding is in its CO row.
- The receipts match their reports byte for byte.
- The spec's §2a now maps each of the operator's asks of 2026-11-20 to what shipped or to its owner.

The blocking problem is the session links. They were added in iteration 2, inside the commit for iteration 1's code fixes, and they leave the candidate red:

- **CI is red.** Hosted `ci.yml` run 44677433773 on 30552b73 fails `scripts/ci.sh fast` at the design/i18n gate, rule SP-2: 3 new places show a machine id to a person. Because the gate stops there, nothing after it (vitest, the map stamp, the docs and register gates) has a result on this candidate.
- **The person consents to an act they cannot identify.** The new «Продолжить в Fabric?» banner stops a running session elsewhere on the person's press. It names that session only by an 8-character id prefix. It does not say which app asked, and it has no test.

The release-gate path is not started yet. That is acceptable before iteration 3, but the steps are listed under PL-21. Two loose ends from iteration 1 remain:

- PRs #66 and #68 are still open, although their ledger row says "fixed".
- The CHANGELOG still does not say that Fabric's own consoles do not come back after a restart.

Opening the app an hour from now, an operator would still find:

- different session counts in Fabric and Dashboards (documented, CO-603 (1));
- no message when Switchboard was not read (CO-603 (7));
- no new controls in the project page's body;
- consoles gone after a Fabric restart;
- a continue prompt that names a session only by its id.
