## Findings

| DA-1 | **Yes** | **A retry after a launch that failed once its process had started brings forward a dead session and reports success.** The task is never started again. `tasks.start` asks `planTaskStart` for "the live session this process holds for the task", but the callback returns *any* session ever tracked for the task. Liveness is never checked. `taskBySession` is never pruned when a session exits: it is deleted only by `untrack`, and `managedLaunch` calls `untrack` only when no process started. When several sessions are tracked, `.find` returns the oldest. Reachable path: the agent exits at once (signed out, crash), so bind or liveness fails and the result is `launch_outcome_unknown`. The person presses *Create and open the console* again. `planTaskStart` returns `running` with the dead id, `openSessionWindow` opens a window for any id without checking it, and `onStarted` moves on as if the agent were working. This makes the 0.3.3 claim "A retry is the same attempt … continues with the same folder, project and task" false on this path, and the brief's second-pass fix ("returns the live session") is not what the wiring does. | `apps/desktop/src/main/index.ts:1629-1630` `(id) => [...taskBySession].find(([, task]) => task === id)?.[0] ?? null`; `managedLaunch.ts:98` `if (!processStarted) deps.untrack(…)`; `index.ts:2849-2850` (the only delete); `index.ts:4308-4323` (window opened for any id); `taskRetry.ts:29-31`; `AgentPaths.tsx:26-27,179`. Probe: `{"plan":"running","sessionId":"dead-session-1","sessionRunning":false}`. `test/task-retry.test.mjs` only passes a stub `liveSession`, so the index.ts lambda is untested. | Make the callback live-only and newest-first, e.g. `[...taskBySession].filter(([sid, t]) => t === id && ptys.get(sid)?.running).at(-1)?.[0] ?? null`, so a dead session falls through to `again`. Add a test that drives the real lambda (extract it) with a tracked, ended session and watch it fail on today's code. |
| DA-2 | **Yes** | **The first-run usage notice tells every 0.3.2 upgrader "Nothing has been sent yet", which is false.** 0.3.2 sent `app_installed`, `app_started` and `app_active` from the first start (its own CHANGELOG says so). ADR-0127 §5 says an install from 0.3.2 sees this notice once, so every upgrader with counts on reads a false privacy statement at the moment they are asked to decide. The notice cannot tell the cases apart: `analytics.status()` returns only `pending-disclosure`. `docs/ANALYTICS.md` repeats the claim as what the notice says. | `i18n/en.ts:821` `'analytics.notice.nothingYet': 'Nothing has been sent yet. …'`; `i18n/ru.ts:1622` «Пока ничего не отправлено…»; `UsageCountsNotice.tsx` renders it unconditionally; `v0.3.2:apps/desktop/src/main/analytics.ts:242-250` (`started()` tracks at first start when on); `docs/ANALYTICS.md:21`; ADR-0127 Decision §5; `CHANGELOG.md` §0.3.2 "on by default in a release build, from the first start". | Expose whether this app already sent counts (state has `installed_at`, or a `previously_sent` flag) in `AnalyticsStatus`, and show a true sentence for upgraders, for example "Fabric 0.3.2 sent usage counts; from now on nothing is sent until you answer". Fix `docs/ANALYTICS.md`/ADR wording; add a notice test for the upgrade state. |
