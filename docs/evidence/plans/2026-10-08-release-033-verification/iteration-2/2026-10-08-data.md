**Answers to the questions asked.**

1. **What the journal records.**
   - `project.created@1` journals the purpose as the plain localized string «From README.md: …» / «Из README.md: …». No structured source is recorded (DA-3).
   - `task.created@1` carries the caller's id after a UUID check (`taskRetry.ts:23`). An id held by another project is refused (`:28`); an id held by another estate is refused at the door (`refuse_foreign_identity`).
   - A retry of a recorded task goes through `launchManaged` → `admit_task_launch`, the same door `tasks.startExisting` uses. It gains no capability and journals no second create.
   - Bringing a live session forward journals nothing.
   - The queue is per main process. Two windows share it. Two app instances on one userData cannot exist: `requestSingleInstanceLock`, `index.ts:4417`. For two processes on one database, see DA-2.
2. **Idempotency and replay.**
   - `task.created@1` is projected `on conflict (id) do nothing` (migration 61:255), and `append_event` projects in the same transaction (migration 81 `append_event` → `apply_projections`). A duplicate create therefore cannot overwrite the row, and replay keeps the first event, so it is deterministic.
   - `projects.create` repeats as a finish, not as a second `project.created@1`.
3. **Event types.** No new event type since v0.3.2: no migration changed, and no new `type:` was found in the `src` diff. The fallback route is an additive `route` field on `terminal.opened@1` (`pty.ts`). The `check-design` gate is green both ways: 101 registered types, 71 appended types.
4. **Schema.** Still 79, with the contract at 79/79 (see the table above).
5. **Analytics.**
   - `installed_at` is written when `app_installed` is QUEUED, not when it is delivered: `analytics.ts:251-253`, and `track` only pushes and schedules. See DA-4.
   - After the person turns counts off, `started` and `track` return early, so `installed_at` is not written.
   - Upgrader without `disclosed_at` and switch on: the state is `pending-disclosure`; nothing is queued, `sentBefore` is true, and the notice is shown once.
   - Upgrader whose switch is off: the state is `off`, so no notice and no `disclosed_at`. A later "on" from Settings records the disclosure; a later "on" from another app brings the notice back. This matches ADR-0127 §3/§5.
6. **Fallback order settings.**
   - Validated on read and on write: `appSettings.ts` `runnerFallback` → `cleanOrder`, at most 16 entries; `localState.ts#writeLocal` validates before it persists.
   - The walk reads the file at launch time (`runnerFallback.ts:52`), and the measurement is cached for 30 s.
   - The two-launch attach race stays ruled as CO-229.
7. **Harness.**
   - Bundles are minted only for connected runners.
   - A pre-spawn throw now takes the credential back (V1-8).
   - Kimi Code has no bundle (`surfaceAdapter: 'none'`).
   - The setup gate is not complete (DA-1).
8. **Lifecycle.** The `AGENTS.md` analytics row now says nothing leaves before the answer, and that agrees with `analytics.ts`. The hourly timer still runs before the answer, but `activeTick` returns early (`analytics.ts` `activeTick` → `availability() !== 'on'`); the row's "nothing at all" is about sends. The 10 s quit deadline is still tested at `quit.test.mjs:101-114`; the 180 s bound covers only the graceful-exit tests.
9. **CI.** `adapter-skills` (`ci.sh:219`), `task-retry` (`:220`), `analytics` (`:222`) and `runner-fallback` (`:228`) are all in the fast tier. `builderChoice.test.ts` runs in the fast-tier `vitest run` (`:192`), through the include `src/shared/**/*.test.ts`. The hosted job runs `ci.sh fast` (`ci.yml:73`).
