## Findings

| ID | Blocking | Finding | Evidence (file:line, command, output) | Suggested fix |
|---|---|---|---|---|
| ER-1 | **yes** | **A repository's README (or manifest description) freezes Fabric's main process for ~27 s per file.** The summary's markup stripping is quadratic on unclosed `<` or `[`, and it runs synchronously in Electron's main process on up to 64 KiB of third-party text. No timeout can fire during it, so `inspect`, every candidate of a scan, scan Stop, the scan deadline and the quit deadline ("Cmd+Q / SIGTERM ends it within 10 s", AGENTS.md lifecycle row) all wait; every window hangs. A cloned repository with several such READMEs freezes a scan for minutes. V1-12 bounded the read, not the work. | `projectDiscovery.ts#plain`: `.replace(/<[^>]+>/g, '')` and `.replace(/\[([^\]]+)\]\([^)]*\)/g, '$1')`; `summaryFrom` returns `clip(plain(raw))`, so the clip comes after the stripping. Timing of `summaryFrom({readme})`: 60 000 × `<` → **18 701 ms**, 30 000 × `[` → **4 469 ms**. Probe `<scratchpad>/rc033-i2/errors/readme-freeze.mjs` (a temp folder holding README.md = "A tool " + 64 KiB of `<`, then `inspectFolder`): "inspect took 27306 ms; longest event-loop stall 27307 ms", exit 1. | Cut `raw` to a few times `SUMMARY_MAX` (e.g. 1 000 characters) BEFORE `plain()`. Make the patterns linear: `/<[^<>]*>/g`, `/!?\[([^\][]*)\]\([^()]*\)/g`. Add a test with 64 KiB of `<` and of `[` under a time bound. |
| ER-2 | no | **V1-1 moved, not closed: a retry still brings forward a session whose launch failed and reports success.** When the launch spawned and then failed (bind not confirmed, or liveness not confirmed), `managedLaunch` asks for a stop and keeps the session tracked (`untrack` only when `!processStarted`). `stop('launch_failure')` sends SIGTERM without force and may return `outcome_unknown` while the process still runs. The renderer's retry then plans `running` and opens that console as the started agent. The run was failed (`fail_task_launch`) and the instruction was never dispatched. The trigger is rare: a post-spawn setup failure plus a process that outlives the stop. | `managedLaunch.ts:92` (stop), `:98` (`if (!processStarted) deps.untrack`); `taskRetry.ts:37-41` (`liveSessionOf` checks `running` only); `index.ts:1633-1635`. Probe `<scratchpad>/rc033-i2/errors/retry-abandoned-session.mjs` (the real `createManagedLaunch` + `planTaskStart`): "first launch: false launch_outcome_unknown … retry plan: running (the failed launch's session) \| instruction dispatched: 0", exit 1. | Untrack the session (or mark it abandoned) whenever the launch returns `started: false`. Have `liveSessionOf` answer only a session bound to the task's current run (e.g. `taskBySession` plus a bound flag set after `bind_task_run`). |
| ER-3 | no | **A session that started but could not be read back is called "not created" and offers a second coding agent in the same folder.** `tasks.start` throws `task-refused:readback-failed` after the session started, so the renderer never learns its `sessionId`. The screen says "The agent was not created: The session started, but …" (two sentences that contradict each other) and shows «Use another coding agent». Pressing it starts a second task and a second agent in the folder the first one is working in. (*Try again* is safe: main plans `running`.) | `index.ts` `startTask` (`throw new Error('task-refused:readback-failed')` after `launched.started`); `AgentPaths.tsx:27` (`sessionId` only from a resolved `tasks.start`), `:33-34` (`failure`), `:292` (button shown when `launched && !sessionId`). Probe `<scratchpad>/rc033-i2/errors/agent-paths.test.tsx` P1: found "The agent was not created: The session started…", clicked «Use another coding agent», second `tasks.start` with a different `taskId` (pass = defect reproduced). | Return the session with a `readBack: false` flag instead of throwing, or have the renderer treat `task-refused:readback-failed` as "session running" (consoleNotOpened copy, no swap button). |
| ER-4 | no | **After leaving and coming back, the agent screens show, and check skills for, a coding agent other than the one the retry runs.** `keptCreate` / `keptConvert` keep the attempt (`launched: true`, same `taskId`) but not the chosen agent. On remount `useBuilders` preselects the default and the picker is locked (`disabled={… attempt.current.launched}`). A retry sends that default as `optionId`, but main's `again` path relaunches the recorded task with its recorded `option_id` and ignores `optionId`. The REQ-04 skills check ("checked before either starts", CHANGELOG) is then made for an agent that does not run. On the adapt screen the failure is not kept either, so «Use another coding agent» is not offered and the person cannot change the agent at all. | `AgentPaths.tsx:18-19` (no agent in `Attempt`), `:49-75` (`setChosen(c => c ?? pick)`), `:323`, `:440`; `index.ts:1636-1639` (`again` ignores `optionId`), `:2826` (`receipt.option_id`). Have `tasks.start` refuse (with a code) a retry whose `optionId` differs from the recorded task's. |

## Not checked

- Real Electron runtime: no app launch, no packaged build, no real PTY or coding agent. Every finding is proven through the real modules with stubbed edges (bridge, `db.rpc`, filesystem in temp folders), not in a running Fabric.
- ER-2's trigger in the real runtime: I did not measure whether any shipped coding agent outlives `stop('launch_failure')`'s SIGTERM window. The probe assumes a stop that returns before the exit.
- `adapterSkills` under a stalled network mount: each timed-out `stat`/`readFile` keeps a libuv thread busy, and repeated *Check again* could exhaust the pool. Not simulated.
- `admitExisting` / admission SQL on the `again` path (e.g. a task whose previous generation is still `outcome_unknown`): the DB tier needs the stack, which I did not touch.
- Russian rendering of main-process refusals on the new paths (`again.says`, `describeExhausted`, `launched.says` are English). CHANGELOG §0.3.3 discloses this under CO-225, so it is not counted as a finding.
- Two windows racing the create screen: `keptCreate` is per renderer, so a second window gets the folder `exists` refusal (read, not probed).
- `check-ops.mjs` covers main only (ruled CO-230). Renderer catches in the changed files were read by hand; ER-8 is the only one found without handling.
- `scripts/ci.sh` (fast or full) was not run, and neither were the documentation, map or register gates.
