## Why `fabric_work_list` showed one session and `fabric_agents_list` none

`fabric_work_list` answers `sessions` from `deps.sessions()`, which is `AgentSurface.projectSessions(projectId)`
(`agentSurface.ts:631`): every session the surface holds a credential for in that project (the enrolled
fabric-mcp session of this Claude Code, `9eb9e613`, enrolled 00:16 UTC) plus Fabric's own running terminals.
`fabric_agents_list` answers from `ptys().list(scope.projectId)` only (`agentSurface.ts:1448`): Fabric's own terminals.
No agent on this machine runs in a Fabric terminal, so the second list is always empty. See TR-6.

## What works

- **Project attribution is right.** All 41 working folders resolve to the correct project (`how: exact` on all 49 enrollments since the restart); no session is attributed to a wrong project.
- **Folder safety holds.** The home folder is refused as too broad (Hermes), never registered as a project.
- **No ghost sessions from before the restart.** The held set is rebuilt from scratch on a Fabric start, so a dead session from an earlier run cannot be shown as live.
- **The enrollment cap did not evict anyone.** No `hub.session.enroll-evicted` line in the ops log; one binding serves 41 sessions across projects within the 8 per project and 64 total limits (`sessionEnroll.ts`).
- **Claims are consistent in the database.** One live claim per task (`work_claims_one_live`), every claim and release journaled (`work.claimed@1`, `work.released@1`).
- **Where the hook path is intact it works.** 1405 `answer=ok` deliveries in hooks.log; for the 16 sessions whose ids did not change, turns and ends arrive.
- **The agent-sync read is safe.** `ls-remote` runs outside the repository, https or ssh only, bounded and cached (`agentSyncLeases.ts`); a failed read is said, never shown as "no leases".
- **0.3.8 already contains two fixes** relevant here (growing backoff for a too-broad folder, typed refusals logged as warnings); they only need the restart (TR-8, TR-9).
