## Release checklist: live checks the tag owes

Each is run on the operator's Mac with the release candidate installed, and its result written here with the date.

1. **Docker stopped at start (CO-294).** With Colima stopped (`colima stop`), start Fabric. Expected: the splash says
   «Запускаю Colima», then «Жду ответа Docker»; the operations log has `stack.start.docker-launched` with `app: Colima`;
   the stack comes up; `docker context show` prints the same context as before the start; OrbStack is not running
   (`pgrep -x OrbStack` prints nothing). Fabric is never launched or quit by hand: through the lifecycle broker.
2. **A reboot (CO-365).** After the next real reboot, the newest `app.started` in the operations log reads
   `atLogin: true` and `background: true`, and Fabric answers on the hub without anyone opening it.
3. **Schema 100 (CO-469, and the archive sources).** The installed database at 98 takes migrations 126 and 127 in the runbook's order
   ([release-mac.md](../../launch/release-mac.md)), after a backup; Fabric 0.3.15 refuses the upgraded database, as it
   should, and the release candidate opens it.
   **Rehearsed 2026-10-28** (runbook steps 2 and 3, not the live upgrade): a read-only dump of the operator's database
   (schema 98, journal 36 952 events, 66 MB) restored into a disposable stack and taken through `main` at `f269e5c6`
   by `scripts/rehearse-upgrade.mjs --from 98`: **PASS**, schema 98 → 99, journal 36 952 → 36 952, no table lost rows;
   the receipt (numbers and the dump's sha256 only, mode 600) sits beside the private dump in
   `~/Library/Application Support/Fabric/backups/`. **Rehearsed again 2026-11-02** after the archive-source fix became migration 127 (schema 100): the same dump through
   `d0db515f`, **PASS**, schema 98 → 100 (admits 100), journal 36 952 → 36 952; the receipt beside the dump is that run's.
   The migration files rehearsed are byte for byte the ones that land. The live upgrade, the 0.3.15 refusal and the candidate opening it
   stay owed at the tag.
