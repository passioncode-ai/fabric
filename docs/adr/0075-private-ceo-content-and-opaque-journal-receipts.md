# ADR-0075 — Private CEO content and opaque journal receipts

**Status:** accepted architecture for the authorized R0 implementation; not implemented or activated by this record.
**Date:** 2026-09-27. **Extends:** ADR-0065/0067 and the private-discussion boundary in [operator interaction](../architecture/operator-interaction.md).

## Decision

1. A discussion belongs to one Person in one Estate. Reopening a Project or Board question returns that person's stable conversation for that subject. Explicit New creates a separate global conversation; selecting knowledge never changes conversation identity, audience or command destination. Project purpose, tasks and accepted decisions remain canonical Project records, not private chat state.
2. Use option B of the [implementation contract](../launch/harness-r0/ceo-conversations.md): protected immutable primary content in the same PostgreSQL database, referenced by opaque journal receipts. The journal records acceptance/order; content is primary data, not a projection that replay can recreate. No second event store or provider-native history becomes authoritative.
3. Shared journal payloads contain only approved opaque identifiers and acceptance metadata. Body, title, excerpts, source/subject references, owner mapping and plaintext content hashes remain in protected records. The ordinary journal actor/time/sequence still reveal participation; this is content privacy, not invisible activity. Trusted host/service-role/database administrators remain outside that privacy boundary.
4. Dedicated commands and readers derive the Person from trusted identity and recheck current membership, owner, Estate and source authority. Generic table reads, an opaque ID, a selected Project or an agent's `operator` label cannot grant access. Content is prepared before persistence, clipping or digesting; recognizable-secret filtering is not a substitute for audience enforcement.
5. Send atomically commits protected content, an opaque event, an idempotent receipt and a pending request. Same operation and canonical intent returns the original receipt; conflicting reuse refuses. Pending means saved, not delivered, processed or permission to execute. No worker is activated by the storage packet. Rebuild/restore never recreates dispatch authority or previously deleted content.
6. Local drafts and frozen offline send intents use a separate validated CAS namespace bound to Person/Estate/conversation. A late response cannot clear newer typing or redirect a message to the newly selected conversation. Revocation prevents new reads/writes; it cannot retract bytes already read or promise filesystem erasure.
7. Owner-scoped portable backup and recovery are mandatory before R0 activation. Ordinary Estate archives explicitly exclude private content. Private export/restore validates owner, Estate, receipts, content integrity and tombstones, with no silent reassignment. Metadata-only restore shows unavailable content and no dispatchable request. This does not introduce a local-only exception or claim existing archives already protect this content.
8. None/single-Project support may be implemented as a bounded first packet. The accepted R0 target still includes none/one/many/all, source-aware bounded context, text/voice attribution and typed outcomes. Unsupported staged inputs refuse explicitly; they are not silently converted or removed from the launch scope.

## Why this boundary

At source [8dde15b](https://github.com/passioncode-ai/fabric/tree/8dde15bff86b4f20d2edb5bdaa1159fa27a9cd9c), migration 1's `member_journal_read` permits Estate members to read journal payloads; service-role feed replay and backup also read them. Adding an owner field to plaintext messages would not make them private. Option A would require changing every generic journal reader/export. Opaque receipts keep those feeds useful while a purpose-built store enforces content access. A public plaintext digest is excluded because short messages can be guessed from their hashes.

This follows the existing instruction that private notes do not become a team transcript. Only an explicit authorized outcome command publishes the allowed result/excerpt to a Project. A shared result may link to a private source without revealing that source to other readers. The agent remains replaceable; the operator can return to the same Project decision and its permitted evidence.

## Implementation and rollout

Three bounded packets: storage/authorization/replay; native service/draft/IPC; UI plus owner backup/cold-restart acceptance. Exact states, ports, source evidence and negative checks are in the [contract](../launch/harness-r0/ceo-conversations.md). The storage packet must fix serialization limits and golden vectors before implementation, qualify a new explicit schema range, and use an owned disposable database for actual transactions. It must demonstrate that raw event append/import and another Person cannot fabricate acceptance or read content.

No live database is migrated by this decision. Rollout retains the maintenance barrier from ADR-0073: stop writers, take a verified compatible backup, install matching readers without starting them, apply the reviewed migration, then start and verify. Before accepted private content exists, rollback may restore the complete previous backup; afterwards use a verified complete private-content backup or fix forward, never drop the new primary store and call it a projection rebuild. Native/provider/voice and full release acceptance remain separate gates. CO-168 remains open.
